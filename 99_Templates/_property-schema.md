# 📐 Master Property Schema

> **Single source of truth** - 이 vault의 모든 노트가 따라야 하는 frontmatter 표준.
> Bases 쿼리와 Dataview는 이 스키마를 전제로 작성된다. 스키마 변경 시 **이 파일을 먼저 갱신**하고 기존 노트를 마이그레이션할 것.

---

## 🌐 공통 필드 (모든 노트)

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `created` | Date `YYYY-MM-DD` | ✅ | 노트 생성일 (file.ctime 폴백 금지 - 항상 명시) |
| `updated` | Date `YYYY-MM-DD` | ⬜ | 독자가 알아야 할 만큼 공개 본문을 고친 날. 오타를 고치거나 속성만 바꾼 날에는 갱신하지 않는다. 사이트는 이 값이 표시 날짜(`published`, 없으면 `created`)보다 늦을 때만 수정일로 보여 준다. |
| `slug` | Text | 공개 폴더 ✅ | 사이트 주소의 마지막 조각. 짧은 영문 소문자와 하이픈으로 쓴다. 아래 공개 노트 규칙을 따른다. |
| `summary` | Text | ⬜ | 목록·검색·공유 미리보기에서 노트의 주제나 관점을 짧게 전한다. 작성 방식과 분량은 아래 노트 유형별 기준을 따른다. |
| `tags` | List | ⬜ | 실제 횡단 탐색·필터에 사용할 때만 아래 기준으로 작성 |
| `aliases` | List | ⬜ | 다른 이름으로도 wikilink 받기 위함 |

> [!note] Bases 구현 규칙
> `created` 누락은 스키마 위반이며 `vault-lint`가 탐지한다. Base의 `file.ctime` 폴백은 누락 노트를 숨기지 않기 위한 **표시용 방어**일 뿐, `created`를 대신하지 않는다. Inbox 7일·30일 기준은 `_inbox.base`와 `_global-health.base`, 프로젝트 14일 기준은 `_dashboard.base`와 `_global-health.base`에 중복 정의되므로 기준 변경 시 두 파일을 함께 수정한다.

> [!note] 공개 노트의 slug
> Slipbox, blog, Development 세 폴더의 노트는 사이트 주소를 가지므로 `slug`를 새 노트에 처음부터 넣는다. 값이 없으면 제목에서 자동으로 만드는데, 한글 제목은 주소에서 퍼센트 인코딩되어 한 글자가 아홉 문자로 늘어난다. 제목 문장을 그대로 옮기지 말고 핵심어 서너 개를 영문 소문자와 하이픈으로 적는다. 글자·숫자·하이픈만 쓸 수 있고, 같은 종류 안에서 겹치면 사이트 빌드가 실패한다. **이미 공개한 노트의 `slug`를 바꾸면 그 주소가 깨지므로 발행 전에 정한다.**

> [!note] 공개 노트의 날짜
> 사이트는 `published`가 있으면 그 날짜를, 없으면 `created`를 노트의 날짜로 표시한다. 글의 `published`는 원문 발행일이다(아래 Blog Posts 절). Slipbox와 Development 노트의 `published`는 선택 필드이고, 그 폴더에서 처음 공개하거나 다른 폴더에서 승격한 날을 적는다. 이때도 `created`는 원본을 작성한 날로 둔다. `created`, `published`, `updated`는 달력에 있는 날을 `YYYY-MM-DD`로 적고, 빌드한 날(한국 시간)보다 늦은 날짜가 있으면 사이트 빌드가 실패한다.

### 태그 사용 기준

태그는 선택 필드다. 폴더·`type`·`status`로 이미 드러나는 노트의 역할을 다시 표기하지 않고, 서로 다른 폴더를 가로질러 실제로 검색하거나 필터링할 주제·프로젝트에만 사용한다. 계층형 태그는 `/`로 구분한다. Frontmatter에서는 `#`를 붙이지 않고, `#task`·`#next` 같은 인라인 태그만 본문에서 사용한다.

`프로젝트/<project-id>`는 폴더 안팎의 관련 노트를 함께 찾을 때 선택적으로 쓴다. 프로젝트 폴더에 속한다는 이유만으로 기본 추가하지 않으며, 붙일 때는 canonical `project_id`와 맞춘다. 기존 태그는 실제 탐색 용도를 확인하고 승인된 범위에서만 정리한다.

```yaml
tags:
  - AI
  - 개발/Java
  - 커리어/성장
```

| 카테고리 | 태그 예시 | 용도 |
|----------|-----------|------|
| `AI/` | `AI`, `AI/에이전트`, `AI/프롬프트` | AI를 빼면 주장이 성립하지 않는 노트. 제목에 AI가 들어가도 주장이 AI 없이 성립하면 AI는 둘째 태그로 둔다 |
| `개발/` | 기술: `개발/Java`, `개발/Spring`, `개발/Kubernetes`. 영역: `개발/프론트엔드`, `개발/인프라`. 활동·맥락: `개발/설계`, `개발/도구`(조건 태그) | 개발 관련 |
| `커리어/` | `커리어/성장`, `커리어/자기관리`, `커리어/동기부여`, `커리어/이직`, `커리어/시니어` | 커리어·자기계발. `성장`은 역량과 학습, `자기관리`는 나를 다루는 방식과 상태 관찰 |
| `조직` | `조직` | 위임·채용·팀 성과·리더십처럼 AI를 걷어내도 성립하는 조직 원칙. 노트가 늘면 `조직/리더십`처럼 나눈다 |
| `프로젝트/` | `프로젝트/onlyoffice-demo` | canonical project_id별 구분 |
| `심리/` | `심리/성격검사` | 성격·정서 같은 심리 개념이나 검사로 나를 설명하는 노트. |
| `철학` | `철학` | 철학·사상·판단. 어떤 기준으로 무엇에 무게를 두고 선택하는가를 다룬 노트 |
| `글쓰기` | `글쓰기` | 글쓰기·커뮤니케이션 |
| `개발` | `개발` | 개발·설계·품질·기술 방법론 |
| `지식관리` | `지식관리` | Obsidian·PARA·Zettelkasten 운영 |

태그 순서에는 뜻이 있다. 첫 태그는 주장이 속한 축이고, 둘째부터는 그 주장이 성립하는 조건이나 맥락이다. 공개 사이트는 첫 공개 태그의 앞 조각을 노트의 topic으로 써서 색과 지도 범례를 정하고, 노트 페이지에는 앞의 두 태그만, 개발 노트 목록에는 첫 태그만 표시한다. 허브 소속과 첫 태그는 별개다.

최상위 태그는 `AI`, `개발`, `커리어` 등 기존 분류를 우선한다. 새 분류가 필요하면 기존 분류로 찾기 어려운 이유와 사이트의 색·범례에 미치는 영향을 함께 검토한다. 하위 태그는 다음 세 조건을 모두 만족할 때 만든다.

- 독자나 저자가 검색창에 칠 단어다. 노트 하나의 내용을 요약한 말은 태그가 아니다.
- 같은 층에 이미 그 대상을 덮는 태그가 없다. `개발/Kubernetes`가 있으면 `개발/K8s`를 만들지 않는다.
- 기술 이름과 개념 단어 모두 실제로 다시 찾을 주제일 때 만든다. 노트가 한 편이어도 별도로 찾아볼 독립적인 주제라면 사용할 수 있다.

깊이는 두 단계까지다. 기술은 제조사 표기(`Kubernetes`, `Astro`)로, 영역과 활동은 한국어 명사(`프론트엔드`, `설계`)로 쓴다. 위 표에는 대표 예시와 헷갈리기 쉬운 구분만 남긴다. 전체 사용 현황은 필요할 때 노트에서 집계한다. 태그 수나 사용된 노트 수만으로 추가·삭제하지 않고, 실제 검색·탐색 가치와 다른 태그와의 중복을 기준으로 유지·통합·삭제를 검토한다.

`inbox`, `slipbox`, `blog`, `📚독서`, `📰article`, `clippings`처럼 위치나 다른 속성과 역할이 겹치는 태그는 새 노트의 기본값으로 넣지 않는다. 기존 노트에 남아 있던 `slipbox` 태그는 2026-09-08에, `blog`·`clippings`·`📚독서`·`📰article` 태그는 2026-09-23에 일괄 정리했다. 다른 노트에서 이 태그들을 발견하면 같은 기준으로 지운다. `type/timeline/*`처럼 현재 템플릿의 Dataview 쿼리가 실제로 사용하는 태그는 유지한다.

### 개발 기술 태그

태그는 구현에 사용한 언어·의존성 전체가 아니라 **노트가 설명하는 주제**를 나타낸다.

- `개발/Java`: Java 언어·JDK API·JVM 자체가 주제일 때 사용한다. 예: ZIP API, `StructuredTaskScope`, 구조적 동시성.
- `개발/Spring`: 빈 등록·의존성 주입·`@Async`·WebFlux·DataBuffer 같은 Spring 기능이 주제일 때 사용한다. Java로 구현된 기능이라는 이유로 `개발/Java`를 함께 붙이지 않는다.
- Kubernetes, ArgoCD, Flyway 등은 실제로 다루는 기술 태그를 사용한다. 여러 기술을 언급한 것만으로 모두 붙이지 않는다.
- `개발/도구`는 도구 활용이 맥락임을 나타내는 조건 태그다. 둘째 이후에만 붙이고 첫 태그로는 쓰지 않는다. Development/Tools 노트도 첫 태그는 그 노트가 다루는 기술이나 주제(`개발/터미널`, `개발/GitHub` 등)다.
- 문제 해결 여부는 폴더와 공개 페이지 분류로 구분하고 태그로 적지 않는다.

## 📥 Inbox (`00_Inbox/`)

빠른 포착 노트. 정리·연결·승격 판단은 나중으로 미루고 원문과 다음 처리 상태만 기록한다.

```yaml
---
created: 2026-07-13
next_action: ""
---
```

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `next_action` | Text | ⬜ | 기본값은 빈 문자열. `promote-slipbox`, `archive-resources`, `link-project/<id>` 중 하나를 사용하며 삭제 결정은 본문 체크박스로 남김 |

본문 정본은 `99_Templates/quick-capture.md`를 따른다. `AI 생성`은 사용자의 주장이 아니며, 사용자가 명시적으로 채택하기 전에는 permanent note의 본문 근거로 사용하지 않는다.

## 🧠 Slipbox (`01_Slipbox/`)

자기 주장을 담은 영구 노트와 탐색을 돕는 허브를 둔다. 단상·스케치는 `00_Inbox/`에 포착한다. 영구 노트는 Zettelkasten 정원 비유로 **성숙도(status)** 를 표현한다.

```yaml
---
created: 2026-01-15
slug: <영문-슬러그>
type: permanent       # permanent | hub(MOC)
status: seedling      # seedling | growing | evergreen
aliases:
  - <대체 이름>
used_in:              # 선택 - 승인된 재사용 근거만 기록
  - "[[이 노트를 다시 쓴 글이나 문서]]"
---
```

| 필드 | 값 | 의미 |
|------|----|----|
| `type: permanent` | 영구 노트 (자기 언어로 정제됨) | 기본값 |
| `type: hub` | MOC (Map of Content) | `status`를 쓰지 않는다. 주장 노트가 아니라 성숙도 기준이 맞지 않는다 |
| `status: seedling` | 생각을 세웠지만 아직 거친 상태 | 본문이 짧거나 AI 초안의 표현과 구조가 남아 있어도 된다 |
| `status: growing` | 내가 다시 읽고 다듬어 명료해졌지만, 아직 고칠 데가 남은 상태 | 내 말로 고쳤고, 주장을 받치는 근거나 예시(경험·출처)가 붙었다. 열린 질문이 남아 있어도 된다 |
| `status: evergreen` | 지금으로서는 크게 바뀌지 않을 만큼 다듬은 상태 | 다시 읽어도 주장(제목)을 바꿀 데가 없다. 남은 「발전시킬 질문」이 없거나, 남아 있어도 주장을 흔들지 않는다 |
| `used_in` | 이 노트를 **다른 맥락에서 다시 쓴** 글·문서 | 자동 기록하지 않음. `_index.base`의 재사용 뷰가 개수를 센다 |

성숙도(`status`)는 노트를 얼마나 다듬었는지 하나만 나타낸다. 표의 신호는 판단을 돕는 단서이고 모두 갖춰야 하는 조건이 아니다. 적용 한계나 반론은 어울리는 노트에서만 쓰고 단계의 조건으로 요구하지 않는다. 단계는 사용자만 정하며, 길이·링크 수·재사용 횟수로 정하지 않는다. 기준은 누가 처음 썼는지가 아니라 내가 결과를 이해하고 내 판단으로 고쳤는지다.

주장을 얼마나 확신하는지는 단계와 따로 본다. 별도 속성을 두지 않고, 필요할 때 본문에 "자기 관찰에서 나온 가설이다"처럼 한 문장으로 밝힌다.

성숙도는 다시 가꿀 노트를 고르는 기준으로 쓰고, 공개 노트에서는 독자에게 그 노트가 얼마나 다듬어졌는지 알리는 표시로 쓴다. 빠르게 포착한 거친 생각은 `00_Inbox/`에 두고 Slipbox에 바로 들이지 않으므로, `seedling`도 한 가지 주장을 세운 영구 노트다.

### 연결 규칙

- 같은 키워드보다 구체적인 주장 관계를 설명할 수 있는 링크를 우선한다. 근거·적용·반례·상하위 관계뿐 아니라 구조적 유사성이나 관점 전환도 후보가 될 수 있다.
- 특정 주장·인용은 블록 링크, 절 전체는 헤딩 링크, 문서 전체가 관련될 때만 문서 링크를 사용한다.
- 본문의 설명에 직접 도움이 되는 어구에 자연스럽게 링크한다. 링크를 넣기 위해 문장이나 논점을 덧붙이지 않는다. 본문에 넣기 어려운 관계는 `## 연관된 노트`에 둔다. 기본은 제목 링크만 적고, 제목과 현재 글의 문맥만으로 연결 이유가 드러나지 않거나 특정 대목·적용 한계를 짚어야 할 때만 짧은 설명을 덧붙인다. 제목이나 본문을 되풀이하는 설명은 생략한다.
- 창의적 연결은 함께 읽을 때 생기는 구체적인 해석이나 질문을 짧게 적는다. 유추·가설을 확정된 근거처럼 쓰지 않으며, 오해할 수 있는 비교는 적용 한계를 밝힌다. 모든 연결에 질문이나 별도 한계 섹션을 강제하지 않는다.
- 생각·개발 노트나 참고노트가 본문에서 이미 같은 역할로 연결되어 있으면 하단 `## 연관된 노트`에서는 생략한다. 본문으로 옮길 때 하단 설명에 별도 의미가 있는지 확인하고 중복만 덜어낸다.
- 블로그 글을 다음 읽을거리로 추천할 때는 `## 연관된 글`에 둔다. 본문에서 문맥을 보충하는 링크와 하단의 다음 읽을거리는 역할이 다르므로 함께 둘 수 있다. 본문에 등장한 글을 모두 모으지 않고, 현재 글을 읽은 뒤 이어 읽을 이유가 있는 글만 고른다. 노트와 글이 함께 있으면 두 섹션으로 나누고, 해당 항목이 없는 섹션은 만들지 않는다. 링크 설명은 위의 선택 기준을 동일하게 따른다.
- 적합한 연결이 없으면 억지로 만들지 않는다. Backlinks가 보여주는 역연결을 본문에 중복하지 않는다.
- 연결 수만으로 `growing`·`evergreen`을 판정하지 않는다.
- 실제 `## 연관된 노트` 형식은 `99_Templates/slipbox-template.md`를 따른다.

### 재사용(`used_in`)에 무엇을 넣는가

노트가 다른 맥락에서 다시 쓰였는지 기록하는 필드다. 재사용은 다시 읽을 계기이지 성숙도의 판정 기준이 아니다. **출처는 재사용이 아니다** - 이 노트를 낳은 자료를 넣으면 노트가 태어난 사실을 재사용으로 세게 되고, 다산성 자료 하나가 자기 자식 노트들의 점수를 통째로 올린다. X에서 파생된 것은 X를 입증하지 못한다.

| 넣는다 | 넣지 않는다 |
|--------|-------------|
| 이 노트를 인용한 블로그 글 | 이 노트를 승격시킨 원본 참고노트 |
| 이 원칙을 적용한 운영 문서·프로젝트 노트 | 이 노트에서 파생된 분석 문서 |
| 다른 자료를 읽다가 이 주장을 불러 쓴 참고노트 | `00_Inbox`의 초안 (승격·흡수될 때 다시 판정) |

후보 탐지는 `vault-lint`가 기계적으로 하고(`reuse_by_note`), **기록은 사람이 승인한 항목만** 한다. 자동으로 채우지 않는다.

## 📝 Blog Posts (`20_Projects/blog/`)

개인 글·기술 글의 **전문 정본**. 초안과 외부 발행본을 이 폴더에 한 번만 보관하고, `01_Slipbox/`에는 이 글에서 분리한 독립 개념만 둔다.

```yaml
---
title: <글 제목>
created: 2026-07-11             # vault 수집·작성일
slug: <영문-슬러그>              # 사이트 주소. 발행 전에 정한다
status: draft                   # draft | published
author: TaeZ
summary: <글의 문제·범위와 읽고 얻을 내용을 전하는 짧은 소개문>
publication: Velog              # 외부 발행본일 때
source: https://...             # 외부 원문 URL
published: 2025-08-29           # 원문 발행일을 확인한 경우에만
thumbnail: "[[이미지.jpg]]"       # 선택. 원본 이미지 위키링크 또는 글 기준 상대 경로
thumbnail_style: plain          # 선택. plain(기본) | soft(가장자리를 옅게 처리)
series: <연재명>                # 연재일 때
series_order: 1
related:
  - "[[관련 글 또는 프로젝트]]"
---
```

| 규칙 | 설명 |
|------|------|
| 정본 위치 | 전문은 `20_Projects/blog/`에만 둔다. 프로젝트별 하위 `blog/` 폴더를 만들지 않는다. |
| 발행본 | `status: published`에는 `publication`, `source`를 필수로 둔다. `published`는 발행일이 확인될 때만 기록한다. |
| 초안 | `status: draft`를 사용한다. 과거 반복본은 `40_Archive/blog-drafts/`로 보낸다. |
| summary | 목록·검색·공유 미리보기에 쓰는 짧은 소개문이다. 아래 블로그 summary 작성 기준을 따른다. |
| 연재 | `series`, `series_order`를 사용한다. 사이트가 이 값으로 이전·다음 편 안내를 붙이므로 본문에 같은 목록을 쓰지 않는다. `related`에는 앞·뒤 글만 넣는다. |
| 프로젝트 글 | 프로젝트 노트 링크로 맥락을 남기고, `프로젝트/<project-id>` 태그는 위 「태그 사용 기준」에 따라 선택한다. |
| 썸네일 | `thumbnail`은 본문 삽입 이미지와 별도로 지정한다. 원본은 유지하고 웹 빌드에서 필요한 크기로 최적화한다. `soft`는 가장자리까지 글자나 도표가 없는 일러스트에만 쓴다. |
| Slipbox | 블로그 전문을 복제하지 않는다. 재사용할 개념은 별도의 `type: permanent` 노트로 압축하고 블로그 글을 링크한다. |

**블로그 summary 작성 기준**

- 제목을 보완해 다루는 문제와 구체적인 범위, 읽고 얻을 내용을 1~2문장으로 전한다. 글의 성격에 맞는 내용을 골라 쓰며 세 요소를 모두 나열할 필요는 없다.
- 질문형·결론형·소개형 모두 사용할 수 있다. 결론을 반드시 미리 밝히거나 특정 문장형을 반복하지 않는다. "살펴봅니다", "비교합니다", "구현 기록" 같은 표현도 다루는 내용이 구체적이면 사용할 수 있다.
- 제목 반복, 내용이 드러나지 않는 막연한 소개, 과장된 약속과 키워드 나열은 피한다. 연재 글은 연재 전체가 아니라 해당 편의 내용을 말한다.
- 작성 분량과 화면 표시 길이는 구분한다. 표시 기준은 summary 전체를 사용하되, 글 목록과 기본 글 카드에서는 최대 3줄로 제한하고 넘치는 부분은 말줄임으로 처리하는 것이다. 글 카드에 직접 작성한 연결 설명이 있으면 그 설명을 우선한다. 페이지 메타 설명·공유 미리보기·RSS에는 전체 summary를 전달한다. 화면에 따라 잘릴 수 있으므로 핵심을 앞에 두되, 첫 문장만 보이는 것을 전제로 원고를 줄이지 않는다.
- 구체성과 본문과의 일치는 원문을 읽고 판단한다. vault-lint는 블로그 summary의 문장 끝 표현만으로 검토 후보를 만들지 않는다.

공개 사이트의 글 카드 문법과 썸네일 표시 위치는 [공개 위키 작성 규칙](https://github.com/taez224/taez224.github.io/blob/main/AUTHORING.md)을 따른다.

### 연재 허브 (`20_Projects/blog/<series>.md`)

연재마다 허브를 하나 두고, 글의 `series` 값으로 연결한다. 사이트는 허브의 파일명이 아니라 제목(`title`, 없으면 첫 `# ` 제목, 그것도 없으면 파일명)이 `series` 값과 같을 때 둘을 잇는다. 연재명에 파일명으로 쓸 수 없는 문자가 있으면 `title`에 연재명을 그대로 적는다. 허브 자체에는 `series`를 넣지 않아 실제 연재 글 목록과 섞이지 않게 한다. 발행한 편이 하나도 없는 허브는 사이트에 페이지가 생기지 않는다.

```yaml
---
title: Think with AI
created: 2026-07-15
type: series
status: active                # active | on-hold | completed
started: 2026-07-15
ended: null                   # completed일 때만
last_published: null          # 실제 최근 발행일, 발행 전이면 null
next_action: 1화 발행
---
```

| 필드 | 규칙 |
|------|------|
| `status` | `active`는 진행 의사가 있음, `on-hold`는 잠정 중단, `completed`는 기획한 흐름이 완결됨을 뜻한다. 공백 기간만으로 자동 전환하지 않는다. |
| `started` | 연재를 시작했거나 연재로 관리하기로 결정한 날짜 |
| `ended` | `completed`일 때만 완결일 기록 |
| `last_published` | 최근 글을 실제 발행한 날짜. 새 글 발행 시 갱신하며 초안 작성일로 대신하지 않는다. |
| `next_action` | 진행 중·잠정 중단 연재를 다시 열 때 판단할 한 가지 행동 |

Blog Base는 `last_published` 또는 발행 전 `started`를 기준으로 30일·90일 공백을 표시한다. 이는 점검 신호일 뿐 `on-hold`나 `completed`를 자동 판정하지 않는다.

## 🔧 DevLog (`30_Resources/Development/DevLog/`)

회사 업무 맥락을 포함할 수 있는 로컬 개발 기록이다. Git에서는 제외하지만 본인이 작성한 경력·글쓰기 근거이므로 QMD 검색에는 포함한다.

| 폴더 | 역할 | 작성 기준 |
|------|------|-----------|
| `daily/` | 사실과 작업 흐름 | 한 일·오류·명령·임시 판단을 편하게 기록 |
| `weekly/` | 선택적 압축 | 프로젝트별 변화·결정·성과·다음 행동만 요약 |
| `monthly/` | 장기 패턴 | 여러 주를 관통하는 패턴이나 블로그·이직 소재가 있을 때만 작성 |

```yaml
---
date: 2026-03-16
projects:
  - <project-id>      # 20_Projects/ 의 project_id와 매칭
---
```

`projects`는 `20_Projects/`의 canonical `project_id`와 맞춘다. 저장소·모듈·도구 이름을 별도 프로젝트 값으로 만들지 않고, 어떤 결과물을 위한 작업이었는지에 따라 귀속한다. Java·Spring·Kubernetes 같은 기술은 하위 폴더를 만들지 않고 `개발/*` 태그로 표현한다. 날짜에서 벗어나 재사용할 수 있는 문제 해결법은 `30_Resources/Development/Troubleshooting/`으로 분리한다.

## 🧠 Development Concepts (`30_Resources/Development/Concepts/`)

공개 가능한 개발 지식 노트다. 개념 설명, 설계 선택을 이해하기 위한 학습 기록, 독립 실험의 결과를 담는다. 이 폴더의 일반 Markdown은 다음 사이트 빌드에 자동으로 포함되며, 이름이 `_` 또는 `.`으로 시작하는 파일·폴더는 제외하고 명시적 `exclude`를 우선한다. 프로젝트·조직·운영 맥락을 그대로 보존하는 기록은 여기에 두지 않는다.

```yaml
---
created: 2026-09-06
slug: <영문-슬러그>
summary: <열기 전의 독자가 무엇을 다루는 노트인지 알 수 있는 한 문장>
tags:
  - 개발/<기술>
---
```

`created`는 모든 노트의 필수 필드이고 `summary`는 노트를 열기 전의 독자가 무엇을 다루는 노트인지 알 수 있는 한 문장이다. 사이트의 페이지 설명, RSS, 검색 결과에 그대로 쓰인다. 설계 판단을 다루면 그 질문이나 구분을, 만들거나 시험한 기록이면 무엇을 어떻게 했는지를 적는다. 노트가 하는 일을 적는 꼬리("~를 정리한다")는 쓰지 않는다. `tags`는 여러 폴더를 가로질러 실제로 검색할 기술 주제가 있을 때만 선택적으로 쓴다. 날짜 필드 `published`와 `updated`는 위 「공개 노트의 날짜」와 공통 필드 규칙을 따르는 선택 필드다. 발행 상태를 나타내는 별도 속성은 두지 않는다. 공개 가능한 내용만 이 폴더에 저장하며, 별도 파일 등록 없이 사이트 빌드에 포함된다.

새 노트는 [[dev-concept-template|Development Concept Template]]의 속성과 작성 안내를 출발점으로 삼는다. 헤딩과 구성은 내용에 맞게 정한다.

## 🧯 Development Troubleshooting (`30_Resources/Development/Troubleshooting/`)

관찰한 증상, 원인과 해결책의 근거, 검증 범위를 남기는 개발 문제 해결 노트다. 재현하지 못했거나 원인이 미확정이면 그 범위를 본문에 밝힌다. 확인 범위는 관련 설명 옆에 쓰고, 여러 설명에 걸쳐 있어 한곳에서 구분하는 편이 명료할 때는 별도 `확인 범위` 절로 모을 수 있다. 파일명은 결론이 아니라 상황을 부르는 명사구이고, `summary`는 알아낸 답 한 문장이다. `created`와 `summary`를 공통으로 사용하고, 기술 주제는 필요한 경우에만 `tags`에 적는다. 오류 문자열로 노트를 찾게 하려면 `aliases`에 원문을 넣는다. 날짜 필드 `published`와 `updated`는 Concepts와 같은 선택 필드다. 별도의 `publish`, `status`, `related`, `evidence_level` 필드는 두지 않는다. 새 노트는 [[dev-troubleshooting-template|Troubleshooting Template]]의 속성과 작성 안내를 출발점으로 삼는다. 문제를 좁히고 해결·검증한 사고 순서를 유지하며, 고정 헤딩으로 나누지 않는다.

```yaml
---
created: 2026-09-06
slug: <영문-슬러그>
summary: <알아낸 답을 한 문장으로>
aliases:
  - <오류 메시지 원문, 필요할 때만>
tags:
  - 개발/<기술>
---
```

## 🛠️ Development Tools (`30_Resources/Development/Tools/`)

특정 도구를 어떤 용도로 어떻게 쓰는지 남기는 노트다. 도구 이름이 들어가더라도 설계 결정을 기록한 글은 Concepts에 둔다. 속성은 Concepts와 같고, `summary`에는 어떤 도구를 어떤 용도로 어떻게 쓰는지를 한 문장으로 적는다. 첫 태그는 노트가 다루는 기술이나 주제로 두고, `개발/도구`는 둘째 이후에 붙인다. 그 밖의 태그는 실제로 가로질러 검색할 때만 더한다. 새 노트는 [[dev-concept-template|Development Concept Template]]을 출발점으로 삼는다. 이 폴더도 사이트 빌드에 자동으로 포함된다.

```yaml
---
created: 2026-09-06
slug: <영문-슬러그>
summary: <어떤 도구를 어떤 용도로 어떻게 쓰는지 한 문장으로>
tags:
  - 개발/<기술>
  - 개발/도구
---
```

## 📰 Articles & Clippings (`30_Resources/References/Articles/`, `30_Resources/References/Clippings/`)

Clippings는 아래의 공통 속성을 사용한다. Git 추적 카드에는 출처 메타데이터와 확인 가능한 요약만 남기며, 개인 열람용 원문 스냅샷은 Git에서 제외된 `_local-snapshots/`로 분리한다.

```yaml
---
title: <원본 제목>
source: https://...           # 원본 URL (Clipper 자동)
author:
  - <원작자>                   # 기존 Clipper의 wikilink 값도 허용
published: 2024-09-14         # 원본 발행일 (Clipper 자동)
created: 2025-02-10           # vault 수집일 (Clipper 자동)
description: <원문에 근거한 한국어 식별 문장 1~2개> # 평가·시사점 추가 금지
thumbnail: <이미지 URL>       # 선택
status: unread                # unread | read | archived
my_take: ""                   # 내 한 줄 평 (정리 시 작성)
---
```

> Clippings는 **읽기 전 수집함**이며 literature note 자체가 아니다. 원문 제목을 한국어 파일명으로 옮기고, 출처 메타데이터와 원문에 근거한 한국어 식별 문장 1~2개, 저장 맥락을 남긴다. 원문을 충분히 확인했을 때만 핵심 주장·방법·사례를 보존하는 `## 내용 요약` 4~7개를 추가하고, 유료벽·로그인·불완전 추출로 사실 확인이 부족하면 이 섹션을 생략한다. `source`가 원문 URL의 정본이므로 본문의 `## 원문` 링크는 만들지 않는다. 전문·장문 번역은 Git 추적 카드에 넣지 않으며, 개인 열람용 원문은 명시적으로 요청한 경우에만 Git에서 제외된 `Clippings/_local-snapshots/`에 둔다.
>
> 읽은 뒤에는 다음 중 필요한 만큼만 진행한다:
> - 반응이 한 줄이면 `my_take`를 채우고 `status: read`로 유지
> - 인용과 생각을 남길 가치가 있으면 `Articles/`에 별도 literature note를 만들고 clipping을 링크
> - 여러 맥락에 재사용할 내 주장이 생기면 이후 검토에서 `01_Slipbox/` 영구 노트로 승격

> 기존 전문 번역형 Articles는 역사 기록으로 유지한다. `source`와 `status`처럼 확인 가능한 속성만 우선 보강하고, 본문은 실제로 다시 사용할 때만 `literature-note` 기준으로 재정리한다. 새 literature note에는 전문을 복제하지 않는다.

## 📅 Periodic Notes (`10_Periodic Notes/`)

```yaml
---
created: 2026-05-27   # 파일명(YYYY-MM-DD)에서 파생, 모든 노트 공통 필드
type: daily           # daily | weekly | monthly (단일 문자열, list 아님)
date: 2026-05-27      # daily: YYYY-MM-DD / weekly: 첫날 / monthly: 1일
week: 2026-W22        # daily/weekly만 (gggg-[W]WW, ISO week)
month: 2026-05        # weekly/monthly만 (YYYY-MM)
tags:
  - type/timeline/daily   # ⚠️ frontmatter tags에 # 금지
---
```

> Templater 템플릿은 `tp.file.title` 기준으로 날짜를 파생시킨다 (백필 시 정확성 확보). `tp.date.now()` 사용 금지.
