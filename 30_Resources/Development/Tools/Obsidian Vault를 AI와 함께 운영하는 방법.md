# Obsidian Vault를 AI와 함께 운영하는 방법

이 vault는 git으로 관리하고 [GitHub](https://github.com/taez224/obsidian)에 올려 둔다. AI 없이 혼자 관리하던 때는 저장 위치, 속성, 출처 표기, 연결 기준을 매번 챙기다 지쳐서 손을 놓곤 했다. 지금은 그 관리를 AI에게 맡기고 쓰는 데 집중한다. 관리를 넘기고 나니 욕심이 생겨, 노트 자체도 일부 맡기는 *바이브 노팅*을 해 보는 중이다.

이 노트는 그 방식을 정리한 것이다. 반복되는 기준은 문서로 빼 두고 AI가 작업마다 그 문서를 읽게 한다. 생각이나 자료를 건네면 AI가 기준에 맞춰 저장하거나 초안을 다듬고, 나는 규칙이 지켜졌는지와 원래 생각이 담겼는지만 본다. 지침과 스킬은 모두 저장소에 있다. 공개 폴더의 노트가 이 사이트로 올라오는 과정은 [[생각의 정원을 만들고 배포하는 과정]]에 적었다.

## 지침을 두는 곳

모든 지침을 한 파일에 넣으면 길어지고, 같은 규칙을 여러 곳에 복사하면 서로 다른 내용이 남는다. 그래서 문서마다 역할을 나눴다.

| 문서 | 맡는 역할 |
| --- | --- |
| `AGENTS.md` | 노트의 저장 위치, 작업에 맞는 스킬, 승인이 필요한 변경 같은 공통 기준 |
| 작업별 `SKILL.md` | 메모 저장, 자료 정리, 개발 노트 작성, 연결 검토 같은 한 작업의 절차 |
| 템플릿 | 생성일·요약 같은 기본 속성과 쓰면서 살펴볼 질문 |
| 속성 규칙 문서 | 날짜·태그·노트 유형처럼 여러 노트가 함께 쓰는 속성의 기준 |

`AGENTS.md`에는 절차를 복사하지 않고 어떤 지침을 볼지만 적는다. 스킬도 속성과 형식은 규칙 문서와 템플릿을 가리킨다. 기준을 고칠 때 한 곳만 바꾸기 위해서다. 질문으로 생각을 넓히는 템플릿의 역할은 [[템플릿은 내용을 채우는 틀이 아니라 생각을 확장하는 질문이어야 한다|생각을 확장하는 템플릿]]에 정리했다.

## 스킬과 검색 도구

Obsidian은 위키링크, 콜아웃, 속성처럼 일반 마크다운에 없는 문법을 쓴다. AI가 그냥 마크다운으로 쓰면 링크가 걸리지 않고 콜아웃은 인용문으로 남는다. 이 문법은 Obsidian CEO Steph Ango가 공개한 [obsidian-skills](https://github.com/kepano/obsidian-skills)로 해결했다. 마크다운 스킬과 함께 Bases, Canvas, CLI 스킬이 들어 있어서, Inbox에 오래 머문 노트나 고립 노트를 보여 주는 Base 대시보드도 AI가 만들고 고친다.

검색은 둘로 나눈다. 제목이나 문장을 정확히 알면 `rg`가 낫다. 파일을 그대로 읽으니 방금 고친 내용도 바로 걸리고 엉뚱한 결과가 섞이지 않는다. 반대로 "포착과 승격을 나눈다"는 생각을 다른 말로 적어 둔 노트는 `rg`로 찾지 못한다. 이때는 [qmd](https://github.com/tobi/qmd)를 쓴다. vault의 마크다운을 로컬에 색인해 두고 키워드 검색과 문장 임베딩을 함께 써서, 표현이 달라도 뜻이 가까운 노트를 올린다. 대신 색인을 다시 만들기 전의 변경은 반영되지 않는다. 어느 쪽을 언제 쓰는지는 qmd가 제공하는 스킬에 이 vault의 검색 절차를 더해 적었다.

노트를 다루는 절차는 내 방식에 맞춰 직접 스킬로 만들었다. 주로 쓰는 것은 이렇다.

| 스킬 | 하는 일 |
| --- | --- |
| `capture-fleeting-note` | 떠오른 생각을 원문 그대로 Inbox에 남긴다 |
| `capture-reference-card`, `literature-note` | 외부 자료를 읽기 전에는 카드로, 읽은 뒤에는 반응과 함께 남긴다 |
| `development-note` | 개발 개념, 문제 해결, 도구 노트를 쓴다 |
| `permanent-note` | 생각을 다시 쓸 수 있는 영구 노트로 다듬는다 |
| `review-zettelkasten` | 기존 노트의 보강·승격·연결 후보를 찾는다 |
| `socratic-dialogue` | 질문으로 전제와 근거, 반례를 점검한다 |
| `vault-lint` | 끊긴 링크, 속성 오류, 고립 노트를 검사한다 |

## AI에게 맡기지 않는 것

날짜와 속성을 맞추는 일은 형식이고, 노트를 합치거나 나누거나 새로 연결하는 일은 의미 판단이다. 형식은 맡기고 의미 판단은 내가 한다. 노트 삭제와 이동, Slipbox 승격, 병합, 구조 노트 생성, 공개 범위 변경, 커밋과 push는 AI가 후보와 이유를 보고하는 데서 끝나고, 적용은 승인 뒤에 한다. 빠르게 남긴 생각을 [[생각 캡쳐와 영구 노트 승격은 분리해야 한다|영구 노트로 승격하는 일]]도 따로 요청할 때만 한다.

AI의 제안은 두 가지를 확인한다. 연결 후보는 [[이 위키를 가꾸는 기준|가꾸는 기준]]의 연결 규칙에 맞는지, 초안은 원래 생각을 과장하거나 확인하지 않은 결론을 보태지 않았는지 본다.

## 규칙을 고친 사례

어색한 문장은 그 자리에서 고친다. 같은 문제가 두 번 나오면 문장이 아니라 지침이나 템플릿을 고친다.

개발 노트 템플릿의 헤딩 셋(‘다루는 질문’, ‘설명’, ‘예제와 적용 경계’)이 노트마다 목차처럼 남았다. 내용은 담겼지만 흐름이 끊겼다. 템플릿에는 속성과 작성 안내만 남기고, 헤딩은 내용에 맞게 정하도록 스킬을 고쳤다.

기술 노트라는 이유로 조사한 구현 내용이 전부 들어가기도 했다. 핵심 원리, 선택 이유, 주요 한계를 기본 깊이로 삼고, 코드와 세부 설정은 이해나 재현에 필요할 때만 넣도록 했다.
