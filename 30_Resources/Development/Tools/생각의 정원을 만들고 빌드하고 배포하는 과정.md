# 생각의 정원을 만들고 빌드하고 배포하는 과정

## 다루는 질문

노트 앱에 쓴 Markdown을 그대로 원본으로 두고 그중 공개할 것만 정적 사이트로 내보내려면 어떻게 구성하는가. 노트를 공개할 때마다 사이트 코드를 고치지 않아도 되게 하려면 규칙을 어디에 두어야 하는가.

## 설명

### 원본은 vault, 배포는 산출물만

사이트용 원고를 따로 두지 않는다. Obsidian vault의 노트가 원본이고, Astro가 그중 공개 대상을 읽어 정적 파일로 만들며, GitHub Pages에는 그 결과만 올린다. 저장소가 공개여도 사이트에 나가는 범위는 빌드가 고른 노트로 한정된다. Git 공개와 사이트 공개는 별개의 문제다.

### 공개 범위는 설정 파일과 frontmatter로

어떤 노트를 내보낼지는 사이트 코드가 아니라 설정 파일 하나와 각 노트의 frontmatter로 정한다.

- 읽을 폴더 목록과 폴더별 규칙을 설정에 둔다. 폴더마다 전부 공개할지, 특정 상태(`status: published`)나 유형(`type: series`)일 때만 공개할지, 그래프에 넣을지를 적는다.
- 제외 폴더를 명시한다. 개인 메모, 일간 기록, 작업 로그, 외부 자료 클리핑, 아카이브, 템플릿은 아예 읽지 않는다.
- 이름이 `_`나 `.`으로 시작하는 파일·폴더는 어디에 있든 공개하지 않는다. 폴더 안의 운영용 색인은 이 규칙으로 뺀다.

이렇게 두면 노트 하나를 공개하는 일은 공개 폴더에 두고 push하는 것으로 끝난다. 반대로 공개 폴더에 있는 미완성 노트도 그대로 나간다. 자동 공개 폴더에는 공개 가능한 내용만 둔다는 운영 규칙이 이 구성의 전제다.

### 빌드는 생성과 검사 두 단계

1. Astro 빌드. 커스텀 Content Layer 로더가 vault를 읽어 노트 컬렉션을 만들고, 위키링크를 풀어 참조·역참조를 잇고, 페이지·검색 데이터·그래프 데이터·그래프 스냅샷 SVG·노트별 OG 카드·RSS·사이트맵을 산출물 폴더에 쓴다.
2. 산출물 검사. 별도 스크립트가 방금 만든 파일을 다시 열어 페이지마다 title·canonical·og:image·RSS 링크가 있는지, 노트마다 카드 PNG가 실제 1200×630인지, 검색·그래프 데이터가 비지 않았는지 확인한다. 하나라도 어긋나면 빌드가 실패한다.

검사를 따로 두는 이유는 생성 단계가 조용히 성공하기 때문이다. 템플릿을 잘못 고쳐 `og:image`가 빠져도 Astro는 경고하지 않는다. push가 곧 배포인 구성에서는 산출물을 보는 검사가 배포 앞에 있어야 한다.

### 배포는 GitHub Actions로

`main` 브랜치에 push하면 워크플로가 돈다. 공개 폴더나 사이트 소스가 바뀐 push만 트리거되도록 경로 필터를 둔다. checkout, Node 준비, 의존성 설치, 폰트·OG 카드본 캐시 복원, 테스트, 빌드(검사 포함), 산출물 업로드 순서다. 테스트나 검사가 실패하면 거기서 멈추고 이전 배포가 남는다.

## 예제와 적용 경계

- 노트만 쓰거나 고칠 때는 노트 앱에서 저장하고 push하면 된다. 로컬 빌드는 필요 없다.
- 사이트 소스를 고칠 때는 push 전에 로컬에서 테스트·빌드·미리보기를 돌린다. `astro preview`는 방금 만든 산출물을 그대로 서빙하므로 배포될 모습과 같다.
- 산출물 폴더는 Git에 넣지 않는다. 빌드가 매번 다시 만든다.
- 이 구성은 공개 여부를 폴더 단위로 나눌 수 있을 때 맞는다. 한 폴더 안에서 노트마다 공개 여부가 갈리면 상태·유형 같은 frontmatter 규칙을 폴더 규칙에 얹어야 한다.
