# 2026-05-23 DevLog

EPIC-1 기능을 다 얹은 `DeploymentFlow` 를 **기능 유지한 채 db·메모리·트랜잭션·리소스·동시성 관점으로 리스크 점검**하고, 그 결과를 **T1~T5 태스크로 쪼개 각각 커밋**한 날(Stop hook 자동 루프). 점검의 절반은 "이미 안전함"을 audit·Javadoc으로 명문화하는 것이었고, 실제 수정은 cooldown GC와 observation leak guard 정도. 더불어 **GitOps 커밋 메시지를 관리자·비즈니스가 읽을 수 있게** 재설계했다.

## gallery — DeploymentFlow 리스크 하드닝 (T1~T5)

### 리스크 분석 → 태스크 분해
- Stop hook 루프로 진행: "기능 유지 + 리스크 분석 → 현황 문서 저장 → 태스크 단위로 쪼개 하나씩 → 완료 시 개선부 정리·커밋 → 전체 완료 시 종료"
- deployment 리스크를 분석해 문서화 (`6c25df358`)

### 실제 수정
- **T1 — cooldown lazy GC**: runtime cooldown 정책에 lazy GC 도입(`6c25df358`), 만료 entry prune(`2bc4541f1`) — cooldown map이 무한 증가하지 않도록
- **T2 — observation resource leak guards**: `ArgoCdObservationTask` 에 resource leak guard 추가(`ac5a48e1f`) + leak guard 테스트 커버(`47cbb12ff`) — #22에서 잡은 @Async/미완료 future 점유의 재발 방지

### 분석 결과 = "이미 안전"을 명문화
- **T3 — PESSIMISTIC_WRITE audit**: 모든 호출자가 이미 가드되어 있음을 audit하고 문서화 (`a4a605913`) — 코드 변경 없이 불변식 확인
- **T4 — 트랜잭션 정책 Javadoc**: `DeploymentFlow` 의 트랜잭션 경계 정책을 Javadoc으로 명시 (`fc67df707`)
- **T5 — observation serial-call 가정**: `ArgoCdObservationTask` 의 serial-call 전제를 문서화 (`efd8524ba`)

## gallery — business-aware GitOps 커밋 메시지

- GitOps push 시 자동 생성되는 커밋 메시지를 **관리자/비즈니스 관점**으로 재설계 (`5b3945603`) — 메시지 조립을 위해 Action/Helper 추출 (`16ece3aee`)
- 이벤트에 **request type** 을 실어 메시지에 반영(무엇을·왜 배포/회수했는지)
- 커밋 메시지 **타이틀에 kollex 이름** 노출 — kollex 자체는 Pod가 뜨지 않아 배포에서 excluded지만, "대표" 맥락이라 히스토리에는 남김
- 단위테스트가 아니라 **실제 deploy를 반복 실행**해 생성 메시지를 눈으로 검증 → `DeploymentFlow` 오케스트레이션 정리 (이어진 `59ae21844`)

## 학습 & 인사이트

- **큰 리팩토링은 검증 가능한 작은 커밋으로 강제 분해한다**: "분석 → 문서 → 태스크 분해 → 하나씩 커밋 → 완료 시 종료" 루프로 가면, `DeploymentFlow` 같은 위험한 코드도 T1~T5처럼 독립적으로 되돌릴 수 있는 단위가 된다. 한 번에 갈아엎는 것보다 회귀 추적이 쉽다.
- **리스크 점검의 산출물 대부분은 "수정"이 아니라 "확인"이다**: T3~T5는 코드 변경이 아니라 audit·Javadoc·가정 명문화였다. "이미 안전한 이유"를 문서로 박아두면, 다음 사람이 같은 의심으로 시간을 쓰지 않는다 — 점검을 무조건 코드 변경으로 끝내려 하면 오히려 멀쩡한 코드를 건드린다.
- **메모리 누수는 "안 비우는 map"에서 온다**: runtime cooldown처럼 키가 계속 쌓이는 구조는 lazy GC(접근 시 만료 entry prune)로 무한 증가를 막아야 한다. 기능엔 안 보이지만 장기 운영에서 터진다.
- **비동기 leak는 guard + 테스트 + 가정 문서가 한 세트**: #22의 observation 누수는 단발 수정으로 끝낼 게 아니라, leak guard(코드) + 테스트 커버 + serial-call 가정(문서)을 함께 둬야 재발하지 않는다.
- **GitOps 커밋 메시지의 독자는 운영자다**: 자동 생성 메시지라도 git 히스토리는 사람이 읽는 운영 로그다. "무엇을·왜(request type)·누구의(kollex)" 를 담으면 히스토리가 곧 배포 감사 추적이 된다. excluded 자원(kollex)이라도 맥락상 의미 있으면 메시지에 남기는 게 가독성에 낫다.
- **포맷 검증은 실제 실행으로**: 커밋 메시지 같은 "사람이 읽는 출력"은 단위테스트로 모양만 맞추기보다 실제 deploy 한 사이클을 돌려 눈으로 확인하는 게 빠르고 정확하다.
