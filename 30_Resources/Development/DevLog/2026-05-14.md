### 이슈 #6 — K8s Secret 프로비저닝 (드릴링 + 구현 WIP)
- **핵심 런타임 함정 발견**: `envFrom.secretRef` 는 **컨테이너 생성 시점에 kubelet이 주입** → Secret을 apply 해도 **이미 떠 있는 Pod의 env는 갱신되지 않음**. 따라서 Secret 값만 바뀐 재배포는 Pod에 반영 안 됨
  - 해결: pod template에 **rollout trigger annotation** 추가 → `Subscription.modifiedAt.toEpochMilli()` 값으로. "정확히 값 변경일 때만"이 아니라 "값이 바뀌면 반드시 rollout"이 목적이므로 약간의 over-trigger는 감수
  - 새 controller/Reloader 추가 없이 **기존 GitOps 흐름 재사용**
- **Secret apply 위치 = "Git push 직전 gate"**: `DeploymentFlow.applyRuntimeSecretGate()` 가 `DeploymentGitOpsTask` 보다 먼저 와야 GitOps와 순서가 맞음 → Task 분할(A) 대신 **변경 범위를 작게 유지하는 옵션 C** 채택 (Task→Task 의존 회피)
- **`stringData` + SSA 충돌**: `K8sSecretProvisioningProxy` 에서 `withStringData(dataByKey)` 를 server-side apply와 함께 쓰면 안 됨(K8s 공식 문서). `createOrReplace` 도 쓰지 않기로 한 결정 재확인 → SSA로 일원화
- **null 처리 = 계약**: `null` value를 `""` 로 바꾸는 건 위험 — #6 계약상 **required missing = 차단, optional missing = skip** 인데 `""` 변환은 이를 우회
- `RuntimeSecretPlanResolver` 버그 정리: `namespace == serviceName` 오결정 → 단일 namespace 시그니처로, `(versionId, key)` 중복 시 **마지막 값이 조용히 이기는** 문제에 검증 추가
- `ManifestRuntimeRefValidator` 설계 강화: 모든 workload/container를 훑어 unprefixed `secretName` 을 잡는 느슨한 설계 + `serviceName → Set<secretName>` 머지로 동명 workload doc이 뭉개지는 문제 보완
- **레이어 경계 준수**: `-crypto-secret` 자동 주입을 위해 feature에 fabric8 라이브러리를 직접 추가하지 말고 **proxy를 거쳐** 해결. 자동 주입도 "Drama면 무조건"이 아니라 `subscriptionSecrets` / catalog `runtimePrerequisites.secrets` 기준

## 학습 & 인사이트

- **Secret을 바꿔도 Pod는 모른다**: K8s `envFrom.secretRef` 는 **컨테이너 생성 시점에만** env로 주입된다. Secret을 apply 해도 떠 있는 Pod의 환경변수는 그대로다. "Secret 값이 바뀌면 반드시 반영"되게 하려면 pod template에 **rollout을 유발하는 annotation**(예: `modifiedAt` epoch)을 심어 재기동을 강제해야 한다 — 이게 없으면 "apply 성공했는데 동작이 안 바뀌는" 유령 버그가 난다.
- **apply 순서가 정확성을 정한다**: Secret은 **Git push(GitOps 동기화) 직전**에 존재해야 한다. 구조를 예쁘게 분할(Task 쪼개기)하기보다, 핵심 리스크인 "apply 위치"부터 정확히 고치는 최소 변경(옵션 C)이 옳다 — 리팩토링 욕심이 버그 수정을 지연시키면 안 된다.
- **`stringData` 와 server-side apply는 상극**: SSA로 가기로 했으면 `withStringData` 를 섞으면 안 된다(K8s 공식). apply 전략은 한 가지로 일원화해야 필드 소유권 충돌을 피한다.
- **빈 값의 의미를 임의로 채우지 마라**: `null → ""` 변환은 편해 보이지만 계약(required=차단 / optional=skip)을 우회한다. "값 없음"의 의미는 도메인 계약이 정하고, 코드는 그걸 보존해야 한다.
- **레이어 경계가 의존성을 막는다**: `-crypto-secret` 주입 때문에 feature에 K8s 클라이언트(fabric8)를 직접 끌어오면 경계가 무너진다. 외부 시스템 호출은 proxy를 거치게 두면 feature는 순수 유스케이스로 남는다.
- **spec-drilling은 게이트지 관문이 아니다**: 모든 이슈가 정밀 드릴링을 거칠 필요는 없다. 간단한 이슈는 바로 구현으로 직행하고, ADR/코드 매핑 결정이 남은 이슈만 드릴한다 — 프로세스를 필수화하면 가벼운 일까지 무거워진다.
- **스킬은 세션에 과적합되기 쉽다**: 방금 한 작업을 그대로 스킬로 박으면 그 세션에만 맞는 절차가 된다. 신설 직후 "이게 일반 케이스에도 통하나"를 점검해 추상화해야 재사용 가능한 스킬이 된다.
- **프론트 멀티스텝 폼은 "작업 유실 방지"가 1순위**: 모달 밖 클릭 한 번에 입력이 날아가면 UX가 아니라 사고다. 닫힘 차단/경고를 먼저 깔고 시각 디테일을 다듬는 순서가 맞다.
