# 2026-05-11 DevLog

**ADR-019(DB/Secret 프로비저닝 책임 분리)** 설계를 확정하고, 그에 딸린 이슈 #2~#6을 "계약 우선(contract-first)"으로 다시 자른 날. 코드 구현보다 **설계 경계와 책임 주체를 못 박는 데** 하루를 썼다 — "오버엔지니어링 하지 마라"가 반복 화두였다. 곁가지로 구독 시 Secret 입력 UI/UX를 설계하고, gallery-proxy 테스트 인프라(jacoco)와 .claude 워크플로를 정비했다.

## gallery — ADR-019 설계 확정

### Secret 프로비저닝 책임 분리
- 검토 대상 전제: **"앱 Secret은 배포 모듈이 K8s API로 직접 생성 / DB Secret은 PreSync Job이 생성 / Deployment는 GitOps·ArgoCD"** — 이 전제 자체가 우리 상황에 맞는지부터 재검토
- PreSync Job best practices + subscription-secret-input-design 참고. 결론은 **간결화** — `Drama-only Secret` 모델로 좁히고, Episode/frontend 설정값은 `configMapValues` 로 분리(Secret이 아니라 ConfigMap 책임)
- 운영 주체 가정 명시: 지금은 인프라팀이지만 **추후 외부 확장 염두**, gitops repo 통제권은 우리가 보유 → 이 가정이 책임 분리 설계의 전제
- sync 전 **ordering 보장** 방식 논의 (Secret이 Deployment보다 먼저 존재해야 함)
- 확정 설계를 ADR-019 본문 + references에 반영 (`5bb4fec32`)

## gallery — 이슈 #2~#6 계약 우선 슬라이싱

### #3을 "저장 위치"가 아니라 "소비 계약"으로 자르기
- 핵심 판단: **#3의 산출물은 "어디 저장하나"가 아니라 "구독 화면/후속 flow가 신뢰할 수 있는 응답 contract와 invariant"** 여야 한다
- API 계약 확정: `SubscribeTargetsResponse { List<SubscribeTargetRdo> targets; RuntimePrerequisites runtimePrerequisites; }`
  - 기존 `SubscribeTargetRdo.secretKeys` **제거** → `SubscribeTargetsResponse` 래퍼로 끌어올림
  - Secret 메타데이터 명칭을 `runtimePrerequisites.secrets` 로 통일
- runtime 요구사항 필드는 **카탈로그 메타데이터(KollexShelfVersion)** 에 귀속 — "카탈로그 secretKeys 소비 계약"이라는 한 줄 결론으로 정리

### US 무게 경계
- #3~#6이 US라기보다 **mini design spec** 에 가까워짐 → 구현 상세를 너무 많이 박으면 구현 전에 결정을 과고정해 이슈가 무거워짐. "어디까지 US에 둘지" 경계 합의

## gallery — Secret 입력 UI/UX 설계 (구독 화면)

- 갤러리 백엔드 + 모노레포 프론트의 기존 configmap 폼을 참조하고, 검증된 엔터프라이즈 서비스 사례를 리서치 → **Vercel식 단순 입력**으로 출발(처음엔 단순하게). secretKey meta는 사실상 password 형태 단일 입력

- `RuntimePrerequisites.fromJson()` 이 **nested `SecretKeyMeta` 자체의 invariant를 재검증하지 않는** 약점 지적 — 중복 key만 보고 `{"key":"bad-key",...}` 같은 부적격 값이 DB/JSON으로 들어오면 **AC-2를 우회**. 검증을 fromJson 단계로 끌어와야 한다는 결론

## 학습 & 인사이트

- **이슈는 "저장 위치"가 아니라 "소비 계약"으로 잘라야 가볍다**: #3을 "secretKeys를 어디에 저장하나"로 잡으면 storage 결정까지 끌고 들어와 무거워진다. 대신 **"구독 화면이 신뢰할 수 있는 응답 contract + invariant"** 로 자르면, 저장 위치는 나중에 바꿔도 다운스트림(프론트/후속 flow)을 깨지 않는다 — contract-first slicing.
- **US와 design spec의 경계**: AC에 구현 상세를 많이 박으면 "구현 전에 이미 결정을 고정"해버려 이슈가 mini design spec이 된다. US는 비즈니스 검증 기준(한 줄 결론)으로 가볍게 두고, 구현 매핑은 spec-drilling/구현 단계로 미루는 게 건강하다.
- **클라이언트 필터링은 검증이 아니다**: 프론트가 `secretKeys` 로 입력을 거른다고 보안이 되는 게 아니다. 서버가 카탈로그 메타데이터(`runtimePrerequisites.secrets`) 기준으로 **재검증**해야 하고, 그 invariant 검증을 `fromJson()` 같은 **역직렬화 경계**에 둬야 우회 경로(AC-2 bypass)가 막힌다.
- **책임 분리는 "운영 주체 가정"에서 출발한다**: "DB Secret을 누가 만드나(PreSync Job)" 같은 기술 결정은, 운영 주체가 인프라팀이고 gitops 통제권을 우리가 쥐고 있으며 추후 외부 확장을 염두에 둔다는 **전제 위에서만** 정당화된다. 전제를 먼저 적으면 설계가 단단해진다.
- **jacoco는 로컬엔 켜고 CI엔 끈다**: 커버리지 리포트를 CI마다 생성하면 빌드가 무거워진다. `System.getenv('CI')` 로 분기해 로컬 개발자에게만 켜두는 off-by-default가 실용적 절충.
- **증분 빌드 캐시가 검증을 속인다**: Gradle `UP-TO-DATE` 가 많으면 "테스트 통과"가 실제 실행이 아니라 캐시 스킵일 수 있다. 검증 스킬은 이걸 가정하지 말고 clean이나 강제 실행으로 진짜 돌았는지 확인해야 한다.
