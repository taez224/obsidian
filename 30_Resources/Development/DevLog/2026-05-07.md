# 2026-05-07 DevLog

QRA를 Gallery로 통합한 뒤 터진 **이벤트 self pub/sub 문제**를 하루 종일 파고든 날. pub/sub 주체가 둘 다 갤러리가 되면서, bro 모드에선 자기 이벤트를 못 받고 kafka 모드에선 두 번 받는 모드별 비대칭이 핵심이었다. 결국 `ApplicationEventPublisher` + `@TransactionalEventListener` 기반으로 in-process 경로를 분리해 정리. 곁가지로 sonarlint 리팩터, PreSync Job DB 프로비저닝 리서치, agent-hub의 Codex `.mcp.json` 정착, qra-view 디자인 토큰 정합화까지.

## gallery (이벤트 아키텍처 / 구독 라이프사이클)

### SubscriptionLifecycleEvent self pub/sub 문제
- **증상**: QRA→Gallery 통합 후 `SubscriptionLifecycleEvent` 의 발행·수신을 모두 갤러리가 담당하게 됐는데, k8s `bro` 프로파일에서 **자기 이벤트를 자기가 수신하지 못함**(listener 트리거 안 됨, sub 로그 무발생). 반대로 `kafka` 모드에선 **중복(2회) 수신**
- **제약**: 외부에서 받는 경로는 살아 있어야 하고(발행은 그대로), 모드별로 동작이 깨지면 안 됨 — "bro 고치면 kafka 깨지고" 식의 trade-off를 실제 코드로 검증하며 좁힘
- **해결 방향**:
  - self-event를 **in-process로 분리** — `EventProxy` 대신 `ApplicationEventPublisher` 로 발행하고 `@TransactionalEventListener` 로 수신 (`40f92bb57`, `85457a10b`)
  - `SubscriptionPvsFlow` 의 in-process 발행을 `ApplicationEventPublisher` 로 전환 (`85457a10b`)
  - 이벤트 핸들러에 `@Transactional(REQUIRES_NEW)` 부여로 트랜잭션 경계 분리 (`3647fb009`)
  - `GalleryVelloEventProxy` 컴포넌트 어노테이션 주석 처리해 중복 발행 차단 (`96f9582f7`)
- **모드별 핵심 분기**: Kafka/Bro/Nats 모드에선 DomainEvent의 `publishEventLocally` 를 스킵 → Kafka 라운드트립으로 돌아올 때 `ShardMessageDispatcher` 를 통해 **1번만 소비**. Local 모드에선 `publishEventLocally` 가 유일한 전달 경로라 유지
- `RepoGitOpsQueuedEvent`, `SubscriptionDeploymentResultEvent` — 외부 수신 경로가 없는 순수 self-consume 이벤트는 별도(옵션 B) 처리
- Kafka consumer 설정 정리 + 잔존 `qra` 참조 제거 (`dd50122d3`, `924c8f8ff`), TRACE 로깅·미사용 consumer 설정 정리 (`881177f5a`)
- `prologueVersion` 7.1.29 ↔ 7.1.43 토글 (`1312f1430`, `4a4a69e73`) — bro/kafka 인프라 의존 버전 맞춤

## 학습 & 인사이트

- **단일 서비스 self pub/sub은 메시징 모드마다 함정이 다르다**: 같은 코드라도 bro에선 "자기 이벤트 미수신", kafka에선 "중복 수신"으로 정반대 증상이 난다. 근본 해법은 **in-process 경로(ApplicationEventPublisher + @TransactionalEventListener)와 브로커 라운드트립 경로를 명확히 분리**하고, 모드별로 `publishEventLocally` 를 켜고 끄는 단일 분기점을 두는 것. 외부 브로커가 있는 모드에선 로컬 발행을 스킵해야 `ShardMessageDispatcher` 가 정확히 1회만 소비한다.
- **모드 비대칭 버그는 "한쪽 고치면 반대쪽 깨진다"가 기본값**: bro/kafka/nats/local 네 모드를 한 분기로 통일하려다 보면 한 모드만 맞추는 국소 수정은 거의 회귀를 부른다. 실제 코드를 끝까지 보고 네 모드를 동시에 만족하는 불변식을 세워야 함.
- **이벤트 경로 수정은 e2e 재현으로만 증명된다**: pub/sub 분기는 단위테스트로 "통과"해도 실제 브로커 라운드트립에서 중복/누락이 난다. `EventTestResource` 발행 → Flow 수신 → 배포 → RuntimeWatch까지 모드별로 끝까지 태워봐야 진짜 고쳐졌는지 알 수 있다. 그 과정에서 SUBSCRIBE는 통과해도 UNSUBSCRIBE는 따로 터질 수 있으므로, 라이프사이클 양 끝을 모두 검증해야 한다.
- **`@TransactionalEventListener` + `REQUIRES_NEW`**: 이벤트 핸들러를 별도 트랜잭션으로 떼어내면 발행 트랜잭션 커밋 이후에 안전하게 소비되고, 핸들러 실패가 원 트랜잭션을 오염시키지 않는다.
- **동시성 락은 "한 번만 잡는다"가 원칙**: `recordResult` 를 호출마다 락 잡던 걸 batch 단위 단일 락(`PESSIMISTIC_WRITE` + `entityManager.refresh`)으로 바꾸면 락 경합과 호출 횟수를 동시에 줄인다.
- **플러그인 경로 변수는 런타임마다 보장 범위가 다르다 (재확인)**: `${CLAUDE_PLUGIN_ROOT}` attach가 Claude Code에선 되더라도 Codex 런타임에선 relative path가 더 안전 — 이상적 변수보다 **양쪽 런타임에서 실제로 동작하는 최소 공통분모**를 택하는 게 맞다.
- **PreSync Job 적합성은 "시크릿 입력 시점"이 가른다**: 구독 시 DB 프로비저닝을 PreSync Job으로 할지는, 사용자가 프론트에서 시크릿을 언제 넣는지(구독 직전 입력 vs 사전 admin prep)에 달렸다. 기술 선택 전에 비즈니스 입력 시점부터 확정해야 오버엔지니어링을 피한다.
