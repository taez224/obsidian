### #14 — unsubscribe 시 crypto-secret 정리
- unsubscribe 시 `-crypto-secret` 을 **정리(cleanup)** 구현 (`dbcd8255e`) → `feature/issue-14` main+release 머지 (`921f95b6f`, `43850de27`)
- **subscriptionId의 `:` 문제 해결**: `1:1-S0004` 같은 ID가 K8s label value 패턴(`[A-Za-z0-9_.-]`, 양끝 alphanumeric)을 위반 → raw ID를 바꾸지 않고 **label/selector 전용 파생값 `toLabelValue()` SSOT 함수**로 projection(`:` → `_`). apply와 delete가 같은 함수를 쓰므로 selector 정합 보장
- **label-based bulk delete** 채택: apply 경로에 ownership label 3개(`app.kubernetes.io/managed-by: gallery-runtime`, `vizend.io/subscription-id`, `vizend.io/runtime-*`) 보강 → 충분히 좁은 라벨로 안전하게 일괄 삭제 (managed-by 단독 삭제는 위험)
- **1회 기록 원칙**: cleanup 결과를 `recordRemovalSuccess` **XOR** `recordRemovalFailure` 로 정확히 한 번만 기록 → 성공 시 target Failed / Subscription Dormant 전이(강한 운영자 인지)
- `Subscription.clearSubscriptionSecrets()` 를 unsubscribe **트랜잭션 내에서** 호출
- `SecretDeleteOutcome` 의 두 번째 필드 의미를 `namespace` 로 정정 (P3 리뷰)
- 이슈 구조: db-secret까지 묶여 있던 #8에서 **crypto-secret만 먼저** 닫도록 child-task로 분리 — "전체 사이클이 도는 최소 단위"를 우선

## 학습 & 인사이트

- **raw 식별자를 sanitize하지 말고 "투영값"을 만들어라**: `subscriptionId` 에 `:` 가 들어가 K8s label 규칙을 위반할 때, 원본 ID를 바꾸면 도메인 전체가 흔들린다. 대신 label/selector에만 쓰는 파생값을 `toLabelValue()` SSOT로 만들고 **apply·delete가 같은 함수를 공유**하면, 원본은 보존하면서 selector 정합까지 보장된다.
- **bulk delete의 안전성은 라벨의 좁기에 비례한다**: `managed-by` 같은 넓은 라벨만으로 일괄 삭제하면 남의 리소스까지 지운다. apply 시점에 ownership label을 충분히(subscription 단위까지) 좁게 붙여두면, label-based bulk delete가 장기적으로 가장 단순하고 안전하다 — 단 "apply가 라벨을 정확히 붙인다"가 전제.
- **결과 기록은 XOR로**: cleanup 성공·실패를 각각 다른 경로에서 기록하면 이중 기록·누락이 생긴다. `recordRemovalSuccess` XOR `recordRemovalFailure` 로 "정확히 한 번"을 코드 구조로 강제해야 상태 전이가 신뢰된다.
- **전체 사이클이 도는 최소 단위부터 닫아라**: db-secret까지 묶인 큰 이슈(#8)를 통째로 하기보다, crypto-secret만 떼어 apply→cleanup이 한 바퀴 도는 최소 사이클을 먼저 완성하면 데모·검증이 가능해진다. 순서는 "의존"이 아니라 "닫히는 단위"로 잡는다.
- **ADR은 결정을 적는 문서지 구현 명세가 아니다**: 구현하면서 ADR에 상세가 계속 쌓이면 "왜 이렇게 정했나"가 "어떻게 짰나"에 묻힌다. 주기적으로 v2 refresh로 결정만 남기고 구현 상세는 코드·spec으로 내려야 문서가 산다.
- **cross-repo 이슈는 추적 주체를 명확히**: 프론트 구현은 monorepo(MR #1116), 이슈는 백엔드 레포(#4·#11)에 있는 구조에서는 "어디서 구현됐나 / 어디서 닫나"를 분리해 추적해야 상태(`status::review`)가 꼬이지 않는다.
