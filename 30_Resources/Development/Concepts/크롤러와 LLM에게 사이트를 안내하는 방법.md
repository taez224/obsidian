# 크롤러와 LLM에게 사이트를 안내하는 방법

가든에 robots.txt와 사이트맵을 두고, 구조화 데이터와 llms.txt를 뒤이어 붙였다. 넣고 나니 각각이 무엇을 약속하는지 분명하지 않았다. 특히 llms.txt는 만들라는 안내에 비해 무엇을 기대할 수 있는지 설명한 자료가 드물었다. 넷을 같이 놓고 보면 이들은 접근 규칙과 목록과 페이지의 정체라는 세 가지를 나눠서 맡는다.

## 크롤러 접근 규칙

robots.txt는 크롤러에게 어느 경로를 요청해도 되는지 알리고 사이트맵의 위치를 함께 적는다. 가든의 robots.txt는 모든 경로를 허용하고 사이트맵 위치만 가리킨다. 비공개 노트는 빌드에서 빠지므로 크롤러에게 가려야 할 경로가 남지 않는다. 공개 여부는 빌드가 정하고 robots.txt는 그 결과를 안내한다.

> [!warning] robots.txt의 한계
> robots.txt는 크롤러에게 보내는 요청이지 접근을 차단하는 수단이 아니다. 막아야 할 경로가 생기면 robots.txt에 적기 전에 그 경로를 공개 규칙에서 먼저 뺀다.

## 같은 목록의 서로 다른 독자

사이트맵과 llms.txt와 RSS는 모두 사이트에 무엇이 있는지 알리는 목록인데, 읽는 독자가 서로 달라서 형식도 달라진다.

| 출력 | 독자 | 담는 것 |
|------|------|---------|
| `sitemap.xml` | 검색 크롤러 | 공개 URL 전체. 기계가 파싱하는 XML |
| `llms.txt` | LLM 크롤러 | 종류별 목록과 한 줄 요약. 사람도 읽는 Markdown |
| `rss.xml` | 사람 구독자 | 최근 항목만 |

사이트맵은 공개 URL을 빠짐없이 나열하고, llms.txt는 사이트가 무엇을 다루는지 요약해서 건네며, RSS는 달라진 것만 알린다. 피드를 종류별로 나누고 종류마다 가져올 항목 수를 정한 이유는 [[RSS 피드로 GitHub 프로필 갱신하기]] 참조.

## 구조화 데이터와 schema.org

HTML은 글자의 생김새만 말한다. `<h1>`을 봐도 기계는 그것이 글 제목인지 사이트 이름인지 알 수 없다. 그래서 페이지마다 제목·저자·발행일을 기계가 읽을 형식으로 따로 적는다. 이때 쓰는 공용 어휘가 schema.org이고, 그 어휘를 JSON으로 적는 표기법이 JSON-LD다. 둘은 서로 다른 층에 속한다. `@context`와 `@type`은 schema.org의 단어가 아니라 JSON-LD의 문법이고, `"@context": "https://schema.org"`는 아래 나오는 이름들을 schema.org 어휘로 해석하라는 선언이다.

가든은 홈에 `WebSite`, 발행한 글에 `BlogPosting`, 개발 노트에 `TechArticle`, 소개 페이지에 `AboutPage`, 나머지에 `WebPage`를 쓴다. schema.org의 타입에는 상속 관계가 있어서, 더 구체적인 하위 타입을 고를수록 그 페이지가 무엇인지 더 많이 알리게 된다. `AboutPage`는 `WebPage`의 하위 타입이라서, 이 값을 넘기면 하나의 페이지라는 사실에 더해 사이트를 소개하는 페이지라는 것까지 알린다. 타입을 따로 넘기지 않은 페이지는 `WebPage`로 남는다. 저자에 붙이는 `sameAs`는 여러 곳에 흩어진 프로필이 모두 같은 사람의 것이라고 알리는 속성이다.

구조화 데이터를 넣는 자리에서 canonical 링크도 함께 내보낸다. 여러 주소로 닿을 수 있는 페이지에 대표 주소 하나를 지정하는 링크다. 피드 항목의 주소를 가든 주소로 맞춘 것도 canonical과 어긋나지 않게 하려는 선택이다.

## 화면에 없는 정보의 위험

구조화 데이터에는 페이지가 이미 가진 제목·요약·날짜·주소만 넣는다. 값이 없으면 빈 문자열을 넣지 않고 필드 자체를 만들지 않는다. 취향이 아니라 위험을 피하려는 선택이다. 구조화 데이터가 화면에 보이는 내용과 어긋나면 검색 엔진이 그것을 스팸 신호로 보고 표시에서 빼거나 수동 조치를 적용한다. 없는 별점이나 실제와 다른 발행일이 자주 지적되는 사례다.

## llms.txt의 채택 상태

llms.txt는 [Jeremy Howard가 2024년 9월에 제안](https://llmstxt.org/)했고 아직 표준이 아니다. 의견을 받는 비공식 명세로 남아 있다.

Google은 검색에 llms.txt를 쓰지 않는다고 밝혔고, 2026년 6월에 갱신한 AI 최적화 안내에서 [검색에 노출되려고 별도의 기계 판독 파일을 만들 필요가 없다](https://searchengineland.com/google-says-normal-seo-works-for-ranking-in-ai-overviews-and-llms-txt-wont-be-used-459422)고 적었다. 크롤러 로그를 집계한 여러 조사도 AI 크롤러 요청 중 llms.txt를 직접 가져간 비율을 1% 아래로 보고한다.

> [!info] 흔한 혼동
> OpenAI와 Anthropic이 자사 개발자 문서에 llms.txt를 두고 있지만, 파일을 내는 것과 남의 파일을 읽는 것은 다른 행위다. 이 둘을 자주 뭉뚱그려 말한다.

그래도 가든은 llms.txt를 낸다. 빌드가 모은 노트 목록에서 함께 생성하는 출력이라 따로 관리할 파일이 늘지 않고, 사이트맵과 달리 사람이 열어도 읽히는 목록이라 그 자체로 쓸 데가 있다. 다만 채택이 아직 넓지 않으므로 이 파일에 검색 노출이나 인용 빈도를 기대하지는 않는다.

> [!note] 확인 범위
> 위 판단은 공개된 조사와 Google의 발표에 근거한 것이고, 이 사이트에서 실제로 누가 llms.txt를 가져갔는지는 확인하지 못했다. 정적 호스팅에서는 액세스 로그를 받지 못하고, 방문 통계는 브라우저에서 동작하기 때문에 크롤러의 파일 요청을 세지 않는다.

## 두지 않은 파일

`ai.txt`와 `.well-known/security.txt`는 두지 않았다. `ai.txt`는 학습 데이터 사용을 거절하는 용도인데, 가든은 공개를 전제로 쓴 글만 올리므로 거절할 내용이 없다. `.well-known/security.txt`는 취약점 신고 창구를 알리는 파일인데, 지금은 신고를 받아 처리할 서비스가 없다. 그럴듯해 보인다는 이유로 파일을 미리 채우지 않고, 필요한 이유가 생길 때 더한다.

## 배포 산출물 검사

이 출력들은 화면에 보이지 않기 때문에 깨져도 눈에 띄지 않는다. 템플릿을 고치다가 메타 태그 한 줄이 빠져도 페이지는 멀쩡해 보인다. 그래서 빌드 뒤 산출물 검사에 넣었다. 모든 페이지에 구조화 데이터가 있는지, 소개 페이지의 타입이 `AboutPage`인지, 검색 엔진 소유권 확인 토큰이 설정값 그대로인지, llms.txt가 제목과 절과 절대 주소를 갖췄는지, 피드가 모두 나왔는지를 확인하고 하나라도 어긋나면 배포하지 않는다. 빌드가 노트를 읽어 사이트로 배포하는 전체 흐름은 [[생각의 정원을 만들고 배포하는 과정]]에 있다.
