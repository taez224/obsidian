# 실시간 갱신 화면은 무엇을 저장소에 두고 무엇을 채널로 보내는가

배포 진행률이나 작업 로그처럼 계속 바뀌는 상태를 화면에 보여 줄 때, SSE 같은 실시간 채널이 상태의 유일한 통로가 되면 연결이 붙은 인스턴스와 상태가 생긴 인스턴스가 어긋나는 순간 화면이 멈춘다. [[SSE 팬아웃 인스턴스 불일치]]는 그 사건 기록이고, 이 노트는 거기서 떼어낸 일반 원리다. 질문은 둘이다. 그 상태가 놓치면 사라지는 이벤트인지 저장소에 남는 현재 상태인지, 그리고 저장소에 남는 상태라면 폴링을 어떻게 싸게 만드는지다.

## 놓치면 사라지는 이벤트와 저장소에 남는 상태

저장소에 남는 상태는 한 번 늦게 읽어도 다음 조회에서 따라잡는다. 이런 상태는 주기 조회로 충분하고, 실시간 채널은 전달을 앞당기는 층으로만 둔다. 놓치면 사라지는 이벤트는 다르다. 이 경우에만 인스턴스 사이의 중계와 끊긴 뒤 이어 받을 커서가 필요하다. 어느 쪽인지 정하지 않고 실시간 채널부터 놓으면, 채널이 진실의 원천이 되어 채널의 결함이 곧 상태의 결함이 된다.

## 폴링에 얹는 조건부 요청

폴링이 저장소를 직접 조회하기 시작하면 조건부 요청을 얹는다. 변경 여부만 판별하는 가벼운 값을 [`ETag`](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.3)로 내려주고 `If-None-Match`가 같으면 304로 끊는다. 본문 직렬화와 전송이 통째로 빠진다.

ETag를 인스턴스별로 캐싱한다면 원본이 바뀔 때 무효화할 수 있어야 한다. 같은 표현에 다른 값을 발급하면 불필요한 200 응답이 늘고, 오래된 태그로 304를 판단하면 갱신을 놓칠 수 있다. 현재 표현의 내용이나 버전으로 일관되게 계산한다. 공유 저장소의 버전을 쓰는 것은 한 가지 방법이며, 캐시 자체가 금지되는 것은 아니다.

## 조회 주기와 계층 분리

진행 중에는 짧게 조회하고 유휴일 때는 길게 조회하는 정책도 검토한다. 서버가 주기를 제안하려면 응답 필드나 별도 헤더를 클라이언트가 해석하도록 API 계약을 정해야 한다.

규모가 커지면 감시 계층과 API 계층을 아예 다른 프로세스로 나눈다. 일하는 쪽이 샤딩되든 리더를 뽑든, 연결을 받는 쪽이 상태를 들고 있지 않으면 어긋날 자리가 없다.

## 다른 시스템은 어떻게 하는가

[GitHub Actions](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs)는 run과 job과 check의 상태를 다시 조회할 수 있는 형태로 남긴다. 웹 화면의 실시간 전송 방식은 공개 문서만으로 확정할 수 없지만, 연결 자체를 진실의 원천으로 삼지는 않는다.

[GitLab의 job 로그 화면](https://docs.gitlab.com/ci/jobs/job_logs/)은 실행 중일 때 처음에는 최대 60초, 한 번 연 뒤에는 3초 간격으로 갱신한다. 사람이 보고 있는 화면인지에 따라 주기를 20배 바꾸는 셈이다. trace는 실행 중 청크로 쌓았다가 완료한 뒤에 보관한다. [폴링 정책 문서](https://docs.gitlab.com/development/polling/)도 ETag와 캐시로 불필요한 조회 비용을 줄이는 쪽이다.

[Kubernetes API](https://v1-32.docs.kubernetes.io/docs/reference/using-api/api-concepts/)는 현재 상태를 읽은 뒤 `resourceVersion`부터 변경을 watch하고, 버전이 오래되거나 연결이 끊기면 다시 읽어 동기화한다. stream과 복구 가능한 상태를 분리한 구조다. [Argo CD의 application server](https://github.com/argoproj/argo-cd/blob/master/server/application/application.go)는 informer와 cache에서 상태를 읽고 watch와 broadcaster로 변경을 전달하며, [고가용성 구성](https://argo-cd.readthedocs.io/en/stable/operator-manual/high_availability/)에서는 감시 컨트롤러와 API 서버의 책임도 분리한다. [Tekton의 HA 문서](https://tekton.dev/docs/pipelines/enabling-ha/)는 leader election의 단점으로 hot-spotting을 명시하고, 워크큐를 버킷으로 쪼개거나 StatefulSet ordinal 해시로 배정하는 방법을 대안으로 둔다.

공통점은 상태와 로그를 저장소에 남기고, SSE나 watch 같은 실시간 채널은 전달을 앞당기는 층으로 둔다는 것이다. 빠른 화면 갱신이 필요하면 인스턴스 간 중계와 커서 기반 복구를 더하고, 수 초의 지연을 허용할 수 있으면 증분 폴링으로 단순하게 가져간다.

## 확인 범위

위 사례들의 동작은 2026년 8월 시점의 공개 문서로만 확인했고, 각 제품을 직접 운영하며 검증한 것은 아니다. 조건부 요청과 조회 주기 정책은 일반 원리이며, 사건 노트의 사례에 무엇을 적용했는지는 그 노트의 확인 범위를 따른다.
