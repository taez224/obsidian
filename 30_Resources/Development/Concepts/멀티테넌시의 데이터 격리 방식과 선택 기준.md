# 멀티테넌시의 데이터 격리 방식과 선택 기준

멀티테넌시에서 저장 방식을 고르는 일은 데이터 경계와 장애·복구·변경의 단위를 정하는 일이다. 데이터 민감도, 복구 요구, 성능 영향, 운영 자동화를 함께 비교한다. [Microsoft Learn: Storage and data approaches](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)

## 세 가지 저장 방식

| 방식 | 격리 경계 | 복구와 운영 | 스키마 변경 부담 |
| --- | --- | --- | --- |
| 행 분리 | 같은 테이블에서 테넌트 키와 접근 정책으로 구분 | 테넌트 단위 복구를 별도로 설계해야 한다 | 테이블 변경은 한 번 적용하지만 모든 테넌트에 영향을 준다 |
| 스키마 분리 | 같은 데이터베이스 안의 테넌트별 스키마 | 테넌트별 복구의 의존 객체와 절차를 확인해야 하며 DB 자원은 공유한다 | 모든 스키마에 변경을 적용하고 실패를 추적해야 한다 |
| 데이터베이스 분리 | 테넌트별 데이터베이스 | 테넌트별 백업·복구와 접근 자격을 나누기 쉽다 | DB마다 변경·검증·버전을 맞춰야 한다 |

세 방식은 데이터 접근·성능·복구의 모든 축에서 같은 순서로 평가되지 않는다. 데이터베이스를 나누어도 서버·클러스터·관리 경로를 공유할 수 있어 물리 서버나 CPU 분리를 자동 보장하지 않는다. 반대로 행 분리도 데이터베이스 정책으로 접근을 제한할 수 있다.

## 스키마는 이름만 달리하는 격리가 아니다

스키마 분리는 테이블 이름에 접두사를 붙이는 방식과 다르다. PostgreSQL 스키마는 이름 공간이지만 권한과 객체 탐색 규칙을 함께 설계해야 한다. 객체 검색 경로인 `search_path`와 부여된 권한이 예상과 다르면 경계가 약해질 수 있으므로 스키마 생성만으로 권한 장벽이 완성되지는 않는다. [PostgreSQL: Schemas](https://www.postgresql.org/docs/current/ddl-schemas.html)

행 분리도 테넌트 키와 `WHERE` 조건 하나로 완전해지지 않는다. 조회·수정·삭제·집계·배치 등 모든 경로가 같은 범위를 사용해야 한다. PostgreSQL row-level security를 사용해 행 정책을 둘 수 있지만 적용 대상과 우회 권한을 검토해야 한다. [PostgreSQL: Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

## 가상의 문서 서비스에서 비교하기

가상의 문서 서비스에서 고객 A가 삭제한 문서를 어제 상태로 되돌리려 한다고 하자. 이때 고객 B가 오늘 작성한 문서는 유지해야 한다. 공유 테이블이라면 A의 데이터만 골라 복구하는 경로가 필요하다. 데이터베이스를 나누면 복구 대상을 구분하기 쉬워질 수 있지만, 실제로 어느 단위의 복구를 지원하는지는 DBMS와 관리형 서비스의 기능을 확인해야 한다.

반대로 모든 고객에게 새 문서 속성을 추가하려면, 공유 테이블은 한 스키마에 변경을 적용하고 분리된 스키마·DB는 각 대상의 적용 여부를 추적해야 한다. 어느 쪽이든 이 상황에서 다음 질문을 비교할 수 있다.

- 테넌트별 복구가 필요한가, 전체 복구로 충분한가?
- 한 테넌트의 부하가 다른 테넌트의 응답 시간에 영향을 줘도 되는가?
- 전체 테넌트 마이그레이션의 자동화와 실패 추적이 준비되어 있는가?
- 접근 규칙을 코드·DB 정책·권한 중 어디에서 검증할 것인가?

테넌트 수만으로 저장 방식을 결정하지 않는다. 같은 수라도 보존·복구 요구와 운영 자동화에 따라 선택이 달라진다. 복구와 스키마 변경 절차까지 시험할 수 있어야 한다.
