# 테넌트 초기화는 누가 언제 어디까지 맡는가

## 다루는 질문

새 테넌트를 추가하거나 기존 애플리케이션을 다시 시작할 때, 데이터베이스와 스키마를 준비하고 실제 접근을 허용하는 일은 누가 언제 어디까지 맡아야 하는가?

## 설명

테넌트 초기화에는 서로 다른 결과를 만드는 작업이 들어 있다. 아래는 책임을 나눠 보는 한 가지 설계 틀이다. 실행 시점도 예시이며, 각 행을 별도 서비스로 만들어야 한다는 뜻은 아니다.

| 단계 | 만드는 것 또는 확인하는 것 | 책임을 맡을 수 있는 주체 | 실행 시점 |
|---|---|---|---|
| 자원 생성 | 데이터베이스, 스키마, 저장소 같은 물리·논리 자원 | 인프라 또는 프로비저닝 모듈 | 신규 테넌트 |
| 스키마 마이그레이션 | 테이블·인덱스·제약조건의 버전 적용 | 데이터베이스 마이그레이션 모듈 | 신규 테넌트, 배포 |
| 업무 초기 데이터 | 기본 역할·설정·초기 참조 데이터 | 업무 모듈 | 신규 테넌트, 필요한 재실행 |
| 준비 검증 | 연결 가능, 현재 버전, 필수 객체와 설정 | 초기화 조정 모듈 또는 준비 상태 검사 | 각 단계 뒤, 요청 허용 전 |
| 업무 접근 허용 | 요청을 처리할 수 있다는 상태 전환 | 애플리케이션의 lifecycle·정책 모듈 | 모든 준비 조건 충족 뒤 |

이 구분에서 주체는 반드시 별도 서비스일 필요가 없다. 하나의 애플리케이션 안에서도 인프라 모듈, 마이그레이션 모듈, 업무 모듈이 각 책임을 가질 수 있다. 반대로 별도 서비스가 있더라도 “생성했다”는 사실만으로 업무 접근을 열어서는 안 된다. 자원 생성은 존재 여부를, 마이그레이션은 버전을, 초기 데이터는 업무 규칙을, 준비 검증은 실제 사용 가능성을 확인해야 한다.

실행 시점도 책임과 분리한다. 배포 때 모든 테넌트를 준비할지, 신규 테넌트 등록 직후 한 테넌트만 준비할지, 애플리케이션 기동 때 기존 테넌트의 상태를 다시 확인할지는 운영 요구에 따라 달라진다. 기동 검사는 누락을 발견하는 데 유용하지만, 그것이 신규 등록 절차와 같은 책임을 가져야 한다는 뜻은 아니다.

Spring Boot는 데이터베이스 스키마를 생성·초기화할 때 한 가지 메커니즘을 사용하는 것을 권장한다. 기본 SQL 초기화와 Flyway가 같은 스키마 변경을 중복으로 소유하지 않도록 정한다. 업무 초기 데이터도 무엇을 마이그레이션으로 관리하고 무엇을 업무 기능이 관리할지 범위를 나눈다. [Spring Boot 데이터 초기화](https://docs.spring.io/spring-boot/how-to/data-initialization.html)

버전이 있는 마이그레이션은 적용 이력과 checksum을 남기므로, 이미 공유 환경에 적용한 파일을 고치기보다 새 마이그레이션으로 앞으로 나아가는 경계를 정해야 한다. [Flyway 버전 마이그레이션](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations)

## 예제와 적용 경계

가상의 문서 서비스에서 새 고객을 등록한다고 하자. 등록 요청은 먼저 테넌트 식별자와 정책을 저장한다. 프로비저닝 모듈은 데이터베이스와 스키마가 없을 때만 만들고, 마이그레이션 모듈은 아직 적용되지 않은 버전을 순서대로 적용한다. 업무 모듈은 기본 역할과 설정을 넣은 뒤, 준비 검증이 모두 통과했을 때만 `Ready` 상태로 바꾼다. 중간 단계가 실패하면 접근을 열지 않고, 어느 단계에서 멈췄는지 다시 시도할 수 있어야 한다.

이 예제에서 기존 애플리케이션의 재시작은 현재 상태를 확인하는 정책으로 둔다. 누락된 자원을 발견했을 때 자동으로 생성할지, 기동을 막을지는 별도로 정할 수 있다. 데이터베이스와 스키마가 이미 있고 버전도 맞으면 마이그레이션은 할 일이 없고, 초기 데이터도 이미 존재하면 중복 생성하지 않아야 한다. 다만 현재 스키마가 애플리케이션이 요구하는 호환 범위를 벗어났다면 준비 검증은 성공으로 처리할 수 없다. 신규 등록과 재시작을 같은 명령으로 묶더라도, “없으면 생성”과 “있으면 검증”의 결과를 구분해야 한다.

재시도와 동시 실행에는 다음 질문이 남는다.

- 같은 테넌트 초기화가 동시에 두 번 들어오면 자원 생성과 초기 데이터가 중복되지 않는가?
- 실패한 단계만 재시도할지, 앞 단계의 상태를 다시 확인한 뒤 전체를 재조정할지 누가 정하는가?
- 여러 테넌트를 병렬 처리할 때 서로 다른 데이터베이스의 작업은 겹쳐도 되는가? 공유 데이터베이스의 스키마 작업은 잠금과 마이그레이션 도구의 동시성 규칙을 따르는가?
- 준비 검증이 통과하기 전 요청을 어디서 막고, 검증 결과와 접근 허용 상태를 어떤 저장소에서 읽는가?

초기화의 결과를 단계별로 정의하면 각 단계의 멱등성·재시도·동시 실행 책임을 구체적으로 검토할 수 있다. 멀티테넌시에서 데이터와 성능 격리 대상을 먼저 나누는 문제는 [[멀티테넌시에서 무엇을 격리해야 하는가]]와 이어진다.
