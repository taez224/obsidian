# 멀티테넌시에서 무엇을 격리해야 하는가

멀티테넌시는 하나의 서비스가 여러 고객이나 조직을 함께 지원하는 구조다. 테넌트는 고객별 데이터와 정책의 경계를 나누는 단위이고, 사용자는 그 안에서 행동하는 주체다. 한 조직에 여러 사용자가 있고, 서비스에 따라 한 사용자가 여러 조직에 속하기도 하므로 둘을 같은 개념으로 다루면 경계가 흐려진다.

## 인증이 끝나도 범위는 남는다

격리의 출발점은 "누가 로그인했는가"가 아니라 "이 요청이 어느 테넌트의 어떤 범위에서 허용되는가"다. 인증은 주체를 확인하는 절차이고, 격리는 그 주체에게 허용된 데이터·기능·자원의 범위를 하위 시스템까지 전달해 제한하는 설계다. [AWS의 SaaS 격리 설명](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/identity-and-isolation.html)은 인증 과정에서 테넌트 소속과 격리 정책을 담은 컨텍스트를 얻어 하위 자원의 접근 범위를 정한다고 본다. 토큰이 유효하다는 사실만으로는 범위가 정해지지 않는다.

데이터 격리가 가장 직접적인 요구다. 같은 저장소를 쓰면서 테넌트별 행·파티션·스키마 같은 논리 경계를 두거나, 더 강하게는 데이터베이스나 저장소 자원을 나눈다. 어느 쪽이든 *"요청 본문의 테넌트 ID를 WHERE 조건에 붙이면 끝"* 이 아니다. 테넌트 범위는 요청이 들고 온 값이 아니라 인증된 주체에서 나와야 하고, 조회·수정·삭제·배치·파일 접근까지 모든 경로가 같은 규칙을 타야 한다. [Azure의 저장소·데이터 설계 안내](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)에서는 공유 데이터베이스에서 행 수준 보안을 쓰려면 사용자와 테넌트 식별자가 애플리케이션을 거쳐 각 쿼리까지 전달되어야 하고, 이를 설계·테스트·운영하기가 만만치 않다고 적는다.

## 데이터만 격리 대상이 아니다

하나의 데이터베이스나 저장소를 여러 테넌트가 나눠 쓰면 한 테넌트의 큰 요청량이 다른 테넌트의 응답 시간과 처리량을 갉아먹는다. noisy neighbor 문제다. 성능 격리는 서로의 사용량이 영향을 미치는 경로를 찾는 일이고, 요청량 제한이나 자원 분리는 그 경로를 확인한 뒤에 고르는 대응이다.

격리 대상을 나눠 보면 넷이다.

- **신원·권한**: 사용자가 어느 테넌트에 속하고 무엇을 할 수 있는가. 인증 주체와 테넌트 정책을 결합해 범위를 전달한다.
- **데이터**: 다른 테넌트의 행·파일·키·백업에 닿을 수 없는가. 공유 저장소의 논리 경계, 샤딩, 전용 데이터 자원 중에서 고른다.
- **성능·용량**: 한 테넌트의 부하가 다른 테넌트에 번지지 않는가. throttling, rate limit, 자원 풀·샤드·전용 자원으로 막는다.
- **운영·복구**: 백업·복원·마이그레이션·삭제를 테넌트 단위로 할 수 있는가. 수명주기 자동화와 테넌트 단위 관측·복구 절차가 필요하다.

넷은 같은 저장 방식에서 같은 수준으로 해결되지 않는다. 데이터 접근 규칙을 지켜도 한 테넌트의 대량 색인 작업이 다른 테넌트의 열람을 느리게 만들면 약속한 응답 시간을 못 지킨다. 특정 지역 보관이나 별도 암호화 키 요구는 저장 위치와 키 관리 경계를 따로 검토하게 만든다.

저장 방식(행·스키마·데이터베이스 분리)은 이 넷 중 어디까지를 어느 수준으로 강제해야 하는지 정한 뒤에 고른다. 방식별 비교와 선택 기준은 [[멀티테넌시의 데이터 격리 방식과 선택 기준]]에 있다.
