# Kubernetes의 원하는 상태와 실제 상태

애플리케이션을 세 개 실행하고 싶다고 하자. 명령을 한 번 보내 세 개를 만드는 것만으로는, 이후 하나가 사라졌을 때도 세 개를 유지할 수 없다. Kubernetes의 선언적 관리는 **유지할 상태를 기록하고, 실제 상태와의 차이를 계속 줄이는 방식**이다. 이 반복을 조정(reconciliation)이라고 부른다. [Kubernetes Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)

## 원하는 상태를 저장하고 실제 상태를 관측한다

Deployment 같은 워크로드 객체에서는 `spec`에 원하는 설정을 적는다. `replicas: 3`은 원하는 복제본 수이고, Pod template에는 실행할 이미지와 컨테이너 설정 등을 둔다. `status`에는 컨트롤러가 관측해 보고한 진행 상황이 담긴다. 두 값은 갱신 시점이 다를 수 있으므로, 설정을 바꾼 직후부터 상태 보고가 같을 것이라고 기대하면 안 된다.

`kubectl apply`가 성공했다는 것은 API가 변경을 받아들였다는 뜻이다. 노드에 자리를 배정하고, 이미지를 내려받고, 컨테이너를 실행하는 작업은 뒤에서 진행된다. API 요청이 성공해도 이미지 오류나 자원 부족으로 원하는 상태에 도달하지 못할 수 있다.

```mermaid
flowchart LR
    A["원하는 상태 기록"] --> B["컨트롤러가 현재 상태 관측"]
    B --> C["차이를 줄이는 작업 요청"]
    C --> D["다른 구성 요소가 작업 수행"]
    D --> B
```

이 그림은 조정의 개념을 단순화한 것이다. 실제로는 한 컨트롤러가 모든 일을 수행하지 않는다. 예를 들어 Deployment 컨트롤러는 ReplicaSet을 관리하고, ReplicaSet 컨트롤러는 필요한 Pod 수를 맞춘다. 스케줄러와 kubelet도 각자의 역할을 수행한다. [Kubernetes Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

## 복제본 수와 사용 가능 여부는 다른 질문이다

다음은 가상의 문서 API를 세 개 실행하려는 상황이다.

| 관측한 상태 | 확인할 질문 |
| --- | --- |
| 목표는 세 개인데 Pod가 두 개뿐이다 | 추가 Pod 생성이나 스케줄링을 막는 조건이 있는가? |
| Pod는 세 개지만 하나가 이미지를 받지 못한다 | 이미지 이름·접근 권한·레지스트리 연결에 문제가 있는가? |
| 컨테이너는 실행 중인데 준비 상태가 아니다 | 준비 상태를 판단하는 조건을 충족했는가? |

Pod가 존재하거나 컨테이너가 실행 중인 것만으로 요청을 처리할 준비가 끝났다고 볼 수는 없다. readiness probe를 설정했다면 그 결과가 준비 상태 판단에 사용된다. 또한 probe가 확인하는 범위가 제한적이라면, 이를 통과했다고 모든 업무 기능이 정상이라고 결론 내릴 수 없다. [Kubernetes Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)

## 자동 조정에도 조건과 한계가 있다

컨트롤러는 차이를 줄이려 하지만, 어떤 설정이든 결국 성공시키는 것은 아니다. 존재하지 않는 이미지를 지정했다면 올바른 이미지로 수정하거나 필요한 자원을 준비해야 한다. 계속 대기하는 상태에서는 원하는 값, 관측한 상태, Event와 로그를 나란히 보며 진행이 막힌 지점을 찾는다.

조정의 대상도 객체마다 다르다. Deployment의 이미지 변경과 별도 Secret 객체의 값 변경은 같은 변화가 아니다. 어떤 객체를 바꿨는지, 그 변화를 소비하는 쪽이 어떻게 반영하는지까지 확인해야 한다. 이 구분은 [[K8s envFrom Secret은 Pod 재기동 없이 갱신되지 않는다|Secret 적용은 성공했지만 실행 중인 환경변수는 바뀌지 않는 문제]]를 이해하는 출발점이 된다.
