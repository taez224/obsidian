## 📝 주요 아이디어

### 추상적 표현 지양

행동이나 구체적인 결과가 결여된 형용사와 명사
#### 주로 나타나는곳
1. **자기소개(상단):** 열정, 헌신, 책임감, 성실, 빠른 학습력, 성장 등
2. **프로젝트 경험(성과):** 품질 개선, 성능 향상, UI/UX 개선, 효율적 처리
3. **기술 스택(숙련도):** 능숙, 익숙, 숙련, 높은 이해도 

#### 좋은 예와 나쁜 예
무조건 안좋은건 아니다. 중요한 건 추상적 표현 뒤에 곧바로 구체적인 근거가 제시되어야 함
- 나쁜 예: 뛰어난 책임감으로 프로젝트를 성공적으로 완료했습니다.
- 좋은 예: 책임감 있게 주 1회 회고를 진행하여 6주만에 고객 불만 접수율을 20% 낮췄습니다.

#### 3단계 프레임워크
1. 기존에 작성한 이력서가 있다면 추상적 표현 밑줄 긋기
2. 옆에 '그래서?' 또는 '왜?' 메모하기
3. 숫자 + 행동 + 맥락으로 재작성

#### 체크리스트
- [ ] 자기소개 영역의 추상어 뒤에 바로 성과,숫자,맥락이 붙어있는가?
- [ ] 프로젝트 경험 영역의 핵심 성과에 측정 가능한 지표를 포함했는가? (정량화가 어려울 경우 정성적 근거로 대체 가능)
- [ ] 사용한 모든 형용사, 추상명사 옆에 구체적 사례를 제시했는가?
- [ ] 처음부터 끝까지 일관되게 표현했는지 점검했는가?

### 수치화의 남용 주의
요즘 이력서 가이드 보면 '수치화'가 중요한 키워드인건 당연지사. 모두가 알고있다. 하지만 숫자도 맥락 없이 사용하면 추상적 표현 만큼이나 설득력을 잃는다.
숫자가 중요한 게 아니라, 숫자를 통해 드러나는 지원자의 경험과 그 의미가 더 중요하다.

#### 흔히 보이는 안티패턴
- 퍼센트(%)만 제시: 응답 속도 60% 개선 (기존엔 몇 초였고, 개선 후엔 몇 초?)
- 수식어만 사용: 트래픽을 크게 늘림 (구제척으로 얼마에서 얼마로 늘었다는 건지?)
- 기준값 없이 증가량만 표현: 가입자가 1만 명 증가

#### 4단계 프레임워크
1. Before(기준값): 어떤 상태에서 시작했는가?
	- 페이지 로딩 시간 4초
2. After(결과값): 개선 후 결과는 어떠한가?
	- 페이지 로딩 시간 1.5초
3. Unit(단위): 어떤 단위를 사용했는가? 
	- 초, ms, %, tps, 건수 등
4. 기간/규모: 어떤 기간이나 규모에서 이뤄졌는가?
	- '3개월간', '일 평균 트래픽 10만 req/min 상황에서'
	- 때때로 생략될 수 있으나 함께 쓰면 더 설득력 있음

	### 기능 나열식 이력서
밋밋해 보이는 이유는 경험이나 역량 부족이 아니라, 경험을 나열하는 표현 방식

#### 흔히 나타나는 경험 나열형 패턴
- 기능 중심 나열형
	- React로 캘린더 UI 구현
	- Spring Boot로 로그인 구현
	- Redis를 이용한 캐싱 처리
	-> 지원자의 주도성,문제해결력, 성장 가능성 등이 보이지 않음. 누구나 했을 법한 경험처럼 느껴짐

#### 4가지 핵심 프레임
1. 왜 이 기능을 맡았는가? - 역할과 주도성 강조
2. 어떤 어려움이 있었고, 어떻게 해결했는가? - 문제 해결 능력과 성장 과정 강조
3. 결과적으로 무엇을 배웠는가? - 성장과 학습력 강조
4. 다음엔 무엇을 다르게 할 것인가? - 자기 개선 능력과 잠재력 강조

#### 나쁜 예와 좋은 예
- 나쁜 예: JWT 기반 인증 구현, REST API 설계 및 개발
- 좋은 예: 
	- 세션 기반 인증을 JWT로 전환하여, 모바일-웹 간 인증 유지 이슈 해결 및 Access/Refresh 토큰 구조 설계 및 만료 처리 로직 구현
	- API 응답 속도 개선 목표로 간단한 부하 테스트(Postman collection runner) 진행 -> 평균 응답 시간 210ms 에서 170ms로 단축 확인(50건 기준)
	- 토큰 검증 과정에서 반복적인 DB 조회로 인한 응답 지연 발생 -> Express 미들웨어 내 검증 로직을 캐시 변수로 처리하여 호출 횟수 감소
	- 인증 관련 로직을 auth 미들웨어로 분리하고, 전체 프로젝트에서 재사용 가능하도록 구조화 -> 이후 프로젝트 2건에 공통 적용

#### 체크리스트
- [ ] 기능만 나열된 문장이 있는지 확인했는가?
- [ ] '왜, 어떻게, 무엇을 배웠는지'가 잘 드러났는가?
- [ ] 모든 경험을 표현하기보다, 가장 중요한 경험 몇 개에 집중했는가?
- [ ] 지원자의 주도성과 문제 해결 과정이 명확히 표현됐는가?


### 밋밋해 보이는가?
좋은 이력서는 많은 것을 보여주는 게 아니라, 하나의 경험이라도 깊이와 서사를 통해 자신만의 이야기를 담아내는 것.

#### 5단계 프로세스
1. **경험 브레인스토밍:** 기억 속 경험을 최대한 많이 꺼내어 수집하는 단계
	- 언제, 어떤 프로젝트/작업을 했는지 기억해내기
	- 기능 이름, 도구, 기술 스택 처럼 떠오르는 단서 메모
	- 정리나 표현은 하지 않고, '무엇을 했는가' 만 최대한 기록
	- 시간순으로 펼치기 -> 세부 작업으로 분해, 기록 기반 회고
	- 하지 말아야할것: 수치화된 지표 작성, 이야기 구조 만들기, 문장 다듬기
	- 흔한 실수: 표제어만 나열, 기억안난다고 포기, 한 가지 관점에만 갇히기
2. **경험 구체화:** 나열한 경험에 의미 있는 맥락과 원인은 부여하여 구체성을 높이는 단계
	- 이 프로젝트는 무엇을 하기 위해, 어떤 필요에 의해, 내가 제안한 의견의 근거는?, 이 경험을 통해 구체적으로 어떤 기술이나 지식을 습득했나?
	- *무엇을 했는가?* 에서 *왜 했는가?* 로!
	- 자신의 역할과 기여도를 명확히 표현 (참여함, 진행함 등 모호한 표현이 아니라!) -> 프로젝트 규모와 나의 역할, 기여도와 책임, 협업과 소통 방식 등
	- 수치는 맥락을 위해 존재함: 숫자를 채우는 것이 중요한 게 아니라, 이력서가 더욱 명확히 읽히도록 도와주는 도구
	- 배운 점을 별도로 기록: 기술적 성장, 협업 경험, 실패와 극복 사례 등
	- 주체적으로 내린 결정은 무엇인가?
3. **영역 나누기:** 경험을 직무 역량, 기술 영역, 산업 분야 등으로 구분하여 구조화하는 단계
	- 대표적인 이력서 구조: 경력, 프로젝트, 대외활동/커뮤니티, 교육/자격증, 기술 스택
	- 가장 중요한 것은 '소속'이 아니라 '맥락'과 '성과'
	- 목표: 경험을 적절한 영역에 배치하여 채용 담당자가 원하는 정보를 빠르게 얻도록 하는 것
4. **템플릿 적용:** 최적의 표현 방식과 시각적 형식을 선택하여 명확성을 높이는 단계
	- 문장 템플릿(STAR): Situation, Task, Action, Result
		- 예시: 로그인 기능 구현 -> 회원가입 및 로그인 과정에서 이탈률이 높았던 상황(S)이었는데, UX 개선을 통한 전환율 향상이 목표였고(T), Spring Security를 활용한 JWT 인증 시스템을 도입하여(A), 로그인 성공률을 90%에서 98%로 향상시켰습니다(R).
	- 문제 해결형 예시: "<기존 문제>를 발견하고, <구체적 해결 방법>을 통해 <성과>를 이루었습니다."
	- 기술 강조형 예시: "<특정 기술>을 사용하여 <문제 해결> 하고, <측정 가능한 성과>를 달성했습니다."
	- UI 템플릿: 핵심 메시지 강조, 문장 길이 조정, 추가 정보 연결
	- 검토 사항:
		- 핵심 성과가 한 눈에 들어오는가?
		- 문장 중목이나 모호한 표현은 없는가?
		- 플랫폼의 글자 제한과 형식에 맞게 문장이 간결하게 작성되었는가?
		- 독자가 문장을 읽고 바로 이해할 수 있는 구조인가?
5. **경험 소거:** 메시지를 흐리거나 중요도가 떨어지는 경험을 과감히 덜어내어 최종적으로 정제하는 단계
	- 소거는 삭제가 아니라 정제다: *채용공고와의 적합성을 기준으로 경험을 분류*
	- 시간이 경과한 경우: 3~5년 이상 지난 기술이거나 현재와 무관한 경험이라면 간략히만 언급하거나 소거한다.
	- 관련성이 부족한 경우: 지원 직무와 연관성이 낮거나 없다면 생략하거나 최소한의 정보만 남긴다.
	- 기여도와 성과가 부족한 경우 및 중복 경험

### 표현 전략
> 상단에 배치된 정보와 문장 초반부를 중심으로 지원자의 방향성과 기여 가능성을 빠르게 파악한다. 

#### 강조와 우선순위
어떤 정보를 먼저 읽히게 할 것인지, 어떤 정보를 상대적으로 뒤로 배치할 것인지
강조는 '덜 강조되는' 다른 항목이 있을 때 비로소 의미를 갖는다.
1. 중요한 프로젝트를 최상단에 배치
2. 처음 읽는 항목에 가장 집중
3. 직무 연관성과 성과 중심으로 순서를 정한다.
4. 반복 업무보다 문제 해결을 우선
5. 지원 직무에 따라 강조 순서를 바꾼다.
6. 공고에서 강조한 역량을 우선 배치한다.
-> 시간순 나열을 깨라는 것이 아니다. 시간순 구조 안에서 무엇을 먼저 보이게 할 것인가!

한 문장 내에서도 강조는 가능하다. 가장 전달하고 싶은 변화가 무엇인지에 따라 강조 포인트를 선택하는 것이 중요

#### 시각적 강조 기법
- 기본적으로 제한적으로 사용한다.
- **볼드체 사용:** 프로젝트 제목이나 핵심 수치, 결과 중심 표현
- **여백 활용:** 주요 섹션 사이에 여백을 두어 가독성 확보
- **구분선이나 색상 사용:** 섹션 구분 목적에 한해 최소한으로 사용
1. 가장 먼저 읽히는 정보가 내가 전달하고 싶은 핵심인가?
2. 강조한 경험이 지원 직무와 직접적으로 연결되는가?
3. 상대적으로 덜 중요한 정보가 과도하게 앞에 배치되어 있지는 않은가?

#### 능동형과 수동형
능동형 문장은 지원자가 그 경험에서 어떤 역할을 했는지를 한눈에 드러낸다. 하지만 반드시 최종 의사결정권을 의미하지는 않는다. *주어진 범위 안에서 어떤 판단과 행동을 했는지를 구체적으로 설명하는 것이 핵심*이다.
- Before: 팀 프로젝트에서 백엔드 구현을 담당했습니다.
- After: 팀 프로젝트에서 백엔드 API 설계를 주도하고, 직접 핵심 비즈니스 로직을 구현했습니다.
흔한 수동형 표현들
- ~을 담당, ~이 수행, ~이 개선, ~에 참여
##### 능동형으로 바꾸는 팁
1. 기능 개발 및 개선
	- Before: 알림 기능 개발에 참여
	- After: 푸시 알림 기능 구현을 맡아 사용자별 발송 조건을 정리하고 로직을 개선해 알림 실패 사례를 줄임
2. 코드 리뷰 및 협업
	- Before: 코드 리뷰를 진행
	- After: 팀 내 코드 리뷰 과정에서 주요 개선 포인트를 정리하고, 신규 인원이 참고할 수 있도록 가이드를 문서화
3. 장애 대응 및 운영
	- Before: 서비스 장애 해결
	- After: 장애 발생 시 로그를 분석해 원인을 파악하고, 재발 방지를 위한 조치를 정리해 적용
4. 자동화 및 기술 도입
	- Before: 배포 자동화를 수행함
	- After: 기존 수동 배포 과정의 병목을 정리하고, 자동화 도입을 통해 배포 과정을 단순화
### AI 활용 분석
- 공고 키워드 추출: 다음 채용 공고에서 필수 역량, 우대사항, 조직 문화 키워드를 추출하고 표로 정리해줘
- 이력서와 공고 매칭도 분석: 아래는 내 이력서와 지원하려는 채용 공고야. 공고의 요구사항과 내 경험의 매칭도를 분석하고, 어떤 부분을 더 강조해야 할지 구체적으로 제안해줘
- 문장 개선 요청: 내 이력서의 다음 문장을 채용공고의 키워드 "Kafka, 대용량 트래픽"에 맞춰 개선해줘 
- 키워드를 직접적으로 언급하지 않고 사례로 자연스럽게 녹이기
- AI의 진짜 가치는 '글을 대신 써주는 것'이 아니라, 경험을 발굴하고 구조화 및 최적화하는 전 과정에 참여시키는 것
	- 스스로 떠올리지 못한 핵심 키워드와 관점을 찾아줌
	- 경험을 채용 담당자 시각에서 재구성
	- 부족한 문장을 설득력 있고 매끄럽게 다듬어줌
	- 실제 채용 리뷰어처럼 냉정하게 평가하고 개선 방향 제시
- 프롬프트 예시:
	- CATS: Context, Angle/Role, Task, Style
		- Context: 이 문장이 어디에 쓰이는지 명확히 설명했는가?
		- Angle/Role: 판단 목적과 평가 기준을 명시했는가?
		- Task: 구체적으로 무엇을 포함하고, 어떻게 작성해야 하는지 명시했는가?
		- Style: 출력 형식(길이, 톤, 문체)을 제한했는가?
	- 채용 1차 서류에서 합격/보류를 판단하는 관점으로 평가. 추상적인 표현은 제거하고, 판단 근거가 되는 정보(구체적 역할, 사용 기술, 측정 가능한 성과)만 남겨줘. 능동형으로 작성. 문제 상황과 해결 방법, 결과를 PSR 구조로 작성

#### 내 이력서를 보고 어떤 생각을 할까?
1. 첫인상/기본 스크리닝
	- 문서의 가독성, 레이아웃, 오탈자 여부 등 형식적 완성도
	- 직무와 무관한 내용이 있는지 필터링
2. 도메인 적합성 판단
	- 해당 직무와 직접적으로 연관된 경험이나 경력이 있는지 확인
	- 산업군, 서비스 유형, 기술 환경의 유사성 평가
3. 기술 역량 매칭
	- 채용공고에서 요구하는 핵심 기술 스택과 이력서의 기술 경험 비교
	- 단순 나열이 아닌 실무 적용 사례가 있는지 본다.
4. 문제 해결/Ownership
	- 문제 상황에서 주도적으로 해결한 경험이 있는지, 과정과 결과가 명확히 드러나는지 확인
5. 협업/문화 적합성
