# 다섯 역할 아키타입 기반 작업 방식 분석

> [!info] 이 문서의 성격
> 이 문서는 [[AI 시대의 다섯 역할 아키타입 - Boris Cherny]]의 Prototyper·Builder·Sweeper·Grower·Maintainer 구분을 [[HEXACO 성격검사 결과 - 2026-07-09 (claude)]]와 Vault, QRA·Gallery·Hive·ONLYOFFICE 저장소의 실제 기록에 대조한 **외부 분석 리포트**다. 성격검사와 역할 분류는 행동의 원인을 증명하지 않으며, 아래 결론도 사용자가 이미 채택한 자기 정의나 고정된 유형 판정이 아니다.

> [!summary] 핵심 결론
> 현재 자료에서 가장 일관되게 드러나는 모습은 **가장 불확실한 부분을 작은 실험으로 확인하고, 실제 시스템을 만든 뒤, 실패와 복구까지 챙기는 Builder**다.
>
> Builder가 중심이지만, 만들고 난 뒤 복잡한 구조를 정리하고 오래 운영할 수 있게 다듬는 Sweeper와 Maintainer의 모습도 강하게 나타난다. Prototyper 성향도 아이디어를 많이 내는 쪽보다는 구현 전에 불확실한 부분을 확인하는 데 가깝다. Grower는 아직 판단할 만큼 경험이 충분하지 않다.

## 분석에 사용한 자료

다음 자료를 대조했다.

1. **역할 정의**: Boris Cherny의 다섯 역할과 사용자의 첫 반응
2. **검사 데이터**: HEXACO 점수와 2025년 대비 변화
3. **행동 근거**: Vault의 경력 원장·DevLog·운영 규칙, QRA·Gallery·Hive·ONLYOFFICE의 코드·테스트·Git 이력·ADR
4. **해석**: 검사와 반복 행동을 함께 읽은 잠정적인 설명

근거의 무게는 `코드·테스트·Git·ADR > DevLog·경력 원장 > 자기 해석·AI 해석` 순서로 두었다. [[보리스 체르니의 5가지 아키타입]]처럼 이미 이 분류에서 파생된 노트는 독립적인 입증 자료로 세지 않았다.

Vault와 저장소에는 기술 구현과 시스템 개선이 자세히 남지만, 사용자 대화·시장 반응·비업무 관계 기록은 상대적으로 적다. 그래서 이 분석은 **업무에서 관찰된 모습**만 다룬다.

## 다섯 역할에 대한 현재 판단

| 역할             | 현재 판단        | 확인한 모습과 한계                                                                                   |
| -------------- | ------------ | -------------------------------------------------------------------------------------------- |
| **Builder**    | 가장 강함        | QRA, Hive, ONLYOFFICE 데모의 0→1이 여러 저장소에서 반복됨                                                  |
| **Maintainer** | 강하게 나타남      | 재시작 복구, 멱등성, Outbox, cleanup, E2E, 보안·회귀 테스트를 기능 완성의 일부로 다룸. 다만 성숙한 제품을 장기간 운영한 경험은 추가 확인 필요 |
| **Sweeper**    | 강하게 나타남      | 레거시 제거, 책임 경계 재편, QRA→Gallery 재통합, 중복 이벤트 제거가 반복됨                                            |
| **Prototyper** | 구현 전 확인에 가까움 | 아이디어를 많이 내기보다 구현 전 가장 불확실한 경로를 작은 PoC로 검증함                                                   |
| **Grower**     | 판단 유보        | 사용자 반응·채택·PMF·사용 지표를 바탕으로 제품을 반복 개선한 기록이 부족함                                                 |

## 역할별 해석

### Builder — 가장 확실한 중심 역할

QRA에서는 Gitea·ArgoCD·k3d 로컬 PoC에서 시작해 구독 이벤트, GitOps 변경, ArgoCD·Kubernetes 관측, 결과 통지까지 하나의 시스템으로 만들었다. 초기 커밋 이후 배포 흐름, 관측, 멱등성, 동시성, 복구가 순차적으로 붙었다.

Hive에서는 세 가지 멀티테넌시 전략을 추상화하고 프로비저닝→스키마→데이터 마이그레이션의 3단계 부트스트랩으로 만들었다. ONLYOFFICE도 편집기 연동 데모에서 멈추지 않고 UUID 식별자, 저장 Saga, 콜백 동시성, 보안 검증, Spring Boot 4, Streaming SSR까지 확장했다.

특정 프로젝트에서 우연히 나타난 모습은 아니다. 가능성을 확인한 뒤 실제로 쓸 수 있는 제품이나 인프라로 만드는 과정이 여러 프로젝트에서 반복됐다.

### Maintainer — 생각보다 강하게 나타난 역할

QRA·Gallery에서는 정상 경로를 구현한 뒤에도 다음 문제를 계속 다뤘다.

- 서버 재시작 후 관측 복구
- 중복 요청과 연속 배포의 수렴
- Outbox와 dispatch lease
- informer cache stale fallback
- 해지 시 Secret·Hook cleanup
- 전체 lifecycle E2E
- 기능 변경과 문서·테스트 동기화

ONLYOFFICE에서도 파일 저장 경쟁 조건, rollback 검증, executor cleanup, path traversal과 MIME 검증까지 같은 패턴이 나타났다. 기능이 한 번 동작하는 상태보다 사람이 계속 책임질 수 있는 상태를 완료로 보는 경향이 강하다.

다만 Boris의 엄격한 정의처럼 이미 성숙한 제품을 장기간 운영한 Maintainer라고 단정하기에는 운영 기간·장애 대응·서비스 지표 자료가 부족하다. 현재 자료만 놓고 보면 Builder에 가깝지만, 운영과 복구까지 함께 챙기는 편이라고 보는 것이 더 정확하다.

### Sweeper — 만든 뒤 구조를 다시 정리하는 역할

QRA를 만든 뒤 Gallery로 다시 합칠 때 기존 구조를 방어하기보다 유지할 것과 없앨 것을 다시 구분했다. ADR-021에는 재통합의 장점뿐 아니라 엄격한 모듈화 포기, Kafka self-consume의 어색함 등의 시행착오를 기록했다.

Hive에서는 분리된 초기화 흐름을 단일 Runner로 합치고 레거시 컴포넌트를 제거했다. ONLYOFFICE에서도 중복 코드와 deprecated API를 반복해서 정리했다. Vault 역시 충돌하는 규칙의 정본을 정하고 캡처·검토·승격·기계 검사를 분리하는 쪽으로 개편했다.

다만 처음부터 최소한의 구조만 남기는 순수 Sweeper는 아니다. 필요한 시스템을 충분히 만든 뒤 실제 마찰과 실패를 근거로 정리한다.

> **먼저 만들고, 실제로 부딪혀 본 뒤 복잡해진 부분을 정리한다.**

이 방식은 강점이지만, 복잡성을 통제하기 위한 스킬·규칙·대시보드 자체가 또 다른 관리 대상이 될 위험도 있다. 시스템을 새로 만드는 것과 기존 시스템을 실제 결과물에 재사용하는 것 사이의 균형을 계속 확인해야 한다.

### Prototyper — 아이디어를 펼치기보다 불확실성을 먼저 확인한다

기록에 남은 PoC는 실험 자체보다 본격적으로 만들기 전에 모르는 부분을 줄이려는 시도였다.

- QRA: 로컬 GitOps 경로를 먼저 확인
- ONLYOFFICE: 편집기·콜백·저장 경계를 데모로 검증
- Markdown→DOCX: Spring Boot·Node·docxtemplater·ONLYOFFICE의 책임을 작은 POC로 분리
- Vault: 스킬과 검색 규칙을 실제 노트에 적용하고, 실패가 드러나면 운영 규칙을 고침

아이디어를 많이 내는 Prototyper라기보다, 본격적인 구현 전에 불확실한 부분부터 확인하는 Prototyper에 가깝다.

### Grower — 아직 판단할 경험이 부족한 역할

Hive의 Devlime 적용 계획과 팀 로컬 검증 지원, QRA 운영 UI, ONLYOFFICE 연재와 Issue·PR 기반 발전 과정에는 Grower와 닿는 부분이 있다. 하지만 현재 자료에는 다음 피드백이 충분히 남아 있지 않다.

- 누가 실제로 사용했는가
- 사용자가 어디에서 막혔는가
- 피드백 때문에 무엇을 바꿨는가
- 채택률이나 반복 사용이 어떻게 달라졌는가
- 기술적으로 좋은 기능을 사용자 가치 때문에 버린 경험이 있는가

Grower가 나와 맞지 않는다기보다, 아직 판단할 경험이 충분하지 않다. Vault에 기술 구현은 자세히 남아 있지만 사용자와 나눈 대화는 적다는 점도 함께 고려해야 한다.

## HEXACO와 실제 행동의 접점

HEXACO만으로 역할을 증명할 수는 없지만, 반복해서 나타난 행동을 이해하는 참고자료로는 쓸 수 있다.

| 검사 신호 | 반복해서 관찰된 행동 | 잠정 해석 |
|---|---|---|
| 창의성 5.81·개방성 5.18 | 새로운 구조와 PoC, 외부 개념의 실무 적용 | 새로운 생각을 실제 운영 방식으로 구체화하는 편 |
| 완벽주의 5.98·근면성 상승 | 구현 뒤 테스트·복구·문서까지 챙김 | 높은 기준이 Builder·Maintainer 행동으로 이어짐 |
| 조직화 3.91·높은 완벽주의 | 스킬·ADR·lint·체크리스트로 누락을 통제 | 머릿속으로 챙기기보다 규칙과 도구에 맡기는 편 |
| 공정성 6.49 | 책임 경계, 출처, 기여 범위, rollback을 명시 | 누가 무엇을 책임지는지와 판단의 근거를 중시하는 편 |
| 낮은 외향성 | ADR·Issue·가이드·코드 리뷰 중심의 리딩 | 사람을 직접 이끌기보다 문서와 결과물로 방향을 맞추는 편. 사용자 탐색과 즉석 조율에는 에너지가 더 들 수 있음 |
| 낮아진 온화함 | 복잡성과 근거 부족을 빠르게 지적 | Sweeper에게 유리하지만 타인의 미완성 접근을 일찍 잘라낼 위험 |

`완벽주의 × 창의성`의 “생성자와 검증자가 한 몸”이라는 해석도 실제 행동과 이어진다. 다만 검증자는 결과를 검사하는 데서 끝나지 않고, 다음 작업부터 같은 문제가 반복되지 않도록 규칙·테스트·시스템을 수정한다.

## 내가 일하는 순서

```text
불확실한 부분을 찾는다
→ 작은 PoC로 먼저 확인한다
→ 실제로 쓸 수 있게 만든다
→ 겹치거나 복잡해진 부분을 정리한다
→ 실패했을 때 복구할 수 있는지까지 확인한다
```

다섯 역할로 다시 정리하면 다음과 같다.

- **중심 역할:** 가능성을 실제 시스템으로 만드는 Builder
- **함께 나타나는 역할:** 구조를 정리하고 운영과 복구까지 챙기는 Sweeper·Maintainer
- **시작하는 방식:** 구현 전에 불확실한 부분부터 확인하는 Prototyper
- **더 경험해 볼 부분:** 사람들의 사용과 피드백을 바탕으로 계속 다듬는 Grower

한 문장으로 압축하면 다음과 같다.

> **작은 실험으로 불확실한 부분을 먼저 확인하고, 실제로 쓸 수 있게 만든 뒤, 실패했을 때 복구할 수 있는지까지 확인해야 일이 끝났다고 보는 엔지니어.**

## 추가 확인이 필요한 질문

1. QRA·Gallery 운영 화면이나 배포 흐름이 실제 사용자·운영자 피드백 때문에 바뀐 사례가 있는가?
2. Hive를 Devlime에 적용하면서 팀원의 사용 경험 때문에 API·설정·가이드를 바꾼 사례가 있는가?
3. 출시 후 몇 달간 직접 운영하면서 지표나 장애를 바탕으로 계속 개선한 시스템은 무엇인가?

위의 세 질문으로 Grower와 Maintainer 경험을 더 정확히 살펴볼 수 있다.
