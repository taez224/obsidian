# Field Guide to Fable

> [!abstract] 한눈에 보기
> 강력한 AI 모델을 잘 쓰는 일은 더 자세한 지시를 작성하는 문제가 아니다. 모델이 스스로 환경을 탐색할 수 있도록 도구를 제공하고, 인간이 미처 정의하지 못한 불확실성을 함께 발견하며, 실행 과정에서 생긴 판단을 이해할 수 있는 상태를 유지해야 한다.

## 자료 정보

- 발표자: Thariq Shihipar, Anthropic Claude Code 팀
- 형식: 약 19분 분량의 발표
- 원문: [Field Guide to Fable](https://www.youtube.com/watch?v=9fubhllmsBU)

발표는 Fable이라는 새로운 모델을 다루지만, 핵심은 특정 모델의 기능 소개보다 **강해진 에이전트와 어떻게 일해야 하는가**에 있다. 발표자는 이를 네 부분으로 설명한다.

1. Claude의 잠재력을 가두지 않기
2. 자신이 모르는 것을 발견하기
3. 코딩 방식의 변화에서 오는 상실감 다루기
4. 기존의 트레이드오프를 너무 빨리 받아들이지 않기

## 1. 모델의 잠재력을 가두지 않는다

발표자는 모델이 설계된다기보다 데이터와 피드백, 연산을 통해 길러진다고 설명한다. 그래서 새로운 모델이 무엇을 할 수 있는지는 처음부터 완전히 알려져 있지 않다. 모델의 실제 능력은 모델 자체뿐 아니라 도구, 프롬프트, 실행 환경을 포함한 **하네스**에 의해 드러난다.

이를 설명하는 사례가 이름이 `aw`로 끝나는 포켓몬 찾기다. 일반 채팅 모델은 모든 포켓몬 이름을 알고 있어도 정답을 찾지 못한다. 반면 Claude Code는 전체 목록을 가져오고 스크립트를 작성해 조건에 맞는 이름을 필터링한다. 모델이 기억과 추론만으로 답한 것이 아니라, 도구를 이용해 문제를 풀 수 있는 형태로 바꾼 것이다.

발표자는 이렇게 모델이 이미 가지고 있지만 적절한 도구와 상호작용 방식이 없어 드러나지 않은 능력을 **capability overhang**이라고 부른다.

또한 모델을 이해하는 일은 규칙이 고정된 물리학보다 경험적으로 관찰하며 성질을 알아가는 생물학에 가깝다고 말한다. 모델의 능력은 유기적이고 불균일하게 발전하므로, 무엇이 가능해졌는지는 실제로 사용하고 실험하면서 발견해야 한다.

### 모델의 발전에 따라 달라진 하네스

- 거대한 컨텍스트를 미리 넣기보다 모델이 Bash와 검색 도구로 필요한 정보를 직접 찾게 한다.
- 약한 모델에는 많은 예시와 제약이 필요했지만, 강한 모델은 예시가 오히려 가능한 행동을 제한할 수 있다.
- 금지 사항을 길게 나열하기보다 판단에 필요한 맥락을 제공한다.
- 모델이 발전하면 기존 시스템 프롬프트와 도구 설계도 다시 검토한다. Claude Code 팀은 최근 시스템 프롬프트의 약 80%를 제거했다.

^harness-evolution

핵심은 모델이 강해질 때 기존 사용법을 그대로 확대하지 않는 것이다. 더 긴 프롬프트나 더 큰 컨텍스트가 아니라, 모델이 환경과 상호작용하는 새로운 방식을 찾아야 한다.

## 2. 좋은 명세보다 미지의 영역을 찾는 능력이 중요하다

발표자는 프롬프트와 계획을 **지도**, 실제 코드베이스와 현실의 제약을 **영토**에 비유한다. 에이전트가 실행 중 지도에 없는 상황을 만나면 사용자가 미리 지정하지 않은 의사결정을 내려야 한다. 이것이 `unknown`이다.

강한 에이전트는 더 넓은 범위를 자율적으로 이동하므로 더 많은 unknown을 만난다. 따라서 병목은 모델의 구현 능력보다 사용자가 지도와 영토의 차이를 얼마나 잘 발견하는가로 이동한다.

### 네 종류의 앎과 모름

| 구분 | 의미 |
|---|---|
| Known knowns | 알고 있고 명시할 수 있는 것. 보통 프롬프트에 적는다. |
| Known unknowns | 모른다는 사실은 알고 있는 것 |
| Unknown knowns | 알고 있지만 너무 당연해서 말로 표현하지 않은 것 |
| Unknown unknowns | 무엇을 모르는지도 모르는 것 |

### Unknown을 발견하는 방법

#### Blind spot pass

본격적으로 구현하기 전에 코드베이스와 관련 자료를 조사하고, 놓친 제약과 위험을 찾아 달라고 한다.

> [!example] 재구성한 예시 프롬프트
> 이 작업을 시작하기 전에 blind spot pass를 수행해줘. 내가 아직 고려하지 않은 제약, 실패 가능성, 아키텍처를 바꿀 수 있는 unknown unknowns를 찾아줘.

#### 서로 다른 프로토타입 만들기

취향이나 요구사항처럼 말로 설명하기 어려운 것은 서로 크게 다른 결과물을 여러 개 만든 뒤 반응하면서 구체화한다. 발표자는 디자인 감각을 설명하는 대신 네 가지 HTML 대시보드 시안을 만들어 달라고 요청한다.

#### 에이전트에게 인터뷰받기

작업 전에 에이전트가 사용자를 질문하게 한다. 질문의 수보다 의사결정에 미치는 영향이 중요하다.

> [!example] 재구성한 예시 프롬프트
> 나를 인터뷰해서 명세에서 빠진 부분을 찾아줘. 특히 답에 따라 아키텍처가 달라질 수 있는 질문을 우선해줘.

#### 참조물 제공하기

긴 설명 대신 원하는 결과와 비슷한 코드, 다른 언어의 구현, HTML 목업 같은 참조물을 제공한다. 하나의 지도를 새로 설명하기보다 이미 존재하는 다른 지도를 보여주는 방식이다.

#### Implementation notes 남기기

실행 중 계획에 없던 상황을 만났다면 무엇이 달랐고 어떤 판단을 내렸는지 기록하게 한다. 최종 결과만 남기지 않고 지도와 영토가 어긋난 지점을 보존하는 것이다.

#### 작업이 끝난 뒤 퀴즈받기

에이전트가 수행한 작업을 사용자가 실제로 이해했는지 확인한다. PR을 만들거나 결과물을 인계하기 전에 변경 이유와 중요한 결정을 설명할 수 있는 상태를 만드는 방법이다.

## 3. 생산성 향상에는 상실감도 따른다

발표자는 직접 코드를 작성하고 코드베이스 전체를 머릿속에서 다루던 감각을 좋아했다고 말한다. 그러나 과거 몇 주가 걸리던 작업을 몇 시간 만에 끝내는 경험을 하고 나면 이전 방식으로 돌아갈 수도 없다고 느낀다.

그는 직접 코드를 쓰는 즐거움만큼 밤새 디버깅하고 실패하던 시간도 기억한다. 그러나 이제 이전 방식으로 돌아갈 수는 없으며, “the only way out is through”라고 정리한다. Fable과 함께 일하는 법을 더 배우되 실행 과정에 계속 참여해야 한다는 결론이다.

## 4. 기존의 트레이드오프를 너무 빨리 받아들이지 않는다

AI 에이전트는 과거에 당연하게 받아들였던 비용 구조를 바꾼다. 발표자는 좋은 것, 빠른 것, 저렴한 것 중 둘만 고르는 대신 일단 셋 모두를 요구해 보라고 말한다. 트레이드오프를 머릿속에서 미리 확정하지 말고 현실이 실제 한계를 보여줄 때까지 더 높은 목표를 시도하라는 뜻이다.

하지만 발표는 낙관론만으로 끝나지 않는다.

> 만드는 일은 쉬워졌지만, 가치를 만드는 일은 여전히 어렵다. — [18:22](https://www.youtube.com/watch?v=9fubhllmsBU&t=1102s)

산출물을 많이 만드는 것과 유용한 문제를 해결하는 것은 다르다. 구현 비용이 낮아질수록 어떤 시도가 실제 가치로 이어지는지 판단하고, 여러 번 실험하며, 결과를 현실에 적용하는 능력이 더 중요해진다.

## 나의 해석

이 발표의 가장 유용한 부분은 Fable의 성능이 아니라 인간의 역할을 다시 정의한 대목이다.

```text
과거: 사람이 계획하고 모델이 실행한다.
현재: 모델과 함께 계획의 빈틈을 찾고, 실행 중 생긴 판단을 사람이 흡수한다.
```

강한 에이전트가 구현 범위를 넓힐수록 인간은 모든 세부 절차를 미리 지정하기 어렵다. 대신 무엇을 모르는지 발견하고, 에이전트가 내린 결정을 추적하며, 결과를 이해하고 검증하는 역할이 중요해진다.

이 관점에서 보면 직접 타이핑하는 비중이 줄어들수록 다음 능력이 중요해진다.

- 무엇을 만들지 결정하기
- 계획에서 빠진 제약을 발견하기
- 에이전트가 내린 판단을 이해하기
- 결과를 설명하고 책임질 수 있기

### 실천 가능한 작업 흐름

영상의 조언을 하나의 에이전트 작업 흐름으로 압축하면 다음과 같다.

1. **Blind spot pass**로 코드베이스와 문제의 숨은 제약을 찾는다.
2. **인터뷰**를 통해 아키텍처를 바꿀 수 있는 결정을 먼저 드러낸다.
3. 말로 설명하기 어려운 요구사항은 **여러 프로토타입**으로 탐색한다.
4. 원하는 결과와 비슷한 **참조 구현**을 제공한다.
5. 작업 중 만난 unknown과 계획에서 벗어난 결정을 **implementation notes**로 남긴다.
6. 완료 후 **설명과 퀴즈**를 통해 사용자가 결과를 이해했는지 확인한다.

다만 “트레이드오프는 실재하지 않는다”는 표현은 문자 그대로 받아들이기보다 **트레이드오프를 미리 가정하지 말고 실제 한계가 드러날 때까지 요구 수준을 높인다**는 뜻으로 읽는 편이 타당하다. 검증 비용, 보안, 유지보수, 팀의 이해와 흡수 능력까지 사라진 것은 아니다.
