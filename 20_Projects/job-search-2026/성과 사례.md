## 1. QRA 프로젝트 0→1 리드

- **한 줄 요약:** QRA 프로젝트 리드로 로컬 PoC부터 서비스 경계, 배포 파이프라인, 운영 UI까지 GitOps 배포 플랫폼을 0→1로 구축했다.
- **기간·소속:** 2026.01~2026.04, Vizend 플랫폼
- **보여주는 역량:** 프로젝트 리딩, 아키텍처 설계, 백엔드·프론트엔드 통합

### 상황

Gallery 내부에 배포 실행과 모니터링 책임이 섞여 있어 독립적으로 확장하고 운영하기 어려웠다. GitOps, ArgoCD, Kubernetes, Kafka, PostgreSQL을 연결하는 별도 서비스와 운영 화면이 필요했다.

### 내 판단과 행동

- 구현 전에 Gitea·ArgoCD·k3d 로컬 PoC로 GitOps→ArgoCD→Kubernetes 경로를 검증했다.
- QRA의 멀티모듈 구조와 배포 도메인을 설계하고 EPIC·ADR로 작업 순서를 정했다.
- 구독 이벤트 수신, GitOps 변경, 배포 관측, 결과 집계를 하나의 lifecycle로 구현했다.
- 운영자가 사용할 qra-view까지 직접 연결해 백엔드 상태 모델이 실제 화면에서 검증되도록 했다.

### 결과

- 구독 요청부터 배포 결과 통지까지 QRA 배포 파이프라인의 전체 사이클을 구축했다.
- 내부 기록 기준 8주 동안 7개 EPIC과 80개 이상의 이슈를 완료했다. 외부 사용 전 수치 확인이 필요하다.
- 이후 QRA 기능이 Gallery로 재통합될 때 재사용 가능한 코드·도메인·운영 자산을 남겼다.

## 2. 비동기 배포 파이프라인 안정화

- **한 줄 요약:** 메시지 재전달, 서버 재시작, 연속 배포로 발생하는 중복 실행과 상태 역전을 lifecycle·lease·outbox 기반으로 방어했다.
- **기간·소속:** 2026.02~2026.03, QRA
- **보여주는 역량:** 분산 시스템, 상태 모델링, 멱등성, 장애 복구

### 상황

동일 요청이 다시 전달되거나 서버가 관측 중 재시작될 수 있었고, 같은 서비스의 새 배포가 시작된 뒤 과거 관측 결과가 도착하면 최신 상태를 덮을 위험이 있었다. ArgoCD sync 성공도 실제 Pod 준비 완료를 보장하지 않았다.

### 내 판단과 행동

- 요청을 `NEW/DUPLICATE/CONFLICT`로 구분하고 batch/result의 중복 기록을 막았다.
- deployment lineage와 `Superseded` 상태를 도입해 최신 배포가 이전 관측을 선점하도록 했다.
- Batch Dispatch Lease와 queue로 동일 GitOps 작업의 중복 실행을 방지했다.
- 서버 시작 시 `Requested` 배포를 복구하고 미완료 Git 작업을 재구성했다.
- ArgoCD 상태, 개별 Deployment health, Pod consecutive readiness를 조합해 성공을 판정했다.
- 결과 이벤트에는 Outbox를, 런타임 감시에는 leader election과 DB 기반 복구를 적용했다.

### 결과

- 재전달·재시작·연속 배포에서 중복 실행과 관측 순서 역전을 방어하는 구조를 만들었다.
- GitOps sync와 실제 서비스 준비 사이의 간극을 배포 성공 조건에 반영했다.
- 실패 시 Kubernetes Event를 보강해 원인 설명력을 높였다.

## 3. 백엔드 상태를 운영 UI로 연결

- **한 줄 요약:** QRA의 배포·런타임 상태 모델을 React/TypeScript 운영 UI로 직접 연결해 요청부터 Kubernetes 리소스까지 추적할 수 있게 했다.
- **기간·소속:** 2026.02~2026.03, QRA/qra-view
- **보여주는 역량:** Full-stack 구현, 운영 UX, API·상태 모델 정합

### 상황

배포 상태가 백엔드 로그와 여러 인프라 시스템에 흩어져 있어 운영자가 진행 단계와 실패 원인을 한눈에 파악하기 어려웠다.

### 내 판단과 행동

- SSE 기반 실시간 배포·런타임 상태를 qra-state와 qra-view에 연결했다.
- 배포 목록·상세, 구독별 SubscriptionStatus, Pod 상태와 mounted configuration을 구현했다.
- Kubernetes 리소스 토폴로지와 상세 Drawer, Manifest/Diff viewer를 구현했다.
- GitOps Repository·Container Registry 설정과 연결 테스트 UI를 구성했다.
- Storybook 시나리오와 브라우저 기반 Vitest로 주요 화면 상태를 검증했다.

### 결과

- 운영자가 배포 요청, 진행 단계, 런타임 상태, 리소스 구성과 실패 근거를 한 흐름에서 확인할 수 있게 했다.
- 백엔드와 프론트엔드를 함께 다루면서 상태 이름과 사용자 표현 사이의 의미 차이를 줄였다.
- QRA 재통합 후에도 관련 모듈이 gallery-view/state/stub으로 이어졌다.

## 4. QRA 재통합과 provisioning 확장

- **한 줄 요약:** 독립 QRA의 배포 역량을 Gallery에 재통합하고, 구독 Secret과 DB 준비·해지 cleanup까지 lifecycle 자동화를 확장했다.
- **기간·소속:** 2026.04~2026.05, QRA/Gallery
- **보여주는 역량:** 서비스 경계 재설계, 마이그레이션, 보안·운영 자동화, E2E 검증

### 상황

제품 경계 변경으로 QRA 기능을 Gallery 내부로 다시 옮겨야 했다. 동시에 구독 즉시 배포를 위해 애플리케이션 Secret과 DB/schema/role을 workload 전에 준비하고, 해지 시 runtime 자산과 외부 데이터 자산의 처리 정책을 분리해야 했다.

### 내 판단과 행동

- facade·feature·domain·proxy·store와 Flyway, 이벤트, 운영 문서를 Gallery 구조에 맞춰 이관했다.
- Secret metadata와 value를 분리하고 value를 암호화 저장한 뒤 배포 직전에 Kubernetes Secret으로 실체화했다.
- ArgoCD PreSync wave로 DB Bootstrap과 Drama별 schema/role reconcile을 workload보다 먼저 실행했다.
- ownership label을 apply와 cleanup의 공통 계약으로 두고 runtime Secret, DB credential Secret, live hook resource를 정리했다.
- 외부 DB/schema/role은 즉시 삭제하지 않고 보존하도록 데이터 보존 경계를 분리했다.
- SUBSCRIBE부터 UNSUBSCRIBE까지 전체 경로를 검증하는 E2E harness를 만들었다.

### 결과

- 서비스 경계가 바뀌어도 QRA의 핵심 배포 자산을 보존하면서 불필요한 서비스 간 호출을 제거했다.
- Secret·DB 준비를 구독 lifecycle 안에서 자동 실행하고 검증할 수 있게 했다.
- 제거해야 할 runtime 자산과 보존해야 할 외부 데이터 자산을 코드·ADR·E2E에 같은 기준으로 남겼다.

## 5. 센아 문서관리 시스템 Tech Lead

- **한 줄 요약:** 4인 팀 Tech Lead로 문서 편집·저장·권한·처리 상태를 연결한 통합 문서관리 시스템을 구축하고 주니어 3명의 개발과 인수인계를 지원했다.
- **기간·소속:** 2024.04~2024.12, 넥스트리
- **보여주는 역량:** 테크리드, Full-stack, 이벤트 기반 설계, 멘토링

### 상황

ONLYOFFICE 기반 문서 편집, 템플릿과 스프레드시트 처리, AWS S3 저장, 인증·인가, 장시간 처리 상태를 하나의 업무 흐름으로 연결해야 했다. 여러 연계 시스템과 라이브러리가 있어 실패 위치와 처리 상태가 사용자에게 보이지 않을 위험이 있었다.

### 내 판단과 행동

- Spring Boot 백엔드와 TypeScript/React 프론트엔드를 함께 담당했다.
- ONLYOFFICE Docs, DocxTemplater, SpreadJS, Aspose, AWS S3의 책임 경계를 나눴다.
- Saga 패턴으로 문서 저장 흐름을 구성하고 Kafka로 처리 상태를 추적했다.
- SSE로 장시간 처리 결과를 사용자에게 실시간 전달했다.
- 문서 분류 체계에 맞는 인증·인가 흐름을 설계했다.
- 주니어 3명의 코드 리뷰와 멘토링, 연계 시스템 기술 문서 배포를 맡았다.

### 결과

- 문서 편집부터 저장·처리 상태·권한까지 흩어진 기능을 하나의 시스템 흐름으로 연결했다.
- 팀원이 연계 방식과 처리 상태를 재현할 수 있도록 코드 리뷰와 문서를 함께 남겼다.
- 성능·사용자·운영 결과 수치는 추가 확인이 필요하다.

## 6. Hive 멀티테넌시 모듈 1인 구축

- **한 줄 요약:** B2B SaaS 데이터 격리를 위한 Spring Boot 멀티테넌시 모듈을 4주·2개 스프린트에 1인 설계·구현하고 팀 적용 가이드까지 전달했다.
- **기간·소속:** 2025.10~2025.11, 넥스트리 Vizend
- **보여주는 역량:** 빠른 설계·구현, 멀티테넌시, 인수인계

### 상황

조직·tenant 단위 데이터 격리를 지원하면서 서비스별로 같은 기반 코드를 반복하지 않도록 공통 모듈과 적용 기준이 필요했다.

### 내 판단과 행동

- Database per tenant와 Schema per tenant 전략을 비교하고 지원 경계를 정했다.
- 첫 2주에는 Spring Boot 기반 핵심 기능을 구현했다.
- 다음 2주에는 적용 가이드 작성과 팀원의 로컬 검증을 지원했다.
- 구현 완료가 아니라 다른 팀원이 적용할 수 있는 상태를 종료 조건으로 두었다.

### 결과

- 4주 안에 핵심 모듈과 팀 적용 가이드를 전달하고 인수인계 후 다음 프로젝트로 이동했다.
- 지원 tenant 수와 실제 적용 서비스는 추가 확인이 필요하다.
