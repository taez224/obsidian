# 면접 준비

## 1분 소개

> 현재 역할 → 강점이 드러나는 경험 → 다음 조직에서 풀고 싶은 문제 순서로 작성한다.

저는 넥스트리에서 제품 백엔드와 풀스택 개발, 테크리드를 거쳐 배포 플랫폼까지 경험한 5년차 백엔드·플랫폼 엔지니어입니다. 최근에는 QRA 프로젝트 리드로 GitOps 기반 배포 오케스트레이션 서비스를 처음부터 구축했습니다. Gallery의 구독 요청을 받아 GitOps를 변경하고, ArgoCD와 Kubernetes 상태를 관측해 결과를 다시 전달하는 전체 흐름을 설계·구현했으며, 재시작 복구와 중복 실행 방지, 런타임 모니터링까지 확장했습니다. React와 TypeScript로 운영 화면도 직접 구현해 백엔드 상태 모델을 실제 사용자 경험까지 연결했습니다. 이후 QRA 기능을 Gallery에 재통합하면서 Secret과 DB provisioning 자동화까지 범위를 넓혔습니다. 다음 조직에서도 여러 시스템에 흩어진 상태와 수동 운영을 명확한 lifecycle과 검증 가능한 자동화로 바꾸는 역할을 하고 싶습니다.

## 리드 경험 요약

- QRA: 프로젝트 리드로 PoC, 아키텍처, 백엔드·운영 UI, 이슈·ADR·검증 흐름을 연결
- 센아 문서관리 신규 구축: 4인 팀 Tech Lead, 주니어 3명 멘토링과 코드 리뷰
- Hive: 1인 설계·구현 후 팀 적용 가이드와 로컬 검증 지원
- 공통 방식: 구현을 직접 수행하면서 결정 근거와 인수인계 자료, 검증 절차를 함께 남김

## QRA 프로젝트 1분 설명

QRA는 Gallery에 있던 배포 실행과 모니터링 기능을 독립시킨 GitOps 배포 오케스트레이션 플랫폼입니다. 저는 프로젝트 리드로 로컬 PoC와 서비스 경계부터 설계했고, 구독 이벤트를 받아 GitOps manifest를 변경하고 ArgoCD sync와 Kubernetes Pod 안정화를 관측한 뒤 결과를 집계해 돌려주는 전체 파이프라인을 구현했습니다. 이 과정에서 메시지 재전달과 서버 재시작, 연속 배포에 대응하기 위해 중복·충돌 요청 구분, Superseded 전이, dispatch lease, Outbox와 leader election을 적용했습니다. 운영자가 이를 볼 수 있도록 qra-view의 실시간 모니터링과 리소스 토폴로지도 직접 구현했습니다. 이후 제품 경계가 다시 조정되면서 QRA 기능을 Gallery로 재통합했고, 그 위에 runtime Secret과 DB provisioning, cleanup E2E를 확장했습니다.

### 가장 어려웠던 기술적 문제는 무엇인가?

  - ArgoCD sync 성공을 배포 성공으로 보지 않은 이유는 무엇인가?
  - 서버 재시작 시 어떤 상태를 기준으로 복구했나?

### 의견 충돌이나 협업 문제를 어떻게 해결했는가?

### 실패하거나 기대와 달랐던 경험은 무엇인가?

- 연결할 [[성과 사례]]: [[성과 사례#4. QRA 재통합과 provisioning 확장]]
- 핵심 답변: QRA를 독립 서비스로 구축했지만 제품 경계가 다시 바뀌어 Gallery에 재통합하게 됐다. 구조가 영구히 유지될 것이라는 전제보다 도메인과 검증 자산을 이동 가능하게 만드는 것이 중요하다는 점을 배웠다.

### AI를 실제 개발에 어떻게 활용했나요?

> 처음부터 지금과 같은 체계를 쓴 것은 아닙니다. Hive에서는 AI를 설계 대안 탐색, 리팩터링, 문서화에 부분적으로 활용했고, 프로젝트 후반에야 `CLAUDE.md`와 계획 승인형 이슈 해결 명령을 도입했습니다. 이 경험에서 대화만으로는 프로젝트 맥락과 검증 기준이 세션마다 달라질 수 있다는 한계를 배웠습니다. 그래서 QRA에서는 `AGENTS.md`, 경로별 규칙과 ADR로 맥락을 제공하고, 요구사항·이슈·구현·DoD 리뷰가 각각 산출물을 남기는 workflow를 설계했습니다. 처음 시도한 에이전트 팀은 오히려 복잡해서 단일 workflow 중심으로 줄였고, Gallery로 옮길 때도 그대로 복사하지 않고 GitLab SSOT·브랜치·라벨·테스트 전략에 맞게 다시 설계했습니다. 이 흐름을 runtime Secret과 DB provisioning, cleanup 구현에 적용하고, full-lifecycle E2E로 실제 상태 변화를 검증했습니다. 제 AI 활용의 핵심은 생성량이 아니라, 시행착오를 규칙과 검증 장치로 바꾸고 결과를 사람이 책임질 수 있는 변경으로 만드는 것입니다.

- **AI가 맡은 일:** 코드베이스 탐색, 대안과 실패 시나리오 제안, 구현·테스트 초안, 리뷰 재료 수집
- **내가 맡은 일:** 요구사항과 책임 경계 확정, 대안 선택, 코드 진입점과 상태 전이 판단, 실제 테스트·E2E 결과 확인
- **실패에서 바꾼 것:** 역할을 많이 나눈 에이전트 팀보다 단일 workflow와 명확한 검증 게이트가 적합하다고 판단해 구조를 단순화
- **발전 과정:** Hive의 대화형 보조 → QRA의 workflow 체계화 → Gallery의 저장소별 재설계와 lifecycle 검증
- **과장하지 않을 것:** 팀 전체 생산성 향상은 측정하지 않았으며, workflow 설계·실제 기능 적용·검증 산출물까지만 주장
- 상세 근거: [[AI 개발 운영체계#저장소 검증 결과]]

## QRA 답변에서 피할 표현

- “AI가 대부분 구현했다” → 요구사항·판단·검증을 어떤 구조로 운영했는지 설명한다.
- “민감정보 노출을 완전히 제거했다” → Git·이벤트 payload 확산을 차단하고 메모리 평문 범위를 제한했다고 설명한다.
- “모든 작업을 혼자 했다” → 직접 구현, 리드·리뷰, 팀 공동 작업을 확인 후 구분한다.
- “QRA가 실패해서 Gallery로 돌아갔다” → 제품 경계 변화에 맞춰 핵심 자산을 재통합하고 확장한 과정으로 설명한다.
- 내부 클래스명만 나열 → 먼저 문제와 판단을 설명하고 필요할 때 구현 세부사항을 제시한다.
