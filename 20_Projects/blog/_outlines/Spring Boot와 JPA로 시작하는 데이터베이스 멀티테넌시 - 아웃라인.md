# Spring Boot와 JPA로 시작하는 데이터베이스 멀티테넌시

넥스트리 기술 블로그의 독자·설명 범위와 절별 역할을 정하는 집필 기준이다. 본문 정본은 [[Spring Boot와 JPA로 시작하는 데이터베이스 멀티테넌시]]이며, 제목·summary·문장은 원고에서 관리한다.

## 집필 방향

- **독자:** Spring Boot와 JPA로 CRUD를 구현해 봤지만 데이터베이스 멀티테넌시는 처음인 개발자.
- **목적:** Hibernate가 세션의 테넌트 ID로 행 조건이나 연결 대상을 선택하는 원리와, 테넌트 전환 시 세션·트랜잭션 경계를 이해한다.
- **전개:** 주문의 테넌트 조건 반복 → 행 분리 → 공통 테넌트 전달 → 주문 조회 검증 → 캐스팅의 스키마·DB 분리 → 조회 검증 → 전환 제약 → 범위와 한계.
- **예제:** 행 분리는 `Order`, 스키마·DB 분리는 Marvel·DC의 `Casting`으로 설명한다. 같은 엔티티·Repository·서비스를 공유하는 비교는 스키마·DB 분리에 해당한다.
- **톤과 깊이:** 존댓말 설명형이다. 동작·구성은 직접 설명하고 실제 선택 이유와 검증 결과는 구분한다. 코드는 원리와 호출 순서를 보여 주는 발췌이며, 본문의 테스트는 저장 → 조회 → 결과 확인을 보여 준다.
- **범위:** 세 분리 방식과 동기 요청의 조회 흐름을 다룬다. 인증·인가·동적 테넌트 등록·마이그레이션·비동기 전파·공용 데이터 조회의 구현은 제외한다. 운영용 완성 구현이나 세 방식을 순차 도입하는 경로를 제시하지 않는다.

## 1. 도입

**역할:** 주문 Repository의 테넌트 조건 반복과 누락 위험에서 출발한다.

- 단건 조회·상태 검색·집계의 `AndTenantId`를 보여 주고, JPA 구현체인 Hibernate의 조건 자동 적용과 스키마·DB 선택으로 이어 간다.

## 2. 테넌트와 세 가지 데이터 분리 방식

**역할:** 테넌트와 사용자를 구분하고, 행·스키마·DB의 데이터 배치와 선택 지점을 비교한다.

- 그림은 같은 배우의 배역 데이터를 세 방식으로 비교한다. 실제 행 분리 코드는 `Order`를 사용한다.
- 시각 자료: `../assets/multitenancy-data-layouts.svg`.

## 3. 행 분리: `@TenantId`로 반복되는 조건 줄이기

**역할:** 테넌트 인자를 뺀 Repository와 Hibernate가 추가하는 SQL 조건을 연결한다.

- `@TenantId`와 RLS를 소개하고, 예제에서 사용할 `@TenantId`의 역할을 설명한다.
- `Order` 코드의 필드·주석과 `(tenant_id, order_id)` 유일성 제약으로 식별자의 역할을 보여 준다.
- 단건 조회·상태 검색·집계 메서드와 조회 SQL을 보여 준다. 네이티브 SQL에는 조건이 자동 적용되지 않는다는 경계를 남긴다.

## 4. 요청의 테넌트를 Hibernate 세션에 전달

**역할:** JPA 작업과 Hibernate 세션의 관계를 짚고, 세 방식에 공통인 테넌트 바인딩과 세션 생성 시점을 설명한다.

- OSIV 비활성화와 외부 트랜잭션 없는 서비스 호출을 전제로, `TenantContext`·필터의 요청 범위 바인딩 → `TenantResolver`의 테넌트 ID 제공 → Customizer 등록 순서로 연결한다.
- `ScopedValue` 선택 이유와 바인딩의 수명을 설명한다. 헤더는 예제의 식별 입력이며 식별 방식 설계는 다루지 않는다. `ThreadLocal` 비교는 부록에 둔다.

## 5. 행 분리 조회 결과 확인

**역할:** 같은 주문 ID와 전체 목록 조회가 테넌트별로 제한되는지 확인한다.

- `bookshop`·`recordshop`에 주문 ID는 같고 상태가 다른 주문을 저장한다.
- `RowModeTest`의 주문 조회·`findAll()` 테스트를 통해 상태와 반환된 행의 테넌트 ID를 확인한다.

## 6. 스키마·DB 분리의 공통 예제

**역할:** 같은 테이블의 행 구분에서 테넌트별 저장 위치의 비교로 넘어간다.

- Marvel·DC에 같은 배우 ID와 다른 배역을 저장한다. `actorSlug`를 기본 키로 사용하는 공통 엔티티·Repository·조회 서비스를 보여 준다.
- 그림 앞에서 프로파일로 설정 파일을 불러오고 `demo.strategy`로 구현을 선택하는 관계를 설명한다.
- 요청 바인딩 → 서비스 세션 → 스키마·DataSource 선택을 `../assets/multitenancy-tenant-flow.svg`로 연결한다.

## 7. 스키마 분리: 같은 DB에서 사용할 스키마 선택

**역할:** 하나의 DataSource에서 세션의 테넌트 ID에 맞는 스키마를 선택하는 원리를 설명한다.

- `shared` DB의 테넌트·스키마 매핑 설정 → `TenantSchemaMapper`와 등록 코드 → `Connection.setSchema()` 호출로 이어 간다.
- Hibernate 7.1 도입과 `@Incubating` 상태는 콜아웃에, 이전 버전 대안은 각주에 둔다.

## 8. DB 분리: 테넌트별 DataSource 선택

**역할:** 스키마 전환과 달리 커넥션을 얻을 DataSource를 고른다는 차이를 보여 준다.

- 테넌트별 풀의 생성 시점과 접속 설정을 설명하고, 세션의 테넌트 ID에 따른 DataSource 선택·풀 종료·Hibernate 등록 코드를 보여 준다.
- `selectAnyDataSource()`와 메타데이터 조회용 `metadata_db`를 설명한다. 자동 설정·풀 관리의 내부 구현은 예제 소스에 둔다.

## 9. 스키마·DB 분리의 조회 결과 확인

**역할:** 공통 조회 코드가 두 설정에서 테넌트별 데이터를 반환하는지 확인한다.

- HTTP 요청·응답 하나와 `TenantApiTest`의 저장·조회 테스트를 보여 준다.
- 두 테스트 클래스의 프로파일과 PostgreSQL 통과 결과를 연결한다. 수정 격리 테스트는 예제 소스에만 둔다.

## 10. 테넌트 전환은 새 세션에서

**역할:** 테넌트 전환의 규칙 → 실험 결과 → 호출 방법을 연결한다.

- 세션의 테넌트 ID는 컨텍스트 변경으로 바뀌지 않으며, `REQUIRED` 호출은 기존 트랜잭션에 참여해 새 세션을 열지 않는다는 규칙을 먼저 설명한다.
- 전파 규칙 설명과 실제 실험 경로를 구분한다. 실험은 하나의 Marvel 트랜잭션 안에서 컨텍스트만 DC로 바꿔 조회하며, 표에서 테넌트 컨텍스트·세션의 테넌트 ID·반환값을 비교한다. 테스트 구현은 예제 소스에 둔다.
- OSIV를 끈 예제에서 외부 트랜잭션 없이 테넌트 바인딩 → 서비스 호출을 각각 수행하는 방법으로 마친다. 운영자 기능·배치의 구현까지 확장하지 않는다.

## 11. 예제의 범위와 한계

**역할:** 예제에서 확인한 분리 원리와 실제 서비스에서 별도로 설계할 사항을 구분한다.

- 사용자·DB 계정 권한, 테넌트별 풀·전체 커넥션 수·공유 부하의 영향, 테넌트 등록·구조 변경·백업과 복구를 세 문단으로 정리한다.
- 분리 방식만으로 보안·성능 격리를 보장하거나 운영 준비가 끝났다고 설명하지 않는다.

## 12. 마치며

**역할:** 테넌트 조건의 반복을 줄이고 업무 코드와 연결 선택을 분리하는 효용으로 닫는다.

- `Order`의 조건 자동 적용과 `Casting`의 공통 업무 코드 사용을 회수한다.
