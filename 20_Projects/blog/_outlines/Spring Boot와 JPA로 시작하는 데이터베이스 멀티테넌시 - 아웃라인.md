# Spring Boot와 JPA로 시작하는 데이터베이스 멀티테넌시

넥스트리 기술 블로그 원고의 독자·설명 범위와 절별 역할을 정하는 집필 기준이다. 본문 정본은 [[Spring Boot와 JPA로 시작하는 데이터베이스 멀티테넌시]]이며, 제목·summary·문장은 원고에서 관리한다.

## 집필 방향

- **독자:** Spring Boot와 JPA로 CRUD를 구현해 봤지만 데이터베이스 멀티테넌시는 처음인 개발자.
- **중심:** 공통 엔티티·Repository·서비스로 테넌트별 데이터를 다루는 원리와, 세션이 열리기 전에 테넌트를 바인딩해야 하는 이유를 설명한다.
- **흐름:** 조건 누락의 영향 → 데이터 분리 방식 → 공통 예제 → 테넌트 전달 → 스키마·DB 선택 → 조회·수정 검증 → 전환의 제약 → 운영 고려사항.
- **코드의 역할:** 원리와 호출 순서를 확인하는 발췌다. 핵심 동작·조건은 보존하고, 전체 실행 프로젝트를 완성하기 위한 보조 구현은 예제 소스에 둔다. 설명·코드의 고정 비율을 목표로 하지 않는다.
- **톤과 깊이:** 존댓말로 개념·코드·확인 결과를 연결한다. 내부 맥락 없이 이해할 수 있는 입문 글로 쓰고, 운영용 완성 구현을 약속하지 않는다.
- **범위:** 미리 준비한 두 테넌트에서 동기 요청의 JPA 조회·수정으로 스키마 분리와 DB 분리를 비교한다. 헤더는 테넌트 식별의 예제 입력이다. JDBC 병용·동적 테넌트 등록·마이그레이션·라이브러리화·비동기 전파의 구현은 다루지 않는다. 운영 절에는 예제와 직접 관련된 검토 항목만 남긴다.

## 1. 도입

**역할:** 메서드마다 반복되는 테넌트 조건에서 데이터 분리 문제로 넘어간다.

- 주문 Repository의 조회·검색·집계 메서드에 붙는 `AndTenantId`와 누락 시 다른 테넌트의 데이터를 읽거나 바꿀 수 있다는 영향을 보여 준다.
- 쿼리 조건 대신 연결할 스키마·DB를 선택하는 방법을 소개하고, 예제 환경과 코드 발췌 기준을 짧게 밝힌다.

## 2. 테넌트와 데이터 분리 방식

**역할:** 테넌트의 뜻과 데이터를 나누는 단위, 조회 범위를 정하는 지점을 구분한다.

- 테넌트와 사용자의 소속 관계를 설명하고 사용자 ID와 테넌트 ID를 구분한다. 스키마의 뜻을 짧게 정의한다.
- 행 단위 분리(Discriminator column)·스키마 분리(Schema per tenant)·DB 분리(Database per tenant)를 데이터 배치 그림과 비교표로 보여 준다.
- 행 단위 분리의 조건 적용도 `@TenantId`·RLS로 자동화할 수 있음을 짚고, 같은 테이블의 행을 구분하는 것과 테넌트별 테이블을 나누는 것의 차이를 설명한다. 테넌트별 데이터를 따로 옮기거나 관리해야 할 때 분리를 고려한다는 선택 이유를 짧게 연결하고, Hibernate 구현 설명은 뒤의 예제로 넘긴다.

**시각 자료:** `../assets/multitenancy-data-layouts.svg`. 테넌트 데이터를 나누는 단위를 색으로 표시하고, 표는 방식 이름과 선택 지점을 비교한다.

## 3. 두 방식의 공통 예제

**역할:** 바뀌는 데이터와 공통 업무 코드를 먼저 보여 주고, 연결 설정의 차이를 드러낸다.

- 같은 배우 ID `ryan-reynolds`에 Marvel은 Deadpool, DC는 Green Lantern을 저장한다. `actorSlug`는 테넌트별 `casting` 테이블의 기본 키다.
- 같은 배우 조회에서 테넌트에 맞는 배역이 나오고, Marvel의 배역명 변경이 DC에 영향을 주지 않는지 확인한다. DB·스키마·테이블은 미리 준비한다.
- 엔티티·Repository 다음에 조회·배역명 변경 서비스와 공통 조회 보조 메서드를 발췌한다. 테넌트 인자·조건 없이 동작하고, 변경 감지로 수정하는 부분을 보여 준다.
- 서비스 코드 뒤에서 공통 YAML과 방식별 설정 파일을 소개한다. `demo.strategy` enum 값으로 구현을 선택하고, `schema`·`database` 프로파일은 해당 설정 파일을 불러온다. 선택한 전략의 설정만 요구하며, `marvel`·`dc`와 실제 스키마·DB 이름을 구분한다. 메타데이터용 `control` DB는 `DATABASE` 전략에서 사용한다.

## 4. 요청의 테넌트를 세션에 전달

**역할:** 공통 서비스가 어느 테넌트의 데이터를 다룰지 정하는 과정을 연결한다.

- EntityManager와 Hibernate Session의 관계, 세션의 테넌트가 유지된다는 성질을 설명한다. 예제에서 새 세션을 여는 조건은 OSIV 비활성화와 외부 트랜잭션 없는 서비스 호출이다.
- 요청 헤더 → 실행 범위 바인딩 → 서비스 트랜잭션·세션 → 커넥션의 저장 위치 선택 순서로 설명한다.
- 하위 호출에서 테넌트 ID를 읽는 목적에 맞춰 `ScopedValue`를 선택한다. `TenantContext.call()`·`callChecked()`·`required()`와 필터 호출부를 보여 주고, 두 실행 메서드의 공통 동작과 필터의 예외 전달을 구분한다. ThreadLocal 비교와 영상 강좌는 보충 설명으로 두고, Java 17/21의 대안은 각주에서 짧게 안내한다.
- `TenantResolver`는 바인딩된 ID를 읽고 등록 여부를 확인해 세션에 전달한다. `HibernatePropertiesCustomizer` 등록은 `TenantConfiguration` 선언과 함께 보여 준다.
- 세션의 테넌트 ID와, 커넥션을 얻을 때 선택하는 스키마·DataSource를 구분해 다음 두 구현으로 이어 간다.

**시각 자료:** `../assets/multitenancy-tenant-flow.svg`. 예제 코드와 프레임워크의 역할, 전략별 대안과 선택되지 않은 DC 저장 위치를 구분한다.

## 5. 스키마 분리: 같은 DB에서 스키마 선택

**역할:** 공유 DB의 커넥션에서 테넌트별 스키마를 선택하는 원리를 확인한다.

- DataSource 하나로 `shared` DB에 연결하고, `marvel`·`dc`를 `marvel_schema`·`dc_schema`로 매핑한다.
- 같은 `TenantConfiguration` 안에서 `demo.strategy=SCHEMA` 조건으로 등록하는 `Schema` 설정과 `TenantSchemaMapper` 빈, 등록 속성을 발췌한다. 세션의 ID를 받은 매퍼가 스키마 이름을 반환하고 Hibernate가 `Connection.setSchema()`를 호출하는 순서를 설명한다.
- Hibernate 7.1 도입은 본문에서 알리고, API 상태·등록 계약의 근거와 이전 버전의 대안은 각주에 둔다. 스키마 복원은 검증 절의 결과로 회수한다.

## 6. DB 분리: 테넌트별 DataSource 선택

**역할:** 스키마 전환과 달리 테넌트 DB에 연결하는 DataSource를 고른다는 차이를 보여 준다.

- `demo.database.datasources`의 접속 정보로 시작 시 테넌트별 HikariCP 풀을 만든다. 업무·컨텍스트 코드는 공통으로 유지한다.
- `MultiTenantConnectionProvider` 구현과 등록 속성을 발췌한다. `selectDataSource()`는 세션이 전달한 ID로 DataSource를 고르고, `selectAnyDataSource()`는 테넌트 ID 없는 메타데이터 조회에 사용할 DataSource를 반환한다.
- `control` DB와 예제 보조 객체의 역할을 필요한 만큼 밝힌다. 풀 생성·자동 설정의 상세 구현은 본문으로 확장하지 않는다.

## 7. 테스트 코드로 조회·수정 확인

**역할:** 공통 서비스가 테넌트별 데이터를 조회하고 수정 영향을 분리하는지 확인한다.

- curl 요청·응답 하나 다음에 공통 테스트 두 개를 보여 준다. 테스트에서는 `TenantContext.call()`로 바인딩하고 외부 트랜잭션 없이 서비스를 호출한다.
- 같은 배우의 서로 다른 배역, Marvel 수정 후 DC의 값 유지, 두 프로파일에서 같은 테스트가 통과한 결과를 연결한다.
- 커넥션 재사용 시 스키마 선택·반납 후 복원은 결과만 짧게 남긴다. 풀 크기·PID·SQL 통계 같은 실험 설정과 계측은 예제의 검증 코드에 둔다.

## 8. 테넌트 전환과 트랜잭션 경계

**역할:** 컨텍스트를 바꾸는 것과 새 테넌트의 세션을 여는 것이 다르다는 제약을 보여 준다.

- 운영자 화면에서 세계관별 배역을 함께 보여 주는 목적 → 조회들을 하나의 트랜잭션으로 묶었을 때 `REQUIRED` 참여 → 컨텍스트만 DC로 바꿔도 Deadpool을 읽는 실험 순서로 이어 간다.
- 실제 실험은 한 트랜잭션 메서드 안에서 컨텍스트만 바꾸고 조회한 경로다. 변경 뒤에도 실제 DB 조회가 실행됐다는 근거만 문장으로 남기고, 계측 코드를 싣거나 운영자 사례의 안쪽 서비스 호출까지 직접 시험한 것처럼 범위를 넓히지 않는다.
- OSIV를 끈 예제에서 외부 트랜잭션 없이 테넌트별로 바인딩·서비스 호출 후 결과를 합치는 방법으로 연결한다. 정상 호출 코드는 앞의 테스트를 가리킨다.
- OSIV를 켜도 한 요청에서 한 테넌트의 조회·수정은 동작하며, 요청 안의 테넌트 전환에서는 기존 세션을 유지한다는 차이를 보충한다. 일반적인 멀티테넌시의 필수 설정으로 OSIV 해제를 단정하지 않는다.

## 9. 운영에 적용하기 전에 확인할 것

**역할:** 예제에서 확인한 동작과 운영에서 별도로 설계할 내용을 구분한다.

- 사용자 접근 권한과 DB 계정 권한은 테넌트 식별·저장 위치 선택과 구분한다. 접근 권한을 사용자 소속 여부만으로 설명하지 않는다.
- 테넌트 추가·풀 수명, 전체 커넥션 수, 공유 자원의 부하, 테이블 구조 변경, 백업·복구, 공용 데이터 조회를 짧은 항목으로 남긴다.
- 예제의 계정·풀 구성을 모든 분리 방식의 필수 구조로 일반화하지 않고, 운영 절차·수치 기준·추가 구현을 늘리지 않는다.

## 10. 마치며

**역할:** 도입의 테넌트 조건 반복을 회수하고, 업무 코드를 유지하며 데이터를 분리하는 효용으로 닫는다.

- 두 방식에서 엔티티·Repository·서비스를 공통으로 사용한 결과와 스키마·DataSource 선택의 차이를 정리한다.
- 테넌트 전달과 연결 선택을 공통으로 처리해, 조회·수정 코드에 테넌트 조건을 반복하거나 데이터 분리 방식에 따라 업무 코드를 바꾸는 부담을 줄이는 의미를 남긴다. 세션 생성 전 바인딩과 전환 제약의 설명은 8절에서 마친다.
