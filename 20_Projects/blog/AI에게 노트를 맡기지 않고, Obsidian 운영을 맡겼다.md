# AI에게 노트를 맡기지 않고, Obsidian 운영을 맡겼다

> [!abstract] 한 줄 논지
> Obsidian을 여러 번 포기한 이유는 생각이 부족해서가 아니라 폴더·태그·링크를 계속 관리해야 했기 때문입니다. AI에게는 이 반복 비용을 맡기되, 원문에 반응하고 무엇을 내 지식으로 남길지 결정하는 일은 남겼습니다.

## 검색은 성공했는데 원문은 최신이 아니었다

QMD MCP로 의미 검색을 테스트했을 때 원하는 노트가 93% 점수로 1위에 올랐습니다.

```text
1위  0.93  포착과 영구 노트 승격은 분리해야 한다
```

검색 결과만 보면 성공이었습니다. 하지만 MCP의 `get`으로 원문을 가져오자 방금 수정한 링크가 보이지 않았습니다. 책 참고노트 전체를 가리키던 링크를 특정 문단의 블록 링크로 바꿨는데, QMD가 돌려준 원문에는 이전 링크가 남아 있었습니다.

현재 Markdown 파일과 QMD 색인이 어긋난 상태였습니다. `qmd update`로 파일 변화를 반영하고 `qmd embed`를 실행한 뒤 다시 조회하자 최신 블록 링크가 나타났습니다.

```text
Indexed: 6 new, 13 updated, 255 unchanged, 1 removed
Embedded: 65 chunks from 19 documents
Status: 274 documents, needsEmbedding 0
```

이 장면이 제가 만들려던 시스템을 가장 잘 보여줍니다. AI가 관련 노트를 찾는 것만으로는 부족했습니다. 어느 검색 경로를 사용할지, 현재 파일과 색인이 같은 상태인지, 검색 결과를 어디까지 믿을지까지 운영 절차에 들어가야 했습니다.

## 알고 있던 제텔카스텐을 실행 절차로 바꾸다

저는 2025년에 《세컨드 브레인은 옵시디언》을 읽고 제텔카스텐의 기본 원리를 이미 정리해뒀습니다. 작은 생각에서 출발하는 상향식 글쓰기, 플리팅 노트와 영구 노트의 차이, 노트 사이의 연결도 알고 있었습니다.

문제는 지식이 아니었습니다. 생각을 가볍게 적은 뒤 다시 검토하고, 기존 노트를 찾아보고, 연결 이유를 적는 일은 매번 제가 기억해서 해야 했습니다. 폴더와 태그를 관리하는 데 지쳐 정작 기록을 미루는 날이 늘었습니다.

Claude Code 연동 내용이 추가된 개정판 《세컨드 브레인은 옵시디언 with 클로드 코드》에서 새롭게 본 것은 QMD였습니다. p.222~230의 제텔카스텐 설명은 익숙했지만, 이번에는 다른 질문을 던졌습니다.

> 이미 알고 있는 원칙을 AI가 반복해서 실행할 수 있는 스킬로 만들 수 없을까?

책의 내용을 한 번 더 요약하는 대신 세 가지를 실행 규칙으로 바꿨습니다.

1. 생각은 먼저 Inbox에 가볍게 포착한다.
2. 영구 노트 승격은 검색과 의미 판단을 거치는 별도 단계로 둔다.
3. 템플릿의 질문은 생각을 확장할 때만 쓰고, AI가 빈칸을 채우는 체크리스트로 만들지 않는다.

## 편해진 시스템이 내 생각까지 대신할 수 있었다

이 선택에는 반대 방향의 걱정도 있었습니다. Obsidian을 자주 멈춘 이유가 관리 부담이었다면, 그 부담을 없애려다 제 반응 없이 AI가 자료에서 핵심과 관계를 정하고, 그럴듯한 초안을 제가 그대로 승인하는 상태가 될 수 있기 때문입니다.

그렇게 만들어진 vault는 잘 정리된 위키처럼 보일 수는 있습니다. 하지만 왜 이 대목을 남겼는지, 어떤 생각과 연결되는지, 무엇을 제 판단으로 채택했는지를 제가 설명할 수 없다면 세컨드 브레인은 제 것이 아닙니다. 시안은 LLM Wiki에서 이런 사용 패턴을 [바이브 노팅](https://thinkingsian.com/vibe-noting/)이라고 부릅니다.

그래서 질문을 바꿨습니다. “AI에게 어떻게 더 많이 정리하게 할까?”가 아니라, “AI가 덜어도 되는 관리 부담과 내가 끝까지 해야 하는 사고는 무엇인가?”였습니다. 검색·중복 확인·형식 검사·후보 정리와 초안 구조화는 맡기되, 원문에 반응하고 초안이 내 생각을 충실히 반영하는지 다듬고 연결·승격을 결정하는 일은 남겨야 했습니다.

## 먼저 vault의 흐름부터 고정했다

AI에게 정리를 맡기기 전에 노트가 이동할 수 있는 경로를 제한했습니다.

```text
개인 생각
  ↓ capture-fleeting-note
00_Inbox ───────────────────┐
                              ↓ 주간 검토 / 사용자 승인
URL만 받은 외부 자료          ↓
  ↓ capture-reference-card
Clippings ── 읽고 반응 ──→ literature-note
                              ↓
삭제 / Resources 유지 / Project 흡수 / Slipbox 승격 후보
                              ↓ 사용자 승인
permanent-note
  ↓
출처 연결 → vault-lint → 필요한 경우 QMD 재색인 → 검색 검증
```

폴더는 PARA와 Slipbox를 섞어 다음처럼 사용합니다.

| 위치 | 역할 | 판단 질문 |
| --- | --- | --- |
| `00_Inbox` | 아직 분류하지 않은 생각 | 나중에 다시 검토할 가치가 있는가 |
| `01_Slipbox` | 여러 글과 판단에서 재사용할 자기 주장 | 원자료 없이 이 노트만 읽어도 이해되는가 |
| `20_Projects` | 끝내거나 전달해야 할 결과물 | 현재 완료 조건이 있는가 |
| `30_Resources` | 책·아티클·외부 자료 | 출처와 자료 맥락이 중심인가 |
| `40_Archive` | 완료·반복·비활성 자료 | 색인에는 남기되, 현재 연결·승격 후보에서는 제외할 수 있는가 |

책 저자의 [공개 예제 볼트의 Slip-box](https://github.com/Sianmin/obsidian-goldenrabbit/tree/main/0.%20Slip-box)에는 별도 Inbox가 없습니다. 이 폴더 안에 링크만 있는 [`Capture.md`](https://github.com/Sianmin/obsidian-goldenrabbit/blob/main/0.%20Slip-box/Capture.md), 목록형 노트, 여러 문단으로 발전한 노트가 함께 있습니다. 공개된 구조만 보면 포착부터 발전까지 한 공간에서 점진적으로 키우는 방식으로 읽힙니다.

제 vault에서는 이 단계를 분리했습니다. 사람이 직접 운영할 때는 같은 폴더 안에서도 노트의 상태를 감각적으로 구분할 수 있지만, AI가 파일을 만들고 옮기기 시작하면 포착과 승격의 경계를 명시하는 편이 안전했습니다. Inbox는 원형을 보존하는 곳이고, Slipbox는 검색과 검토를 거쳐 재사용할 주장으로 정제된 곳입니다. 이 구분은 제텔카스텐의 필수 구조가 아니라 AI에게 작업 권한을 나누기 위해 제가 선택한 운영 방식입니다.

여기서 중요한 것은 자동 분류가 아닙니다. AI가 선택할 수 있는 경로와 승인 없이 바꾸면 안 되는 상태를 먼저 정한 것입니다. Archive는 예전 자료를 다시 찾기 위해 색인에는 남기되, 현재 생각을 연결하거나 승격할 후보에서는 제외합니다.

## QMD를 Codex의 의미 검색 계층으로 연결했다

[QMD](https://github.com/tobi/qmd)는 로컬 Markdown을 색인해 BM25 전문 검색, 벡터 의미 검색, LLM rerank를 제공하는 온디바이스 검색 도구입니다. Obsidian 전용 플러그인은 아니지만, vault가 Markdown 파일로 구성돼 있어 잘 맞았습니다.

기본 구성은 다음과 같습니다.

```bash
npm install -g @tobilu/qmd
qmd collection add /path/to/obsidian-vault --name PKM
qmd context add qmd://PKM/01_Slipbox "재사용 가능한 자기 주장을 담은 영구 노트"
qmd context add qmd://PKM/30_Resources "책·아티클·개발 기록을 보관한 참고 자료"
qmd update
qmd embed
```

공식 문서는 collection의 경로별 `context`를 QMD의 핵심 기능으로 소개합니다. 이 설명은 검색 결과와 함께 반환돼 에이전트가 문서의 성격을 판단하는 데 쓰입니다. 매번 `intent`에 “Slipbox는 영구 노트이고 Resources는 참고 자료”라고 반복하는 대신, 변하지 않는 폴더의 역할은 context로 한 번 등록했습니다. 반면 이번 검색에서 무엇을 찾는지는 질의마다 `intent`에 적습니다.

Codex에서는 QMD MCP를 등록했습니다. `command`에는 `which qmd`로 확인한 실행 파일의 절대 경로를 넣습니다.

```toml
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
writable_roots = ["/Users/<user>/.cache/qmd"]

[mcp_servers.qmd]
command = "/absolute/path/to/qmd"
args = ["mcp"]
startup_timeout_sec = 20
tool_timeout_sec = 60
```

`writable_roots`는 QMD의 SQLite 인덱스를 읽고 쓰기 위한 설정입니다. 뒤에서 다룰 Metal GPU 실행 권한과는 별개입니다.

## 정확 검색과 의미 검색을 분리했다

QMD를 연결했다고 모든 검색을 QMD에 맡기지는 않았습니다. 제목과 문자열을 알고 있다면 현재 파일을 직접 읽는 `rg`가 더 빠르고 예측 가능합니다.

```bash
# 제목·파일명
rg --files | rg "포착과 영구 노트"

# 본문의 정확한 부분 문자열
rg -n -F "승격은 분리해야 한다" 01_Slipbox
```

표현이 달라질 수 있는 개념 검색은 QMD MCP의 structured query를 사용합니다. 실제로 `포착과 승격의 분리` 노트를 찾을 때 사용한 형태를 줄이면 다음과 같습니다.

```json
{
  "intent": "포착과 영구 노트 승격을 분리해야 한다는 현재 Slipbox 주장을 찾는다.",
  "searches": [
    {
      "type": "lex",
      "query": "\"포착과 영구 노트 승격\" 분리 Inbox"
    },
    {
      "type": "vec",
      "query": "생각은 빠르게 기록하고 나중에 검토해 영구 지식으로 승격한다"
    },
    {
      "type": "hyde",
      "query": "포착은 속도와 원형 보존이 중요하고 승격은 재사용 가능성과 연결을 판단해야 한다."
    }
  ],
  "limit": 15,
  "rerank": true
}
```

각 항목의 역할은 다릅니다.

| 항목       | 역할                                          |
| -------- | ------------------------------------------- |
| `intent` | 이번 검색의 목적과 피할 개념적 오탐을 설명하는 보조 문맥              |
| `lex`    | 제목·고유명사·정확한 표현을 앵커로 사용                      |
| `vec`    | 같은 의미를 다른 표현으로 쓴 문서를 탐색                     |
| `hyde`   | 원하는 문서가 담고 있을 법한 문단으로 의미 탐색을 보강             |

공식 MCP 스키마는 `intent`를 “질의를 명확히 하는 배경 문맥”이라고 설명하면서, 이것만으로 검색하지는 않는다고 명시합니다. 소스를 더 확인해보면 intent는 reranker 입력 앞에 붙고, 검색에 사용할 청크와 snippet을 고르는 데에도 반영됩니다. 즉 무의미한 필드는 아니지만 hard filter도 아닙니다.

따라서 `intent`에는 “책 요약이 아니라 내가 채택한 운영 원칙”처럼 **의미상 가까우나 틀린 결과**를 피하는 조건을 적습니다. `_workspace와 40_Archive는 제외` 같은 경로 규칙을 넣으면 파일을 제거하지 못하면서 순위 판단에 불필요한 단어만 보탤 수 있어 뺐습니다. collection이 분리돼 있다면 `collections`로 범위를 제한하고, 지금처럼 vault 전체가 하나의 `PKM` collection이면 에이전트가 반환된 `file` 경로를 직접 검사합니다.

```javascript
const slipbox = results.filter(
  result => result.file.startsWith("PKM/01-Slipbox/")
);
```

structured query에서는 첫 번째 `searches` 항목이 2배 가중치를 받습니다. 그래서 위 예시는 가장 확실한 제목·표현을 담은 `lex`를 먼저 두었습니다. 제목을 모르는 개념 탐색이라면 가장 믿을 만한 `vec` 문장을 첫 번째에 두는 편이 낫습니다. 후보를 좁힌 뒤에도 결과 snippet만 믿지 않고 `get`으로 원문을 읽는 것이 공식 권장 흐름입니다.

마지막 판단은 snippet이 아니라 원문을 읽고 내립니다. 중요한 승격과 연결에서는 `rg`의 정확 후보와 QMD의 의미 후보를 합친 뒤 원문을 비교합니다.

## `ignore`는 SDK에만 있고 CLI엔 없었다

검색 결과에 `99_Templates`와 `_workspace`가 계속 섞여 나왔습니다. 새 영구 노트 템플릿이나 임시 산출물 폴더가 "노트"라는 검색어에 걸려 나오는 건 당연했지만, 매번 결과에서 걸러내는 게 거슬렸습니다.

먼저 `context`부터 다시 봤습니다. 앞서 등록한 폴더별 설명(`qmd context add`)은 검색 결과마다 자동으로 따라붙어 문서 성격을 알려주는 배경 정보일 뿐, 결과를 걸러내는 필터가 아니었습니다. 검색 결과 각 줄에 붙는 `Context: ...` 문구가 바로 이 값입니다.

원하는 건 필터였습니다. `qmd collection add --help`를 확인했지만 `--ignore`나 `--exclude` 플래그는 없었습니다. 대신 공식 README의 SDK 섹션에는 이런 예시가 있었습니다.

```typescript
await store.addCollection("myapp", {
  path: "/src/myapp",
  pattern: "**/*.ts",
  ignore: ["node_modules/**", "*.test.ts"],
})
```

CLI에 없는 옵션이 SDK에는 있었습니다. 짧은 스크립트로 기존 `PKM` 컬렉션에 `ignore: ["99_Templates/**", "_workspace/**"]`를 추가하고 `qmd update`를 실행했습니다.

```text
Indexed: 0 new, 2 updated, 272 unchanged, 0 removed
```

0 removed. 반영되지 않았습니다.

소스를 확인하니 원인이 나왔습니다. CLI의 `update` 명령은 SDK가 쓴 SQLite 값이 아니라 YAML 설정 파일(`~/.config/qmd/index.yml`)의 `ignore` 필드를 읽습니다.

```javascript
const result = await reindexCollection(storeInstance, col.pwd, col.glob_pattern, col.name, {
  ignorePatterns: yamlCol?.ignore,
})
```

`store.addCollection()`은 DB에는 값을 썼지만 YAML은 건드리지 않았습니다. CLI가 실제로 참조하는 소스와 SDK가 값을 쓰는 소스가 서로 달랐던 겁니다. YAML에 같은 값을 직접 추가하자 그제서야 반영됐습니다.

```yaml
collections:
  PKM:
    path: /Users/taez/Projects/obsidian
    pattern: "**/*.md"
    ignore:
      - "99_Templates/**"
      - "_workspace/**"
      - "30_Resources/References/Clippings/_local-snapshots/**"
```

```text
Indexed: 0 new, 0 updated, 259 unchanged, 15 removed
```

15개가 빠졌고, 이후 검색에서 템플릿과 워크스페이스 파일은 더 이상 나오지 않았습니다. 뒤에는 저작권상 Git에 올리지 않는 원문 전문 보관소인 `Clippings/_local-snapshots`도 같은 목록에 넣었습니다. 자료카드는 검색할 수 있어야 하지만, 원문 전문은 현재 지식을 연결하거나 승격할 근거가 아니기 때문입니다. CLI, MCP, SDK가 같은 SQLite 인덱스를 공유하므로 이 설정은 Codex의 QMD MCP 검색에도 동일하게 적용됩니다.

## 한국어 검색은 모델 하나로 해결되지 않았다

처음에는 임베딩 모델을 바꾸면 한국어 검색 품질이 전반적으로 좋아질 거라고 기대했습니다. QMD 기본 모델 대신 `Qwen3-Embedding-0.6B`를 지정하고 vault를 다시 임베딩했습니다.

결과는 단순하지 않았습니다. 어떤 검색에서는 제 업무 경험이 담긴 노트를 더 잘 찾았지만, 다른 검색에서는 제목만 비슷한 빈 독서 노트가 상위에 올라왔습니다. 모델 변경 전후 top 15의 원문을 직접 읽어보니 오탐의 종류만 달라진 경우도 있었습니다.

여기서 검색 정책을 바꿨습니다.

| 검색 목적 | 사용 방식 |
| --- | --- |
| 한글 제목·파일명·부분 문자열 | `rg` |
| 빠른 lexical 검색 | CLI `qmd search` |
| 표현이 다른 개념·주장 | QMD MCP `query` |
| 검색 결과의 실제 판단 | 상위 후보 원문 조회 |

한국어는 단어가 조사나 다른 단어와 붙어 쓰입니다. BM25 토큰화가 부분 문자열을 놓칠 수 있으므로 정확 검색은 `rg`에 맡겼습니다. 임베딩 모델도 한 번의 인상으로 결정하지 않고, 실제 vault에서 자주 찾는 연결·승격·글쓰기 질문으로 확인해야 했습니다.

당시 QMD 2.5.3의 `bench`에는 벡터 단독 컬럼이 고정된 임베딩 모델을 쓰지 않는 알려진 문제가 있었습니다([GitHub #690](https://github.com/tobi/qmd/issues/690)). 그래서 이 글에서는 모델의 우열을 말하지 않겠습니다. 남길 결론은 하나입니다. 검색 품질도 그럴듯한 한 문장이 아니라, 내가 실제로 다시 찾을 질문과 상위 후보 원문으로 검증해야 합니다.

## 같은 QMD도 실행 경로에 따라 달랐다

Codex의 기본 셸에서 CLI `qmd query`를 실행했을 때 다음 계열의 오류가 발생했습니다.

```text
failed to create command queue
failed to allocate context
failed to initialize backend
```

처음에는 QMD 캐시 쓰기 권한 문제라고 생각했습니다. 그러나 `writable_roots`를 추가해 SQLite 접근을 해결한 뒤에도 Metal 오류는 남았습니다.

비교 결과는 명확했습니다.

| 실행 방식 | 결과 |
| --- | --- |
| Codex 셸의 `rg` | 정상 |
| Codex 셸의 CLI `qmd search` | 정상 |
| Codex 셸의 CLI `qmd query` | Metal 컨텍스트 오류 |
| 같은 세션의 QMD MCP `query` | 의미 검색과 rerank 정상 |
| 샌드박스 밖 `qmd update`, `qmd embed` | 정상 |

그래서 Codex용 검색 규칙을 `AGENTS.md`에 남겼습니다.

```text
정확 검색       → rg
lexical 검색    → CLI qmd search
의미 검색       → QMD MCP query
원문 조회       → QMD MCP get
대량 변경 후 색인 → 샌드박스 밖 qmd update && qmd embed
```

도구가 실패했을 때 같은 명령을 반복하지 않고, 어느 실행 경로로 전환할지까지 에이전트 규칙에 포함했습니다. 다음 세션의 AI가 같은 진단을 처음부터 반복하지 않게 하기 위해서입니다.

이 규칙도 그대로 머물지 않았습니다. 이후 실행 상세는 검색할 때만 로드되는 `qmd` 스킬로 옮기고, 매 세션 로드되는 `AGENTS.md`에는 위와 같은 라우팅 경계만 남겼습니다. 운영 규칙 자체도 어디에 두는 것이 맞는지 다시 검토하는 대상입니다.

## 하나의 거대 스킬 대신 책임을 나눴다

처음에는 “옵시디언 정리”라는 하나의 거대 스킬로 만들 수도 있었습니다. 하지만 포착·검토·승격·검사는 입력과 실패 비용이 다릅니다.

| 스킬·도구 | 맡긴 일 | 금지한 일 |
| --- | --- | --- |
| `capture-fleeting-note` | 개인 생각 원문을 Inbox에 빠르게 포착하고, 필요할 때만 AI 초기 해석을 접어 분리 | 검색·분류·자동 승격, AI 보충을 사용자 주장으로 취급 |
| `capture-reference-card` | 아직 읽지 않은 URL을 Git-safe 자료카드로 Clippings에 보관 | 원문 전문·장문 번역·자동 링크·태그 부여 |
| `literature-note` | 읽고 반응한 대목의 인용과 내 생각을 Articles에 기록 | 반응 없는 자료의 전체 요약·번역, 자동 승격 |
| `review-zettelkasten` | 중복·연결을 조사하고 삭제·보관·보강·승격 후보 제안 | 승인 전 파일 변경 |
| `permanent-note` | 승인된 생각을 독립적인 영구 노트로 정제 | AI 제안을 사용자 주장으로 간주 |
| `vault-lint` | frontmatter·죽은 링크·고립 노트·Base 검사 | 의미상 연결을 자동 결정 |
| `rg` | 정확한 제목·파일명·부분 문자열 검색 | 의미가 비슷한 생각 추론 |
| QMD MCP | 표현이 다른 생각을 의미 검색하고 후보 순위 제시 | 검색 결과만으로 연결 확정 |

공통 규칙은 `AGENTS.md`에 두고, 각 `SKILL.md`에는 해당 작업의 실행 절차만 남겼습니다. Claude Code와 Codex는 `.agents/skills`의 같은 정본을 심볼릭 링크로 참조합니다.

Quick Capture의 `AI 생성`도 별도 경계를 뒀습니다.

```markdown
## 원문

사용자가 남긴 생각

## AI 생성

1. 생각을 이어갈 관찰
2. 다음 검토에서 확인할 질문
```

AI 보충은 필요할 때만 원문과 분리해 접어 둡니다. 사용자가 원문만 요청하면 만들지 않습니다. 이후 영구 노트로 승격할 때도 사용자가 명시적으로 채택하지 않은 `AI 생성` 내용은 본문 후보가 되지 않습니다.

## URL을 보관하는 일과 읽은 자료에 반응하는 일을 분리했다

이 경계는 외부 자료에서 가장 크게 드러났습니다. 처음에는 HBR URL을 받으면 Articles에 전문 번역형 노트를 만들었습니다. 원문은 남았지만, 제가 어떤 대목을 읽었고 왜 중요하다고 봤는지는 거의 남지 않았습니다. 자료를 읽은 흔적이라기보다 AI가 대신 정리한 번역본에 가까웠습니다.

그래서 외부 자료도 상태를 나눴습니다. URL만 받은 자료는 제목·출처·짧은 식별 문장만 담은 Clipping 카드로 남깁니다. 실제로 읽고 인용하거나 동의·의심한 지점이 생겼을 때만 별도 literature note를 씁니다. 원문 전문이 필요하면 Git에서 제외한 local snapshot에 두고, 검색과 승격의 근거에서는 제외합니다.

이 변화는 노트를 덜 만들기 위한 규칙이 아닙니다. 제가 아직 읽지 않은 자료, 제가 반응한 자료, 제가 채택한 주장을 같은 종류의 노트로 취급하지 않기 위한 규칙입니다.

## Inbox를 분리하니 영구 노트의 허들도 달라졌다

처음에는 예제 볼트의 짧은 노트를 참고해 `seedling은 핵심 주장 1~2문단이면 충분하다`는 규칙을 만들었습니다. 문장 자체는 틀리지 않았지만, AI는 이 숫자를 허용 가능한 최소 형태가 아니라 목표 분량처럼 받아들일 수 있었습니다.

제 구조에서는 이미 Inbox가 빠른 포착을 맡습니다. `permanent-note`까지 Inbox 메모를 한두 문단으로 줄여 옮기기만 한다면 승격 단계를 따로 둔 의미가 약해집니다. 승격할 때는 원본을 다시 열지 않아도 주장을 이해하고 재사용할 수 있도록 필요한 배경·논리·적용 경계를 정리해야 합니다.

그래서 분량 제한을 없앴습니다. 중심 주장만으로 명료하면 1~2문단에서 끝내고, 실제 경험이나 참고자료의 맥락이 필요하면 더 길게 씁니다. AI도 모든 섹션을 채우지는 않지만, 원본에 있는 설명·예시·반례가 이해에 도움이 되면 함께 정리합니다. 제한한 것은 길이가 아니라 근거 없이 내용을 발명하는 행동입니다.

이 조정 이후 `seedling`도 짧은 노트라는 뜻으로 쓰지 않습니다. 중심 주장은 명료하지만 아직 충분히 검토하거나 적용하지 않은 상태입니다. `growing`은 글자 수나 링크 수가 늘었을 때가 아니라 근거·반례·적용이 붙거나 실제 글과 판단에서 재사용되기 시작했을 때 검토합니다.

## Inbox 노트 하나를 끝까지 처리했다

워크플로를 만든 뒤 `제텔카스텐이란?`이라는 Inbox 노트로 전체 파이프라인을 돌렸습니다. 책의 p.222~230 내용과 제 생각이 한 파일에 섞여 있던 메모였습니다.

`review-zettelkasten`은 바로 파일을 만들지 않고 다음 안을 먼저 제시했습니다.

1. 책의 내용과 출처 맥락은 참고노트에 흡수한다.
2. 재사용할 수 있는 사용자 주장 세 개를 영구 노트로 분리한다.
3. 반복 탐색 수요가 확인되지 않았으므로 MOC는 만들지 않는다.
4. 흡수가 끝난 Inbox 원본은 승인 후 처리한다.

승인 뒤 다음 노트가 만들어졌습니다.

- [[제텔카스텐은 상향식으로 글감을 성장시키는 시스템이다]]
- [[포착과 영구 노트 승격은 분리해야 한다]]
- [[템플릿은 내용을 채우는 틀이 아니라 생각을 확장하는 질문이어야 한다]]

여기서 출처 링크도 다시 다듬었습니다. 영구 노트가 책 전체에서 나온 것처럼 연결하지 않고, 실제 근거가 있는 블록으로 좁혔습니다.

참고노트의 원문에는 안정적인 block ID를 붙입니다.

```markdown
1. 떠오른 생각을 가볍게 포착한다.
2. 책이나 아티클을 읽으며 선택적으로 참고 노트를 남긴다.
3. 나중에 다시 검토해 새 영구 노트로 승격하거나 기존 노트를 보강한다.

^capture-review-promote
```

영구 노트에서는 해당 블록을 직접 가리킵니다.

```markdown
[[세컨드 브레인은 옵시디언 with 클로드 코드#^capture-review-promote|세컨드 브레인은 옵시디언 with 클로드 코드]]
```

특정 주장·인용은 블록 링크, 절 전체가 맥락이면 헤딩 링크, 문서 전체가 관련될 때만 문서 링크를 사용합니다. 이번 전수 점검에서는 Resources를 가리키는 기존 링크 11개를 블록 링크 8개와 헤딩 링크 3개로 정밀화했습니다.

## 대화 속 주장 하나를 영구 노트로 정제했다

`review-zettelkasten`이 Inbox 전체를 검토하는 스킬이라면, `permanent-note`는 대화 중 나온 생각 하나를 재사용할 주장으로 정제합니다. 최근 저는 경영학의 흡수 역량이 AI 시대에는 조직뿐 아니라 개인에게도 중요해졌다는 생각을 말로 풀어냈습니다.

> AI가 외부 지식이라면, 무엇이 나에게 유효한지 판단하고 내 상황에 맞게 변형해 실제 이익으로 연결하는 능력이 중요해진다.

스킬은 이 문장을 곧바로 새 파일로 만들지 않았습니다. `rg`로 ‘흡수 역량’이라는 정확한 표현을 찾고, QMD MCP의 structured query로 같은 결론과 이어지는 주장을 검색했습니다. 기존 블로그 두 편에는 조직 단위의 흡수 역량이 있었고, Slipbox에는 흡수 조건·회수율·이해 부채가 나뉘어 있었습니다. 하지만 조직 개념이 개인 역량으로 이동했다는 주장은 없었습니다.

```text
사용자 주장
  ↓ rg 정확 검색 + QMD 의미 검색
같은 주장 없음 / 이어지는 노트 있음
  ↓ 상위 후보 원문 확인
새 영구 노트 생성
  ↓
출처 block link + 관계 설명 + MOC 탐색 경로
```

그래서 [[AI 시대에는 개인에게도 흡수 역량이 중요하다]]를 만들고, 개인의 흡수 과정을 `유효성 판단 → 맥락화와 변형 → 활용`으로 정리했습니다. 조직 수준의 정의가 있던 발행 글에는 block ID를 붙여 출처를 정확히 가리켰고, [[AI 활용과 팀 역량]] MOC의 ‘개인의 사고와 생성’ 갈래에도 탐색 경로를 추가했습니다.

이 노트는 여러 문단과 연결 다섯 개를 갖고 있지만 `seedling`입니다. 길이나 링크 수가 아니라 아직 충분히 검토·적용됐는지로 성숙도를 판단하기 때문입니다. 반대로 한두 문단이어도 다시 이해하고 활용할 수 있을 만큼 명료하다면 영구 노트가 될 수 있습니다. `permanent-note`가 맞추는 것은 분량이 아니라 재사용 가능한 주장의 경계입니다.

이번에는 노트 하나만 추가했기 때문에 QMD를 수동으로 재임베딩하지 않고 다음 세션 시작의 자동 갱신에 맡겼습니다. 아래의 전체 검증 절차는 여러 파일을 승격·이동하거나 같은 세션에서 바로 의미 검색을 검증할 때 사용합니다.

## 이번에는 내가 노트를 쓰고 AI가 원문과 대조했다

앞의 두 사례는 AI가 후보를 만들고 제가 승인하는 방향이었습니다. 반대 방향도 시험했습니다. Anthropic 엔지니어의 발표 영상을 보고 [[Field Guide to Fable - Thariq Shihipar|literature note]]를 직접 쓴 뒤, 리뷰를 AI에게 맡겼습니다. AI는 요약본을 다시 읽는 대신 영상 자막 전문을 확보해 노트와 문장 단위로 대조했습니다.

세 가지가 나왔습니다. 발표 내용을 프롬프트 예시로 재구성한 문단이 실제 인용과 같은 blockquote 형식으로 있어, 몇 달 뒤 다시 읽으면 발표자가 한 말인지 제가 만든 예시인지 구분할 수 없었습니다. 요약 섹션에는 발표에 없는 제 종합이 발표자의 주장처럼 섞여 있었습니다. frontmatter에는 원본 공개일(`published`)이 빠져 있었습니다.

노트만 고치고 끝냈다면 이 발견은 대화 로그와 함께 사라졌을 겁니다. 그래서 같은 실수를 다음에 어디서 막을지 물었고, 문제의 성격에 따라 정착 위치가 갈렸습니다.

| 발견 | 성격 | 정착 위치 |
| --- | --- | --- |
| `published` 누락 | 기계 검사로 잡힘 | `vault-lint` 스캐너 규칙 + 회귀 테스트 |
| 인용과 재구성이 같은 형식 | 사람이 지켜야 할 저작 규율 | 새 `literature-note` 스킬의 원칙 |
| 요약에 해석이 섞임 | 사람이 지켜야 할 저작 규율 | 같은 스킬의 원칙 + 원문 대조 절차 |
| URL 보관 경로 없음 | 라우팅 공백 | `capture-reference-card` 신설 + `AGENTS.md` 라우팅 한 행 |

라우팅 공백은 점검 전까지 몰랐던 부분입니다. `capture-fleeting-note`는 외부 URL 정리를 범위 밖으로 선언해뒀지만, URL만 받은 자료를 보관할 목적지가 없었습니다. 경계만 있고 목적지가 없던 셈입니다.

정착의 효과는 바로 확인됐습니다. Articles 폴더에 필수 필드 규칙을 추가하고 스캐너를 돌리자 기존 노트 8건 중 7건에서 `status` 누락이 잡혔습니다. 실수 하나에서 나온 규칙이 과거에 쌓인 노트까지 소급해서 검사한 겁니다.

스킬 초안은 AI가 썼지만 그대로 두지 않았습니다. 제가 세 군데를 고쳤습니다. URL만으로는 literature note나 전문 번역을 만들지 않고 자료카드로 보관하게 했고, AI가 만든 해석은 제가 채택하기 전에는 노트에 기록하지 못하게 했고, 저장 전에 확보한 원문 전체와 다시 대조하는 절차를 넣었습니다. 고친 스킬은 다시 AI가 나머지 스킬들과 모순이 없는지 점검했습니다. 승인 경계가 한 방향이 아니라 양쪽으로 작동한 첫 사례였습니다.

## 검증도 파이프라인의 일부로 넣었다

여러 파일을 바꾼 작업에서는 파일을 만들었다고 끝내지 않았습니다. 의미 판단과 기계 검사를 분리해 검증했습니다.

```text
1. rg로 정확한 파일과 링크 확인
2. vault-lint로 frontmatter·죽은 링크·Base 검사
3. Obsidian metadata cache에서 block ID와 heading 인식 확인
4. qmd update로 변경 파일 재색인
5. qmd embed로 의미 검색 벡터 갱신
6. QMD MCP query로 검색 순위 확인
7. QMD MCP get으로 최신 원문 재확인
```

실제 결과는 다음과 같았습니다.

```text
frontmatter issues: 0
base issues: 0
새로 만든 dead link: 0
QMD documents: 274
needsEmbedding: 0
목표 영구 노트: 93%, 1위
```

이 과정에서 `intent`가 경로를 강제로 제외하지 않는 문제, reranker 점수가 높아도 초기 RRF 순위 때문에 최종 순위가 밀리는 문제, 현재 파일과 QMD 색인이 어긋나는 문제를 발견했습니다. 공식 문서의 `--explain`은 RRF와 rerank가 최종 점수에 어떻게 반영됐는지 보여줍니다. 검증 결과는 단순한 합격표가 아니라 다음 운영 규칙의 입력이 됐습니다.

## 일부러 자동화하지 않은 것

코드와 노트는 실패하는 방식이 다릅니다. AI가 쓴 틀린 코드는 언젠가 테스트가 깨지지만, AI가 쓴 그럴듯한 노트는 누가 어떤 근거로 채택했는지가 남지 않으면 아무 신호 없이 vault에 남습니다. 《세컨드 브레인은 옵시디언》의 저자 시안은 별다른 비판 없이 노트 작성을 AI에게 맡기는 것을 [바이브 노팅](https://thinkingsian.com/vibe-noting/)이라 부르는데, 제가 경계한 것이 바로 이 조용한 실패입니다. 노트에는 실행 시점의 검증이 없으니, 첫 경계는 노트가 만들어지는 시점에 두고 이후 재사용에서 다시 확인해야 했습니다. 그래서 자동화를 더 붙일 수 있었지만 다음 판단은 남겨뒀습니다.

- Inbox를 자동으로 permanent note로 만들지 않습니다.
- 읽지 않은 URL을 받았다고 literature note나 전문 번역을 만들지 않습니다.
- QMD 순위만 보고 노트를 연결하지 않습니다.
- 사용자 입력·원문 근거 없이 AI가 만든 보충을 사용자 주장으로 승격하지 않습니다.
- 영구 노트가 세 개 생겼다는 이유만으로 MOC를 만들지 않습니다.
- 모든 고립 노트를 오류로 취급하지 않습니다.
- `40_Archive`는 검색 인덱스에는 남기되, 현재 연결·승격 후보에서는 제외합니다. 템플릿과 달리 완료된 실제 콘텐츠라 예전 자료를 다시 찾아야 할 때가 있습니다.
- 삭제·병합·승격·MOC 생성은 후보 보고까지를 작업의 완료로 봅니다.

AI가 맡은 일은 후보를 찾고 반복 검사를 돌리는 것만은 아닙니다. 제 생각과 원문이 있을 때는 초안 구조화도 맡길 수 있습니다. 다만 그 초안이 무엇을 강조하고 어떤 관계를 만드는지는 제가 다듬어 채택합니다. 무엇을 내 생각으로 남길지, 검색 오류를 감수하고도 자동화할지는 여전히 제가 결정합니다. 특히 마지막 규칙은 완료 압박이 강한 에이전트 모드를 위한 것입니다. AI가 승인 대기를 미완성으로 오해하고 밀어붙이지 않도록, 멈출 지점을 완료의 정의 안에 넣었습니다.

## 직접 적용할 때의 최소 체크리스트

같은 구조를 만들려면 다음 순서로 시작할 수 있습니다.

- [ ] Inbox·Slipbox·Projects·Resources의 역할을 한 문장씩 정의한다.
- [ ] 개인 생각·읽지 않은 URL·읽고 반응한 자료·채택한 주장의 입력 경로를 나눈다.
- [ ] Inbox를 분리한다면 permanent note 승격에서 무엇을 더 정제할지 정한다.
- [ ] QMD 컬렉션을 만들고 현재 vault를 색인한다.
- [ ] 폴더별 역할처럼 변하지 않는 정보는 QMD context로 등록한다.
- [ ] 템플릿·워크스페이스·원문 전문 보관소 같은 검색 노이즈는 collection의 `ignore`(YAML)로 제거한다.
- [ ] 사용하는 에이전트에 QMD MCP를 등록한다.
- [ ] 정확 검색은 `rg`, 의미 검색은 QMD MCP로 나눈다.
- [ ] 포착·검토·승격·검사의 책임을 별도 스킬로 나눈다.
- [ ] 영구 노트의 고정 분량 대신 독립적으로 이해·재사용할 수 있는지를 기준으로 둔다.
- [ ] `AGENTS.md`에 승인 경계와 실패 시 전환 경로를 적는다.
- [ ] 참고노트의 특정 근거는 block link로 연결한다.
- [ ] 변경 후 lint·재색인·의미 검색·원문 조회를 함께 검증한다.
- [ ] 작성 실수가 나오면 성격에 따라 lint 규칙·스킬 원칙·라우팅 중 어디에 정착시킬지 정한다.

처음부터 모든 폴더와 태그를 정리할 필요는 없습니다. Inbox 하나와 영구 노트 하나로 파이프라인을 먼저 통과시켜보는 편이 낫습니다. 실제로 사용해본 뒤 반복되는 판단만 규칙과 스킬로 올리면 됩니다.

## 글도 파이프라인의 끝은 아니었다

글을 발행 가능한 상태로 다듬었다고 지식의 흐름이 끝나는 것은 아닙니다. 이제 블로그 작업을 마칠 때는 이 글에서 실제로 사용한 Slipbox 노트와, 쓰는 동안 생긴 영구 노트 후보를 짧게 확인합니다. 후보가 없다면 `환류 후보 없음`으로 끝냅니다.

링크 수를 점수로 삼지는 않습니다. 기존 생각을 실제로 사용했는지, 새 생각을 억지로 영구 노트로 만들지 않았는지만 봅니다. 글은 Slipbox의 증거를 받아 발전하고, 글을 쓰며 생긴 독립적인 주장은 다시 후보로 돌아갑니다. 이 짧은 확인이 입력만 정교하고 재사용은 기억에만 맡기는 구조를 막아줍니다. 앞에서 노트에는 실패 신호가 없다고 했는데, 실제 글에서 다시 쓰였는지는 그나마 남는 가장 정직한 작동 신호이기도 합니다.

## AI에게 맡긴 것은 지식이 아니라 운영 비용이었다

글의 시작에서 QMD는 원하는 노트를 정확히 찾았지만 이전 원문을 돌려줬습니다. 검색 점수만 봤다면 그 차이를 놓쳤을 겁니다. 파일·색인·검색·원문 확인을 하나의 파이프라인으로 묶었기 때문에 상태 불일치를 발견할 수 있었습니다.

예전에는 Obsidian을 잘 쓰려면 제가 폴더·태그·링크를 부지런히 관리해야 한다고 생각했습니다. 지금은 반복되는 검색과 검사를 AI에 맡기고, 제가 내려야 할 판단을 명시적으로 남깁니다.

제목에서 말한 “AI에게 노트를 맡기지 않는다”는 AI가 한 문장도 쓰지 않는다는 뜻이 아닙니다. AI가 노트를 초안으로 쓰는지 자체가 기준은 아닙니다. AI가 덜어준 것은 세컨드 브레인을 유지하기 위한 반복 비용이고, 저는 원문과 대화에서 나온 생각이 정말 제 주장인지, 기존 노트와 왜 연결되는지, 지금 채택할지를 확인합니다. 이 확인 없이 그럴듯한 결과를 승인만 하면 편해지기는 해도 제텔카스텐의 효과는 사라집니다.

이 경계가 실제로 지켜지는지는 앞으로의 사용으로만 확인할 수 있습니다. 몇 달 뒤에도 왜 이 노트를 남겼는지 설명할 수 있는지, 기존 노트에서 새 판단을 만들고 있는지, AI가 만든 초안을 실제 글과 판단에 다시 쓸 수 있는지 보겠습니다. 제가 다시 Obsidian을 쓰게 된 이유는 그 절차를 매번 혼자 기억하지 않아도 되기 때문입니다.
