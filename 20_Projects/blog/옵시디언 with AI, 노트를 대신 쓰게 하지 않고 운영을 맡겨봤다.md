# 옵시디언 with AI, 노트를 대신 쓰게 하지 않고 운영을 맡겨봤다

> [!abstract] 한 줄 논지
> 옵시디언에 AI를 붙이는 핵심은 노트를 대신 쓰게 하는 것이 아니라, 알고만 있던 지식관리 원칙을 검색·제안·승인·검증 가능한 실행 절차로 바꾸는 데 있었습니다.

## 옵시디언을 잘 관리하려다 쓰지 않게 됐다

옵시디언을 제대로 써보겠다고 마음먹을 때마다 폴더와 태그부터 고쳤습니다. Inbox, PARA, Zettelkasten, MOC까지 구조는 점점 그럴듯해졌지만 정작 저는 노트를 덜 쓰게 됐습니다. 생각 하나를 기록하려고 해도 어디에 넣을지, 어떤 태그를 붙일지, 무엇과 연결할지부터 고민해야 했기 때문입니다.

이번이 첫 시도도 아니었습니다. 2026년 1월에도 계층형 태그를 만들고, 모든 영구 노트에 최소 한 개 이상의 링크를 두는 규칙을 정했습니다. 규칙은 생겼지만, 노트가 쌓일수록 기존 내용을 다시 찾고 연결하는 일은 여전히 제 몫이었습니다. 시스템을 관리하는 일이 생각을 기록하는 일보다 무거워지면 오래가지 못했습니다.

제텔카스텐의 원리를 몰랐던 것도 아닙니다. 2025년에 《세컨드 브레인은 옵시디언》 초판을 읽으며, 현실의 지식 활동은 주제를 먼저 정하는 하향식 방식보다 메모에서 시작하는 상향식 방식에 가깝다는 대목을 이미 기록해뒀습니다. 플리팅 노트와 영구 노트, 연결을 통해 글감을 키운다는 설명도 알고 있었습니다.

하지만 아는 것만으로는 시스템이 굴러가지 않았습니다. 가볍게 포착한 뒤 다시 검토하고, 기존 노트를 검색하고, 의미 있는 연결을 만드는 일은 여전히 제가 매번 기억해서 해야 하는 일이었습니다. 원칙은 노트에 적혀 있었지만 실행 절차가 되지는 못했습니다.

그러다 Claude Code 연동 내용을 보강한 개정판 《세컨드 브레인은 옵시디언 with 클로드 코드》를 읽었습니다. p.222~230의 제텔카스텐 설명 자체는 낯설지 않았습니다. 이번에 새로 알게 된 것은 QMD라는 검색 도구였습니다. AI가 vault 전체를 뒤지는 방식이 아니라, 필요한 노트를 검색해 읽게 만들 수 있다는 점에서 다른 질문이 생겼습니다.

> 이미 알고 있는 이 원칙을, AI가 반복해서 실행할 수 있는 스킬로 만들 수 없을까?

이번에 달라진 것은 지식이 아니라 실행 방식이었습니다.

## 알고 있던 원칙을 이번에는 실행 가능하게 만들었다

초판에서 기록해둔 내용과 개정판의 같은 대목을 나란히 놓고, 실행 절차로 옮길 원칙을 세 가지로 좁혔습니다.

첫째, 제텔카스텐은 완성된 분류 체계를 먼저 만드는 방식이 아니라 작은 생각을 연결하며 글감을 키우는 상향식 시스템입니다.

둘째, 생각을 **포착하는 일**과 영구 노트로 **승격하는 일**은 분리해야 합니다. 포착할 때는 속도와 원형 보존이 중요하지만, 승격할 때는 재사용 가능성과 다른 생각과의 관계를 판단해야 합니다.

셋째, 템플릿은 모든 칸을 채우게 만드는 양식보다 반대 관점, 구체적인 예, 다른 노트와의 연결을 묻는 질문에 가까워야 합니다. 빈칸을 없애는 것이 아니라 생각의 빈자리를 발견하는 도구여야 합니다.

중요한 것은 이 내용을 다시 요약하는 일이 아니었습니다. 원칙마다 AI가 해야 할 일과 하지 말아야 할 일을 정하는 일이었습니다. AI에게 노트를 대신 써달라고 하기보다, 제가 매번 버거워했던 검색과 정리의 비용을 맡기기로 했습니다.

## QMD는 쌓인 노트를 다시 찾는 검색 계층이다

QMD는 로컬의 Markdown 문서를 하나의 지식베이스처럼 색인하고 검색하는 도구입니다. 옵시디언 전용 플러그인은 아니지만, 노트가 Markdown 파일로 저장되는 옵시디언과 잘 맞습니다. 제 환경에서는 vault를 `PKM`이라는 컬렉션으로 색인하고, AI가 CLI나 MCP를 통해 필요한 노트를 검색합니다.

파일명이나 정확한 표현을 알고 있을 때는 키워드 검색으로 충분합니다. 하지만 시간이 지나면 같은 생각을 다른 말로 적어둔 경우가 많습니다. 이때 QMD는 임베딩을 이용한 의미 검색으로 표현이 달라도 비슷한 내용을 찾을 수 있습니다.

제가 사용하는 구조화 검색은 질문을 몇 가지 단서로 나눕니다.

| 항목 | 역할 |
| --- | --- |
| `intent` | 무엇을 찾고 무엇을 제외할지 검색 목적을 정함 |
| `lex` | 제목·고유명사·정확한 표현처럼 키워드가 중요한 단서 |
| `vec` | 찾으려는 생각을 자연어로 풀어 쓴 의미 단서 |
| `hyde` | 원하는 문서가 있다면 담고 있을 법한 내용을 가상으로 작성한 단서 |

QMD는 이 단서로 후보 문서를 찾고 순위를 매깁니다. AI는 검색 결과의 짧은 조각만 보고 판단하지 않고, 후보 문서의 원문을 다시 읽습니다. 덕분에 매번 vault 전체를 읽히지 않으면서도 기존 생각을 놓칠 가능성을 줄일 수 있습니다.

제텔카스텐에서 QMD의 역할은 새 노트를 많이 만드는 것이 아닙니다. 새 영구 노트를 만들기 전에 같은 주장이 이미 있는지 확인하고, 이어지는 생각이나 반대되는 관점을 찾는 것입니다. 같은 주장이 있으면 기존 노트를 보강하고, 실제 관계를 설명할 수 있을 때만 새 노트와 연결합니다.

노트를 옮기거나 수정한 뒤에는 `qmd update`로 파일 변화를 반영하고, `qmd embed`로 의미 검색에 필요한 임베딩을 갱신합니다. 이번에는 승격한 노트가 다시 검색되는지 확인하는 데도 QMD를 사용했습니다.

다만 QMD가 돌려주는 것은 어디까지나 후보입니다. 두 노트가 의미상 연결되는지, 어느 쪽을 보강할지, 원문을 삭제해도 되는지는 QMD가 결정하지 않습니다. 검색 비용은 줄었지만 판단의 책임은 그대로 남습니다.

## 제텔카스텐 원칙을 AI 스킬의 책임 경계로 옮겼다

처음에는 하나의 거대한 “옵시디언 정리 스킬”을 만들 수도 있었습니다. 하지만 포착과 승격의 목적이 다르다면 AI 스킬의 책임도 나누는 편이 자연스러웠습니다.

| 스킬·도구 | 맡긴 일 | 맡기지 않은 일 |
| --- | --- | --- |
| `capture-fleeting-note` | 떠오른 생각을 Inbox에 빠르게 기록 | 내용을 확장하거나 영구 노트로 판단하기 |
| `review-zettelkasten` | 중복·연결을 조사하고 삭제·보관·승격 후보 제안 | 승인 전에 파일을 만들거나 옮기거나 삭제하기 |
| `permanent-note` | 승인된 생각을 독립적인 영구 노트로 정제 | 입력에 없던 주장을 사실처럼 본문에 추가하기 |
| `vault-lint` | frontmatter·죽은 링크·고립 노트 검사 | 의미상 연결할 노트를 대신 결정하기 |
| QMD | 키워드 검색과 의미 검색으로 기존 노트 찾기 | 검색 결과만 보고 연결을 확정하기 |

운영 원칙은 간단합니다.

> **포착은 가볍게, 정리는 몰아서, 연결은 필요할 때, 판단은 사람이 한다.**

AI는 후보와 근거를 제시합니다. 삭제·병합·승격·연결처럼 지식 구조를 바꾸는 일은 제가 승인한 뒤에만 실행합니다. 자동화의 속도보다 판단의 책임이 어디에 남는지가 더 중요했습니다.

## Inbox 노트 하나로 파이프라인을 돌려봤다

워크플로를 만든 뒤, 출발점이 된 메모를 직접 넣어봤습니다. 책의 제텔카스텐 부분을 읽으며 `제텔카스텐이란?`이라는 Inbox 노트에 핵심 내용과 제 생각을 섞어 적어둔 상태였습니다.

먼저 `review-zettelkasten`이 원문을 읽고, 앞에서 설명한 QMD 구조화 검색으로 현재 Slipbox를 조사했습니다. 같은 주장을 맡고 있는 영구 노트가 있는지, 이어지거나 반대되는 생각은 무엇인지 확인하기 위해서였습니다.

검색 결과 직접 중복되는 영구 노트는 없었습니다. AI는 곧바로 파일을 만들지 않고 다음 승격안을 먼저 제시했습니다.

1. 책 참고노트에 p.222~230의 출처 맥락과 제 생각을 흡수한다.
2. 재사용할 수 있는 주장 세 개를 영구 노트로 분리한다.
3. 아직 반복 탐색 수요가 확인되지 않았으므로 MOC는 만들지 않는다.
4. 모든 내용이 흡수되면 Inbox 원문은 삭제한다.

제가 전체 적용을 승인한 뒤 실제 파일이 변경됐습니다.

- [[제텔카스텐은 상향식으로 글감을 성장시키는 시스템이다]]
- [[포착과 영구 노트 승격은 분리해야 한다]]
- [[템플릿은 내용을 채우는 틀이 아니라 생각을 확장하는 질문이어야 한다]]

마지막에는 `vault-lint`로 frontmatter와 링크를 검사하고, QMD 인덱스와 임베딩을 갱신한 뒤 방금 만든 세 노트가 의미 검색으로 다시 찾아지는지도 확인했습니다.

```text
Inbox 원문
  ↓ QMD 중복·연결 검색
참고노트 보강 + 영구 노트 승격안 제시
  ↓ 사용자 승인
파일 생성·연결 + 원문 처리
  ↓
vault lint → QMD 재색인 → 검색 검증
```

## 일부러 자동화하지 않은 것들

이 과정에서 더 인상적이었던 것은 자동화한 작업보다 자동화하지 않은 작업이었습니다.

- 모든 Inbox를 자동으로 영구 노트로 바꾸지 않았습니다.
- 키워드가 같다는 이유만으로 노트를 연결하지 않았습니다.
- 영구 노트가 세 개 생겼다는 이유만으로 MOC를 만들지 않았습니다.
- 모든 고립 노트를 없애려고 하지 않았습니다.
- AI가 제안한 삭제와 이동을 승인 없이 실행하지 않았습니다.

옵시디언을 다시 쓰게 만든 것은 정리가 완전히 자동화됐다는 안도감이 아니었습니다. 지금 떠오른 생각은 가볍게 남겨도 되고, 복잡한 정리는 나중에 AI와 함께 검토할 수 있다는 확신이었습니다.

## 검증을 자동화해도 범위는 사람이 정한다

물론 첫 실행부터 완벽하지는 않았습니다.

승격 작업을 마친 뒤 새 영구 노트와 책 참고노트에는 죽은 링크가 없다고 확인했습니다. 하지만 나중에 전체 운영 문서를 다시 읽으면서, 삭제한 Inbox 원문을 가리키는 링크가 한 곳 남아 있다는 사실을 발견했습니다.

검사 도구가 틀린 것은 아니었습니다. 제가 결과를 볼 때 이번에 변경한 파일만 좁혀서 확인했기 때문입니다. 자동화된 검증이 있어도 무엇을 검사할지 잘못 정하면 놓칠 수 있습니다.

이 경험은 AI와 옵시디언의 역할을 다시 확인해줬습니다. AI는 넓은 vault를 빠르게 검색하고 일정한 규칙으로 검사하는 데 강합니다. 하지만 검사 범위를 정하고, 결과가 실제 의도와 맞는지 판단하는 책임까지 사라지지는 않습니다.

## AI가 맡은 것은 지식이 아니라 정리 비용이었다

예전에는 옵시디언을 잘 쓰려면 폴더, 태그, 링크를 부지런히 관리해야 한다고 생각했습니다. 이제는 조금 다르게 생각합니다. 시스템의 목적은 깔끔한 vault를 만드는 것이 아니라, 생각을 다시 찾고 발전시켜 글과 판단에 사용하는 것입니다.

AI가 대신 써준 문장이 많아지는 것만으로는 세컨드 브레인이 만들어지지 않습니다. 무엇이 내 생각인지, 어떤 근거에서 나왔는지, 왜 다른 노트와 연결되는지를 내가 판단할 수 있어야 합니다.

그래서 제가 만든 “옵시디언 with AI”의 핵심은 자동 작성이 아닙니다. AI가 검색과 정리의 마찰을 줄여주고, 저는 남길 생각과 연결의 의미에 집중하는 운영 방식입니다.

옵시디언을 다시 쓰기 시작한 이유도 AI가 모든 것을 해줘서가 아닙니다. 모든 것을 혼자 관리하지 않아도 되면서, 중요한 판단은 여전히 제 손에 남아 있기 때문입니다.

## 초안에서 더 채울 부분

- 개정판을 다시 읽게 된 계기와 초판 때와 달라진 문제의식
- 예전 Obsidian 정리가 멈춘 구체적인 시점 또는 방치된 Inbox 사례
- 승격 전후 화면과 승인 과정 이미지
- 이 워크플로를 1~2주 사용한 뒤 실제로 기록 빈도나 회수 경험이 달라졌는지
- 남아 있던 죽은 링크를 어떻게 처리하고 검사 범위를 개선했는지
