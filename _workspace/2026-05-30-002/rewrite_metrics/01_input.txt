# 개발은 다시 산업화되고 있다

## 들어가며

소프트웨어 조직이 지금 겪는 변화는 “AI가 코드를 대신 써 준다”는 수준에서 끝나지 않는다. 개발은 점점 개인의 타이핑 기술보다 시스템이 설계된 방식에 더 크게 좌우되고 있다. 제조업에서 기계가 들어온 뒤 바뀐 것도 단순한 생산량만은 아니었다. 작업이 어디서 이뤄지는지, 누가 무엇을 결정하는지, 품질을 어디서 잡는지, 책임을 어떻게 기록하는지, 숙련을 어떻게 길러내는지가 함께 바뀌었다. 오늘의 AI coding agent도 같은 질문을 소프트웨어 조직 앞에 다시 놓고 있다.

그래서 “AI coding agent는 소프트웨어 공장이다”라고 바로 말하면 절반만 맞는다. 맞는 절반은 생산 기술이 들어오면 사람의 일을 둘러싼 공정·품질·감사·훈련 체계를 다시 설계해야 한다는 점이다. 틀리는 절반은 소프트웨어를 물리적 조립 라인처럼 이해하는 순간 문제 정의, 설계 판단, 맥락 이해라는 개발의 핵심을 놓친다는 점이다. 지금 필요한 건 찬반 논쟁보다 비유가 유효한 곳과 깨지는 곳을 구분하는 일이다.

## 제조업의 전환은 기계보다 시스템을 바꿨다

공장 시스템은 단지 “손일을 기계가 대신한 체제”가 아니었다. 브리태니커가 정리하듯, 공장 시스템은 18세기 산업혁명 속에서 등장했고 집이나 부속 작업장에서 손도구로 일하던 domestic system을 대체했다. 물과 증기 같은 동력이 생산을 한 장소에 집중시켰고 고용주가 도구와 원재료를 소유하며 노동자는 그 공간과 시간표 안으로 들어갔다. 그 결과 생산은 분산된 생업에서 집중된 조직 활동으로 바뀌었다.

이 변화의 핵심은 기계 그 자체보다 노동의 재배열이었다. interchangeable parts와 대량생산은 한 사람이 시작부터 끝까지 책임지는 장인식 생산을 밀어내고, 더 잘게 쪼개진 공정과 표준화된 인터페이스 위에 덜 숙련된 노동도 투입할 수 있게 만들었다. 이후 scientific management와 조립 라인은 이 흐름을 더 밀어붙였다. 작업은 측정되고 반복은 최적화됐으며 현장의 판단 일부는 관리와 설계 쪽으로 이동했다. 산업화는 사람을 없앤 것이 아니라 사람의 위치를 바꿨다.

하지만 초기의 공장 시스템이 낳은 것은 효율만이 아니었다. 장시간 노동, 위험한 작업장, 아동노동, 저임금, 도시의 열악한 주거가 함께 왔다. 브리태니커는 이 조건들이 노동조합 운동의 배경이 되었다고 정리한다. 러다이트 운동도 기계가 추상적으로 싫어서가 아니라, 기계 도입이 생계와 통제권을 어떻게 바꾸는가에 대한 반응으로 나타났다. 1802년 Health and Morals of Apprentices Act는 환기·청결·교육 같은 최소 기준을 두었지만 집행은 약했고 1833년 Factory Act는 더 본격적인 inspectorate를 도입해 감시와 집행 능력을 강화했다. 산업화는 처음부터 잘 설계된 체제가 아니었다. 실패와 갈등 뒤에 뒤늦게 제도화된 체제였다.

산업혁명의 교훈은 기계를 막으라는 것이 아니었다. 기계가 들어온 뒤에도 옛 질서를 그대로 유지할 수 있다고 믿는 쪽이 더 큰 착각이었다. 품질관리, 감독, 훈련, 노동법, 안전규제는 기계의 부속물이 아니라 새 생산체제를 버티게 만드는 기반 시설이었다. 이 점은 오늘의 소프트웨어 조직에도 거의 그대로 돌아온다.

## 소프트웨어 개발은 왜 오래도록 수공업적이었는가

소프트웨어 개발이 오랫동안 수공업적으로 보였던 이유는 개발자가 낭만적인 장인이어서가 아니다. 소프트웨어의 어려움은 많은 경우 타이핑 자체보다 무엇을 만들어야 하는지 정의하고 바뀌는 요구를 흡수하고 서로 얽힌 구조를 이해하는 일에 있었다. 프레드 브룩스가 오래전에 지적했듯, 소프트웨어에는 도구와 언어가 줄여 줄 수 있는 우연적 복잡성도 있지만 문제 자체에서 오는 본질적 복잡성도 있다. 그래서 개발은 오래도록 단순 반복 작업의 집합이 아니라 설계와 맥락 판단이 큰 비중을 차지하는 활동으로 남았다.

같은 이유로 소프트웨어는 제조업식 인력 투입 논리가 잘 안 통했다. 브룩스의 고전적 논지는, 늦어진 프로젝트에 사람을 추가한다고 일정이 선형적으로 줄어들지 않는다는 것이었다. 커뮤니케이션 비용, 온보딩 비용, 설계 의존성이 계속 생기기 때문이다. 이 점은 지금도 유효하다. AI가 코드 작성의 일부를 줄여 주더라도, 시스템 경계·아키텍처·디버깅·배포 리스크를 이해하는 일까지 저절로 사라지는 것은 아니다.

그래서 과거의 개발 조직은 공장보다는 공방에 가까웠다. 한 명의 개발자나 작은 팀이 코드만이 아니라 문제 이해, 설계, 구현, 테스트, 배포, 유지보수까지 상대적으로 넓게 떠안는 경우가 많았다. 이는 비효율의 낭만이 아니라 소프트웨어 산출물이 복제는 싸지만 변경은 맥락 의존적이라는 사실의 결과였다. AI coding agent의 등장이 흥미로운 이유도 여기에 있다. AI는 제조업의 기계처럼 반복을 줄이지만 개발이 여전히 설계 중심 일이라는 사실까지 없애지는 못한다.

## AI coding agent는 개발 공정을 어떻게 바꾸는가

오늘의 AI coding agent는 더 이상 “괜찮은 자동완성기”에 머물지 않는다. GitHub Copilot은 에디터 안의 제안 기능을 넘어서, GitHub 안팎에서 Copilot·Claude·Codex 같은 에이전트에게 일을 할당하고 그들이 백그라운드에서 계획하고 탐색하고 실행하도록 설계돼 있다. GitHub는 에이전트 사용을 위한 감사 로그와 중앙 통제를 강조하고 Copilot code review를 제품 라인에 포함시킨다. OpenAI의 Codex는 각 작업을 코드베이스가 실린 독립된 클라우드 샌드박스에서 병렬 처리하며 파일 수정과 테스트 실행, 린트·타입체커 수행, 터미널 로그와 테스트 결과를 인용한 검증 가능한 흔적까지 제공한다. Anthropic의 Claude Code는 코드 읽기·파일 수정·명령 실행·커밋·PR 생성·CI 연계·MCP 연결·auto memory·skills·hooks·background agents를 전면에 내세운다. VS Code 역시 로컬, 백그라운드, 클라우드 에이전트를 하나의 개발 경험 안에서 다루고 에이전트가 직접 워크스페이스를 수정하고 터미널 명령을 실행하며 체크포인트로 되돌릴 수 있게 만든다.

이 변화는 “코드를 더 빨리 써 준다”보다 더 큰 의미를 가진다. 개발 공정의 무게중심이 작성에서 운영으로 이동하기 때문이다. 이제 중요한 것은 어떤 모델이 가장 똑똑하냐보다 어떤 작업을 에이전트에게 넘길 것인지, 어떤 권한을 허용할 것인지, 어느 시점에 인간 승인을 요구할 것인지, 어떤 테스트와 로그를 증거로 남길 것인지, 어떤 규칙 파일과 메모리를 프로젝트에 심을 것인지다. Claude Code가 permission mode를 세분화하고 protected path를 두며, GitHub가 audit log와 governance를 강조하고 VS Code가 permission level과 session type을 별도 설정으로 두는 이유도 여기에 있다. 문제는 더 이상 모델 하나가 아니라 에이전트가 움직이는 운영 체제다.

채택은 빠르지만 신뢰는 그만큼 빠르지 않다. Stack Overflow의 2025 Developer Survey에 따르면 응답자의 84%는 AI 도구를 이미 쓰거나 곧 쓸 계획이라고 답했다. 그러나 같은 조사에서 AI 도구의 정확성을 신뢰한다는 응답은 33% 정도였고, 불신한다는 응답은 46%였다. AI agent만 따로 보면 과반은 아직 agents를 쓰지 않거나 단순 Copilot/autocomplete 수준에 머문다고 답했다. 반면 실제 agent 사용자 집단 안에서는 69%가 생산성 향상을, 약 70%가 특정 작업 시간 감소를 보고했다. 도입은 확산 중이지만 agent는 아직 완전한 기본값이 아니며 체감 이익도 팀 수준보다 개인 효율에 더 치우쳐 있다.

실증 연구도 한 방향으로 정리되지 않는다. 한 실무 연구는 Copilot이 문서화·자동완성에서는 최대 50%, 반복 코딩·테스트·디버깅에서는 30~40% 수준의 시간 절감을 줄 수 있다고 보고했다. 반면 최근 종단 연구는 AI coding assistant가 개발자의 시간을 코드 작성에서 검증과 감독 쪽으로 옮기고, “supervisory engineering work”라는 새로운 성격의 일을 만들고 있다고 지적한다. 인간-자동화 연구는 생성형 AI가 쉬운 일은 더 쉽게 만들지만 어려운 일은 오히려 더 어렵게 만들 수 있고 사람의 역할을 생산에서 평가로 밀어내며 그 과정에서 생산성 기대와 실제 경험이 어긋나는 역설이 생긴다고 말한다. 최신 비교 연구도 에이전트 성과가 task type에 강하게 의존한다고 보여 준다. 문서 작업과 새 기능 개발, 버그 수정은 같은 난이도의 일이 아니다. “AI는 개발자를 2배 빠르게 만든다” 같은 문장은 연구보다 슬로건에 가깝다.

## 닮은 점은 많지만, 공장 비유는 여기서 멈춰야 한다

가장 강한 유사성은 개별 생산자의 손기술보다 생산 시스템의 설계가 더 중요해진다는 점이다. 제조업에서 공장 시스템이 등장한 뒤 생산성은 기계 배치, 표준화, 작업 분업, 감독 체계에 크게 좌우됐다. 지금의 AI coding agent 시대에서도 산출물의 품질과 속도는 점점 더 모델 한 개의 “지능”보다 작업 스코프, 권한 경계, 검토 흐름, 로그, 테스트, 규칙 파일, 세션 관리에 의해 좌우된다. 개발자는 단지 코드를 쓰는 사람이 아니라 에이전트가 움직일 생산 시스템의 설계자이자 운영자가 된다.

두 번째 유사성은 병목의 이동이다. 공장 시스템은 생산량을 키웠지만 품질문제·안전문제·감독문제도 함께 키웠다. AI coding agent도 비슷하다. 코드를 더 빨리 만들수록 검토 부담, 보안 부담, 배포 리스크가 아래로 밀려간다. 장기 연구가 말하는 “creation에서 verification으로의 이동”은 이 변화를 짚는다. 지금의 병목은 작성보다 검증에 가깝다. 과거 제조업이 품질과 안전의 제도화를 늦게 배우며 큰 비용을 치렀듯, 소프트웨어 조직도 같은 실수를 반복할 수 있다.

다만 이 비유는 특정 지점에서 멈춰야 한다. 소프트웨어는 물리적 조립품이 아니다. Copilot cloud agent, Codex, Claude Code, VS Code의 agent session은 여러 작업을 병렬로 돌리고 되돌리고 분기시키고 다시 합칠 수 있다. 물류·재고·기계 마모·운송 동선 같은 제조업의 제약이 그대로 작동하지 않는다. 동시에 소프트웨어 개발은 반복 생산 못지않게 문제 발견과 설계, 커뮤니케이션, 아키텍처 판단의 일이다. AI coding agent는 조립 라인보다는, 표준화된 도구 위에서 고도의 비정형 판단이 계속 필요한 지식노동용 생산 시스템에 더 가깝다.

또 하나의 차이는 규모다. 공장 시스템이 대체로 자본과 설비를 중앙에 집중시켰다면, AI coding agent는 작은 팀과 개인에게도 “마이크로 팩토리”를 준다. Anthropic의 대규모 사용 분석은 AI 활용이 전반적으로 augmentation 57%, automation 43% 쪽에 분포한다고 보고했고, GitHub와 VS Code, Anthropic, OpenAI의 제품 설계는 공통적으로 개인 사용자도 에이전트 기반 워크플로에 들어오게 만들어 놓았다. AIDev 데이터셋이 93만 건이 넘는 agent-authored PR을 11만 개 넘는 저장소에서 포착한 사실은 이 흐름이 이미 일부 데모가 아니라 실무 표면 위에 올라왔음을 보여 준다. 이 변화를 “대기업의 공장화”로만 읽어서는 부족하다. 개인 개발자 한 명이 더 큰 공정을 관리하게 되는 방향도 동시에 열려 있다.

이 비유의 설명력은 대략 다음 정도다.

| 비교 축 | 제조업 산업화에서의 변화 | AI coding agent 시대의 대응물 | 유사성 강도 |
|---|---|---|---|
| 개별 숙련보다 시스템 설계 중요 | 작업장 집중, 기계 배치, 분업, 감독 | 에이전트 세션, 권한, 테스트, 로그, 규칙 파일, 감사 | 강한 유사성 |
| 생산량 증가 후 검증 병목 | 대량생산 뒤 검사·안전·감독 문제 확대 | PR 증가, 리뷰 병목, 배포 리스크, 보안 검증 부담 | 강한 유사성 |
| 숙련의 재배치 | 현장 판단 일부 축소, 관리·설계·감독 강화 | 작성 일부 자동화, 계획·검토·품질설계·감사 강화 | 부분적 유사성 |
| 노동 저항과 불안 | 기계 자체보다 생계·통제권 변화에 반응 | 도구 불신, 책임 증가, 학습경로 약화 우려, 감시 우려 | 부분적 유사성 |
| 표준화와 창의성의 긴장 | 표준공정 확대와 현장 자율성 충돌 | 규칙 기반 agent workflow와 설계 판단의 충돌 | 부분적 유사성 |
| 조립라인식 반복 생산 | 물리적 제품의 선형 흐름 | 병렬적·가역적·탐색적 소프트웨어 작업 | 약한 유사성 |
| 대공장 집중 | 자본집약적 대규모 시설 | 개인과 소규모 팀의 생산성도 함께 확대 | 비유가 위험한 지점 |

개발자의 불안을 단순한 반기술주의로 취급하는 태도는 여기서 특히 틀린다. 러다이트를 “기계를 무서워한 사람들”로만 읽으면 역사를 잘못 읽는 것이다. 오늘의 개발자 역시 마찬가지다. 불안의 핵심은 새 도구에 대한 감정적 거부가 아니라 정확하지 않은 출력, 디버깅 비용의 증가, 책임 소재의 모호화, 내가 정말 이해하고 있는가에 대한 의심이다. 실제로 Stack Overflow 조사에서는 “거의 맞지만 완전히 맞지 않은 해답”이 가장 큰 불만이었고 “AI가 만든 코드를 디버깅하는 데 시간이 더 든다”는 응답도 매우 높게 나왔다. 이 불안은 기술혐오가 아니다. 아직 공정이 덜 설계된 상태에 대한 합리적 경계에 가깝다.

## 지금 소프트웨어 조직이 다시 설계해야 할 것

산업화는 기계를 들여온 순간 끝난 것이 아니라, 그다음에 검사와 통제, 훈련과 규제, 책임과 감독을 붙이면서 하나의 체제가 됐다. AI coding agent 시대의 소프트웨어 조직도 비슷하다. 에이전트를 도입하고도 코드리뷰, 테스트, 보안, 승인, 온보딩, 책임 표시를 옛 방식 그대로 두면 개발 속도만 빨라지고 실패는 더 빨리, 더 멀리 퍼진다. 보안 쪽 증거는 이미 쌓이고 있다. Copilot 생성 코드의 실증 연구는 오픈소스 프로젝트 안에서도 상당한 비율의 보안 약점을 포착했고 package hallucination 연구는 없는 패키지를 추천하는 공급망 위험을 보여 줬다. GitGuardian의 2026 보고서는 2025년 GitHub에서 약 2,900만 개의 시크릿이 노출됐고 AI 보조 커밋의 누출률이 GitHub 평균보다 대략 두 배 높았다고 전했다.

그래서 조직이 해야 할 일은 “에이전트를 더 많이 쓰자”가 아니라 어디까지 맡기고 어디서 막을지를 설계하는 것이다. Claude Code가 permission mode를 `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`로 나누고 protected path를 별도로 두는 이유도, VS Code가 session type과 permission level을 분리하는 이유도, GitHub가 audit log와 enterprise control plane을 내세우는 이유도 같다. AI가 더 강해졌기 때문에 사람의 통제가 덜 중요해진 것이 아니다. 오히려 통제의 설계가 제품 기능이 됐다.

지금 대부분의 팀이 부딪히는 문제를 공정 관점에서 정리하면 다음과 같다. AI coding agent의 문제는 대체로 모델의 지능 부족만이 아니라, 조직이 어떤 공정 위에서 그 지능을 쓰게 만들었는가에서 생긴다.

| 다시 설계할 항목 | 그대로 두면 생기는 문제 | 지금 필요한 대응 |
|---|---|---|
| 리뷰와 품질관리 | 코드 과잉생산, 검토 병목, 오류의 대량 유입 | 작은 작업 단위, 필수 테스트, CI 게이트, 리뷰 책임자 명확화 |
| 권한과 실행 통제 | 무분별한 파일 수정, 터미널 오남용, 배포 사고 | permission mode, 샌드박스, protected path, allowlist |
| 보안과 공급망 | hallucinated dependency, 시크릿 유출, 외부 도구 오남용 | secret scanning, dependency 검증, provenance, 최소권한 |
| 교육과 성장 경로 | 주니어의 이해 부채, 검토 능력 약화 | plan mode 활용, 코드 읽기·디버깅·리뷰를 훈련 경로로 남기기 |
| 책임과 감사 | “누가 쓴 코드인가”의 흐림, 승인자의 과부하 | agent 태깅, 로그 보존, human sign-off, 변경 이력 표준화 |
| 플랫폼 운영 | 팀마다 제멋대로의 AI 사용, 벤더 종속 심화 | 공통 규칙 파일, 중앙 정책, 플랫폼 팀 또는 AI workflow owner 지정 |

이 재설계의 핵심은 기술보다 운영에 있다. 교육 문제만 봐도 그렇다. 최근 종단 연구는 AI coding assistant가 작업 시간을 줄이는 대신 사람의 초점을 생성보다 검증 쪽으로 옮기고, 개발 경험 일부는 오히려 악화될 수 있다고 지적한다. 자동화 연구 전통도 비슷하게 경고한다. 인간은 점점 드문 개입자이면서 동시에 최종 책임자로 남고 그 결과 쉬운 일은 줄지만 어려운 일의 부담은 더 무거워진다. 그렇다면 조직은 주니어에게 “지루한 일은 전부 AI가 한다”라고 말할 게 아니라 리뷰·디버깅·리팩터링·운영 사고 대응을 성장 경로로 의도적으로 남겨야 한다. 그렇지 않으면 생산성은 올라도 실력의 사다리는 끊어진다.

미래의 위험도 기술 운명처럼 받아들일 필요는 없다. 코드 과잉생산, AI-generated legacy, 공급망 공격, 책임 불명확성, 플랫폼 종속은 모두 가능성이 높은 시나리오지만 자동적으로 발생하는 숙명은 아니다. AIDev 데이터셋과 여러 실증 연구는 이미 agent-authored PR이 대규모로 존재함을 보여 주지만, 다른 연구는 성과가 작업 종류와 조직 맥락에 크게 좌우된다고 말한다. AI coding agent는 개발자를 사라지게 하는 단선적 자동화라기보다, 좋은 조직에서는 공정 혁신의 증폭기, 나쁜 조직에서는 혼란의 증폭기가 될 가능성이 더 크다.

## 아직 모르는 것

장기적으로 무엇이 굳어질지는 아직 확정되지 않았다. 특히 세 가지는 더 지켜봐야 한다. 첫째, 주니어 개발자의 성장 경로가 실제로 얼마나 약화되는지. 둘째, AI 코드가 장기 유지보수성에 어떤 영향을 주는지. 셋째, 조직별로 생산성 이익과 개발 경험 악화가 어느 비율로 갈리는지다. 현재 근거는 빠르게 늘고 있지만 대부분 2024년 이후 자료이고, 많은 연구가 특정 과업·특정 도구·특정 사용자 집단에 묶여 있다. 지금 가능한 가장 정직한 결론은 “대전환은 진행 중이지만, 귀결은 아직 제도 설계에 달려 있다”는 정도다.

## 결론

제조업 산업화의 교훈은 기계를 막으라는 것이 아니었다. 기계가 들어온 뒤에도 예전의 노동 구조, 품질관리, 교육, 책임 체계를 그대로 둬도 된다고 믿지 말라는 것이었다. 지금의 AI coding agent도 비슷하다. 코드 생성 속도만 보고 있으면 본질을 놓친다. 변화의 핵심은 개발자가 장인에서 단순한 버튼 누르는 관리자로 떨어지는 데 있지 않다. 장인·감독자·품질관리자·공정 설계자의 역할을 동시에 떠안는 위치로 이동한다는 데 있다.

AI coding agent 시대의 질문은 “개발자가 사라지는가”가 아니다. 질문은 “개발자가 어떤 생산 시스템의 책임자가 되는가”다.
