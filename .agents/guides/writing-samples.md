# 문장 견본

TaeZ가 실제로 쓰거나 직접 고친 문단과, AI가 쓴 문장을 TaeZ가 고친 전후 쌍이다. [공통 글쓰기 기준](writing.md)이 피할 것과 판단 방법을 정한다면 이 파일은 목표로 삼을 문장을 보여 준다. 문장이나 표현을 베끼지 말고 문단이 생각을 어떻게 움직이는지를 참고한다. 종결체·분량·구조는 산출물의 규칙을 따른다. 견본에 없는 방식이라는 이유로 문장을 고치지 않는다. 견본 문장은 원래 노트에서 띄어쓰기와 연결어미 뒤 쉼표만 바로잡았다.

## 문단

> 내가 그동안 요즘 사람들이 'taste'가 중요하다고 했는데 무슨 말인진 알겠으면서도 딱 와닿진 않았거든. 뭔가 취향으로 퉁치기에는 좀 안 맞는 것 같았다.

아직 납득하지 못한 상태에서 생각을 시작한다. 출처: Inbox 메모 「taste가 아니라 맥락상의 우위」

> 흔히 '취향'이나 '안목'으로 번역되지만 그것만으로 taste를 다 설명할 수는 없는 것 같다. (…) 그중 지금 필요한 것을 꺼내 연결하고 무엇에 더 무게를 둘지 정하는 일. 나는 그게 taste에 가깝다고 생각한다.

확신하지 못한 부분을 "것 같다"로 남긴 채 정의를 세운다. 출처: 「Taste는 지금 필요한 것에 무게를 두는 감각이다」

> 내 생각에 AI가 대체하는 개발자는 성장하지 않는 개발자.. 는 너무 추상적이고 정확하게 말하면 **비판적 사고를 하지 않는 개발자**이다.

말하던 중에 더 정확한 말로 좁혀 간다. 출처: 「대 지브리 시대에서 개발자로 살아남기」

> 처음엔 그냥 통합 피드 하나만 뒀다가 GitHub 프로필에서 각 카테고리별 최신 글을 보여주고 싶어서 피드를 나눴다.

사후에 붙인 이유가 아니라 실제 동기와 순서를 그대로 쓴다. 출처: 「RSS 피드로 GitHub 프로필 갱신하기」

> AI 없이 혼자 관리하던 때는 정작 노트를 쓰는 데보다 저장 위치, 태그 같은 프론트매터, 링크 관리 등을 챙기다가 지쳐서 손을 놓곤 했다. 지금은 그런 관리를 상당 부분 AI에게 맡기고 나는 지식을 관리하는 데 집중한다.

실제로 힘들었던 지점을 짚고 지쳤던 경험을 꾸미지 않는다. 출처: 「Obsidian Vault를 AI와 함께 운영하는 방법」

> 내 사이트의 오류·의견 제보 기능에서는 분류 항목을 두지 않았다. 독자가 "버튼이 링크를 가린다"처럼 겪은 일만 적으면 충분하고 그것이 오류인지 개선 제안인지까지 판단할 필요는 없다고 생각했다.

주장을 내가 실제로 내린 설계 결정으로 착지시킨다. 출처: 「운영자를 위한 분류가 사용자의 선택 부담을 늘릴 수 있다」

> Qra에 SSE 관련 컨벤션이 없다는 사실은 만들기 전에도 알고 있었다. 그 사실이 이번 결정에 중요하게 작용할 줄은 생각하지 못했다. 무엇이 그 조건을 의식하게 만드는지 되짚어 보면 실패 경험 때문인 것 같다. 비슷한 상황에서 데인 적이 있어야 그 조건이 눈에 걸린다.

알고 있던 것과 실제로 의식한 것을 구분한다. 출처: 「Taste는 지금 필요한 것에 무게를 두는 감각이다」의 이전 버전

> 같은 입력을 몇 번 다시 보내 보니 값이 0.02~0.04쯤 달라졌다. 기준값 바로 근처의 글은 호출마다 목록에 들어가거나 빠질 수 있다.

직접 해 본 관찰을 수치로 적고 그 수치가 뜻하는 결과까지 말한다. 출처: 「Jev와 System One 모델」

> 다른 모델로 바꾸거나 같은 모델에 다른 일을 시키면서도 똑같은 규칙, 하네스, 스킬로 마이크로하게 목줄을 채우면 (…) 모델의 능력에 한계나 제약이 생기는 것 아닐까?

다른 분야의 개념을 끌어와 단정하지 않고 질문으로 남긴다. 출처: Inbox 메모 「에이전트 하네스와 SLII 리더십」

> 부수적인 걸 본질적인 것처럼 방치하면 개선 기회를 놓치고 본질적인 걸 부수적인 것처럼 없애려 하면 위험을 숨기는 결과가 된다.

반대 방향의 두 실패를 대칭 구조로 한 문장에 담는다. 출처: Inbox 메모 「소프트웨어공학 2가지 복잡성 AI 시대 재정리」

> 모든 지침을 한 파일에 넣으면 길어지고 같은 규칙을 여러 곳에 복사하면 관리가 힘들고 금방 서로 어긋난다. AI 입장에선 서로 충돌되는 지침은 차라리 없는 것만도 못하다.

문단을 전환 문장이 아니라 판단으로 닫는다. 출처: 「Obsidian Vault를 AI와 함께 운영하는 방법」

## 고친 방향

| AI가 쓴 문장 | TaeZ가 고친 문장 |
| --- | --- |
| 같은 규칙을 여러 곳에 복사하면 서로 다른 내용이 남는다. 그래서 문서마다 역할을 나눴다. | 같은 규칙을 여러 곳에 복사하면 관리가 힘들고 금방 서로 어긋난다. AI 입장에선 서로 충돌되는 지침은 차라리 없는 것만도 못하다. |
| 가든의 공개 기록을 갱신할 때마다 GitHub 프로필의 목록을 따로 고치지 않도록 RSS를 연결했다. | 나는 이 사이트에 새로운 노트나 글이 등록될 때마다 내 GitHub 프로필 페이지의 최근 글 목록이 갱신되도록 RSS를 연결했다. |
| 사이트 조립·공개 본문 처리를 모듈화 / 홈 최근 글 배치 정리 | 사이트 조립 리팩토링 / 홈 최근 글 목록 정리 |

전환 문장을 판단으로, "~하지 않도록" 같은 부정형 목적을 행위자와 결과로, 추상 명사구를 통용되는 개발 용어로 바꿨다. 길이를 줄이려고 고친 것이 아니어서 첫 쌍은 오히려 길어졌다.
