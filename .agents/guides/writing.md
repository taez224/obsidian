# 공통 글쓰기 기준

노트·글·주석·메시지에 적용하는 공통 한국어 작성 기준이다. 산출물의 장르·분량·종결체는 해당 스킬과 사용자 요청을 따른다. 문장 내부는 `fluent-korean` 지침을 따른다. 조사와 어미를 생략하지 않고, 의미를 담은 문장 성분을 빼지 않는다. 전문은 [fluent-korean](../../.claude/output-styles/fluent-korean.md)에 있고 원문 출처는 snflkd/fluent-korean(MIT)이다. 분량·구조·종결체를 정하는 이 가이드와 각 스킬의 규칙이 그 위에 온다.

외부 글쓰기 가이드는 독자가 이해하고 사용할 수 있는지 점검하는 참고 기준이다. 개인 글의 목소리와 전개는 사용자가 고른 표현, 실제 경험과 질문, 글의 목적을 따른다. 회사 문서의 형식이나 모범 사례와 다르다는 이유만으로 고치지 않는다. 개성을 보태려고 없던 경험·감정·말버릇을 만들지도 않는다.

## 개성을 살리는 편집

개성은 사용자가 고른 표현과 생각이 움직이는 방식에서 찾는다. 실제 경험의 유머·망설임을 매끈한 일반론으로 바꾸지 않는다. 사용자가 쓰거나 다듬은 원고에 있는 비유와 조어는 사용자가 고른 표현이므로 일반 어휘로 바꾸지 않는다. 독자가 문맥으로 알기 어려우면 처음 나올 때 짧은 설명을 붙이는 쪽을 먼저 제안한다. 사용자가 이미 쓰는 조어가 있는 개념을 다시 다룰 때는 새 동의어를 만들지 않는다. 반복을 덜 때도 그 문장이 새 관찰이나 판단의 차이를 더하는지 먼저 본다. 개성을 살리려고 1인칭·곁말·비유를 새로 채우지는 않는다.

도입·전개·끝맺음과 각주·콜아웃은 글의 목적과 재료에 따라 고른다. 장면으로 시작하거나 끝내기, 질문 남기기, 짧은 결론으로 닫기 중 어느 것도 공통 틀이 아니다. 한 글에서 채택한 선택은 같은 역할과 조건에서 참고하며, 다른 글을 그 형식으로 맞추거나 다양성을 위해 잘 작동하는 형식을 억지로 바꾸지 않는다.

태그·분류는 개성을 표시하는 장식보다 다시 찾는 경로로 고른다. 기준은 [속성 스키마](../../99_Templates/_property-schema.md)를 따르며, 자기 관점은 본문의 판단과 노트 사이의 구체적인 관계에서 드러낼 수 있다.

## 문장

- 문장은 짧게, 대상은 구체적으로 쓴다. 범위·경계·책임·주체 같은 추상명사가 쌓이면 실제 대상(DB, 쿼리, 파일, 역할, 사람)으로 바꾼다.
- "문장은 짧게"는 문장 수와 군더더기를 줄이라는 뜻이지, 문장에서 조사와 어미를 덜어내라는 뜻이 아니다. 짧은 노트일수록 성분을 갖춘 문장이 덜 모호하다.
- 직설을 기본으로 쓴다. 비유·안내·대비는 이해·구분·강조에 필요한 경우에만 남긴다. 표현의 형태나 등장 횟수만으로 고치지 않고, 같은 역할을 반복하거나 내용 없이 효과만 만드는 부분을 덜어낸다. 이 기준은 AI가 새로 쓰는 문장에 적용한다. 사용자가 고른 표현은 [개성을 살리는 편집](#개성을-살리는-편집)의 보존 기준을 따른다.
- 문장이 자연스러운지는 금지 표현 목록과 대조해 판단하지 않는다. 동료에게 말로 설명한다면 이 순서와 이 말로 하겠는지 읽어 본다. 영어로 되돌렸을 때 구나 문장 구조가 그대로 대응되면 다시 읽을 후보로 삼는다. AI 초안에서는 영어 구조를 옮긴 문장이 반복해서 남는다. 예를 들어 "…를 맥락상의 우위로 표현하는 쪽을 선호합니다"(prefer to)는 "…로 표현합니다"로, "실행이 이어지는 동안에도"(while execution continues)는 "일이 진행되는 동안에도"로 고쳤다. 문제는 단어가 아니라 그 문장이 영어 구조를 옮겼는지이므로, 같은 단어도 문맥에 맞으면 그대로 둔다. 전수점검에서는 처음에 어색함을 느끼지 못한 문장에도 이 검사를 쓴다. 수정 여부는 한국어 문맥과 더 자연스러운 대안으로 판단하며 의미·조건·시제를 보존한다. 기술 용어나 단어가 대응한다는 이유만으로 고치지 않는다. 번역투를 피하라는 기준은 문장 구조에 대한 것이다. 정착된 번역어가 없는 기술 용어와 API 이름은 원어로 쓰고, '커넥션 제공자'처럼 번역어를 새로 만들지 않는다. 직접 쓰거나 방금 고친 문장일수록 내용이 익숙해 어색함을 놓치기 쉬우므로 같은 방법으로 다시 읽는다.
- 연결어미(-고, -며, -면서, -지만, -는데, -아서·-어서, -니, -면, -다가 등) 다음에는 쉼표 없이 잇는 것을 기본으로 한다. 직접 쓴 문장에는 이 쉼표가 드물고 AI 초안에서 이유 없이 생기기 때문이다. 꾸밈 범위가 갈리거나 두 절을 맞세울 때처럼 끊어 읽어야 뜻이 분명해지는 곳에만 쓴다. 문장이 길기만 하면 쉼표 대신 문장을 나눈다. 나열(A, B, C)이나 삽입구를 구분하는 쉼표는 그대로 쓴다.
- em dash(U+2014)와 en dash(U+2013)를 쓰지 않는다. 링크 뒤 설명은 하이픈, 소제목 뒤는 콜론이나 문장 분리.
- 종결체와 문장 리듬은 산출물의 규칙이 정한다. 개발 노트는 평어체를 쓰고, 블로그는 종결어미 리듬을 기계적으로 균일하게 맞추지 않는다. 지침 원문이 "~합니다"체라는 이유로 산출물의 종결체를 바꾸지 않는다.
- 외부 윤문 스킬을 적용할 때도 이 볼트에서는 다음 기준을 우선한다. 가능성·추정·조건·권고의 강도와 시제는 의미의 일부이므로 보존한다. 문장 길이와 종결어미를 일정한 조합으로 맞추지 않는다. 패턴의 빈도는 검토 후보를 찾는 데만 쓰고, 변경률은 과도한 수정을 감시하는 데만 쓴다. 수정할 이유가 없으면 원문을 유지하며, 등급이나 변경률을 맞추려고 고치지 않는다.

## 내용과 구성

- 한 절에서 하려는 말은 하나다. 같은 뜻을 원칙·목록·조건으로 되풀이하지 않고, 새 정보 없이 앞 문단을 되짚거나 다음 문단을 예고하는 문장은 뺀다.
- 새 예시·개념·인용·인물은 앞 문장과 이어지는 연결을 두고 꺼낸다. 독자에게 갑자기 나타난 것처럼 읽히면 빼기 전에 왜 지금 이것이 나오는지 밝히는 문장부터 검토한다.
- 헤딩은 절의 내용이나 역할을 독자가 짐작할 수 있게 쓴다. 명사구·질문형·주장형 등 구체적인 형식은 장르와 해당 작업 스킬을 따른다. 표현을 과장하거나 본문보다 강하게 단정하지 않는다.
- 문장마다 사실이어도 독자가 받을 인상이 사실과 같은지 읽는다. 여러 방법 가운데 하나를 설명하면서 그것만 있는 것처럼 읽히거나, 이름이 비슷한 예시를 함께 꺼내 독자를 헷갈리게 하지 않는다.
- 지어낸 장면("가상의 서비스에서…")과 "확인할 질문" 표로 내용을 채우지 않는다. 실제 사례가 없으면 일반 원리만 쓴다.
- `summary`는 [속성 스키마](../../99_Templates/_property-schema.md)의 노트 유형별 기준을 따른다. 블로그에서는 읽기 전의 소개문으로 쓰며, 원고의 분량과 화면 표시 길이를 구분한다. 목록의 줄 수 제한을 이유로 첫 문장만 남기거나 결론을 먼저 밝히도록 강제하지 않는다.
- 공개 폴더(Slipbox, blog, Development 세 폴더)에는 사용자가 공개하기로 한 경험과 자기 해석을 담을 수 있다. 비공개 정보는 제외하고, 독자가 모르는 내부 맥락은 이해에 필요한 만큼 설명한다. vault 내부 경로와 시간이 지나면 바뀌는 운영 수치는 넣지 않는다. 개인 서술이 있다는 이유만으로 삭제하거나 공개 범위를 바꾸지 않는다. 대화에서 편집 방향을 정하려고 말한 목적·동기는 공개 원고에 쓸 내용으로 자동 취급하지 않는다. 브랜딩이나 포트폴리오 목적도 본문에 쓰기로 한 것이 아니면 소재와 관점을 고르는 데만 반영한다.

## 링크와 각주

- 링크는 역할에 따라 둔다. 독자가 눌러서 가 볼 대상(다른 노트, 도구, 저장소, 공식 문서, 소개하는 글)은 그 대상을 부르는 본문 어구에 건다. 본문이 “AWS의 SaaS 격리 설명은 …”처럼 출처를 직접 부르면 그 어구에 걸어도 된다. 문장 끝에 인용 링크만 덧붙이지 않는다.
- 링크 없이 읽어도 자연스러운 문장을 먼저 쓰고, 관련 어구에 링크를 건다. “자세한 내용은 [[노트]]에 적었다”처럼 다른 문서를 소개하기 위한 문장은 줄인다. 표시 문구는 문맥에 맞게 쓰되, 연결될 내용은 짐작할 수 있어야 한다.
  예: “기준은 [[이 위키를 가꾸는 기준]]에 적었다”보다 “노트를 [[이 위키를 가꾸는 기준|꾸준히 가꾸어 나간다]]”.
- 공개 글에서 주장·수치·인용의 근거는 각주로 다는 것을 기본으로 한다. 본문이 출처를 직접 소개하며 링크했고 어느 주장을 뒷받침하는지 분명하면, 같은 링크만 담은 각주를 거듭 달지 않는다. 뒤의 다른 주장이나 특정 수치에 근거가 필요하면 그 대목에 각주를 단다. 각주에는 링크와 자료 제목·발행처를 적고, 특정 대목을 인용하면 페이지·절·표 번호·타임스탬프를 함께 남긴다. 판본·버전·발행 시점에 따라 의미가 달라지면 그 정보도 적는다. 같은 근거 대목을 다시 부를 때는 같은 각주를 재사용할 수 있다. 흔히 알려진 사실에는 출처를 억지로 붙이지 않고, 참조 표시는 뒷받침하는 주장 가까이에 둔다.
- 각주는 근거를 찾는 정보와 짧은 보충 설명을 담는다. 각주를 열지 않아도 본문의 주장과 필수 조건이 이해되어야 한다. 곁말에 필자의 반응이나 연상을 담을 수 있지만, 핵심 판단·반례를 각주로 밀어내거나 별도 논의를 길게 이어 가지 않는다. 도구 목록처럼 흐름에 부수적인 세부는 각주로 옮길 수 있지만, 사용법 글의 도구·버전·설정처럼 실행에 필요한 정보는 본문에 둔다. 인라인 각주와 이름을 붙인 각주는 작성 방식의 차이이며 사이트에서는 같은 번호 체계로 표시된다.
- 참고 자료(Clippings·Articles·Books)를 공개 글의 근거로 쓰면 원 출처를 연결하고, 내가 반응한 블록까지 이어야 하면 같은 각주에 그 블록 링크를 함께 둔다. 자료 자체를 기록하는 자료카드·참고노트는 해당 스킬의 `source`·자료 정보·인용 위치 형식을 따른다. 같은 원자료를 모든 문단의 각주에 반복하지 않는다.
- 본문과 각주에 넣지 못한 연결·자료는 마지막 절(`연관된 노트`, `참고 자료`, `출처`)에 둔다. 다음 읽을거리로 추천하는 블로그 글은 본문에 링크가 있어도 `연관된 글`에 둘 수 있다. `연관된 노트`와 `연관된 글`의 구분·중복 판단·선택적 설명은 속성 스키마의 연결 규칙을 따른다. `참고 자료`와 `출처`는 자료의 역할을 파악하는 데 필요한 설명을 남긴다.
- 공개 노트에서 비공개 노트로 가는 링크는 사이트에서 자물쇠나 일반 텍스트로 보여 공개 독자의 행선지가 되지 못한다. 원 출처가 없는 개인 기록·운영 문서·프로젝트 노트는 링크 없이도 문장이 통하게 쓰고, 링크는 vault 안의 연결이 필요할 때만 남긴다.

## 콜아웃과 그림

공개 폴더 노트의 Markdown 표시 방식은 사이트 [AUTHORING.md의 본문 문법](https://github.com/taez224/taez224.github.io/blob/main/AUTHORING.md#본문-문법)이 정본이다. 로컬 작업에서는 `../taez224.github.io/AUTHORING.md`를 읽는다. 이 절은 무엇을 언제 쓸지 정한다. 범용 `obsidian-markdown` 스킬은 문법 참고용이며, 사이트의 지원 범위나 편집 선택을 대신하지 않는다.

| 독자에게 필요한 역할 | 둘 곳 |
| --- | --- |
| 주장을 이해하는 데 필요한 정의·전제·한계·반례 | 해당 논지의 본문이나 헤딩 아래 |
| 행동하기 전에 알아야 할 데이터 손실 등 위험 | 해당 행동 바로 앞의 펼친 `[!warning]`. 제목에는 위험 대상을 적는다 |
| 선택할 수 있는 다른 방법이나 설정 | `[!tip]` |
| 건너뛰어도 본문을 이해할 수 있는 보충 설명 | 짧으면 본문 곁말이나 `[!note]`·`[!info]`, 길면 접힌 콜아웃 |
| 근거 자료의 식별 정보·짧은 곁말 | 각주 |

- 콜아웃은 본문과 구별해 읽을 이유가 있을 때 쓴다. 본문 알림이 두 개를 넘거나 연달아 나오면 역할이 겹치거나 본문이 잘게 끊기는지 다시 본다. 이는 과밀을 점검할 신호이며 개수 제한이 아니다. 단계마다 필요한 경고를 개수에 맞춰 합치거나 빼지 않는다. 접힌 로그·원문 인용은 읽지 않아도 본문을 따라갈 수 있는 보조 자료일 때 둔다.
- 구조나 자료의 성격을 표시하는 콜아웃은 해당 스킬·템플릿을 따른다. 발전시킬 질문, 글 카드, 비교, Quick Capture의 AI 해석, 참고노트의 요약·재구성한 예시가 여기에 해당한다. 콜아웃의 종류는 내용의 역할로 고르고 색이나 서체를 바꾸기 위해 고르지 않는다.
- 개인 사례가 일반 설명을 보충할 때는 내용에 맞는 제목의 `[!note]`로 구분할 수 있다. 경험 자체가 논지의 출발점이나 근거라면 본문에 둔다. `내 노트 정리에서는` 같은 제목은 해당 사례의 선택이지 글마다 되풀이할 고정 코너가 아니다.
- 접기는 선택해서 읽게 하는 표시이며 비공개 처리가 아니다. 템플릿의 작성 안내는 완성본에서 지우고, 독자에게 필요한 범위 설명은 본문으로 옮긴다. 공개할 내용과 작성 메모를 접힘 여부로 구분하지 않는다.
- 정보가 있는 그림의 대체 텍스트에는 그림이 전하는 내용을 적고, 복잡한 도식의 핵심 관계는 본문에서도 설명한다. 순수 장식은 빈 대체 텍스트로 둔다. 캡션은 이 글에서 그림을 읽는 방법이나 범위를 보완할 때 쓰며 모든 그림에 붙이지 않는다. 세부를 전부 나열하거나 대체 텍스트와 같은 문장을 반복하지 않는다. 문법은 사이트 안내, 판단 기준은 [W3C 이미지 안내](https://www.w3.org/WAI/tutorials/images/)를 참고한다. 논지를 운반하는 도식은 블로그 스킬의 `visual-argument-review`를 따른다.
- 같은 대상을 설정만 바꿔 견줄 때는 `[!compare]`·`[!compare-stacked]`를 쓴다. 본문 중간에서 다른 공개 글을 별도 영역으로 소개할 때는 `[!article]` 글 카드를 쓰고, 하단 `연관된 글`의 카드는 속성 스키마의 연결 규칙을 따른다. 문장에 필요한 링크만으로 충분하면 카드를 덧붙이지 않는다.
- 표는 같은 기준으로 대조할 값이 있을 때 쓴다. 긴 설명을 칸마다 채우거나 많은 열을 펼쳐야 하면 본문·목록·나눈 표가 더 읽기 쉬운지 검토한다. 모바일에서 비교 관계를 잃지 않는지는 실제 표시로 확인한다.

## 공개 화면 확인

- 공개 원고를 새로 쓰거나 표시 요소를 바꾸면 사용한 문법만 `AUTHORING.md`와 대조한다. 노트 임베드·수식·플러그인 문법은 Obsidian에서 보인다는 이유로 사이트에서도 같다고 가정하지 않는다. 비공개 링크와 임베드에 기대지 않고 본문을 이해할 수 있어야 한다.
- 사이트 발행 전 검수나 반영 요청에서는 미리보기로 바뀐 요소를 확인한다. 좁은 화면의 표·비교 도식, 각주의 열기·하단 이동·본문 복귀, 접힌 보충 자료, 이미지의 설명과 크기를 해당할 때 본다. 색을 직접 지정한 그림은 밝고 어두운 화면에서 확인한다. 같은 화면을 바꾸지 않았다면 매번 전체 검사를 반복하지 않는다.
- 제목·summary·썸네일이 목록·상세·공유 화면에서 맡는 역할을 대조한다. 속성에 적었다는 이유로 모든 화면에 같은 방식으로 표시된다고 가정하지 않는다. 표시 위치와 공개 범위는 사이트 안내를 따른다.
- 원문·코드 대조와 실제 화면 확인을 구분해 보고한다. 미리보기를 확인하지 못했으면 그 범위를 밝히고, Markdown이나 lint 검사만으로 사이트 표시까지 통과했다고 하지 않는다. 이 확인은 새 공개 승인·커밋·배포 권한을 뜻하지 않는다.

## 작업 목적과 AI의 역할

요청한 산출물과 현재 대화에서 드러난 목적을 함께 보고 AI가 맡을 범위를 정한다. 앞서 정한 목적은 유지한다. 사용자가 방향을 바꾸면 바뀐 부분만 조정한다. 다음 구분은 내부 판단에 쓰며 목적 선택 질문, 별도 계획서, 상태 속성을 추가하지 않는다.

| 목적 | AI가 맡을 일 | 사용자에게 남길 일 |
| --- | --- | --- |
| 생각 저장 | 원래 표현을 보존하며 저장·형식 처리 | 원래 생각과 감정. 설명·학습 과제를 요구하지 않음 |
| 이해 | 필요한 설명·예시·근거와 혼동한 부분의 확인 | 자기 설명을 시도하겠다고 한 부분. 설명 요청을 퀴즈로 바꾸지 않음 |
| 관점 발전 | 실제 근거, 다른 해석과 반례를 검토 재료로 제시 | 어떤 해석을 채택할지 판단. 소크라테스식 문답은 요청했을 때만 사용 |
| 글·노트 완성 | 요청한 범위의 구성·초안·문장 정리 | 자기 주장과 최종 채택. 새 주장을 사용자 생각으로 보태지 않음 |
| 직접 연습 | 사용자가 시도한 부분의 피드백과 필요한 도움 | 직접 쓰거나 구성하겠다고 한 부분. 완성안을 원하면 그 범위에서 제공 |

목적이 분명하지 않으면 해당 스킬의 기본 산출물까지 수행한다. 장기적으로 성장하고 싶다는 말이나 학습 주제를 다룬다는 이유만으로 작성 요청을 훈련으로 바꾸지 않는다. 확인은 빠진 정보 때문에 요청한 결과나 도움의 범위를 정할 수 없을 때만 필요한 만큼 한다. 이미 대화에서 확인한 내용을 다시 묻거나 목적 분류를 매번 보고하지 않는다.

이 구분은 해당 스킬의 저장·편집·승격 경계와 산출물 기본값 안에서 적용한다. 블로그 초안의 작성 조건(아웃라인 확정 뒤)이나 사용자 주장 채택 기준을 넓히지 않는다.

## 작성 전후 대조

집필과 검토는 사용자가 정한 목적·독자·설명 깊이를 기준으로 한다. 대화나 기존 집필 계약에서 확인한 내용은 그대로 사용한다. 리뷰에서 새 질문이 나왔거나 원고가 상세해졌다는 이유만으로 범위를 넓히거나 재승인을 요구하지 않는다. 새로운 사실 오류가 드러나면 해당 판단과 근거를 다시 확인한다.

새로 쓰거나 구성을 크게 바꿀 때는 집필 전에 이 기준과 [문장 견본](writing-samples.md), 해당 작성 스킬을 읽고, 이번 글의 중심·남길 구체적인 사례나 판단·덜어낼 내용을 짧게 정한다. 일반 규칙을 되풀이하지 않고 실제 편집 선택으로 적어 작업 중 기준으로 삼는다. 별도 계획 문서를 요구하지 않는다. 오탈자·국소 문구 수정에는 이 절차를 반복하지 않는다.

완료 전에는 작성자가 그 기준을 실제 제목·summary·본문·그림과 대조한다. 확인한 내용을 모두 옮겨 보고서가 되지 않았는지, 일반화하거나 줄이면서 누가 무엇을 했고 왜 골랐는지가 사라지지 않았는지 본다. 덧붙인 대비·요약·예외 문장도 읽는다. 실제 대립이 없는 대비, 앞 내용을 다시 결론 내리는 문장, 필요하지 않은 반론을 먼저 부정하는 문구는 덜고 필요한 조건은 직접 설명한다. 독자 점검에서 이해된다는 평가를 받아도 이 대조를 대신하지 못한다. 어긋난 부분을 고친 뒤 완료하며, 보고에는 적용한 편집 선택과 확인 범위를 짧게 남긴다.

수정 의견을 받으면 그 지적이 사실·주장의 채택·표현·배치 중 무엇을 바꾸는지 구분한다. 본문에서 빼야 한다는 이유만으로 관련 자료까지 삭제하거나, 자료가 유용하다는 이유로 본문 주장을 늘리지 않는다. 해당 판단만 다시 검토하고, 관련성이 남은 자료는 추가 읽을거리로 분리할 수 있다. 이 구분은 편집 판단에 사용하며 별도 분류표나 승인 절차를 만들지 않는다.

사용자가 직접 고친 문장에서 다음 글에도 참고할 선택이 드러나면 [문장 견본의 축적 기준](writing-samples.md#견본을-축적하고-사용하는-기준)을 따른다. 모든 수정을 수집하거나 선택 이유를 매번 묻지 않는다.
