# Jev 레이더의 읽기 묶음

기존 주간 레이더에 `comprehension_debt` 관심사의 연구 조건 분류와 읽기 묶음을 추가했다. `config.json`의 `reading.enabled`가 켜져 있으면 기존 실행 명령과 launchd 실행에서 함께 동작한다. 다른 관심사와 화제성 목록은 기존 흐름을 따른다.

## 입력과 결과

외부 API에는 이미 피드에서 수집한 공개 제목·초록만 보낸다. 저장 자료는 References의 `source` URL로 대조하며 비공개 요약·my_take·본문은 보내지 않는다. 기준 자료는 수집 기록에서 찾을 수 있는 저장·읽음·이미 앎 자료뿐이다. 볼트 전체의 근거 보유량을 나타내지 않는다.

- 연구 조건: 현업 개발자, 지연 측정, AI 없는 수행, 이해·역량 측정
- 조건별 결과: 명시됨 / 명시적 제외 / 모델 미확인 / 낮은 확신도 / 미분류. 미분류는 초록 없음·미실행·예산 제한·API 오류로 다시 나눈다
- 자료 유형: 실증 연구 / 적용 경험 / 해설 / 미확인
- 출력: `_workspace/radar/YYYY-MM-DD-reading.md`와 같은 이름의 JSON
- 원시 판단 캐시: `_workspace/radar/reading-cache/` (입력·모델·질문 해시별)
- 사용자 반응: `_workspace/radar/reading-feedback.jsonl` (로컬 전용)

같은 arXiv 논문의 버전·PDF·Hugging Face 주소와 동일 제목은 묶는다. 저장 카드의 저장 맥락에 소개글에서 원문을 저장했다고 명시된 GeekNews·Hacker News URL은 원문 URL의 별칭으로 연결한다. 임의의 인용 링크는 같은 자료로 취급하지 않는다. 다른 제목의 해설이 같은 연구를 다루는 경우까지 완전히 식별하지는 못하며, 제목 단어 중복은 순위 감점으로만 쓴다.

읽기 묶음은 관련성, 기준 자료에서 드문 조건, 묶음 내 조건·유형의 다양성, 제목 중복을 조합한다. 가중합은 정답 확률이 아니다. 기본 30분은 논문 15분·글 8분의 읽기 슬롯이며 원문 분량에서 측정한 독서 시간은 아니다. 기존 0.8 문턱 목록과는 같은 시간·개수 예산으로 비교한다. 낮은 점수 자료도 한 건 별도로 보여 누락을 확인한다.

## 실행

```sh
# 기존 수집부터 전체 실행
uv run --with typesafe-sdk --with feedparser python .agents/scripts/jev-radar/radar.py

# 이미 수집한 공개 자료로 추가 분류 및 묶음 생성
uv run --with typesafe-sdk --with feedparser python .agents/scripts/jev-radar/reading.py build --input _workspace/radar/2026-09-26.json --live

# 새 API 호출 없이 저장된 판정으로 재조합
uv run --with typesafe-sdk --with feedparser python .agents/scripts/jev-radar/reading.py build --input _workspace/radar/2026-09-26.json --minutes 30
```

독립 build는 기존 레이더의 shown 상태와 노트 파일을 바꾸지 않는다. 전체 레이더 실행은 제안 목록의 shown 이벤트만 남기며 읽음으로 처리하지 않는다. 추가 API 예산은 실행당 추정 상한 $0.05, 최대 60개다. 실제 사용량 비용을 별도로 기록한다. 실패하면 해당 자료의 조건은 미확인으로 남기고 기존 레이더는 계속 출력한다.

## 피드백

관심사 목록과 읽기 묶음 모두 같은 체크박스를 쓴다. 읽고 도움이 됐으면 체크하고, 링크가 있는 줄 끝에 `이미앎`·`관심밖`·`지금아님`을 적을 수 있다. 제목이나 URL 안의 단어는 반응으로 읽지 않는다. 체크 해제·표시 삭제는 해당 항목에서 기록한 이벤트만 취소하며, 별도 대화로 남긴 읽음·저장 기록은 유지한다. 반응을 바꿨다가 이전 반응으로 돌아가도 새 변경으로 반영한다. 단순 파일 재생성은 취소로 처리하지 않는다.

사용자는 결과 목록의 날짜·번호와 반응을 대화로 알려줄 수도 있다. 에이전트가 해당 날짜 JSON에서 URL을 확인한 뒤 아래 명령으로 기록한다. 상태를 추측해서 기록하지 않는다.

```sh
python3 .agents/scripts/jev-radar/reading.py feedback 'https://example.org/article' useful
```

| 반응 | action | 처리 |
| --- | --- | --- |
| 열어봄 | opened | 열람 기록만 저장 |
| 저장 | saved | 이후 묶음에서 제외. 도움 됨으로 학습하지 않음 |
| 읽음 | read | 이후 묶음에서 제외하고 기준 자료에 포함 |
| 도움 됨 | useful | 기준 자료와 긍정 반응에 포함 |
| 이미 앎 | already_known | 기준 자료에 포함. 관심 밖으로 학습하지 않음 |
| 지금은 아님 | not_now | 7일 동안 보류 |
| 관심 밖 | off_topic | 해당 URL 제외 및 부정 반응 |

가중치는 판정 캐시에 연결된 서로 다른 자료의 도움 됨·관심 밖 반응이 8개 이상일 때만 조정한다. 특징별 반응도 3개 이상 있어야 하며 변동 폭을 작게 제한한다. 클릭·저장·무응답은 학습 라벨이 아니다. 새로운 주간 자료에서 개선되는지 확인한 뒤 조정 폭을 바꾼다.

## 검증

```sh
python3 -m unittest discover -s .agents/scripts/jev-radar -p 'test_*.py' -v
```

테스트는 임시 폴더와 가짜 API 응답을 사용한다. 실제 외부 전송·사용자 피드백 기록은 하지 않는다. 추천의 유용성은 사용자가 실제로 읽고 남긴 반응으로 별도 확인해야 한다.

## 주장 연결과 체크박스 반응

`claims.py`가 맡는다. `config.json`의 `claim_links.enabled`가 켜져 있으면 주간 실행에서 함께 동작한다.

- 주장 연결: 관심사 절에서 초록이 200자 이상인 항목을 게시된(`origin/main`) Slipbox 영구 노트의 제목과 비교한다. 1단계는 주장마다 Noul로 "같은 현상을 다루는가"를 묻고, 0.7 이상인 주장 최대 2개에 대해 2단계 Choice로 초록의 가장 직접적인 문장을 고른다. 문장 확신도 0.5 이상만 목록에 `→ [[주장]] ← "문장"`으로 붙인다. 강화인지 반박인지는 묻지 않는다. 외부로는 공개 초록과 게시된 노트의 제목만 보낸다.
- 체크박스 반응: 관심사 절의 항목은 `- [ ]` 체크박스로 나온다. 읽고 도움이 된 글을 체크하면 `useful`, 줄 끝에 `이미앎`·`관심밖`·`지금아님`을 적으면 각각 `already_known`·`off_topic`·`not_now`로, 다음 실행 때 `reading-feedback.jsonl`에 기록한다. 각 파일·항목의 마지막 표시를 `checkbox-state.json`에 기록해 변화가 있을 때만 이벤트를 남긴다. 최근 4개 날짜의 주간 목록과 읽기 묶음을 함께 읽으며, 읽기 묶음을 단독 재생성하기 전에도 반응을 가져온다.
- 시험(2026-09-26): 저장한 논문 5편 중 4편이 맞는 주장·문장과 이어졌고, 대조군 3편 중 1편이 잘못 이어졌다. "좋은 기술은 불필요한 마찰을 줄인다"처럼 넓은 주장은 관련 없는 논문에도 붙기 쉽다.

## 관심 주제의 중심도

관심 점수(Noul)는 글이 그 주제를 다룬다고 얼마나 확신하는지를 말한다. 주제를 스쳐 언급한 글도 높게 나오므로, 점수가 `central.floor`(0.65) 이상인 관심 주제마다 중심도를 Score(스쳐 언급 0 / 부분 1 / 중심 2)로 한 번 더 묻는다. 제목과 초록만 보낸다.

- `apply: false`(시험): 선정은 기존 0.8 문턱 그대로 두고, 목록 줄에 `중심도 1.8 중심`처럼 표시만 붙인다. 문턱 아래지만 중심 주제로 판정된 글은 각 관심사 아래에 `promote_max`건까지 따로 보여 준다.
- `apply: true`: floor 이상에서 중심도 `minimum`(1.0) 미만을 빼고 중심도 순으로 고른다. 읽기 묶음도 스쳐 언급을 빼고 중심도를 기본 점수로 쓴다. 중심도 판정이 없는 글은 기존 기준으로 돌아간다.
- 관심사 절 안에서는 내 주장과 연결된 글을 먼저 보여 준다.

`apply`는 시험 표시에 반응이 쌓인 뒤 켠다. 스쳐 언급으로 표시된 글에 `관심밖`이 모이고 문턱 아래 중심 주제에 체크가 모이는지 본다. 설계 근거와 두 주 치 시험은 `_workspace/radar-score-test-2026-09-30/`에 있다.

## 안 읽은 자료카드와 본문 다시 판정

- `backlog.py`: `unread` 자료카드의 `source`에서 공개 텍스트를 새로 가져와(arXiv는 API, 영상은 제외, 나머지는 defuddle) 게시된 Slipbox 주장과 잇는다. 카드의 요약·`my_take`는 보내지 않는다. 긴 글은 2,500자 조각으로 나눠 판정하고 조각별 결과 중 가장 좋은 것을 남긴다. 순위는 여러 카드에 걸리는 넓은 주장의 무게를 낮추고, 같은 주장으로만 이어진 카드는 하나만 고른다. 원문(`backlog-cache/text-*`)과 판정(`links-*`)을 캐시하므로 매주 비용은 새 카드분만 든다. 가져오지 못한 원문은 30일 뒤 다시 시도한다.
- 본문 다시 판정(`fetch_full`): 요약이 한 줄뿐인 HBR은 모든 글의 본문을 가져와 판정한다. 2026-09-26에 30건을 비교해 보니, 본문으로 0.8을 넘은 5건의 한 줄 점수가 0.05~0.58이라 한 줄 점수로 거르면 놓쳤다. `floor`는 "관련 있음"이 아니라 "본문을 가져와 볼 만함"의 기준이다.
- defuddle은 설정 경로, nvm의 최신 Node부터 설치된 버전, PATH 순으로 찾고, 찾은 bin 폴더를 PATH 앞에 둬 같은 Node로 실행한다. Node를 올려도 설정을 고칠 필요가 없다. Medium 태그 피드는 요약이 짧고 본문이 막혀 2026-09-26에 뺐다(`config.json`의 `removed_sources`).

## 요즘 관심사

`topics.py`가 맡고, 관심사는 `_workspace/radar/관심사.md`에서 읽는다. 한 줄 형식은 `- 이름 | 설명 | 검색어: 단어, 단어`이다. 코드나 설정에 주제를 적지 않는다.

- 후보: 이번 주 수집 자료 중 검색어가 든 글, 그리고 관심사별 HN(5점 이상)·arXiv·GitHub(별 5개 이상, 이번 주 생성) 검색 결과. 이미 보여 준 글은 뺀다. GitHub 검색은 인증 없는 한도(분당 10회) 때문에 7초 간격을 둔다.
- 판정: Jev에 "정말 이 주제인가"(동음이의어 거르기)와 "실제로 만들거나 적용한 사례인가"만 묻는다. 둘 다 0.7 기준.
- 순위: 활용 사례와 소식·논의로 나누고, 출처마다 따로 화제성(HN 점수·GitHub 별) 상위 3건을 뽑는다. 점수의 크기가 출처마다 달라 한 순위표에 섞지 않는다.
- 목록 맨 위에 나오며, 항목은 다른 절처럼 체크박스로 반응을 남길 수 있다.

## 관심사 후보

`suggest.py`가 맡는다. 외부 호출 없이 로컬에서 센다. 최근 14일에 만든 DevLog·Inbox·자료카드·일일 노트에 두 번 이상 나왔지만 그 전 노트에는 드물었던 영문 이름을 목록의 "관심사 후보" 절에 근거(폴더별 노트 수)와 함께 보여 준다. 관심사 노트에 이미 있는 이름·검색어, `## 제외` 절의 이름, 레이더 출처 이름(레이더 작업을 적은 DevLog에서 생기는 잡음)은 뺀다. 한국어 이름은 형태소 분석 없이 세기 어려워 세지 않는다. 채택은 사람이 `관심사.md`에 한 줄을 옮겨서 한다.

## 한 화면 목록

`compose.py`가 맡는다. 레이더는 지금까지의 목록을 `YYYY-MM-DD-전체.md`에 쓰고, 그 목록에서 훑어볼 항목만 추려 `YYYY-MM-DD.md`를 만든다. 요즘 관심사는 활용 사례를 출처마다 한 건씩 최대 2건과 소식 1건, 화제는 HN AI 글 10건, 관심 질문은 점수순 4건, 믿고 보는 저자는 2건이다.

- 짝 후보(↔): 고른 글의 원문을 2,500자 조각으로 나눠 게시된 주장과 잇고, 안 읽은 자료카드와 참고노트 중 같은 주장에 닿은 것을 붙인다. 여러 자료에 걸리는 넓은 주장은 무게를 낮추고 저장 자료 하나는 한 번만 쓴다. 같은 현상을 다룬다는 연결은 단서일 뿐이라, 결론 대신 "어디서 다르게 볼까?"라는 질문으로 보인다.
- 함께 읽기: Claude가 같이 읽을 질문과 읽을 대목을 준비한 묶음을 `YYYY-MM-DD-함께읽기.md`에 두면 맨 위에 넣는다. 거기 쓴 글과 저장 자료는 훑어보기와 짝 후보에서 뺀다.
- 체크박스는 원문 하나에만 둔다. 체크는 "읽고 도움이 됐다"는 뜻이다. `-전체.md`의 체크박스도 반응으로 기록한다.
- 시험한 뒤 뺀 것: 짝의 관계(반대 결과·조건·구체 사례·같은 말)를 Choice로 묻는 단계. 이번 질문과 선택지에서는 거의 모두 "구체 사례"로 나왔다.
