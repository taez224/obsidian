# Review Zettelkasten

포착된 메모와 참고 자료를 다시 읽어 생각으로 발전시키는 의미 기반 정원 관리 workflow다. `vault-lint`의 기계적 헬스 검사와 역할을 분리한다.

## 원칙

1. **자동 적용하지 않는다.** 먼저 후보와 이유를 제시하고 승인된 변경만 수행한다.
2. **전문을 옮기지 않는다.** Resources의 책·아티클·클리핑은 참고노트로 유지하고, 재사용할 자기 주장만 별도 permanent note로 압축한다.
3. **새 파일보다 기존 생각의 성장을 우선한다.** 같은 주장이 있으면 합치거나 보강한다.
4. **관계를 설명할 수 있는 노트를 연결한다.** 설명을 실제로 덧붙일지는 `99_Templates/_property-schema.md`의 Slipbox 연결 규칙을 따른다.
5. **원자성은 수단이다.** 독립적으로 재사용할 수 있을 때만 분리하고, 한 생각을 템플릿에 맞추려고 쪼개지 않는다.

## 1. 검토 범위 정하기

요청에 따라 다음 세 모드 중 하나로 처리한다.

| 모드 | 시작 조건과 적용 절 |
| --- | --- |
| 기본 검토 | 메모·참고자료에서 발전시킬 생각을 찾는 요청. 2~6절을 모두 적용한다 |
| 관심사 기반 재독 | 관심 주제의 기존 Slipbox를 다시 읽으며 생각을 잇는 요청. 입력이 이미 permanent note이므로 2절을 건너뛰고 3~6절을 적용하며, 제안은 `새 영구 노트`·`기존 노트 보강`·`연결 추가`·`보류`로 한정한다 |
| 연결 재점검 | 생각·개발 노트와 블로그의 연결을 갱신하는 요청. 아래 절차와 4~6절을 적용하고 `연결 추가`·`연결 제거`·`연결 재배치`·`보류`를 제안한다. 병합·분리·구조 노트는 사용자가 검토 범위에 포함했을 때만 다룬다 |

**관심사 기반 재독**은 사용자가 지정한 MOC 또는 permanent note에서 시작해 관계가 분명한 기존 permanent note만 함께 읽는다. 아무 후보도 억지로 만들지 않는다.

**연결 재점검**은 새로 생기거나 내용이 바뀐 노트에서 출발한다. 매번 전체 노트를 다시 읽지 않는다.

- 사용자가 지정한 파일·주제·기준 날짜·기준 커밋이나 대화에서 이미 정한 범위를 사용한다. 변경 기준이 없고 출발 노트도 정해지지 않았다면 기준만 확인한다. Git 이력·diff와 미추적 파일을 함께 살피고, `created`·`updated`나 파일 수정 시각만으로 변경 목록을 확정하지 않는다. 이력으로 확인할 수 없는 범위는 밝힌다.
- 기본 대조 범위는 `01_Slipbox/`, `30_Resources/Development/Concepts/`·`Troubleshooting/`·`Tools/`, `20_Projects/blog/`의 원고와 관련 허브다. DevLog·아웃라인·관리 문서는 연결 후보에서 제외한다. 사용자가 범위를 좁혔다면 그 범위를 우선한다.
- 변경 노트의 핵심 주장·사례와 기존 링크를 읽고 4절의 검색으로 관련 기존 노트만 함께 읽는다. 변경 노트에서 기존 노트로 갈 연결과 기존 노트에서 변경 노트로 갈 연결을 모두 살피되, 서로 링크를 달기 위해 역방향 링크를 만들지는 않는다. 변경량이 많으면 주제별로 나누고 검토한 범위와 남은 범위를 구분한다.
- 본문 링크와 하단 `연관된 노트`·`연관된 글`을 함께 본다. 관계가 약해졌거나 대상이 바뀐 링크, 같은 역할의 중복, 본문으로 옮길 연결, 이어 읽을 블로그를 구분한다. 배치·중복·선택적 설명은 속성 스키마의 연결 규칙을 따르고, 제거·이동 시 별도 설명이나 특정 절·블록으로 가는 기능을 잃지 않는지 확인한다.
- 공개 노트의 `연관된 글` 추천은 `status: published`인 블로그를 대상으로 한다. 제출했더라도 `draft`이면 보류하고, 발행 상태나 공개 범위를 링크 작업에 맞춰 바꾸지 않는다. 초안 원고 자체의 본문 연결은 검토할 수 있다.

읽으면서 함께 확인할 것은 다음과 같다.

- 허브 미등록 목록은 `vault-lint` 스캐너의 `hub_gaps`를 쓰되, 허브 원칙상 싣지 않을 노트도 있으므로 목록 자체를 결함으로 보지 않는다.
- 태그 순서는 `99_Templates/_property-schema.md`의 태그 사용 기준으로 확인한다.

사용자가 기존 주장을 바로 정리하기보다 질문을 주고받으며 검토하고 싶어 하면 먼저 `socratic-dialogue`를 사용한다. 문답 중 사용자가 확인한 결과만 이 스킬의 승격·보강·연결 후보로 가져온다.

기본 검토는 사용자가 파일이나 폴더를 지정하면 그 범위만 본다. 범위가 없으면 다음 순서로 제안한다.

1. `00_Inbox/_inbox.base`의 7일 이상 체류 노트
2. 사용자가 최근 읽은 Books·Articles와 `status: read`인 Clippings
3. `01_Slipbox/_index.base`의 "기록된 재사용이 있는 seedling" 뷰. 연결이 약한 노트는 `vault-lint`의 고립 노트 점검으로 확인한다

소규모 검토는 대화에서 처리한다. 후보가 6개 이상이면 `_workspace/zettelkasten-review-YYYY-MM-DD/report.md`에 임시 리포트를 만들고 `_workspace/README.md`의 수명 정책을 따른다. 삭제는 승인 후 수동으로 한다.

## 2. 각 노트의 역할 판정하기

| 입력 | 기본 위치 | 판정 기준 |
| --- | --- | --- |
| 순간적인 개인 생각 | `00_Inbox/` | 아직 맥락이 부족하면 유지, 가치가 없으면 삭제, 재사용 가능한 주장이 생기면 승격 |
| 책 전체 독서 기록 | `30_Resources/References/Books/` | 책 메타정보·인용·읽으며 든 생각을 유지하고 permanent note 후보만 추출 |
| 아티클·클리핑 | `30_Resources/References/Articles/` 또는 `Clippings/` | 단순 요약은 Resources에 남기고 `my_take`와 독립 주장 여부를 확인 |
| 프로젝트에만 필요한 메모 | `20_Projects/<project>/` 또는 프로젝트 링크 | 일반화할 학습이 있을 때만 별도 permanent note 생성 |
| 자기 완결적 주장 | `01_Slipbox/` | 새 permanent note 또는 기존 노트 보강 |
| 링크 군집의 안내도 | `01_Slipbox/`의 `type: hub` | 서로 다른 permanent note 3개 이상을 하나의 질문이나 글감으로 반복해 찾을 때만 생성한다. 태그나 수량만으로 만들지 않고, 그 전에는 기존 링크와 Backlinks를 쓴다 |

## 3. 생각 후보 추출하기

각 입력에서 다음을 구분한다.

- 원자료가 말한 사실·주장
- 사용자가 동의하거나 반박한 부분
- 기존 경험과 연결한 해석
- 다른 글에서도 재사용할 수 있는 독립 주장

사용자의 해석이 없는 외부 요약을 permanent note로 승격하지 않는다. 사용자에게 관점을 묻거나 AI가 `my_take` 후보를 제안할 수는 있지만, 사용자가 명시적으로 채택한 뒤에만 참고노트에 기록한다. 독서 메모 보강도 같은 승인 경계를 따른다.

Quick Capture의 `AI 생성`은 `AGENTS.md`의 핵심 경계대로 사용자의 주장으로 쓰지 않는다. 그 안의 외부 사실·인용은 출처를 확인한 뒤 참고자료나 발전시킬 질문 후보로만 제안한다.

## 4. 정확 검색과 의미 검색으로 기존 생각과 대조하기

검색 실행 방식은 `qmd` 스킬을 따른다. 영구 노트 발전 후보는 `01_Slipbox/`를 중심으로 대조하고, 연결 재점검은 1절의 생각·개발 노트·블로그 범위를 함께 검색한다. 후보마다 찾는 것은 **같은 주장, 이어지는 주장, 반대되는 주장**이며, 단순한 주제 일치보다 실제 주장 관계를 우선한다. QMD 결과가 현재 파일과 다르면 현재 원문을 기준으로 판단한다.

`rg` 후보와 QMD 후보를 병합한 뒤, 상위 후보 원문을 가져와 읽고 기본 검토에서는 다음처럼 분류한다. 앞의 다섯은 `30_Resources/Obsidian 운영 워크플로.md`의 주간 결정과 같은 말이고, 이 분류가 5절 표의 `제안`이 된다. 연결 재점검의 제안은 1절의 연결 분류를 사용한다.

- `삭제`: 다시 쓸 정보나 생각이 없음
- `Resources 보관`: 출처 맥락을 벗어나면 의미가 약해 참고노트로 남김
- `프로젝트 흡수`: 프로젝트에만 필요하고 일반화할 학습이 없음
- `새 영구 노트`: 독립적이고 기존 노트에 없는 주장
- `기존 노트 보강`: 결론이 같고 새 사례·반례·근거가 있음. 운영 워크플로에서는 "기존 permanent note에 합치기"다
- `연결 추가`: 서로 다른 주장이지만 관계가 명확함
- `보류`: 사용자의 해석이 더 필요함. 재사용됐지만 `seedling`인 노트처럼 다시 읽을 후보도 여기에 둔다

## 5. 승인 제안하기

병합·분리가 검토 범위에 포함되면 노트의 경계를 먼저 판단하고, 그 결과에 맞춰 링크를 배치한다.

- 같은 질문에 같은 답을 반복하면 한 정본에 모을 후보로 제안한다. 파일 전체 병합과 반복 문단만 기존 노트에 모으는 안을 구분한다.
- 주제가 같아도 질문·대상·적용 조건이 다르면 각각 유지한다. 분리는 원칙 3·5를 따른다.
- 분리·병합 후보에는 옮길 내용, 원본에 남길 주장·사례·출처, 영향을 받는 링크를 함께 적는다. 공개 독자의 이해에 필요한 설명은 `permanent-note`의 독립성 기준으로 확인한다.

다음 형식으로 묶어 제안한다.

| 원본 | 제안 | 대상 또는 제목 | 이유 | 원본 처리 |
| --- | --- | --- | --- | --- |
| `<path>` | 모드별 분류 또는 승인된 범위의 병합 / 분리 / 구조 노트 | `<note>` | 한 줄 | 유지 / 삭제 후보 / Resources 보관 |

새 영구 노트나 내용 보강 후보에는 제목과 핵심 주장 초안도 함께 보여준다. 연결만 바꾸는 후보는 원본 위치·추가/제거/재배치·대상·이유를 적고 본문 표현 변경은 최소화한다. 후보가 없으면 없다고 보고한다. 적용 전에는 파일을 만들거나 옮기거나 삭제하지 않는다.

## 6. 승인된 항목 적용하기

- 새 영구 노트와 기존 노트 보강은 `permanent-note`의 작성 원칙과 `99_Templates/_property-schema.md`를 따른다.
- Books·Articles·Clippings 원본은 유지한다. 출처와 블록·헤딩 링크는 `permanent-note`의 「연결과 출처」를 따른다.
- Inbox 원본은 승격 후에도 자동 삭제하지 않는다. 승인 항목에 원본 처리가 포함된 경우에만 삭제하거나 보관한다.
- `Resources 보관`은 참고노트로 남기는 결정이다. Inbox 메모는 `next_action: archive-resources`로 표시하고, 실제 이동 위치는 승인 항목에서 정한다.
- `프로젝트 흡수`는 프로젝트 하위 노트나 허브에 반영하는 결정이다. Inbox 메모는 `next_action: link-project/<id>`로 표시한다. 허브의 현재 상태와 다음 행동은 `sweep-project-context`가 맡고, 하위 노트 형식은 `99_Templates/_property-schema.md`의 프로젝트 하위 노트 절을 따른다.
- 병합·분리는 승인된 표에 적은 옮길 내용, 남길 주장·출처, 영향을 받는 링크대로 적용한다. 옛 노트의 `aliases`와 `used_in`은 남기는 노트로 옮기고, 제목·파일명 변경과 공개 URL 보존은 `permanent-note`의 원본 처리 절을 따른다. 삭제되는 파일은 별도로 승인받는다.
- 링크 위치와 `## 연관된 노트`·`## 연관된 글`의 구분은 원칙 4의 속성 스키마 연결 규칙을 따른다. 노트 목록 형식은 `99_Templates/slipbox-template.md`를 참고한다.
- `growing`과 `evergreen`은 사용자만 정하며, 길이·링크 수·AI 보강·재사용만으로 올리지 않는다. 재사용된 노트는 다시 읽을 후보로만 제안한다. 정의는 `99_Templates/_property-schema.md`의 Slipbox 절을 따른다.
- 구조 노트는 설명문을 억지로 채우지 않고 링크 군집과 탐색 순서를 중심으로 작성한다.
  형식은 `99_Templates/hub-note.md`를 따른다 (frontmatter `type: hub`).
  새 공개 허브에는 속성 스키마에 맞는 `slug`를 작성하고, 기존 허브를 수정할 때는 발행된 slug를 유지한다.
- 적용 후 QMD 수동 갱신은 사용자가 함께 요청했을 때만 실행한다. 대규모 변경이어도 요청이 없으면 post-commit hook에 맡긴다.

완료 보고와 검토 리포트에서는 `적용 완료`, `미적용`, `보류`를 구분한다. 미적용 항목은 승인 대기인지, 승인됐지만 아직 실행하지 못했는지, 사용자가 제외했는지와 이유를 적는다. 적용된 항목을 다시 후보로 안내하지 않으며, 후속 요청에서는 현재 파일과 적용 기록을 확인한다.

## Vault-lint와의 경계

- `vault-lint`: 죽은 링크, frontmatter, 고립 노트, 허브 미등록(`hub_gaps`) 같은 기계적 상태 점검
- `review-zettelkasten`: 메모의 의미를 읽고 승격·병합·발전·구조화를 판단

두 작업을 함께 요청받으면 `vault-lint`로 상태를 확인한 뒤 이 스킬로 의미 판단을 수행한다.
