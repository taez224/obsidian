# 독자 시점 점검

작성자의 맥락을 모르는 독자가 글의 핵심을 이해할 수 있는지, 그 과정에 목적과 무관한 학습 부담이 끼어 있는지 검토한다. 장르별 작성 스킬의 규칙을 대신하지 않는다.

## 두 가지 쓰임

| 쓰임 | 따를 절 |
| --- | --- |
| 사용자가 독자 시점 점검을 요청 | 범위와 기준, 검토 순서, 보고. 이 세션에서 그 글을 쓰거나 고쳤다면 첫 읽기를 독립 독자 점검으로 대신한다 |
| 작성 스킬이 완성 초안의 점검을 요구 | 범위와 기준, 독립 독자 점검, 지적 처리 |

## 범위와 기준

- 독자가 받아들인 중심 생각을 제목, `summary`, 도입이 약속하는 내용과 대조한다. 주 에이전트는 이 약속 자체도 사용자가 정한 목적·독자·설명 깊이와 맞는지 확인한다. 독자가 현재 원고를 이해했다는 사실만으로 원래 집필 목적에 맞는다고 판단하지 않는다.
- 개발 노트, 블로그, 영구 노트의 장르·독자·종결체·헤딩 기준은 해당 작성 스킬과 공통 글쓰기 기준을 따른다. 필요한 기준만 읽고 다시 정의하지 않는다.
- `summary`는 [속성 스키마](../../../99_Templates/_property-schema.md)의 노트 유형별 역할로 읽는다. 블로그는 제목과 소개문을 함께 보고 주제·범위를 짐작할 수 있는지, 그 약속이 본문과 맞는지 확인한다. 판정 기준은 「블로그 summary 작성 기준」을 따른다.
- 읽는 동안에는 초안에 없는 작성 맥락이나 다른 노트로 빈 부분을 메우지 않는다. 외부 출처의 사실 확인은 요청되었거나 장르 스킬이 요구할 때 별도로 수행한다. 확인하지 않은 내용은 독자 이해의 문제와 사실 확인의 문제를 구분해 보고한다.
- 독자가 누구인지 요청과 장르에서 추론할 수 있으면 진행한다. 독자에 따라 결론이 달라지는데 추론할 수 없을 때만 확인한다.
- 사용자의 검토 요청은 파일 편집을 허용하지 않는다. 수정 요청이 있으면 지정된 범위만 고치고, 작성자의 표현·유보·생각의 흐름을 보존한다.

## 검토 순서

1. **첫 읽기:** 링크나 툴팁에 기대지 않고 글 전체를 읽어, 독자가 얻는 핵심과 전개를 짧게 적는다. 이미 정한 목적·독자·설명 깊이를 기준으로 삼고, 기준이 없으면 제목·도입·요청에서 추론한다.
2. **설명 범위와 구조:** 문단·예시·코드·도식이 글의 목적에 어떤 역할을 하는지 본다. 새로운 용어·타입·구조·절차를 빼거나 더 직접적인 형태로 바꿔도 목적 달성에 지장이 없는지 먼저 따진다. 역할이 약하면 설명을 보태기 전에 제외·교체·보충 자료 이동을 검토한다. 낯설거나 길다는 이유만으로 필요한 개념·조건을 덜어내지는 않는다. 문단 연결, 근거와 주장의 관계, 마무리를 살피며 모든 글에 도입·요약·교훈을 강제하지 않는다.
3. **이해:** 정의가 예시의 한 속성으로 개념을 좁히거나 넓히지 않는지 본다. 새 이름·사례·코드의 역할과 필요한 전제가 본문·헤딩·코드에서 드러나는지 확인한다. 지시 대상·주체·인과·대조와 제목이 약속한 내용도 대조한다. 연결은 의미 관계로 판단하며 연결어를 억지로 넣지 않는다.
4. **표현:** 남길 내용에 필요한 약어·관용 표현만 풀어 쓴다. 표준 기술 용어는 유지하고, 문장 수정은 이해를 막거나 논지를 흐리는 곳에 집중한다.

## 독립 독자 점검

- 작성자는 자기 맥락을 알고 있어서 자기 글의 막힌 곳을 스스로 찾기 어렵다. 이 세션에서 초안을 쓰거나 고친 에이전트가 직접 읽는 점검은 이 한계를 넘지 못하므로 읽기 전용 하위 에이전트에게 맡긴다. 이미 있는 글을 처음 읽는 상태로 점검해 달라는 요청은 주 에이전트가 직접 읽어도 된다.
- 하위 에이전트에는 읽을 범위와 목적·독자·설명 깊이만 전한다. 기준은 요청과 작성 스킬에서 가져오며, 작성자의 배경이나 원하는 수정안은 주지 않는다.

  ```text
  <대상 파일 경로> 하나를 처음부터 끝까지 읽어라. 다른 파일, 검색, 웹은 쓰지 않고 파일도 고치지 않는다.
  너는 <예상 독자>이고, 이 글이 속한 저장소나 작성자의 사정은 모른다.
  검토 기준은 <글의 목적과 설명 깊이>다.
  다음을 보고하라. 지적마다 원문을 인용하고 이유와 최소 조정을 적어라.
  1. 독자가 얻는 핵심
  2. 목적에 비해 불필요하게 배워야 하는 내용과, 빼거나 바꿔도 목적 달성에 지장이 없는 이유
  3. 남길 내용에서 이해가 막힌 곳과 빠진 연결. 문제를 억지로 만들지 않는다.
  ```

- 하위 에이전트를 쓸 수 없으면 주 에이전트가 읽되 자체 검토였다고 밝히고, 독립 점검을 생략했다고 알린다. 독립된 외부 독자가 실제로 읽은 것처럼 가장하지 않는다.
- 독립 독자 점검은 기본 한 번으로 한다. 큰 수정으로 흐름이 달라졌거나 새 문제가 드러났으면 해당 범위를 다시 점검할 수 있다. 같은 취향이나 이미 해소한 지적을 이유로 전체 점검을 반복하지 않는다.

## 지적 처리

작성 스킬이 부른 점검에서 주 에이전트가 하위 에이전트의 보고를 반영할 때의 기준이다.

- 수정 후보는 [공통 글쓰기 기준의 작성 전후 대조](../../guides/writing.md#작성-전후-대조)를 따른다. 후속 질문에도 같은 목적·깊이를 적용하며, 후보가 불필요한 대비·타입·설명을 추가하거나 다른 절과 겹치지 않는지 다시 본다.
- 이해가 막혔다는 이유만으로 정의·구현을 추가하지 않는다. 목적에 필요한 내용의 연결만 보완하고, 불필요한 학습 부담은 검토 순서 2번으로 처리한다. 본문에서 덜어낼 내용과 원본 자료·구현에 필요한 내용을 구분한다.
- 새 후보가 원문보다 낫다는 근거가 없으면 유지한다. 객관적 오류와 선택적 편집은 구분하며, 작성자의 판단을 수정 명령으로 대신하지 않는다.
- 독자 이해의 판정과 작성자의 목적·문체 대조를 구분한다. 완료 보고는 실제로 점검한 범위만 밝힌다.

## 보고

- 기본 보고에는 독자가 얻는 핵심, 목적에 비해 과한 설명·구조, 필요한 이해의 연결을 담는다. 지적이 없으면 점검한 축과 남긴 이유를 말하며, 이를 문체·사실·발행 준비까지의 종합 통과로 보고하지 않는다.
- 지적마다 위치·원문, 이해를 막거나 불필요한 학습을 요구하는 이유, 최소 조정을 제시한다. 객관적 오류·목적상 불필요한 부담·취향에 따른 개선을 구분한다.
- 기본 검토에서는 작동하는 문장을 모두 나열하지 않는다. 문장을 하나씩 빠짐없이 점검하는 요청은 `.agents/skills/sentence-audit/SKILL.md`를 따른다.
- 글 전체를 대신 다시 쓰지 않는다. 구체적인 문구 대안은 문제가 있는 곳에만 제안하고, 추가 교훈·생각거리·링크를 억지로 만들지 않는다.

스킬을 보완할 때는 [독자 점검 평가](evals/cases.md)를 참고한다. 일반 점검에서는 평가 자료를 읽지 않는다.
