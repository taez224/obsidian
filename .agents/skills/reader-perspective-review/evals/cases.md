# 독자 점검 행동 평가

스킬 보완 때만 읽는다. [cases.json](cases.json)의 자료는 모두 합성 사례이며 실제 경험·실행 근거로 인용하지 않는다.

| ID | 확인할 행동 |
| --- | --- |
| selection-rule-and-incidental-types | 채널 선택 기준이 중심 생각임을 읽고, 래퍼·로그·응답 타입을 배우는 부담이 그 목적에 기여하지 않는다는 지적을 한다. |
| heading-and-evidence-boundary | 성공·실패가 하나씩인 결과로 동일 상태 항목의 순서 보존까지 확인했다고 확대한 주장을 찾는다. 확인된 실패 우선 결과로 한정하거나 추가 예시를 별도 제안하며, 새 결과를 이미 관측한 것처럼 쓰지 않는다. |
| necessary-extension-and-clear-flow | ChannelSelector와 PrioritySelector가 앱의 선택 호출 지점을 보여 주므로 필요함을 인정한다. 낯선 타입이라는 이유만으로 없애거나 조건만 남기지 않는다. |

보완한 스킬만 실행한 점검은 단일 버전 관찰로 보고한다. 개선 효과를 비교할 때는 변경 전이나 스킬 없는 기준선도 같은 조건으로 실행한다.

실행 격리·변경 전후 비교·통과/실패/보류·중복 결함 처리는 [공통 평가 절차](../../taez-insight-blog-writer/evals/cases.md)를 따른다. 실행자에게는 스킬·요청·원자료만 주고 판정 기준과 기대 결함은 숨긴다.

- 각 result_check를 별도로 판정하고, 필요한 문제의 발견과 정상 내용의 보존을 나누어 집계한다. 수정 개수나 예상 문구와의 일치로 채점하지 않는다.
- 정상 사례의 선택적 윤문은 허용한다. 근거 없는 오류 판정, 의미·조건 변경, 추가 구현·확인 요구를 과잉 수정으로 본다.
- 문장/문단 목록과 형식 검사는 검토 범위 확인용이며 판단 품질의 증거가 아니다. 실제 응답을 기준으로 판정한다.
- 실행 결과는 `_workspace/`에 두고, 이 폴더에는 입력과 기준만 보관한다.
