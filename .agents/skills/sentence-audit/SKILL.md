# 문장 전수점검

노트나 글의 문장을 하나씩 읽고, 고칠 문장마다 바로 적용할 수 있는 완성안을 낸다. 문체 기준은 `.agents/guides/writing.md`와 그곳이 가리키는 fluent-korean이 정본이다. 이 스킬은 그 기준을 문장 단위로 적용하는 절차만 정한다.

## 준비

- 대상 파일 전체를 먼저 읽는다. 제목, `summary`, 헤딩, 표 셀, 이미지 캡션, 콜아웃 본문, 다이어그램의 독자용 문구도 대상이다. 코드 식별자, 원문 인용, 수치 데이터는 윤문 대상에서 제외한다.
- `summary`는 [속성 스키마](../../../99_Templates/_property-schema.md)의 노트 유형별 역할에 맞춰 점검한다. 블로그의 소개형 표현은 문장 끝 동사보다 구체성과 본문과의 일치로 판단한다. 화면에서 잘리는 문제는 문체 문제와 구분하며, 첫 문장만 표시되는 구현에 맞추려고 원고를 축약하지 않는다.
- 읽으면서 두 가지를 메모한다. 노트가 같은 대상을 부르는 낱말(예: 한 곳은 "후보", 다른 곳은 "목록"), 그리고 본문이 실제로 한 행동과 그 순서다.
- 각 문장을 유지·수정 후보·근거 확인 필요 중 하나로 판단한다. 같은 행에 문장이 여러 개면 문장별로 구분한다. 앞서 에이전트가 고친 문장도 새 점검에서 제외하지 않는다.
- 종결체와 독자는 해당 장르 스킬을 따른다. 개발 노트는 평어체다.
- 하위 에이전트에게 맡길 때는 4번의 읽기 방법을 지시하고, 금지 표현 목록을 대조 기준으로 주지 않는다. 이미 정한 용어·이름·구성은 다시 제안하지 않도록 함께 전한다.

## 문장마다 대조할 네 가지

1. **한 일을 정확히 말하는가.** 동사가 실제 행동과 맞는지 본다. "고르다"와 "거르다", "적용하다"와 "분류하다"처럼 뜻이 가까운 말 가운데 본문의 행동에 맞는 쪽을 쓴다. "~에 적용해 봤다"처럼 무엇을 했는지 숨기는 동사는 구체적인 동사로 바꾼다.
2. **용어가 자연스럽고 일관되는가.** 원어의 뜻과 맞거나 본문에서 반복된다는 이유만으로 자연스러운 표현으로 보지 않는다. 이 글의 독자가 실제로 같은 대상을 이렇게 부를지 살피고, 번역한 분류명·UI 이름은 실제 가리키는 대상과 대조한다. 통용되는 기술 용어와 코드 식별자는 유지한다. 같은 대상은 노트 전체에서 같은 말로 부르고, 앞 절의 말을 뒤 절이 받아야 흐름이 보인다. 표기가 섞여 있으면 정착된 번역어나 음차로, 없으면 원어나 API 이름으로 맞춘다. 통일하려고 새 번역어를 만들지 않는다.
3. **주어, 시제, 대응이 맞는가.** 누가 무엇을 했는지 확인한다. 서로 다른 주체가 판정하고 실행하는 일을 한 주어에 묶거나, 대상 자체와 그 대상의 값·상태를 혼동하지 않는다("종류가 기준을 넘었다"와 "확신도가 기준을 넘었다"). 주어가 빠지거나 엉뚱한 명사가 주어처럼 읽히는 곳("~라고 밝힌다"의 주어가 제품이 되는 경우), 한 문단 안에서 시제가 섞이는 곳, 경험을 말하다 일반 권고("~하는 것이 좋다")로 바뀌는 곳, "하나씩"처럼 개수가 맞지 않는 짝을 찾는다. 어디에 넣었는지, 무엇이 동작하는지 같은 성분을 독자가 작성자의 맥락으로 보충해야 하는지도 본다. "대신", "반면", "그래서" 같은 연결어는 두 절의 관계를 주장하므로 그 관계가 실제로 성립하는지 확인한다. 성립하지 않으면 연결어를 맞추려고 없는 장점이나 원인을 끌어들이지 말고, 두 사실을 나란히 적는다.
4. **번역투, AI투, 상투어가 없는가.** 공통 글쓰기 기준의 읽기 방법을 문장마다 적용한다. 말로 설명하듯 읽고 영어로 되돌려 보며, 익숙해서 놓친 구나 문장 구조도 검토 후보로 찾는다. 대응하는 표현을 찾는 일과 고칠지 판단하는 일을 구분하고, 수정 여부는 한국어 문맥과 더 자연스러운 대안으로 정한다. 피동("평가되어", "전달되므로"), 영어 형용사 직역("과신하고 일관되지 않다"), "~것이 목표", "해당 ~", "구조화된 ~" 같은 명사구, 굳지 않은 문어("쓸모가 있는가"), 흔한 수식("쏟아지는")은 방향을 보여 주는 예다. 예에 없다는 이유로 통과시키지 않고, 예에 있다는 이유만으로 고치지 않는다. 번역투는 문장 구조의 문제이며, 기술 용어를 우리말로 옮기라는 뜻이 아니다. 용어는 2번 기준을 따른다.

고치면서 수치나 사실을 새로 넣어야 하면 `_workspace`, 실행 기록, Git 이력에서 근거를 먼저 찾는다. 기록이 없으면 추측으로 채우지 않고 사용자에게 묻는다.

## 추천안 쓰기

- 고칠 문장마다 **완성된 추천안 하나**를 낸다. 어색한 곳만 고친 최소 수정안을 먼저 내고 다시 묻게 만들지 않는다. 트레이드오프가 실제로 다를 때만 둘째 안을 둔다.
- 추천안도 네 가지 기준과 같은 읽기 방법으로 다시 점검하고 앞뒤 문장과 이어 읽는다. 용어만 바꾸면서 수식어가 겹치거나 주체·대상이 빠지지 않았는지 확인한다. 한 문장만 자연스럽고 문단의 시점이나 시제가 흔들리면 문단 단위로 맞춘다.
- 작성자가 직접 고친 문장은 표시한다. 고칠 이유가 네 가지 점검 안에 있을 때만 제안하고, 어조나 선택으로 보이면 유지한다.
- 논지, 절 구성, 예시 교체는 제안하지 않는다. 그런 문제가 보이면 따로 알린다.

## 보고

1. **고칠 문장** 표: 행 | 지금 | 추천안 | 이유(네 가지 가운데 무엇에 걸리는지 한 줄).
2. **그대로 둘 문장**: 빠짐없이 행 번호로 적고, 일부만 고치는 행은 유지한 문장도 명시한다. 전수점검은 유지한 문장까지 다뤘다는 것을 보여야 끝난다.
3. 작성자가 직접 고친 문장이나 기록이 필요한 항목은 표 아래에 따로 적는다.

검토 요청만으로는 파일을 고치지 않는다.

## 적용

- 적용 직전에 파일을 다시 읽는다. 다른 세션이나 작성자가 그사이 고친 문장은 덮어쓰지 않는다.
- 여러 문장을 한 번에 바꿀 때는 모든 원문이 현재 파일과 정확히 맞을 때만 적용한다. 맞지 않는 문장이 있으면 그 문장을 다시 읽고, 새 문장이 이미 괜찮으면 그 항목을 빼고 적용한다.
- 적용 뒤에는 `git diff --check`로 형식만 확인하고, 바꾼 문장과 뺀 항목을 알린다.

스킬을 보완할 때는 [문장 라우팅·조건 구분 평가](../taez-insight-blog-writer/evals/cases.md)를 참고한다. 일반 문장 점검에서는 평가 자료를 읽지 않는다.
