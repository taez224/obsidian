# 블로그 스킬 행동 평가

스킬을 변경할 때 요청 범위와 편집 판단이 유지되는지 확인한다. 일반 글 작성·검토 때 읽을 문서는 아니다.

## 고정 입력

[cases.json](cases.json)에 사용자 요청, 원자료, 관찰할 행동을 보관한다. 검토용 정상 원고는 표현을 바로잡은 CSV 글을 사용한다. 아웃라인에는 캐시 구현·실험 메모와 코드 리뷰 경험 메모를, 조건 구분 회귀에는 CSV 글의 마지막 조건만 달리한 판을 사용한다. 유형 경계·문제 해결·닫힌 결정 사례는 평가용 자료이며 실제 경험이나 실행 기록으로 인용하지 않는다. 각 사례는 임시 실행 기록 없이 재실행할 수 있다.

| ID | 확인할 행동 |
| --- | --- |
| technical-review | 교정된 CSV 설명 글에 불필요한 수정을 요구하지 않는가 |
| insight-outline | 주어진 경험만으로 아웃라인을 만들고 전문을 쓰지 않는가 |
| sentence-routing | 문장 요청을 sentence-audit로 보내고 전체 검토를 시작하지 않는가 |
| technical-outline | 이미 확정된 집필 범위를 재승인받지 않고 아웃라인을 만드는가 |
| retry-condition-regression | 재시도 가능 여부와 중복 없는 재시도의 조건을 구분하는가 |
| company-insight-boundary | 회사 기술블로그의 경험·판단 글을 통찰형으로 처리하는가 |
| troubleshooting-outline | 증상·원인·해결·결과 확인으로 끝내고 통찰형 절차를 요구하지 않는가 |
| closed-decisions-review | 닫힌 편집 결정은 유지하면서 새로운 사실 오류를 구분하는가 |

## 실행과 판정

1. 변경 전 스킬과 reference를 보존한다. 변경 전후에 같은 요청·원자료·모델·도구 제한을 사용한다.
2. 각 사례는 앞선 평가 맥락이 없는 새 세션에서 실행한다. 평가자에게는 `prompt`와 `artifact`만 전달하고 `process_checks`·`result_checks`, 의심되는 결함, 기대 답변, 이전 결과는 주지 않는다. 실행 환경에서는 스킬 사본과 원자료 밖의 파일, 실제 vault를 읽지 않게 하고, 스킬이 vault 검색을 요구하면 확인하지 못했다고 적게 한다.
3. 문장 라우팅 사례는 블로그 스킬과 sentence-audit의 description만 먼저 제공한다. 선택한 스킬의 본문만 읽게 한다. 조건 구분 회귀 사례는 sentence-audit를 사용한다. 나머지는 해당 버전의 블로그 스킬과 필요한 reference를 사용한다.
4. `process_checks`는 실행 기록(읽은 파일·명령)으로, `result_checks`는 사용자에게 준 답변 본문만으로 판정하고 따로 집계한다. 결과 판정을 할 때는 실행 기록과 버전을 알 수 있는 경로를 가린다. 판정은 통과·실패·보류로 하고, 근거가 모호하면 보류와 그 이유를 남긴다. 문구·헤딩 일치로 채점하지 않고, 새로운 지적은 원자료에서 근거를 확인한다.
5. 실행 결과에는 사용한 런타임·모델 정보, 수정 전후 판정과 제한을 남긴다. 한 번 통과했다는 이유로 다른 모델이나 실제 작업에서도 보장된다고 쓰지 않는다.

## 결과 판정 기준

결과는 지적·수정의 근거, 원래 의미·조건·강도, 사용자에게 주는 추가 부담으로 판정한다. 절 수나 지적·확인 요청의 개수로 판정하지 않고, 모호한 문구를 가장 불리한 뜻으로만 읽어 감점하지 않는다.

- **추론과 관측:** 구현 로직이나 일반 원리로 뒷받침되는 추론은 관측과 구분해 쓰면 허용한다. 확인하지 않은 기간·횟수·상태를 관측한 것처럼 쓰면 실패다.
- **필수 확인:** 빠진 정보 없이는 요청 범위에서 핵심 사실을 바르게 설명하거나 필요한 수정을 고를 수 없을 때만 필수 확인으로 본다. 이미 주어진 사실, 제외한 범위, 없어도 되는 세부를 채워야 한다고 요구하면 실패다. 해당 주장을 한정하거나 빼는 대안도 인정한다. 알림과 요구는 특정 표현이 아니라 사용자 답변 없이 기본안이 완성되는지로 구분한다.
- **닫힌 공개 범위:** 공개 자료가 전부라고 정했으면, 그 밖의 사실이 있어야 완성되는 절이나 제목을 기본안에 넣지 않는다.
- **선택·후속 제안:** 기본안이 추가 자료 없이 완결되고 제안이 따로 구분되면 범위를 다시 연 것으로 보지 않는다. 다만 기본안의 채울 것·확인 필요에 새 사실을 넣으면 "선택"이라는 단서만으로 통과시키지 않는다.
- **편집 결정:** 요청 범위 안에서 근거를 갖춘 구성·제목·배치 선택지는 허용한다. 이미 주어진 자료에서 주어를 고르는 일과 원자료 밖의 사실을 확인하는 일을 구분한다. 정한 제외 범위를 다시 묻거나 스스로 정할 수 있는 결정을 필수 질문으로 넘기면 실패다.
- **원자료 정확성:** 문장 수나 인용 번호가 틀리면 정확성 오류로 기록한다. 오류가 의미·조건·강도를 바꾸는지는 심각도 설명에서 구분한다. 정확성을 요구하는 항목의 통과 여부와 오류의 심각도를 혼동하지 않는다.
- **파생값:** 표의 파생값이나 해석은 관측값과 구분해 표시하면 허용한다.
- **중복 결함:** 한 결함이 여러 항목에 걸리면 항목별 판정은 남기되 같은 결함 ID로 묶는다. 보류 판정만 있는 묶음은 확정 결함 수에 합산하지 않고 따로 집계한다. 통과 개수를 독립적인 오류 수나 품질 배수로 해석하지 않는다.

이 폴더에는 재실행할 입력·통과 기준과 선별한 결함 장부만 유지한다. 실행 결과는 대화에서 보고하고, 상세 출력·스킬 사본·실행 기록은 `_workspace/`나 임시 폴더에 보관한다. 결과 파일을 이 폴더에 누적하거나 최신 결과 파일로 유지하지 않는다. 실제 모델 호출이 없는 형식 검사는 행동 평가 통과로 세지 않는다.

기존 실패 사례를 다시 시험하는 것은 회귀 확인이다. 큰 변경에서는 보완에 사용하지 않은 새 자료로도 확인하고, 동일 사례만 통과하도록 문구를 맞추지 않는다. 스킬 자체의 효용을 비교할 때는 스킬 없는 기준선도 별도로 실행한다.
