# 블로그 스킬 행동 평가

스킬을 변경할 때 요청 범위와 편집 판단이 유지되는지 확인한다. 일반 글 작성·검토 때 읽을 문서는 아니다.

## 고정 입력

[cases.json](cases.json)에 사용자 요청, 원자료, 관찰할 행동을 보관한다. 검토용 정상 원고는 표현을 바로잡은 CSV 글을 사용한다. 아웃라인에는 캐시 설명 글과 코드 리뷰 경험 메모를, 조건 구분 회귀에는 CSV 글의 마지막 조건만 달리한 판을 사용한다. 각 사례는 임시 실행 기록 없이 재실행할 수 있다.

| ID | 확인할 행동 |
| --- | --- |
| technical-review | 교정된 CSV 설명 글에 불필요한 수정을 요구하지 않는가 |
| insight-outline | 주어진 경험만으로 아웃라인을 만들고 전문을 쓰지 않는가 |
| sentence-routing | 문장 요청을 sentence-audit로 보내고 전체 검토를 시작하지 않는가 |
| technical-outline | 이미 확정된 집필 범위를 재승인받지 않고 아웃라인을 만드는가 |
| retry-condition-regression | 재시도 가능 여부와 중복 없는 재시도의 조건을 구분하는가 |

## 실행과 판정

1. 변경 전 스킬과 reference를 보존한다. 변경 전후에 같은 요청·원자료·모델·도구 제한을 사용한다.
2. 각 사례는 앞선 평가 맥락이 없는 새 세션에서 실행한다. 평가자에게는 `prompt`와 `artifact`만 전달하고 `checks`, 의심되는 결함, 기대 답변, 이전 결과는 주지 않는다.
3. 문장 라우팅 사례는 블로그 스킬과 sentence-audit의 description만 먼저 제공한다. 선택한 스킬의 본문만 읽게 한다. 조건 구분 회귀 사례는 sentence-audit를 사용한다. 나머지는 해당 버전의 블로그 스킬과 필요한 reference를 사용한다.
4. 실제 답변과 읽은 파일을 보고 `checks`별 통과·실패·미확인을 판정한다. 문구·헤딩 일치로 채점하지 않고, 새로운 지적은 원자료에서 근거를 확인한다.
5. 실행 결과에는 사용한 런타임·모델 정보, 수정 전후 판정과 제한을 남긴다. 한 번 통과했다는 이유로 다른 모델이나 실제 작업에서도 보장된다고 쓰지 않는다.

이 폴더에는 재실행할 입력·통과 기준과 선별한 결함 장부만 유지한다. 실행 결과는 대화에서 보고하고, 상세 출력·스킬 사본·실행 기록은 `_workspace/`나 임시 폴더에 보관한다. 결과 파일을 이 폴더에 누적하거나 최신 결과 파일로 유지하지 않는다. 실제 모델 호출이 없는 형식 검사는 행동 평가 통과로 세지 않는다.

기존 실패 사례를 다시 시험하는 것은 회귀 확인이다. 큰 변경에서는 보완에 사용하지 않은 새 자료로도 확인하고, 동일 사례만 통과하도록 문구를 맞추지 않는다. 스킬 자체의 효용을 비교할 때는 스킬 없는 기준선도 별도로 실행한다.
