# 🧭 Visual Argument Review — 도식이 하는 주장 검토

> 도식·인포그래픽이 장식이 아니라 논지를 운반할 때 사용한다. 목표는 예쁜 그림이 아니라,
> 본문과 같은 사실·범위·위계를 더 빨리 읽히게 하는 그림이다.

## 언제 쓰나

- 화살표, 단계, 비교, 중첩, 강조로 인과나 개념 관계를 설명할 때
- 기술 구조나 판단 과정을 본문보다 압축해 보여줄 때
- 발행 직전 도식의 문구·배치·렌더를 바꿨을 때

장식 이미지, 분위기용 삽화, 본문과 독립된 사진에는 이 절차를 강제하지 않는다.

## 검토 순서

### 1. 그림의 주장을 한 문장으로 적는다

그림을 먼저 보고 독자가 3초 안에 가져갈 문장을 적는다. 저자가 의도한 문장이 아니라
실제 크기·색·화살표·위치가 만드는 문장이어야 한다. 이 문장이 본문의 핵심 구분과 다르면
문구를 더 붙이기 전에 시각 위계를 고친다.

### 2. 사실과 주장 범위를 대조한다

- 본문에 없는 연결·원인·순서·수치가 그림에서 새로 생기지 않았는가
- 정성 판단을 눈금·퍼센트·정밀한 위치로 그려 정량 데이터처럼 보이게 하지 않았는가
- 한 사례를 보편 구조나 권장 기본값처럼 강조하지 않았는가
- 예외나 경계를 본문보다 강하게 지우지 않았는가

### 3. 개념의 역할과 시각 위계를 맞춘다

- 중심 주장, 설명 메커니즘, 사례·증거가 크기와 포함 관계에서도 같은 위계인가
- 가장 진한 색·굵은 선·큰 면적이 실제로 가장 중요한 의미를 맡는가
- 같은 색이나 기호가 서로 다른 뜻을 겸하지 않는가
- 화살표가 데이터 흐름, 인과, 반복, 선택 중 무엇을 뜻하는지 구분되는가

### 4. 캡션의 역할을 확인한다

캡션은 그림을 문장으로 전부 되풀이하지 않는다. 그림만으로 오독하기 쉬운 **읽는 규칙이나
범위 한 가지**를 보완한다. 캡션 없이는 핵심 관계가 성립하지 않는다면 그림 자체를 먼저 고친다.

### 5. 실제 발행 크기로 렌더한다

- SVG와 원본 소스만 읽지 말고 실제 렌더를 확인한다
- 주 발행면의 데스크톱 폭을 우선하고, 좁은 화면을 지원한다면 해당 폭도 확인한다
- 글자 잘림, 겹침, 화살표 머리와 선의 충돌, 마커 방향, 여백, 대비를 본다
- 작은 보조 문구가 논지를 독점하면 크기를 키우거나 구조를 단순화한다
- 다국어 발행이면 이미지 안 언어 계약을 먼저 정하고 전수 확인한다

## 보고 형식

1. 그림만 보고 남은 주장 한 문장
2. 사실 오류 또는 본문 불일치
3. 시각적 오독 위험
4. 실제 렌더 결함
5. 보존할 요소와 고칠 요소

문제를 채우려고 만들지 않는다. 사실과 위계가 맞고 실제 크기에서 읽히면 통과다.

## 자동화 경계

스크립트는 파일 참조, SVG 파싱, viewBox, 작은 글자 후보, 중복 ID, 렌더 가능 여부를 관측할 수 있다.
그림의 주장, 강조의 의미, 사례와 정의의 구분은 자동 판정하거나 자동 수정하지 않는다.
