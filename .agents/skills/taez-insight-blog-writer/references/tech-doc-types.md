# 기술 글의 문서 유형

발행면과 관계없이 개념 설명, 학습, 특정 작업·문제 해결이 목적인 블로그 기술 글을 쓸 때, 아웃라인보다 먼저 문서 유형과 문서 계약을 정한다. 경험에서 판단을 끌어내는 통찰형 글은 SKILL.md 4~5단계를 따르고 이 파일을 읽지 않는다. Slipbox·Development 노트에는 적용하지 않는다.

유형 구분은 토스 [테크니컬 라이팅 가이드](https://technical-writing.dev/)의 「문서 유형 정하기」(CC BY-NC-SA 4.0)와 [Diátaxis](https://diataxis.fr/)를 요약해 옮겼다. 블로그에 맞게 참조 문서 유형은 뺐다.

## 유형 고르기

두 질문으로 고른다.

1. 독자는 읽고 나서 **무언가를 하려는가**, 아니면 **이해하려는가**?
2. 독자는 이 기술을 **처음 배우려는가**, 아니면 **배경지식이 있는 상태에서 특정 작업이나 문제를 해결하려는가**?

| 유형 | 독자의 목적 | 블로그에서 흔한 모습 |
| --- | --- | --- |
| 설명형 | 개념·원리·선택 배경을 이해한다 | "X란 무엇이고 왜 쓰는가", 방식 비교, 동작 원리 |
| 학습형 | 처음부터 끝까지 따라 해서 결과물을 만든다 | 시작하기, 튜토리얼 |
| 문제 해결형 | 특정 작업을 수행하거나 사용 중 생긴 문제를 해결한다 | How-to, 트러블슈팅 |

글의 주된 목적을 기준으로 유형을 고르되, 필요한 요소를 함께 쓸 수 있다. 유형이 섞였다는 이유만으로 나누지 않고, 서로 다른 목표 때문에 독자의 흐름이 갈릴 때 분리를 검토한다.

## 문서 계약

아웃라인 맨 위에 필요한 항목만 둔다. 기존 요청과 대화에서 정한 내용으로 채우고, 절 구성이 달라질 만큼 불명확한 부분만 묻는다. 확인된 내용을 다시 승인받기 위해 멈추지 않는다.

```markdown
## 문서 계약

- 유형: 설명형 (보조: 예제 코드)
- 독자: 아는 것 / 모르는 것
- 읽고 나면: 독자가 할 수 있게 되는 것 한 문장
- 다루지 않는 것: 생략하는 범위와 이유
- 예제 환경: 언어·프레임워크 버전, 예제 저장소 (원자료에 있을 때만)
```

- 계약과 아웃라인의 빈칸은 채워 달라는 요구가 아니다. 원자료에 없는 예제 환경·코드 발췌·명령·설정값은 비워 두고, 그것 없이도 글의 목표를 이룰 수 있으면 채울 것으로 요구하지 않는다. 넣으면 글이 나아지는 세부는 필수 확인과 나눠 선택 항목으로 적는다. 사용자가 제외한 범위는 확인 질문으로도 다시 열지 않는다.
- **다루지 않는 것**은 독자가 본문에 포함된다고 오해할 만한 범위만 한 번 밝힌다. 생략 항목을 모두 나열하지 않고, 본문이 생략한 동작을 약속하지 않게 한다.
- 계약은 검토의 기준이다. 검토에서는 선언한 유형의 체크리스트로만 결함을 판정한다. 다른 유형의 기준(예: 설명형 글에 학습형의 "모든 코드가 그대로 실행된다")은 결함이 아니라 선택 사항으로 보고한다.

## 유형별 기준

### 설명형

- **개요**: 무엇인지, 어떤 문제를 풀려고 생겼는지, 읽고 나면 무엇을 판단할 수 있는지.
- **배경과 선택 조건**: 독자가 가장 먼저 떠올릴 대안보다 이 방식을 고르는 조건을 적는다.
- **동작 조건**: 어떤 조건에서 어떻게 동작하고, 값이 없거나 틀리면 무엇이 일어나는지.
- **선행 지식**: 독자가 모를 개념은 처음 나올 때 한두 문장으로 정의한다.
- **그림**: 구조·흐름이 문장보다 그림으로 빨리 읽힐 때만 둔다.
- **코드**: 원리를 보여 주는 최소 발췌로 충분하다. 생략은 계약의 「다루지 않는 것」으로 덮는다. 예제 버전은 적고, 독자 환경에서 핵심 API가 다를 때만 한 줄로 대안을 안내한다.

### 학습형

- **목표와 사전 요구사항**: 끝나면 무엇이 만들어지는지, 필요한 버전·도구.
- **단계**: 순서대로, 쉬운 것부터. 단계마다 확인할 결과를 둔다.
- **코드**: 본문의 모든 코드를 실제로 실행해 확인한다. 독자가 막히면 글이 실패한 것이다.
- **곁가지**: 자주 막히는 지점과 심화 내용은 마지막 절이나 접힌 콜아웃으로 보낸다.

### 문제 해결형

- **제목과 도입**: 독자가 수행하려는 작업이나 해결하려는 증상을 구체적으로 밝힌다.
- **순서**: How-to는 작업 목표 → 필요한 조건 → 절차 → 결과 확인, 트러블슈팅은 증상 → 환경 → 원인 → 해결 → 결과 확인을 따른다.
- **출발점**: How-to는 작업·사용법 자료, 트러블슈팅은 `30_Resources/Development/Troubleshooting/` 노트. 내부 맥락은 독자가 적용할 수 있는 최소 환경으로 바꾼다.
- 통찰형의 논지·움직임·목소리 검토는 돌리지 않는다. 글은 결과 확인에서 끝내고, 배운 점이나 교훈을 정리하는 절을 따로 붙이지 않는다.

## 유형과 무관한 구조 기준

토스 가이드의 「정보 구조 만들기」에서 블로그에 맞는 것만 옮겼다.

- 기능이나 배경보다 독자가 얻을 것을 먼저 쓴다.
- 한 글에서 하나의 목표만 다룬다. 헤딩이 H4까지 내려가면 글을 나눌 신호다.
- 같은 대상은 끝까지 같은 이름으로 부른다. 아웃라인 단계에서 핵심 용어 서너 개를 정해 둔다.
- 같은 수준의 헤딩은 같은 형식으로 쓴다(헤딩 형식 자체는 `.agents/guides/writing.md`를 따른다).
