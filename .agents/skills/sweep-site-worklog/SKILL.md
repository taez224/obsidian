# Sweep Site Worklog

작업 이력은 커밋 로그의 축약본이 아니라 사이트 구성이 지금 모습이 된 결정을 모은 마일스톤 목록이다. 커밋이 있었다고 해서 항목을 만들지 않는다. 초반처럼 큰 결정이 몰린 시기에는 줄이 촘촘하고, 다듬는 시기에는 몇 주 동안 새 줄이 없을 수 있다.

## 대상

| 항목 | 값 |
| --- | --- |
| 소스 | `~/Projects/taez224.github.io`의 Git 이력 |
| 출력 | `30_Resources/Development/Concepts/생각의 정원을 만들고 배포하는 과정.md`의 `## 작업 이력` |

- vault 저장소의 커밋은 소스에 넣지 않는다. 이 노트는 사이트 구성을 다루므로 사이트 저장소만 읽는다.
- 사이트 저장소는 근거로 읽을 뿐 수정하지 않는다.
- 다른 노트에 작업 이력 절을 새로 만들지 않는다.

## 1. 커밋 수집

날짜 인자는 `YYYY-MM-DD` 하루나 `YYYY-MM-DD YYYY-MM-DD` 범위를 받는다. 인자가 없으면 작업 이력 맨 위 항목의 마지막 날짜 다음 날부터 오늘까지를 읽는다.

```bash
cd ~/Projects/taez224.github.io
git fetch -q origin   # PR은 GitHub에서 병합되므로 로컬 main보다 origin/main이 최신이다
SINCE=2026-09-24; UNTIL=$(date +%F)   # 요청받은 범위를 넣는다
git log origin/main --no-merges --since="$SINCE 00:00" --until="$UNTIL 23:59:59" --date=short --pretty=format:'%ad %h %s'
git log origin/main --no-merges --since="$SINCE 00:00" --until="$UNTIL 23:59:59" --pretty=format:'=== %h %s' --stat
```

- 커밋이 없으면 그 사실만 보고한다.
- 커밋 메시지만으로 범위가 모호하면 diffstat에서 바뀐 디렉터리를 확인한다. 개별 diff는 꼭 필요할 때만 읽는다.
- 아직 커밋하지 않은 변경은 완료된 작업으로 보지 않는다.

## 2. 마일스톤 가리기

결과가 같은 커밋을 한 갈래로 모은 뒤, 갈래마다 마일스톤인지 판단한다. 하나의 목표를 여러 날과 여러 커밋에 걸쳐 이룬 경우, 예를 들어 타입 전환이나 한 번의 점검 반영은 갈래 하나다.

| 남긴다 | 생략한다 |
| --- | --- |
| 구조·도구·배포 방식을 정한 결정 (프레임워크 이관, 저장소 분리, 언어·런타임 전환) | 버그 수정, 회귀 수정 |
| 독자가 새로 쓸 수 있게 된 기능 (생각 지도, 각주, 화면 모드 전환) | 배치·색·간격·아이콘 정렬 조정 |
| 품질을 지키는 체계를 처음 들인 일 (브라우저 회귀 검사, 접근성 점검) | 이미 있는 기능을 다듬은 일 (호버 미리보기, 표시 방식 변경) |
| | 의존성 갱신, 지침 문서 정리, 되돌린 커밋 |

- 판단이 애매하면 "석 달 뒤 이 사이트가 왜 이렇게 생겼는지 설명할 때 꺼낼 일인가"로 가른다.
- 마일스톤이 없으면 항목을 제안하지 않는다. 생략한 갈래는 보고에 한 줄로만 적는다.

## 3. 항목 문안

형식은 `- **YYYY.MM.DD** ` 뒤에 명사형 나열이며, 한 줄이나 두 줄로 40자에서 80자 사이를 유지한다. 마일스톤이 여러 날에 걸치면 `- **2026.09.20~23**`처럼 범위로 적는다.

- 파일명·설정 파일·속성 이름은 백틱으로 감싼다. 굵게 쓰는 것은 날짜와 모델명뿐이다.
- 기존 항목과 같은 굵기를 유지한다. 기준 예시는 다음과 같다.

```markdown
- **2026.09.12** TypeScript 적용, Node 26 전환, `DESIGN.md` 추가.
```

- 문장의 결은 `.agents/guides/writing.md`를 따른다. 목록 항목이므로 명사형 종결을 쓴다.
- 맨 위 항목과 같은 마일스톤이 이어졌으면 새 줄을 만들지 않고 그 줄의 날짜 범위를 늘려 합칠 문안을 제안한다.
- 기존 항목은 승인 없이 지우거나 고치지 않는다.

## 4. 보고와 적용

보고는 수집 범위, 제안 문안, 생략한 갈래 순으로 짧게 한다. 제안까지 마치면 완료로 본다.

적용 승인을 받으면 다음을 지킨다.

- 편집 직전에 노트를 다시 읽는다. 사용자가 이미 직접 쓴 항목을 덮어쓰지 않는다.
- `## 작업 이력` 목록의 맨 위에 항목을 넣는다.
- frontmatter `updated`를 항목 날짜로 갱신한다.
- 다른 절의 설명은 고치지 않는다. 구성이 바뀌어 본문 설명이 틀렸다면 후보로만 보고한다.

## 기계 확인

- 추가한 wikilink가 있으면 대상 노트의 존재를 확인한다.
- `git diff --check`를 실행한다.

## 다른 스킬과의 경계

- 세션 트랜스크립트로 하루·주·월 DevLog를 쓰는 작업은 `devlog`다.
- 프로젝트 허브의 현재 상태와 남은 일을 갱신하는 작업은 `sweep-project-context`다.
- 노트의 절 구성이나 개념 설명을 다시 쓰는 작업은 `development-note`다.
