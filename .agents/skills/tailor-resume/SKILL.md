# Tailor Resume

이력서 전용본은 원장의 사실을 공고에 맞게 고른 판이다. 문장을 새로 지어내지 않고, 원장에 있는데 빠진 사실을 찾아 넣는 것이 이 작업의 대부분이다.

## 대상

| 항목 | 위치 |
| --- | --- |
| 전용본 HTML | `20_Projects/job-search-2026/assets/resume-taejun-<회사>.html` |
| 사실 정본 | `경력 원장.md`, `QRA·Gallery 기술 경력 원장.md` (같은 폴더) |
| 회사 노트 | `20_Projects/job-search-2026/<회사> - <포지션>.md`, 형식은 `회사 지원 템플릿.md` |
| 점검 기준 | [resume-criteria.md](references/resume-criteria.md) |
| 공고 원문·중간 파일 | 세션 scratchpad |

- `20_Projects/job-search-2026/`은 vault Git에서 제외돼 있고(`.gitignore`), 폴더 안에 자체 로컬 Git이 따로 있다. 커밋은 승인받은 뒤 그 저장소에 한다. 미커밋 편집이 잦아 HEAD가 편집 전 기준이 되지 못하므로, 전용본을 고치기 전에 scratchpad에 사본을 남긴다.
- 사용자나 다른 세션이 같은 파일을 동시에 고치는 일이 잦다. 적용 직전에 사본과 diff를 떠서 새 편집을 확인하고, 같은 줄은 그 편집을 우선한다.

## 1. 공고 원문 확보

- 원티드 공고는 처음부터 사용자에게 원문 붙여넣기를 요청한다. 브라우저 창에서는 막히고, 웹 조회 도구는 요약 모델을 거치면서 우대사항을 "없음"으로 돌려줬다(2026-09-29 서로 다른 공고 두 건에서 연속).
- 다른 사이트에서 웹 조회로 가져온 공고는 절 목록(주요업무, 자격요건, 우대사항, 기술 스택)을 사용자에게 보여 주고 빠진 절이 없는지 확인받는다. "없음"이라는 결과는 믿지 않는다.
- 원문은 scratchpad에만 둔다. 원티드 공고는 재배포·재가공이 금지돼 있어 vault에는 직접 쓴 요약만 남긴다.

## 2. 전용본 만들기

1. 기존 전용본 가운데 새 공고와 주요업무가 가장 가까운 판을 출발점으로 고른다. 후보가 둘 이상이면 판마다 공고와 맞는 점을 한 줄씩 들어 제안하고, 모호하면 사용자에게 묻는다. 일반 공개본(`resume-taejun-kos.html`)은 익명 표기라 출발점으로 쓰지 않는다. 제출한 전용본은 제출 뒤에 고쳤을 수 있으니, 회사 노트의 `제출한 자료`와 이후 변경 기록을 확인한다.
2. 파일명은 `resume-taejun-<회사>.html`이다. 기존 파일이 있으면 덮어쓰지 않는다.
3. 고객사 실명은 회사에 직접 내는 채용 제출본에서만 쓴다(`경력 원장.md` 29행, 2026-09-29 기록). 일반 공개본(`resume-taejun-kos.html`)처럼 공개되는 판은 익명이다. 한국관광공사는 어디서나 실명이다.

## 3. 점검

점검 기준과 실제 사례는 [resume-criteria.md](references/resume-criteria.md)에 있다. 문장 기준은 새로 넣거나 고친 문장에만 적용하고, 공고 기준은 새 공고로 처음부터 다시 적용한다.

1. 공고의 주요업무·자격요건·우대사항마다 원장을 검색해, 경험은 있는데 이력서에서 빠진 사실을 찾는다.
2. 원장에 없는 사실은 추측하지 않는다. 사용자에게 묻거나 사내 저장소의 코드로 확인한다. 저장소 경로는 `QRA·Gallery 기술 경력 원장.md`에 있다.
3. 저장소는 읽기만 한다. checkout·pull·stash를 하지 않는다. `git branch --show-current`로 작업 트리의 브랜치를 먼저 보고, main의 내용은 `git grep <패턴> origin/main`이나 `git show origin/main:<경로>`로 읽는다. 커밋이 main에 들어갔는지는 `git branch -a --contains <sha>`로 커밋마다 따로 확인하고, main에 없는 커밋은 main 반영으로 쓰지 않는다. `origin/main`은 마지막 fetch 시점 기준이다.
4. 확인한 사실은 6절대로 원장에 기록한다.

점검 결과는 후보로 보고하고, 승인받은 항목만 적용한다.

## 4. 중립 모의 심사

사용자가 요청할 때만 실행한다. 프롬프트와 실행 조건은 [cats-prompt.md](references/cats-prompt.md)에 있다.

1. `scripts/resume_text.py`로 전용본을 텍스트로 추출해 scratchpad에 둔다.
2. 읽기 전용 서브에이전트에게 공고 파일과 이력서 텍스트 두 개만 읽게 한다. vault의 다른 노트와 웹 조회는 막는다. 회사 노트에는 우리 판단이 섞여 있어 넘기지 않는다.
3. 이력서는 "지원자 A"라는 3인칭으로 넘긴다. "내 이력서"라고 쓰면 요청자 본인의 이력서로 읽혀 평가가 후해질 수 있다.
4. Angle은 공고 문장에서만 뽑아 채운다. 우리가 아는 강점으로 채우지 않는다.

결과 해석:
- 판정 문구의 차이는 한 번 실행한 결과라 모델 편차일 수 있다. 구체적 지적이 사라졌는지가 더 믿을 만한 신호다.
- 개선 제안 표의 빈칸 수치(N분 → N초 등)는 따르지 않는다. 나중에 실제로 측정할 수 있는 항목만 따로 표시한다.
- 결과 전문은 사용자에게 파일로 전달하고, 요약은 회사 노트의 「서류 모의 심사」 절에 남긴다.

## 5. 인쇄 분량 측정

전용본은 A4 두 쪽이고, 1쪽은 인쇄 여유 10mm 이상을 유지한다(HTML의 CSS 주석 기준). 2쪽은 여유가 0mm 미만이면 3쪽이 되므로 넘치지 않아야 하고, 가능하면 1쪽처럼 10mm 이상 둔다. 스크립트는 두 쪽의 여유를 모두 출력하니 `pages[1].spareMm`도 확인한다.

1. 브라우저 창에서 `file://` 경로로 전용본을 연다.
2. 창 폭을 1100×1400으로 맞춘다. 860px 이하에서는 모바일 CSS가 적용돼 측정값이 틀어진다.
3. [measure-fit.js](scripts/measure-fit.js)를 실행한다. `pretendardLoaded`가 `true`인지 먼저 본다. `false`면 폰트가 로딩 중이거나 CDN에서 받지 못한 것이므로 잠시 뒤 다시 연다. 폰트 없이 잰 값은 쓰지 않는다.
4. 측정이 끝나면 창 크기를 되돌린다.

- 불릿 한 줄은 약 4.8mm다. 넘치면 경험 소거 후보나 간격 조정 안을 수치와 함께 제시하고 사용자가 고르게 한다.
- 실제 인쇄 결과로 쪽수와 쪽 나뉨을 확인하려면 헤드리스 Chrome으로 PDF를 만들 수 있다. `--headless=new --disable-gpu --no-pdf-header-footer --print-to-pdf=<출력 경로>`만 쓰면 사용자의 Chrome이 실행 중이어도 약 5초에 끝나고, `pdfinfo`로 쪽수를 본다. `--user-data-dir`나 `--virtual-time-budget`을 붙였을 때는 프로세스가 끝나지 않았으니 붙이지 않는다(2026-09-29 재현). `scripts/print_pdf.sh <전용본.html> <출력.pdf>`가 이 방식으로 PDF를 만들고, 30초 안에 끝나지 않거나 2쪽이 아니면 실패로 끝난다.
- 출력 PDF는 scratchpad에만 둔다. `assets/`의 제출본 PDF는 Git에서 복구할 수 없는 것이 있어서, 스크립트는 이미 있는 파일을 덮어쓰지 않고 `.pdf`가 아닌 경로를 거부한다. scratchpad의 임시 PDF를 같은 이름으로 다시 만들 때만 `PRINT_PDF_OVERWRITE=1`을 붙인다.

## 6. 원장과 노트 기록

- 사용자가 새로 확인해 준 사실은 원장의 해당 프로젝트 절에 `(YYYY-MM-DD 본인 확인)`으로 기록한다. 고객사 내부망 근거면 `내부망 반출 불가`를 함께 적는다. 코드로 확인한 사실은 파일과 커밋을 적는다.
- 회사 노트에는 공고 요약, 적합도 표, 전용본 경로와 이전 판과의 차이, 모의 심사 요약, 면접에서 답할 구도를 둔다.
- 지원 현황 표의 상태와 다음 액션을 갱신한다. 제출한 뒤에는 `제출일`과 `제출한 자료`(실제 제출 파일)를 적고, 이후 HTML을 고치면 제출본과 다르다는 사실을 남긴다.
