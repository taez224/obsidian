# 이력서 문장 점검 기준

강승현, 『AI를 이기는 개발자 커리어 관리 가이드』(2026)의 이력서 절을 바탕으로, 2026-09 전용본 두 건을 만들며 실제로 걸린 사례를 붙여 정리했다.

기준은 두 종류다. 문장 기준은 공고와 상관없이 문장 자체의 품질을 본다. 공고 기준은 같은 문장이라도 공고에 따라 판단이 달라진다.

## 문장 기준

### 추상 표현

형용사와 추상명사가 문제가 아니라, 그 뒤에 근거가 바로 붙지 않는 것이 문제다.

- 자주 나오는 곳: 요약(성실, 성장), 성과(품질 개선, 효율적 처리), 기술 목록(능숙, 높은 이해도).
- 점검법: 추상어에 표시하고 "그래서?", "무엇을?"을 물은 뒤, 행동과 맥락(가능하면 숫자)으로 다시 쓴다.
- 실제 사례: `기여했습니다`(무엇을 맡았는지 없음), `설정과 DB 마이그레이션을 조정했습니다`(무엇을 바꿨는지 없음), `보완했습니다`, `저장 정합을 유지했습니다`, `이상이 생기면`(어떤 상태인지 없음. 코드에서 CrashLoopBackOff·OOMKilled·Evicted로 확인해 바꿨다).
- 기술 목록에 활동(코드 리뷰)이나 본문에 근거가 없는 항목(ADR)을 넣지 않는다.

### 수치

숫자는 맥락이 있을 때만 설득력이 있다.

- 네 요소: 전(기준값), 후(결과값), 단위, 규모나 조건. 넷째는 생략할 수 있지만 있으면 더 강하다.
- 금지: 퍼센트만 쓰기, 수식어만 쓰기("크게 늘림"), 기준값 없이 증가량만 쓰기.
- 기록 없는 수치는 만들지 않는다. 정량화가 어려우면 전후 작업 변화를 정성적으로 쓴다("담당자가 화면에서 직접 하던 확인을 자동 판정으로 대체").
- 실제 사례: PDF 불릿은 전·후·단위는 있었지만 조건이 없어 "왜 1.7GB가 문제였나"가 읽히지 않았다. "더 큰 PDF는 처리되는데 특정 PDF에서만"이라는 조건과 `로컬` 측정이라는 사실을 넣었다.

### 기능 나열

기능 이름만 있으면 누구나 했을 법한 일로 읽힌다. 불릿마다 "왜 필요했나 → 무엇이 어려웠나 → 어떻게 풀었나"가 보이는지 본다.

| 판정 | 뜻 | 처리 |
| --- | --- | --- |
| 문제에서 해결로 이어짐 | 필요나 어려움이 문장에 있다 | 유지 |
| 결과만 있음 | 무엇을 했는지와 효과는 있지만 왜 필요했는지가 없다 | 문제 한 구절을 앞에 붙인다 |
| 기능만 나열 | 구현한 기능 이름만 있다 | 원장에서 문제를 찾아 다시 쓰거나 경험 소거 후보로 올린다 |

- 원장에 `해결한 문제`가 기록된 항목은 대개 첫째 판정이 나온다. 기능 나열로 남는 불릿은 원장에 문제 기록이 없는 경우가 많으니, 사용자에게 어려웠던 점을 묻는다.
- "무엇을 배웠나", "다음엔 무엇을 다르게 할까"는 모든 불릿에 넣지 않는다. 대표 사례 한두 개에서 판단이 바뀐 과정이 보이면 충분하고, 나머지는 면접 소재로 둔다.

### 능동형

문장의 주어가 지원자이고, 주어진 범위 안에서 한 판단과 행동이 보여야 한다. 최종 결정권을 과장하라는 뜻은 아니다.

- 흔한 수동형: `~을 담당`, `~에 참여`, `~이 수행`, `~이 개선`. 뒤에 구체적 행동이 붙으면 둘 수 있다.
- 주어가 중간에 바뀌는 구절을 찾는다. 실제 사례: `…확인을 서비스가 대신하고`(주어가 서비스), `적용 가이드를 배포해 타 팀이 시범 적용,`(내 행동과 남의 행동이 서술어 없이 이어짐).
- 자기 제안이 드러나면 쓴다. 실제 사례: `SSE로 구현했습니다` → `SSE 도입을 제안해 구현했습니다`. 자기 제안을 근거에 따라 되돌린 과정은 그 자체로 배움의 근거가 된다.
- 의도한 동작에 부정적 어휘를 쓰지 않는다. 실제 사례: `재시작을 유발했고` → `Pod가 다시 시작되게 했고`.

### 이력서 말투

- 실제 이력서에서 흔히 쓰는 형식과 표준 용어를 먼저 쓴다. 풀어 쓴 자작 표현보다 통용되는 용어가 낫다.
- 피할 것: 서술형 연결어(`이후`, `~하자`), 딱딱한 문어체(`~에 비추어`), 완곡어(`함께`), 세 문장 이상의 불릿, 목적어가 빠진 문장.
- 다른 곳(역할 줄, 프로젝트 소개)이 이미 전하는 정보를 불릿에서 되풀이하지 않는다.
- 문장을 제안할 때는 조사와 목적어를 갖춘 완성안을 한 번에 낸다.

## 공고 기준

### 표현 전략

심사자는 위에 있는 정보와 문장 첫머리를 먼저 읽는다. 강조는 덜 강조된 것이 있을 때만 효과가 있다.

- 먼저 읽히는 곳은 요약, 하이라이트, 불릿의 굵은 제목, 문장 첫머리다. 공고의 주요업무와 가장 가까운 근거가 여기서 보이는지부터 본다. 실제 사례: 관측 서비스 공고에는 하이라이트 1을 "배포 자동화"에서 "Kubernetes 상태 수집·감시"로 바꿨다.
- 굵은 제목은 영역 이름(`~관리`, `~변경`)보다 결정이나 결과를 담는다. 실제 사례: `배포 상태의 화면 전달 방식 변경` → `SSE에서 polling으로 전환`.
- 성과 수치가 하나뿐이면 제목이나 굵은 글씨로 앞에 드러낸다.
- 시간순 구조는 유지하되, 그 안에서 공고와 관련이 큰 불릿과 프로젝트를 먼저 둔다.
- 같은 내용이 요약, 하이라이트, 프로젝트 소개에 반복되면 한 곳만 남긴다.
- 시각 강조(굵게, 색, 구분선)는 제목, 핵심 수치, 섹션 구분에만 쓴다.

### 경험 소거

소거는 삭제가 아니라 공고 적합성에 따른 정제다.

- 후보: 공고와 관련이 낮은 경험, 3~5년 넘게 지나 지금 직무와 무관한 경험, 기여나 성과가 불분명하거나 다른 항목과 겹치는 경험.
- 처리: 빼거나, 한 줄로 줄이거나, 기타 프로젝트 줄로 옮긴다.
- 분량이 넘칠 때 뺄 순서를 회사 노트의 지원 전략에 미리 적어 둔다.

### 없는 것과 빠진 것

심사자는 이력서에 없는 경험을 "경험 없음"으로 읽는다. 공고 요건마다 원장을 검색해, 경험은 있는데 다른 전용본을 줄이면서 빠진 사실을 먼저 찾는다. 실제 사례: 모의 심사에서 "기술 X는 PoC에만 있음", "기술 Y 근거 약함"으로 지적된 두 항목은 모두 원장에 있었고, 전용본에 넣자 지적이 사라졌다.
