# Sweep Project Context

프로젝트 허브는 원자료에서 파생한 현재 상태의 정본이다. DevLog·문서·Repository를 복제하지 않고, 서로 다른 기록을 대조해 지금 유효한 맥락만 허브에 반영한다.

## 원칙

1. **원자료 우선**: 기존 허브의 서술을 사실로 가정하지 않고 근거와 대조한다.
2. **상태 구분**: 구현 완료, 설계·계획, 개인 추론, 미확인을 섞지 않는다.
3. **하나의 프로젝트 ID**: 저장소명이 여러 개여도 결과물 기준의 canonical `project_id`로 모은다.
4. **후보 우선**: 사용자가 “바로 반영해줘”라고 명시하지 않았다면 변경 후보와 근거를 먼저 제안한다.
5. **복제 금지**: DevLog·소스코드·Daily의 전문을 프로젝트 폴더에 다시 적지 않는다.
6. **외부 상태 비변경**: Repository, 이슈, MR, 배포 환경은 근거로 읽을 뿐 수정하지 않는다.

## 1. 대상과 경계 확인

1. `20_Projects/<project-id>/<project-id>.md` 형태의 프로젝트 허브를 찾는다.
2. 저장소명·서비스명·과거 프로젝트명이 섞여 있으면 허브, `AGENTS.md`, 사용자 설명을 대조해 canonical `project_id`를 확정한다.
3. 허브의 목표, 현재 상태, 다음 행동, 마일스톤, 주요 근거를 먼저 읽는다.
4. frontmatter를 바꿀 가능성이 있으면 `99_Templates/_property-schema.md`의 Project 규칙을 확인한다.
5. 사용자가 Repository 경로를 주었거나 허브에서 연결한 경우에만 실제 Repository를 읽는다. 해당 Repository의 `AGENTS.md`·`CLAUDE.md`가 있으면 먼저 따른다.

프로젝트가 특정되지 않고 여러 후보가 의미 있게 갈리면 임의로 합치지 말고 사용자에게 확인한다.

## 2. 근거 수집

### Vault

- `rg`로 `project_id`, 프로젝트 링크, 저장소명, 주요 기능명을 정확 검색한다.
- `30_Resources/Development/DevLog/`에서 `projects`가 canonical `project_id`와 일치하는 기록을 찾는다.
- 프로젝트 폴더, Troubleshooting, Blog, Career 자료에서 프로젝트를 직접 근거로 삼는 문서를 찾는다.
- 간접 표현이나 오래된 맥락을 찾을 때는 `qmd` 스킬의 검색 절차를 따른다. `_workspace/`, `40_Archive/`, 로컬 스냅샷은 현재 상태 후보에서 제외하고, 판단 전 원문을 읽는다.
- QMD 결과와 현재 파일이 다르면 현재 파일과 `rg` 결과를 우선한다. 사용자가 QMD 갱신을 직접 요청한 경우에만 수동 재색인한다.

### Repository

- 코드, 테스트, 실행 결과, Git 이력, ADR·설계 문서, 가이드를 필요한 범위만 읽는다.
- 이슈와 MR은 접근 가능하고 현재 상태 판단에 필요할 때만 확인한다.
- dirty working tree의 변경은 완료된 결과로 단정하지 않는다.
- 다른 Repository를 추가로 읽어야 한다면 프로젝트 경계와 연결 근거를 먼저 확인한다.

### 근거 우선순위

1. 코드·테스트·실행 결과
2. Git 이력·이슈·MR
3. ADR·설계 문서·가이드
4. DevLog·Periodic Notes
5. 과거 요약·블로그·경력 문서

낮은 순위의 기록이 높은 순위의 근거와 충돌하면 충돌을 보고하고 높은 순위만으로 결론을 좁힌다.

## 3. 주장 상태 표시

| 상태 | 의미 |
| --- | --- |
| 확인됨 | 현재 코드·테스트·공식 기록으로 확인 |
| 설계됨 | 계획·ADR에는 있으나 구현 완료 근거 없음 |
| 추론 | 여러 근거에서 합리적으로 읽히지만 직접 확인되지 않음 |
| 미확인 | 근거가 부족하거나 접근하지 못함 |
| 오래됨 | 과거에는 맞았으나 현재도 유효한지 확인 필요 |

“남아 있는 일”도 완료되지 않았다는 근거가 있을 때만 확정한다. 오래된 TODO 하나만으로 현재 작업이라고 단정하지 않는다.

## 4. 변경 전 보고

다음 순서로 간결하게 보고한다.

1. **대상과 검색 범위**: project_id, 확인한 Vault 영역, Repository
2. **확인된 현재 상태**: 구현·운영·문서 상태
3. **변화와 충돌**: 허브와 원자료가 다른 부분
4. **남은 일**: 확인된 작업과 미확인 후보 분리
5. **파생 후보**: Troubleshooting, Slipbox, Blog, Career로 발전시킬 만한 항목
6. **허브 변경안**: 섹션 단위로 무엇을 바꿀지와 근거
7. **불확실성**: 확인하지 못한 환경·이슈·시점

각 핵심 주장에는 파일·헤딩·블록·커밋·이슈처럼 다시 확인할 수 있는 근거를 붙인다. 검색 snippet이나 QMD 점수만 제시하지 않는다.

읽기 요청이면 여기서 끝낸다. 허브 갱신 요청이지만 적용 승인이 명확하지 않으면 후보 보고를 완료 상태로 본다.

## 5. 승인된 변경 적용

- 현재 상태, 다음 행동, 마일스톤, 주요 근거, 파생 결과물 중 필요한 섹션만 수정한다.
- 목표는 실제 프로젝트 범위가 바뀌고 사용자가 승인한 경우에만 수정한다.
- `status`, `ended`는 종료·중단 근거와 사용자의 의도가 분명할 때만 바꾼다.
- 링크는 문서 전체, 헤딩, 블록 중 주장 범위에 맞는 정밀도를 사용한다.
- 원자료를 장문으로 옮기지 않고 한두 문장 요약과 근거 링크만 남긴다.
- Slipbox, Blog, Career 문서를 자동 생성하거나 갱신하지 않고 후보로만 보고한다.
- 근거로 읽은 DevLog와 Repository는 수정하지 않는다.

## 6. 검증

- 허브의 폴더명, `project_id`, `프로젝트/<project-id>` 태그가 일치하는지 확인한다.
- 새로 바꾼 현재 상태와 다음 행동에 근거가 있는지 확인한다.
- 완료된 일과 로드맵, 사실과 추론이 섞이지 않았는지 확인한다.
- 추가한 wikilink 대상이 존재하는지 확인한다.
- `git diff --check`를 실행한다.
- 최종 보고에 사용한 검색 방식과 주요 근거, 반영하지 않은 불확실성을 남긴다.

## 다른 스킬과의 경계

- 프로젝트 기록에서 영구 노트 승격·연결·MOC를 판단하면 `review-zettelkasten`을 사용한다.
- frontmatter·죽은 링크·고립 노트의 기계 검사는 `vault-lint`를 사용한다.
- 의미 검색과 재색인은 `qmd` 스킬을 따른다.
- QMD는 평소 post-commit에 맡기며, 사용자가 직접 요청하지 않으면 이 스킬이 자동 갱신하지 않는다.
