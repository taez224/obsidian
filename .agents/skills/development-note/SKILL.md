# Development note

개발하며 생긴 질문을 다시 이해하고 적용할 수 있는 노트로 만든다. 신규 작성과 기존 노트 검토를 모두 다루되, 이번 요청에 필요한 범위만 수행한다.

## 정본과 역할

아래 경로는 이 스킬을 둔 vault의 루트 기준이다. 해당 절과 선택한 템플릿만 읽고 규칙을 중복 정의하지 않는다.

- `30_Resources/Obsidian 운영 워크플로.md`의 **개발 노트와 공개 페이지**: 저장 위치, 공개 범위, 본문 연결.
- `99_Templates/_property-schema.md`의 **개발 기술 태그**, **Development Concepts**, **Development Troubleshooting**, **Development Tools**: 속성과 주제별 태그.
- `99_Templates/dev-concept-template.md`: 개념·설계·학습 노트와 도구 노트의 출발점.
- `99_Templates/dev-troubleshooting-template.md`: 문제 해결 기록의 출발점.

외부 자료 한 편을 읽고 남긴 반응이 중심이면 `literature-note`, 프로젝트의 현황·다음 행동을 모으는 요청이면 `sweep-project-context`를 사용한다. 명시적인 Slipbox 승격은 `permanent-note`, 영구 노트의 의미 검토·병합은 `review-zettelkasten`으로 연결한다. 기술 노트를 자동으로 Slipbox에 승격하지 않는다.

## 요청 범위와 기존 노트 확인

- 조사·후보 제안만 요청했으면 그 결과까지, 작성·수정을 요청했으면 해당 노트까지 수행한다. 기존에 승인한 범위는 다시 승인받지 않는다.
- 긴 프로젝트 이력을 다룰 때는 현재 관심 질문으로 범위를 좁힌다. 소재가 모호하면 후보와 근거 위치부터 제시하고, 기간 전체의 DevLog나 모든 구현을 복원하지 않는다.
- 신규 작성 전에는 `qmd` 스킬의 정확 검색과 의미 검색으로 중복 후보를 찾고 원문을 읽는다. 기존 노트 검토에서는 대상과 직접 관련된 근거에 집중한다. 같은 내용을 새 노트로 복제하지 않는다.
- 저장소·DevLog는 근거로 읽는다. 코드 수정, 이력서 성과 작성, 사이트 개편을 작업에 자동으로 포함하지 않는다.

## 설명을 뒷받침하는 근거 확인

다음을 구분해 읽고, 문장의 단정 강도는 확인한 근거를 넘기지 않는다. 별도 등급이나 메타데이터 필드를 만들 필요는 없다.

- **일반적인 기술 원리**: 관련 버전의 공식 문서·공개 소스로 확인한다. 개념을 설명하는 데 회사 저장소가 필요하지 않으면 읽지 않는다.
- **코드에서 확인한 동작**: 호출 경로·조건·버전을 대조한다. 현재 코드와 과거 장애 시점의 코드를 섞지 않는다. 특정 증상과 원인 사이의 빠진 단계를 찾는다.
- **당시 관찰과 진단**: 기록·로그·사용자 설명에 근거해 적는다. 코드상 가능한 결함을 실제 환경에서 관측한 사실로 바꾸지 않는다.
- **재현·수정 후 검증**: 실제 실행한 범위와 결과만 기록한다. 검증이 빠진 부분은 추정 또는 확인할 조건으로 남길 수 있다. 모든 노트에 새 실험을 요구하지 않는다.
- “항상”, “모든”, “같다”, “없다”, “지원한다”처럼 결과를 보장하는 표현은 적용 조건과 확인 범위를 함께 적는다. 실제로 측정하지 않은 성능·시점·브라우저 호환성은 보장으로 쓰지 않고 추정이나 미검증 범위로 남긴다.

원인을 검토할 때는 증상에서 해결책으로 바로 건너뛰지 않는다. 예를 들어 미완료 Future와 스레드 점유 사이에는 누가 어디서 결과를 기다리는지 확인이 필요하다. 이 사례의 결론을 다른 라이브러리·버전·환경의 일반 규칙으로 복사하지 않는다.

## 작성 또는 보강

### 위치와 형식

- 개념·설계 선택·구현 방법은 Concepts, 확인 가능한 문제와 해결 과정은 Troubleshooting, 특정 도구를 어떤 용도로 어떻게 쓰는지는 Tools에 둔다. 구체적인 위치·태그·연결 방식은 정본을 따른다.
- 검증 범위는 개념의 적용 조건과 설명의 한계를 이해하는 데 필요한 만큼 남긴다. 현재 적용 상태·배포 대기·다음 작업처럼 시간이 지나면 바뀌는 현황은 개념 노트에 옮기지 않는다.
- 템플릿은 속성과 작성 안내의 출발점이며 목차가 아니다. 헤딩은 `.agents/guides/writing.md`의 기준을 따르고, 짧은 노트는 소제목 없이 써도 된다. Templater 표현은 실제 값으로 치환하고, 안내 주석·빈 절·예시용 링크는 완성본에 남기지 않는다.
- 콜아웃은 각 템플릿의 안내를 따른다. 사이트 전용 표시(비교 callout, 글 카드, 캡션)는 `.agents/guides/writing.md`에 있다.
- 종결체는 `.agents/guides/writing.md`를 따른다(개발 노트는 평어체). 웹에 공개된다는 이유만으로 방문자 소개문이나 존댓말로 바꾸지 않는다. 사용자가 별도 독자·장르·문체를 지정하면 그 요청을 따르고, 기존 노트는 요청한 범위 밖의 문체까지 일괄 변경하지 않는다.

### 제목과 summary

- 제목은 본문이 확인한 것보다 강하게 단정하지 않는다. 본문이 유보한 판단을 제목이 확정하면 제목만 읽고 넘어간 독자에게 잘못 전달된다.
- 트러블슈팅의 제목은 `99_Templates/dev-troubleshooting-template.md`의 안내대로 독자의 상황을 부르는 명사구로 쓴다. 사건 기록의 제목이 일반 원리를 선언하면 노트가 확인한 범위보다 넓게 말하게 되고, 주장을 담는 영구 노트의 목소리가 된다.
- Concepts에는 원리 설명과 비교뿐 아니라 특정 문제의 설계 판단과 선택 이유도 남긴다. 다른 맥락에서 독립적으로 재사용할 주장은 `permanent-note` 후보로 검토하되, 판단이 있다는 이유만으로 자동 분리하거나 승격하지 않는다.
- `summary`의 장르별 정의는 속성 스키마의 개발 절과 각 템플릿 안내를 따른다. 상세 절차·근거·작업 이력·수치·조건은 본문에 둔다.
- 트러블슈팅의 증상·오류 원문·`확인 범위`는 `99_Templates/dev-troubleshooting-template.md`의 안내를 따른다. 독자가 재현하거나 적용 조건을 판단하는 데 필요한 정보만 남긴다.

### 본문의 깊이와 용어

- 공개 개발 노트의 독자는 AI 코딩 도구를 쓰는 개발자로 보고, 문제·원인·선택·검증의 흐름을 따라갈 수 있게 쓴다. Concepts와 Troubleshooting에서는 도구·프레임워크의 전체 사용법을 설명하기보다, 이 vault나 프로젝트에서 어떤 선택을 왜 했는지, 무엇을 맡기지 않는지, 깨져서 고친 사례를 쓴다. 다만 독자가 외부 도구·라이브러리·모델이나 그 새 버전 자체를 알아보러 오는 글은 소개하는 대상을 중심에 둔다. 대상이 무엇이고 어떻게 동작하는지를 공식 자료와 직접 실행해 확인한 예시로 먼저 보이고, 작성자의 환경에 적용한 선택과 한계는 뒤에 모은다. 도입은 배경 목록으로 시작하지 않는다. 문제를 다루는 노트는 그 문제에서, 도구나 버전 변경을 소개하는 노트는 독자가 무엇을 확인하러 왔는지에서 시작한다.
- 조사한 내용을 모두 본문에 옮기지 않는다. 기본은 핵심 원리·선택 이유·주요 한계까지 설명하고, 구현 세부와 코드는 그것 없이는 이해하거나 재현하기 어려울 때만 넣는다. 사용자가 상세 구현이나 재현 절차를 요청하면 그 목적에 맞게 깊이를 늘린다.
- 실험·측정을 했으면 결론을 뒷받침하는 수치만 남기고, 수치마다 무엇과 견주었는지와 몇 개 중 몇 개인지를 함께 적는다. 견준 기준이 사람이 정한 값(직접 붙인 라벨, 정한 임계값)이면 그 점을 밝힌다. 표본 구성·비용·스크립트 변경·후속 계획은 본문에 넣지 않는다. 이미 DevLog에 있으면 거기 남기고, 새 기록이 필요하면 사용자에게 제안만 한다. 분량을 줄일 때는 반복과 처리 시간 같은 운영 수치부터 덜고, 독자가 판단을 따라가는 데 필요한 예시는 남긴다.
- 독자가 낯설어할 수 있고 이해에 영향을 주는 개념·용어는 처음 나올 때 이 글에서의 역할을 짧게 설명한다. 설명은 독자가 문제·원인·선택·한계를 따라가는 데 필요한 범위로 제한하며, 모든 용어를 정의하거나 본문 밖에 용어집을 만들지 않는다.
- 익숙한 기술 용어와 코드 식별자가 핵심 메커니즘이나 선택을 나타내면 그대로 쓴다. 독자를 위해 쉽게 쓴다는 이유로 필요한 기술 용어를 삭제하거나 억지로 일반어로 바꾸지 않는다.
- 작성자의 로컬 맥락을 알아야만 뜻이 드러나는 표현·비유·작성자만 아는 축약어로 구현 대상을 대신 부르지 않는다. 기능·역할·관계가 드러나는 구체적인 말로 바꾸거나 설명을 덧붙이며, UI 영역·요소·상태·데이터 흐름은 실제 대상을 지칭한다. 일반적인 사용법과 직접 사용·검증한 내용을 구분한다.
- 트러블슈팅은 무엇을 관찰했고, 어떤 근거로 원인을 좁혔으며, 왜 그 해결책을 골랐고 어디까지 확인했는지 따라갈 수 있게 쓴다. 문단·소제목·목록·코드·표는 설명에 맞게 선택한다. 개념 설명은 독립적으로 찾아 읽을 가치가 있고 분리 후에도 원본의 원인·해결을 이해할 수 있을 때만 Concepts 후보로 제안한다. 길다는 이유만으로 분리하지 않는다.
- 기존 노트의 생각 흐름과 유용한 예제는 보존한다. 코드·설정·수치가 개념 이해나 재현에 필요하면 남기고, 단순 운영 메모라는 이유만으로 기술적 세부사항을 일괄 삭제하지 않는다. 반대로 이해에 도움이 없는 옵션 나열이나 작업 이력을 채우지 않는다.
- 내부 용어는 문맥에 맞는 역할로 풀어 쓰되, 불명확한 도메인 개념을 임의로 테넌트·사용자 같은 일반 용어와 동일시하지 않는다. 이해에 도움이 되는 클래스·메서드명과 구현 설명은 유지할 수 있다.
- 실제 접근 정보·자격증명·고객 정보는 공개 본문과 첨부에 넣지 않는다. 내부 코드와 기록의 상세 위치가 공개에 부적절하면 비공개 근거 기록에 두고, 공개 노트에는 필요한 기술 설명과 확인 범위를 남긴다.

### 링크와 태그

- 문장과 문단의 결, 링크 위치와 근거·행선지 구분, 공개 노트에서 뺄 것은 `.agents/guides/writing.md`를 따르고, 개발 노트의 연결 기준은 운영 워크플로의 개발 노트 절을 따른다.
- 주장·원인·예제를 바꾸면 제목·요약·그림도 같은 뜻인지 검토한다. 기술 태그는 입력에서 그대로 복사하지 말고 `99_Templates/_property-schema.md`의 개발 기술 태그 기준으로 핵심 주제를 다시 판단한다.

## 검증과 완료

- 수정한 본문의 사실·적용 조건·출처와 실제 변경을 대조한다. 소스 확인만 한 것을 재현 성공이나 운영 검증으로 보고하지 않는다.
- frontmatter·링크·템플릿 잔여 문구와 diff를 확인한다. 명칭·태그만 고쳤다면 그 변경에 맞는 가벼운 확인으로 끝낸다.
- 공개한 노트를 고쳤다면 `updated`는 속성 스키마의 공통 필드 기준으로 적는다. 날짜는 `date +%F`로 확인하고 `created`는 바꾸지 않는다.
- 본문을 고쳤다면 완료 전에 본문만 읽는 독자가 작성자의 로컬 맥락이나 원자료를 다시 찾지 않아도 문제·원인·선택·검증 범위를 따라갈 수 있는지 확인한다. 이해를 막는 용어만 보완하고, 용어 설명이 일반적인 배경 강의나 같은 내용의 반복으로 커지지 않게 한다.
- 새로 쓰거나 구성을 크게 바꾼 공개 노트는 읽기 전용 하위 에이전트에게 독자 시점 점검을 맡긴다. 작성자는 자기 맥락을 알고 있어 이 점검을 스스로 하기 어렵기 때문이다. 에이전트에게는 노트 파일 하나를 끝까지 읽게 하고 다른 노트·검색·웹은 막으며, 작성 맥락은 주지 않는다. 독자는 AI 코딩 도구를 쓰는 개발자이고 이 vault는 모른다고 알려 준다. 요점 세 문장, 이해가 막힌 곳, 길다고 느낀 곳을 보고받고, 지적마다 해당 문장을 인용하게 한다. 요점이 `summary`와 어긋나거나 막힌 곳이 작성자의 환경을 전제한 것이면 본문을 고치고, 나머지 지적은 후보로 보고 판단한다. 점검은 한 번만 하고 수정한 뒤에는 반복하지 않는다. 하위 에이전트를 쓸 수 없는 환경이면 이 점검을 생략했다고 알린다.
- Concepts·Troubleshooting·Tools는 일반 Markdown을 자동 공개하는 폴더다. 이 위치에 작성·수정할 때 본문·요약·첨부·링크를 운영 워크플로의 개발 노트 절 기준으로 확인하고 공개 가능한 내용만 둔다. 사이트 반영이 요청 범위라면 빌드 결과의 포함·제외 범위와 연결을 확인한다.
- 노트 작성이나 공개 적합성 검토만으로 커밋·push·배포까지 승인됐다고 보지 않는다. 승인 범위는 `AGENTS.md`의 승인과 편집 절을 따른다.
- 결과에는 작성·수정한 노트, 보완한 핵심 설명, 남은 불확실성과 공개 반영 여부를 짧게 알린다. QMD 수동 재색인은 요청받았을 때만 수행한다.
