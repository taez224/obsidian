# Development note

개발하며 생긴 질문을 다시 이해하고 적용할 수 있는 노트로 만든다. 신규 작성과 기존 노트 검토를 모두 다루되, 이번 요청에 필요한 범위만 수행한다.

## 정본과 역할

아래 경로는 이 스킬을 둔 vault의 루트 기준이다. 해당 절과 선택한 템플릿만 읽고 규칙을 중복 정의하지 않는다.

- `30_Resources/Obsidian 운영 워크플로.md`의 **개발 노트와 공개 페이지**: 저장 위치, 공개 범위, 본문 연결.
- `99_Templates/_property-schema.md`의 **개발 기술 태그**, **Development Concepts**, **Development Troubleshooting**, **Development Tools**: 속성과 주제별 태그.
- `99_Templates/dev-concept-template.md`: 개념·설계·학습 노트와 도구 노트의 출발점.
- `99_Templates/dev-troubleshooting-template.md`: 문제 해결 기록의 출발점.

외부 자료 한 편을 읽고 남긴 반응이 중심이면 `literature-note`, 프로젝트의 현황·다음 행동을 모으는 요청이면 `sweep-project-context`를 사용한다. 명시적인 Slipbox 승격은 `permanent-note`, 영구 노트의 의미 검토·병합은 `review-zettelkasten`으로 연결한다. 기술 노트를 자동으로 Slipbox에 승격하지 않는다.

## 요청 범위와 기존 노트 확인

- 조사·후보 제안만 요청했으면 그 결과까지, 작성·수정을 요청했으면 해당 노트까지 수행한다. 기존에 승인한 범위는 다시 승인받지 않는다.
- 긴 프로젝트 이력을 다룰 때는 현재 관심 질문으로 범위를 좁힌다. 소재가 모호하면 후보와 근거 위치부터 제시하고, 기간 전체의 DevLog나 모든 구현을 복원하지 않는다.
- 신규 작성 전에는 `qmd` 스킬의 정확 검색과 의미 검색으로 중복 후보를 찾고 원문을 읽는다. 기존 노트 검토에서는 대상과 직접 관련된 근거에 집중한다. 같은 내용을 새 노트로 복제하지 않는다.
- 저장소·DevLog는 근거로 읽는다. 코드 수정, 이력서 성과 작성, 사이트 개편을 작업에 자동으로 포함하지 않는다.

## 설명을 뒷받침하는 근거 확인

다음을 구분해 읽고, 문장의 단정 강도는 확인한 근거를 넘기지 않는다. 별도 등급이나 메타데이터 필드를 만들 필요는 없다.

- **일반적인 기술 원리**: 관련 버전의 공식 문서·공개 소스로 확인한다. 개념을 설명하는 데 회사 저장소가 필요하지 않으면 읽지 않는다.
- **코드에서 확인한 동작**: 호출 경로·조건·버전을 대조한다. 현재 코드와 과거 장애 시점의 코드를 섞지 않는다. 특정 증상과 원인 사이의 빠진 단계를 찾는다.
- **당시 관찰과 진단**: 기록·로그·사용자 설명에 근거해 적는다. 코드상 가능한 결함을 실제 환경에서 관측한 사실로 바꾸지 않는다.
- **재현·수정 후 검증**: 실제 실행한 범위와 결과만 기록한다. 검증이 빠진 부분은 추정 또는 확인할 조건으로 남길 수 있다. 모든 노트에 새 실험을 요구하지 않는다.
- “항상”, “모든”, “같다”, “없다”, “지원한다”처럼 결과를 보장하는 표현은 적용 조건과 확인 범위를 함께 적는다. 실제로 측정하지 않은 성능·시점·브라우저 호환성은 보장으로 쓰지 않고 추정이나 미검증 범위로 남긴다.

원인을 검토할 때는 증상에서 해결책으로 바로 건너뛰지 않는다. 예를 들어 미완료 Future와 스레드 점유 사이에는 누가 어디서 결과를 기다리는지 확인이 필요하다. 이 사례의 결론을 다른 라이브러리·버전·환경의 일반 규칙으로 복사하지 않는다.

## 작성 또는 보강

### 위치와 형식

- 개념·설계 선택·구현 방법은 Concepts, 확인 가능한 문제와 해결 과정은 Troubleshooting, 특정 도구를 어떤 용도로 어떻게 쓰는지는 Tools에 둔다. 설계 결정을 기록한 글은 도구 이름이 들어가더라도 Concepts에 둔다. 구체적인 위치·태그·연결 방식은 정본을 따른다.
- 검증 범위는 개념의 적용 조건과 설명의 한계를 이해하는 데 필요한 만큼 남긴다. 현재 적용 상태·배포 대기·다음 작업처럼 시간이 지나면 바뀌는 현황은 개념 노트에 옮기지 않는다.
- 템플릿은 속성과 작성 안내의 출발점이며 목차가 아니다. 헤딩은 각 절에서 실제로 설명하는 내용을 짧은 명사구로 적고, 템플릿 안내 항목의 이름을 헤딩으로 옮기지 않는다. 짧은 노트는 소제목 없이 써도 된다. Templater 표현은 실제 값으로 치환하고, 안내 주석·빈 절·예시용 링크는 완성본에 남기지 않는다.
- 콜아웃은 들어내도 본문이 그대로 성립할 때만 쓴다. 상자를 지웠을 때 설명이 무너진다면 그 내용은 본문이므로 문단과 소제목으로 쓴다. 핵심 답이나 관점은 `summary`에서 먼저 보여주고 본문에서는 근거·선택·해결을 설명한다. 같은 결론을 요약 상자로 다시 반복하지 않는다.
- 개발 노트는 평어체를 기본으로 한다. 웹에 공개된다는 이유만으로 방문자 소개문이나 존댓말로 바꾸지 않는다. 사용자가 별도 독자·장르·문체를 지정하면 그 요청을 따르고, 기존 노트는 요청한 범위 밖의 문체까지 일괄 변경하지 않는다.

### 제목과 summary

- 제목은 본문이 확인한 것보다 강하게 단정하지 않는다. 본문이 유보한 판단을 제목이 확정하면 제목만 읽고 넘어간 독자에게 잘못 전달된다.
- 트러블슈팅의 제목은 독자가 자기 상황과 맞춰 볼 수 있게 그 상황을 부르는 명사구로 쓰고, 결론이나 원인을 부제로 붙이지 않는다. 사건 기록의 제목이 일반 원리를 선언하면 노트가 확인한 범위보다 넓게 말하게 되고, 주장을 담는 영구 노트의 목소리가 된다.
- Concepts에는 원리 설명과 비교뿐 아니라 특정 문제의 설계 판단과 선택 이유도 남긴다. 다른 맥락에서 독립적으로 재사용할 주장은 `permanent-note` 후보로 검토하되, 판단이 있다는 이유만으로 자동 분리하거나 승격하지 않는다.
- `summary`는 목록·검색 결과·노트 상단에서 읽히는 한 문장이고, 장르마다 담는 것이 다르다. Troubleshooting은 알아낸 답을, Concepts는 다루는 질문이나 구분을, Tools는 어떤 도구를 어떤 용도로 어떻게 쓰는지를 말한다. "~를 정리한다", "~를 확인한다"처럼 노트가 하는 일을 말하는 꼬리는 쓰지 않는다. 상세 절차·근거·작업 이력·수치·조건은 본문에 둔다.
- 트러블슈팅의 증상·오류 원문·확인 범위는 `99_Templates/dev-troubleshooting-template.md`의 안내를 따른다. 본문을 소제목으로 나눈 노트는 설명의 마지막에 `확인 범위` 절을 둔다. 소제목이 없는 노트만 확인 범위를 관련 문장에 포함한다. 독자가 재현하거나 적용 조건을 판단하는 데 필요한 정보만 남긴다.

### 본문의 깊이와 용어

- 공개 개발 노트의 독자는 주니어 개발자도 문제·원인·선택·검증의 흐름을 따라갈 수 있게 쓴다. 도구·프레임워크의 전체 사용법을 설명하기보다, 이 vault나 프로젝트에서 어떤 선택을 왜 했는지, 무엇을 맡기지 않는지, 깨져서 고친 사례를 쓴다. 도입은 배경 목록이 아니라 문제나 이야기에서 시작한다.
- 조사한 내용을 모두 본문에 옮기지 않는다. 기본은 핵심 원리·선택 이유·주요 한계까지 설명하고, 구현 세부와 코드는 그것 없이는 이해하거나 재현하기 어려울 때만 넣는다. 사용자가 상세 구현이나 재현 절차를 요청하면 그 목적에 맞게 깊이를 늘린다.
- 독자가 낯설어할 수 있고 이해에 영향을 주는 개념·용어는 처음 나올 때 이 글에서의 역할을 짧게 설명한다. 설명은 독자가 문제·원인·선택·한계를 따라가는 데 필요한 범위로 제한한다. 익숙한 기술 용어와 코드 식별자가 핵심 메커니즘이나 선택을 나타내면 그대로 쓴다. 주니어 독자를 가정한다는 이유로 필요한 기술 용어를 삭제하거나 억지로 일반어로 바꾸지 않는다. 작성자의 로컬 맥락을 알아야만 뜻이 드러나는 표현·비유·작성자만 아는 축약어로 구현 대상을 대신 부르지 않는다. 기능·역할·관계가 드러나는 구체적인 말로 바꾸거나 설명을 덧붙이며, UI 영역·요소·상태·데이터 흐름은 실제 대상을 지칭한다. 모든 용어를 정의하거나 본문 밖에 용어집을 만들지는 않는다. 일반적인 사용법과 직접 사용·검증한 내용을 구분하고, 실제 사례가 없으면 만들어 채우지 않는다.
- 트러블슈팅은 무엇을 관찰했고, 어떤 근거로 원인을 좁혔으며, 왜 그 해결책을 골랐고 어디까지 확인했는지 따라갈 수 있게 쓴다. 문단·소제목·목록·코드·표는 설명에 맞게 선택한다. 개념 설명은 독립적으로 찾아 읽을 가치가 있고 분리 후에도 원본의 원인·해결을 이해할 수 있을 때만 Concepts 후보로 제안한다. 길다는 이유만으로 분리하지 않는다.
- 기존 노트의 생각 흐름과 유용한 예제는 보존한다. 코드·설정·수치가 개념 이해나 재현에 필요하면 남기고, 단순 운영 메모라는 이유만으로 기술적 세부사항을 일괄 삭제하지 않는다. 반대로 이해에 도움이 없는 옵션 나열이나 작업 이력을 채우지 않는다.
- 내부 용어는 문맥에 맞는 역할로 풀어 쓰되, 불명확한 도메인 개념을 임의로 테넌트·사용자 같은 일반 용어와 동일시하지 않는다. 이해에 도움이 되는 클래스·메서드명과 구현 설명은 유지할 수 있다.
- 실제 접근 정보·자격증명·고객 정보는 공개 본문과 첨부에 넣지 않는다. 내부 코드와 기록의 상세 위치가 공개에 부적절하면 비공개 근거 기록에 두고, 공개 노트에는 필요한 기술 설명과 확인 범위를 남긴다.

### 링크와 태그

- 문장과 문단의 결, 링크 위치, 공개 노트에서 뺄 것은 `AGENTS.md`의 글쓰기 절을 따른다.
- 주장·원인·예제를 바꾸면 제목·요약·그림도 같은 뜻인지 검토한다. 기술 태그는 입력에서 그대로 복사하지 말고 핵심 주제로 다시 판단한다. Spring 기능이 중심이면 Java로 구현되었거나 JDK 문서를 인용했다는 이유로 `개발/Java`를 추가하지 않는다. 예를 들어 `@Async`의 반환 Future 처리 문제는 `개발/Spring`, JDK 자체의 동시성 API 설명은 `개발/Java`가 중심이다.
- 관계가 분명한 기존 노트는 관계를 설명하는 본문 문장 안에 링크하는 것을 우선한다. 본문에 자연스럽게 넣기 어려운 보조 관계만 마지막 `연관된 노트`에 이유와 함께 연결한다. 근거·적용·반례·구분 관계가 없는 링크, 미작성 노트의 링크, 중복 `related` 속성은 만들지 않는다. 외부 자료도 같다. 출처를 부르는 본문 어구에 링크하고, 본문에 넣지 못한 자료만 `참고 자료`에 남기며, 문장 끝에 인용 링크만 덧붙이지 않는다.

## 검증과 완료

- 수정한 본문의 사실·적용 조건·출처와 실제 변경을 대조한다. 소스 확인만 한 것을 재현 성공이나 운영 검증으로 보고하지 않는다.
- frontmatter·링크·템플릿 잔여 문구와 diff를 확인한다. 명칭·태그만 고쳤다면 그 변경에 맞는 가벼운 확인으로 끝낸다.
- 공개한 노트의 원인·해결·설명·예제처럼 독자가 알아야 할 본문을 고쳤다면 `updated`에 `date +%F`로 확인한 날짜를 적는다. 오타·표현·링크·태그·속성만 고쳤다면 적지 않으며 `created`는 바꾸지 않는다. 뜻은 속성 스키마의 공통 필드를 따른다.
- 완료 전에는 본문만 읽는 독자가 작성자의 로컬 맥락이나 원자료를 다시 찾지 않아도 문제·원인·선택·검증 범위를 따라갈 수 있는지 확인한다. 이해를 막는 용어만 보완하고, 용어 설명이 일반적인 배경 강의나 같은 내용의 반복으로 커지지 않게 한다.
- Concepts·Troubleshooting·Tools는 일반 Markdown을 자동 공개하는 폴더다. 이 위치에 작성·수정할 때 본문·요약·첨부·링크를 정본의 공개 기준으로 확인하고 공개 가능한 내용만 둔다. 개별 `files` 등록은 필요 없으며, 운영용 파일·폴더 제외와 첨부파일 검토는 운영 정본을 따른다. 사이트 반영이 요청 범위라면 빌드 결과의 포함·제외 범위와 연결을 확인한다.
- 노트 작성이나 공개 적합성 검토만으로 커밋·push·배포까지 승인됐다고 보지 않는다. 반대로 이미 승인된 공개 작업은 같은 승인을 반복해서 묻지 않고 검증 후 마무리한다. 사이트 구현 절차를 이 스킬에 복제하지 않는다.
- 결과에는 작성·수정한 노트, 보완한 핵심 설명, 남은 불확실성과 공개 반영 여부를 짧게 알린다. QMD 수동 재색인은 요청받았을 때만 수행한다.
