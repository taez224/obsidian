# Jev의 Obsidian 볼트 활용 아이디어와 실험 설계

TypeSafe 공식 문서, 공개 프로젝트, 기존 한국어 실험을 바탕으로 한 활용·실험 초안이다. 기능의 효용과 채택 여부는 아래 비교 실험으로 판단한다.

**2026-09-25 중단.** 1단계를 조정용 표본까지 진행했다. Jev는 조정용 24문단(있음 4)을 AUC 0.975로 갈랐지만, 같은 질문에 Claude Sonnet은 24문단을 모두 맞혔다. 글을 쓸 때는 이미 Claude가 검색 결과를 읽고 거르므로, 문단 수십 개 규모에서는 Jev의 속도와 비용이 작업을 바꾸지 않는다. 최종 평가와 2단계 이후는 진행하지 않는다. 아래 후보도 같은 기준으로 본다. 판단이 정확해졌을 때 작업이 달라지는지, 그리고 LLM이 이미 개입하지 않는 큰 규모의 작업인지를 먼저 확인한다. 기록은 2026-09-25 DevLog에 있다.

첫 실험은 **공개 노트 한 문단에 실제 시도와 관찰 결과가 명시돼 있는지**를 판별한다. 기존 실험에서 유용했던 국소적 판단부터 확인하고, QMD 검색 후보의 선별에 도움이 되는지 이어서 평가한다. 주장과 원문을 대조하는 요약 검증은 그다음에 관계 판단의 한계를 측정하는 별도 실험으로 둔다.

## 설계의 출발점

Jev는 글을 생성하는 대신, 주어진 자료와 질문에 대해 정해진 선택지·점수·확률을 반환하는 모델이다. 검색과 원문 추출은 코드가 담당하고, Jev에는 후보 문단에 특정 정보가 있는지처럼 좁은 판단을 맡긴다.

[[Jev와 System One 모델|기존 한국어 실험]]에서는 요약문과 예고 문장 판별이 유용했지만, 노트 쌍의 관계 분류는 잘되지 않았다. 공식 문서도 여러 단계를 거치는 추론과 불필요하게 큰 입력을 약점으로 명시한다.[^limits] 따라서 노트 두 편 전체를 비교하기보다 **짧은 문단과 구체적인 질문**으로 판단 대상을 좁히는 설계가 출발점이다. 문장 하나인지 둘인지가 성패를 보장하는 규칙은 아니다. 문장 안에서도 숨은 전제를 추론하면 어려울 수 있고, 두 문장의 명시적 수치나 조건 대조는 쉬울 수 있다. 첫 실험은 필요한 사실이 입력에 직접 드러나는 경우로 한정한다.

QMD는 이 볼트에서 사용하는 로컬 Markdown 검색 도구다. QMD가 검색 후보를 가져오고, Jev는 후보마다 필요한 정보가 있는지 판단한다. 원문을 해석해 설명하거나 새로운 질문을 만드는 일이 필요하면 생성 모델을 별도로 사용한다.

실험에는 다음 원칙을 적용한다.

- 진행 중인 표본·판단·검토 기록은 `_workspace/jev-vault-experiments/`에 둔다. 실험을 마치면 결과 요약은 해당 날짜의 DevLog에, 원자료와 재현 파일은 `DevLog/assets/<실험일>-jev/`에 보관하고 참조 경로를 갱신한다. 노트의 속성이나 본문을 자동으로 고치지 않는다. `status`의 성숙도 판정과 `used_in` 기록은 [[99_Templates/_property-schema|속성 스키마]]의 사용자 판단·승인 기준을 따른다.
- 날짜의 순서, 개수, 수치 비교는 코드로 계산한다. 의미 비교에는 필요한 양쪽 원문을 함께 제공한다.
- 첫 기준 실험에서는 영어 지시문과 한국어 자료를 사용한다. 영어 지시문이 이 과제에서도 더 낫다고 검증된 것은 아니므로, 언어별 성능 비교는 별도 실험으로 분리한다.
- Choice·Score의 confidence는 답의 분포가 얼마나 집중됐는지를 나타낸다. 정답률이나 행동 허가로 해석하지 않는다. Noul은 별도의 confidence가 없으며, 임계값은 유형별로 조정용 표본에서 정한다.[^confidence]
- 로컬 스크립트 실행과 로컬 추론은 다르다. Jev API 호출에 넣는 내용은 외부로 전송된다. Git 제외 여부는 전송 여부를 결정하지 않는다. 외부 전송은 실제 게시된 공개 노트·발행 글의 공개 버전으로 제한한다. 공개 폴더의 미발행 변경분도 자동 포함하지 않는다. Clippings의 요약, DevLog, 개인 일기는 보내지 않는다. 공개 원문에서 파생됐다는 이유로 비공개 요약의 전송 범위가 넓어지지는 않는다.
- 반복 실행하는 발행 검사는 기존 결정론 스크립트를 유지한다. Jev의 결과는 별도 검토 보고서로 사용한다.

## 활용 후보

### 1. 글에 부족한 근거 탐색

글의 문단을 선택하고 필요한 근거의 종류를 지정한다. 직접 겪은 사례, 관찰한 결과, 적용 조건, 한계 등이 대상이다. 결과는 해당하는 원문 대목 최대 세 개와 위치다.

1. QMD로 관련 문단 후보를 찾는다.
2. Jev에 각 후보가 실제 사건·결과를 명시하는지, 적용 조건이나 한계를 담는지 각각 묻는다.
3. 코드는 선택한 원문과 출처 위치를 보여준다.
4. 사용자가 해당 문단을 실제 근거로 쓸 수 있는지 판단한다.

기존 실험은 노트 본문에 구체적인 근거·적용 사례·한계가 있는지 점수를 매겼다. 여기에 검색을 연결하면 근거가 얇은 노트를 발견한 뒤 이미 써둔 경험을 찾아 보강할 수 있다. 다만 구체적인 사례가 있다는 판단과 그 사례가 주장을 입증한다는 판단은 다르다.

공식 [문단 선별 예제](https://docs.typesafe.ai/cookbooks/classifying_rag_passages)와 [원문 위치 선택 예제](https://docs.typesafe.ai/cookbooks/semantic_find)가 구현의 출발점이다. **QMD 검색만 했을 때보다 실제 채택하는 문단이 늘어나는지**로 효용을 검증한다.

### 2. 새 기록과 과거 질문의 재회

볼트에는 더 발전시킬 질문을 남기는 형식이 있다. 새 개발 기록이나 독서 반응을 저장할 때, 그 기록에 과거 질문을 다시 생각할 만한 내용이 있는지 확인한다.

입력은 과거 질문 하나와 새 기록의 관련 문단 하나다. Jev에는 문단이 질문에서 요구한 이유·조건·사례를 제공하는지 묻는다. 선택지는 직접 제공, 일부 단서, 같은 주제만 언급, 판단 불가로 나눌 수 있다.

결과는 과거 질문과 새 원문을 나란히 보여주는 형태다. 질문의 해결 여부나 노트의 연결은 자동으로 결정하지 않는다. 사용자가 질문을 고치거나 생각을 이어갈 수 있게 한다.

과거에 무엇을 고민했는지 기억해야만 검색할 수 있다는 부담을 줄이는 것이 기대 효과다. 질문이 요구한 정보를 찾는 관계 판단이므로, 단일 문단의 특징 판별보다 뒤에 평가한다. 공식 문단 선별 패턴을 볼트의 미해결 질문에 적용하는 제안이다.

**다시 보여준 질문 가운데 실제로 생각을 이어간 비율**을 평가한다. 같은 주제라는 이유만으로 후보를 많이 만드는 경우는 실패로 본다.

### 3. AI 편집 전후의 의미 변경 검토

원문과 수정문의 대응 문장을 비교해 다음 변화가 있는 대목만 표시한다.

- 가능성이나 가설이 확정적인 주장으로 바뀌었는가?
- 특정 상황의 경험이 일반적인 원칙으로 확대됐는가?
- 구현했다는 기록이 운영에 도입했다는 주장으로 바뀌었는가?
- AI가 제안한 내용이 사용자가 판단한 내용으로 바뀌었는가?

문장 대응과 숫자 변경은 코드로 처리하고, Jev는 각각의 의미 변화만 판단한다. 결과에는 편집 전후의 문장을 그대로 보여준다. 개발 기록을 블로그나 경력 자료로 옮길 때, 표현을 다듬다가 사실과 단정 강도가 달라진 곳을 찾는 데 쓸 수 있다.

공식 [인용 검증 예제](https://docs.typesafe.ai/cookbooks/citation_check)의 주장과 근거 문맥 대조를 편집 전후에 적용한 설계다. 의미 비교가 필요하므로 앞의 두 후보보다 검증 난도가 높다.

의미를 유지한 윤문과 의도적으로 확신·범위를 바꾼 수정문을 섞어 평가한다. **의미가 달라진 편집을 놓치는 비율과 정상적인 윤문을 잘못 지적하는 비율**을 함께 본다.

### 4. 주장 수정 후 함께 검토할 문단 탐색

노트의 중심 주장을 바꾸면, 그 주장을 활용한 다른 글에는 이전 표현이 남을 수 있다. 변경 직후 함께 확인할 문단을 찾는 기능이다.

다른 글에서 재사용한 관계를 기록하는 `used_in` 속성과 명시적 링크로 후보를 좁힌다. 해당 글의 관련 문단이 수정 전 주장에 의존하는지 검토하고, 함께 읽을 위치를 보여준다.

날짜가 최신이라는 이유만으로 수정된 노트를 정답으로 취급하면 안 된다. 이미 발행한 글은 당시 판단의 기록일 수 있다. 불일치 가능성을 보여준 뒤, 수정 여부는 글의 역할을 보고 결정한다.

[Jev Second Brain](https://github.com/fellowship-dev/jev-second-brain)의 원문 경로·내용 버전·검토 기록을 보존하는 구조를 참고할 수 있다. 관계 분류 기능은 MVP 단계다.

**함께 검토하라고 제시한 문단이 실제 수정이나 설명 보완으로 이어졌는지**를 평가한다. 원문이 바뀌면 이전 판단도 다시 확인할 수 있어야 한다.

### 5. 읽지 않은 자료의 진입점 선택

자료카드를 열 때 현재 질문을 하나 입력하면, 확인 가능한 원문에서 먼저 읽을 문단을 찾아준다. 추천 단위를 글 전체에서 원문의 특정 대목으로 줄이는 방식이다.

사용자가 읽기 시작할 위치를 찾는 데 도움을 주되, 개인 반응을 담는 `my_take`와 읽음 상태는 자동으로 채우지 않는다. 원문을 확보하지 못한 카드에서는 자료에 답이 있다고 판정하지 않는다.

[[읽지 않은 글을 읽은 척 저장하지 않기로 했다|자료를 저장한 상태와 읽고 반응한 상태를 구분하는 운영]]과 연결되는 활용이다. 요약을 더 쌓지 않아도 저장한 자료를 실제로 여는 계기를 만들 수 있다.

공식 원문 위치 선택 예제는 답의 존재 여부와 위치 선택을 따로 판단한다. 같은 발췌와 위치 ID를 인용 후보 선택에도 재사용할 수 있다. 다만 읽을 위치를 찾는 질문과 주장을 직접 표현한 인용을 고르는 질문은 따로 정의한다. **클릭 수보다 실제로 읽고 반응을 남겼는지**를 효용으로 본다.

## 보류할 운영·검수 후보

첫 실험과 직접 연결되지 않는 후보는 착수 조건과 평가 방법만 남긴다.

- **6. 자료카드 읽기 큐:** 관심 질문과 원문 발췌로 순위를 매긴다. 반복·반례를 보려면 기존 주장의 본문과 조건도 필요하다. QMD 순위보다 실제 읽기·반응이 늘어나는지 평가하며, 비공개 카드의 API 전송은 별도 범위 결정 전까지 보류한다. [jev-research-pipeline](https://github.com/shimo4228/jev-research-pipeline)을 참고한다.
- **7. 요약 검증:** 주장과 발췌의 뒷받침·상충·미지원·문맥 부족을 구별한다. 발췌에 없다는 결과를 원문 전체에 없다는 뜻으로 바꾸지 않는다. 준비한 48문항은 아래 경계 측정에 사용한다.
- **8. 재사용 후보 정밀화:** 원래 주장·조건과 사용된 문단을 함께 비교한다. 기계적 링크 탐지보다 후보 적중률이 높아지는지와 재사용 누락을 함께 본다. 후보 4에는 사람이 확인한 관계부터 입력한다.
- **9. 공개 범위 검사 보조:** 공개 예정 문단의 접속 정보·자격증명은 로컬 규칙으로 먼저 검사한다. 검사하려고 비공개 원문을 외부에 보내지 않는다. 별도 허용된 합성 사례가 생기면 누락·오탐을 기존 검사와 비교한다.
- **10. 영구 노트 제목·summary 검사:** hub를 제외하고 제목과 핵심 주장이 맞는지, summary가 글이 하는 일만 말하는지 본다. 정상 문장의 오탐과 사용자 판단 일치율을 함께 잰다.
- **11. 블로그 구성·문체 검사:** 절 제목은 첫 문단만이 아니라 해당 절 전체와 대조한다. 문체 검사는 [snifftest](https://github.com/DanRWilloughby/snifftest)를 참고해 별도 평가하며, 기존 정규식 대비 추가 탐지와 오탐을 기록한다.

그 밖에 DevLog 목적지 추천, 관계별 Noul 재시험, 다음에 읽을 공개 노트 추천, 개인 신호 추적이 있다. 각각 복수 목적지의 누락·과잉 추천, 관계별 정밀도·재현율, 실제 후속 읽기, 자기 보고와 표현의 일치를 평가할 수 있다. DevLog와 개인 일기의 외부 전송은 현재 범위에서 제외하며, 개인 표현을 건강 상태의 진단으로 해석하지 않는다.

## 단계별 실험 계획

단일 문단 판단, 검색에서의 효용, 관계 판단의 한계를 구분한다. 질문·정답·임계값·진행 기준은 최종 평가 전에 고정하고 결과를 본 뒤 낮추지 않는다. 모델을 사용할 가치가 없다는 결론도 허용한다.

### 1단계: 단일 문단의 시도·결과 판별

**질문:** 문단에 실제로 수행한 시도와 그 뒤 관찰한 결과가 함께 명시돼 있는가?

이 판단은 후보 1의 구성 요소다. 가정한 예시, 일반적인 권고, 앞으로 할 계획은 제외한다. 결과가 수치일 필요는 없지만 실제 관찰인지 문단에서 확인할 수 있어야 한다. 사례의 진실성이나 다른 주장을 입증하는지는 묻지 않는다.

**표본**

- 실제 게시 여부와 게시된 본문을 확인한 노트·발행 글 12개에서 자연 문단 48개를 목표로 한다. 개인 초안·비공개 자료·공개본 이후의 로컬 수정은 제외한다.
- 노트 단위로 조정용 6개와 최종 평가용 6개를 나눈다. 같은 사례를 다시 쓴 글과 유사 문단도 같은 쪽에 둔다. 과적합은 사람이 표본을 보고 질문이나 규칙을 고칠 때 생기므로, 예전에 Jev에 보낸 문단이라는 이유로는 빼지 않는다. 이전 실험에서 라벨을 붙이며 읽은 문장이 든 문단만 제외한다.
- 모델 출력을 보기 전에 사람이 `있음 / 없음 / 문맥 부족`을 확정한다. 최종 평가에는 있음 12개·없음 12개를 확보한다. 수량이 부족하면 새 공개 문단을 보강하고, 문맥 부족 항목은 별도 보고한다.
- 클래스 균형을 위해 고른 표본이므로 볼트 전체의 사례 비율을 추정하지 않는다. 합성 변형은 이 단계의 진행 기준에 포함하지 않는다.

**비교와 고정**

전부 후보로 제시하는 기준선, Jev Noul, 생성 모델 1종의 같은 예/아니오 판단을 비교한다. 두 모델에는 동일한 문단과 판정 기준만 보내고 정답은 보내지 않는다. 모델·버전과 입력 해시를 기록한다. 영어 지시문·한국어 문단을 기준 조건으로 삼는다.

질문 문구는 조정용 표본에서 최대 두 번 바꾼다. Jev의 `예` 확률 문턱도 조정용에서만 정한다. 호출 실패는 `없음`으로 처리하지 않으며 재시도 이후에도 실패하면 평가 미완료로 기록한다.

**최종 평가의 진행 기준**

- 실제 사례 문단 12개 중 10개 이상을 후보로 찾을 것.
- 사례가 없는 문단 12개 중 잘못 추천한 것은 2개 이하일 것.
- 각 결과를 개수와 분모로 보고하고, 생성 모델과 호출 시간·비용을 함께 비교할 것.

기준을 만족하면 검색 효용 평가로 진행한다. 이 기준은 작은 파일럿의 진행 조건이며 자동 채택 조건은 아니다. 두 차례 문구 조정 후에도 조정용에서 구분하지 못하면 최종 표본을 열지 않고 질문 정의·입력 부족·모델 오판을 분석한다.

### 2단계: 근거 탐색의 실제 효용

후보 1을 질문 10개로 시험한다. 조정용 4개, 최종 평가용 6개로 나누고 질문마다 QMD 후보 15개를 고정한다. 검색 대상과 입력은 게시된 공개 자료로 제한한다.

QMD 기본 순위, 1단계의 특징 판별을 추가한 순위, 생성 모델 선별의 상위 세 개를 비교한다. 문단에 시도·결과가 있다는 사실만으로 질문의 근거가 되지는 않으므로, 실제 유용성은 사용자가 모델 이름을 가린 상태에서 평가한다. 중복 문단의 유용성 라벨은 한 번만 정해 각 순위에 적용한다.

최종 질문 6개 중 4개 이상에서 유용한 문단을 하나 이상 찾고, 상위 세 개에 포함된 유용한 문단의 총수가 QMD보다 3개 이상 늘면 새 글쓰기 작업에서 실사용 평가를 시작한다. 후보 안에 필요한 문단이 없었던 경우는 검색 실패로 따로 기록한다. 이미 본 자료를 다시 찾는 시간으로 시간 단축 효과를 주장하지 않는다.

### 3단계: 요약 대조의 한계 측정

후보 7은 두 텍스트의 조건·범위·주체를 대조해야 한다. 기존 관계 분류의 실패를 고려해, 강점 확인과 분리한 경계 측정으로 둔다. 공식 [인용 검증 예제](https://docs.typesafe.ai/cookbooks/citation_check)가 있다는 사실만으로 한국어 요약 대조를 쉬운 과제로 보지 않는다.

준비한 `pilot-01`은 출처 12개, 실제 요약에서 고른 주장 24개와 합성 변형 24개다. 원래 주장은 근거가 명확한 부분을 골랐으므로 자연 발생 오류의 대표 표본이 아니다. **현재는 비공개 Clippings에서 가져온 문장이 포함돼 외부 전송을 보류한다.** 이 자료 범위가 별도로 정해지거나 공개 노트 기반 표본으로 다시 구성되기 전에는 API를 실행하지 않는다.

실행 조건이 갖춰지면 기존 출처별 분할을 유지하고, 사람이 라벨을 확정한 뒤 전수 검토 기준선·Jev Choice·생성 모델을 비교한다. 선택지는 `supports`, `contradicts`, `not_supported`, `unclear`이며, `supports` 이외 또는 조정용에서 정한 낮은 confidence는 검토 대상으로 둔다. `not_supported`는 제공된 발췌 안의 근거 부족이고 `unclear`는 필수 문맥의 모호함이다.

**채점은 세 묶음으로 분리한다.**

| 표본 | 기록할 결과 | 진행 기준 |
| --- | --- | --- |
| 근거가 있는 실제 요약 | 정상 요약을 검토 대상으로 잘못 보낸 수 | 최종 정상 12개 중 2개 이하 |
| 의도적으로 만든 오류 | 오류 종류별 탐지·누락 수 | 최종 합성 오류 12개 중 11개 이상 탐지. 합성 오류 구별의 기준일 뿐 운영 채택 근거가 아님 |
| 자연 발생 오류 | 별도 수집한 실제 오류의 탐지·누락과 검토 시간 | 현재 표본으로는 판정 불가. 새 표본과 기준을 실행 전에 정함 |

사람 검토로 최종 라벨 수가 달라지면 실행 전에 수량과 개수 기준을 다시 고정한다. 오류가 8개뿐인 조건에서 90%는 8개 전부를 찾아야 한다는 뜻이다. 서로 다른 분모의 비율을 합격 기준으로 섞지 않는다. 문맥 부족은 오류와 분리하고, 유보된 정상 항목은 검토 부담에 포함한다.

합성 표본을 통과해도 정상 요약의 검토를 자동 생략하지 않는다. 먼저 자연 발생 오류가 포함된 새 표본에서 검토량과 누락을 확인한다. 질문 조정이나 오류 분석에 사용한 최종 표본은 다음 실험의 새 홀드아웃으로 재사용하지 않는다.

### 후속 실사용: 과거 질문 재발견

후보 2는 관련성·관계 판단이므로 앞선 실험의 성공을 그대로 적용하지 않는다. 공개된 미해결 질문 5개와 이후 게시된 공개 기록으로 시험하고, 첫 2주 동안 제안은 총 5건 이내로 제한한다. 최소 2건에서 질문 수정·재독 후 메모·실제 적용이 생기면 확대를 검토한다. 도움이 된 사례가 없으면 보류하며, 새 기록 자체가 적으면 관찰 부족으로 남긴다.

진행 중 자료는 `_workspace/jev-vault-experiments/`에 둔다. 종료한 실험은 해당 날짜 DevLog에 결과를 요약하고 `30_Resources/Development/DevLog/assets/<실험일>-jev/`에 원자료·질문·평가표·재현 파일을 보관한다. 2026-09-24의 원자료는 이미 `DevLog/assets/2026-09-24-jev/`에 있다. 이번 준비 표본을 과거 실험 폴더에 합치지 않는다. 채택한 활용과 확인된 한계만 개념 노트에 반영한다.

준비했던 48문항(`pilot-01`)은 API 호출 0건인 채로 2026-09-25에 삭제했다.

실행 기록에는 표본 ID, 공개 URL·확인일, 공개본·입력 해시, 출처별 분할, 사람이 확정한 라벨·근거, 모델·질문 버전, 확률, 호출 시간, 토큰 사용량, 오류·재시도를 넣는다. 문단 특징을 판별한 결과와 사용자가 실제 근거로 채택한 결과는 다른 필드로 남긴다.

첫 단계의 두 모델 합계 비용 상한은 1달러로 둔다. 실행 시점의 요금과 입력량을 먼저 계산하고 재시도를 포함해 상한을 적용한다. 원문 전체의 불필요한 복제는 피하고, 모델·질문·입력 해시가 같은 응답만 재사용한다.

## 판단의 한계

확신도가 높다고 정확성이 보장되지는 않는다. 독립 평가 연구에서 Jev는 15개 평가 과제 중 14개에서 과제별 최고 LLM보다 낮은 성능을 보였고, 일부 과제에서는 높은 확신도도 신뢰하기 어려웠다.[^evaluation] 이 연구는 한국어 개인 볼트의 활용을 직접 검증한 결과는 아니다. 적용할 판단마다 실제 오탐과 사용 결과를 확인해야 한다는 근거로 참고한다.

활용의 최종 가치는 실제로 유용한 원문을 다시 읽고 작업에 썼는지로 확인한다.
